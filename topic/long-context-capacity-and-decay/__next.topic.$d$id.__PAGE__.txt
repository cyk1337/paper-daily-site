9:T553,Long-context capability should no longer be treated as a scalar. Claimed window size answers how many tokens fit; effective capability answers how far the model can still retrieve, track, and aggregate reliably, and what shape the decay takes. The key change in 2024–2025 is that measurement and mechanism finally connect. RULER decomposes single-needle NIAH into retrieval, tracking, and aggregation pressures. LongBench v2, LV-Eval, BABILong, and Loong add realistic tasks, length stratification, and reasoning pressure. Wu et al. then provide causal evidence for retrieval heads, tying “why the curve drops” to “which parts of the attention map are doing the work.” A steadier reading is to decompose long-context capability into three axes: pattern capacity, pattern diversity, and decay slope. Capacity governs how many independent paths can be sustained in parallel; diversity governs whether retrieval heads, induction heads, sinks, and mover-like patterns cover enough subskills; decay slope distinguishes uniform decay, U-shape, and cliff failures. On the engineering side, GQA/MQA/MLA and sequence-level sparse attention suggest that most heads are sparse at most positions already; compression and sparsification need not destroy capability, provided they do not damage the small subset of heads and tokens that carry retrieval and anchoring.a:T688,A steadier reading is that long-context capability is not a single number like 128K, 1M, or 10M, but a three-dimensional object. The first axis is pattern capacity: how many retrieve / track / aggregate paths can be sustained in parallel within one context. The second is pattern diversity: whether specialized patterns such as retrieval heads, induction heads, and attention sinks cover the subskills the task needs. The third is decay slope: when performance falls with length and position, does it degrade smoothly, form a lost-in-the-middle U-shape, or hit a cliff near the training length. RULER [RULER2024], LV-Eval [LVEval2024], LongBench v2 [LongBenchV22024], and BABILong [BABILong2024] already show that NIAH can measure “can it find,” but is weak as a primary metric; the real gaps now appear in tracking, aggregation, and reasoning. Wu et al. [Wu2024RetrievalHead] then weld measurement to mechanism: roughly the top 5% of retrieval heads carry most long-range retrieval, and masking them drives long-context factuality close to random. Taken together, Liu et al. [LostMiddle2023], Xiao et al. [StreamingLLM2023], Xiong et al. [EffectiveLongContext2023], and Fu et al. [DataEngineering128K2024] show that U-shape, uniform decay, and cliff are not three names for one problem but visible signatures of different root causes. On the engineering side, a longer window does not automatically beat RAG; when the task is sparse evidence lookup, RAG is often cheaper [RetrievalMeetsLongContext2023]. But once the task requires cross-span aggregation or multi-hop reasoning, retrieval alone starts to fail [Goldman2024RetrievalOnly][BABILong2024][LongBenchV22024].b:T69b,NIAH became popular after 2023 because it compresses the long-context problem into a clean retrieval test: place a needle in a long haystack and test whether the model can recover it from any position. The problem is that these tasks cover only one path by construction—locating a single piece of evidence; once a model learns stable sparse lookup, the score saturates too early. [RULER2024] directly challenges the prior that single-task long-context evaluation can represent overall ability: it does not build a harder needle, but decomposes pressure into multi-key retrieval, variable tracking, and aggregation. The result is clear: models that all look “usable” on NIAH separate again on tracking and aggregation. [LongBench2023] had already argued that multitask evaluation is closer to real use than a single task; [LongBenchV22024] pushes that judgment into realistic long-context tasks and shows that retrieval correlates only weakly with reasoning and aggregation. [BABILong2024] further embeds short reasoning tasks into long haystacks, showing that “find, then compose, then reason” is a three-stage chain; passing the first stage does not imply passing the next two. [LVEval2024] adds explicit length stratification: only by comparing 16K to 256K under the same task distribution can one tell whether a model degrades smoothly or falls off a cliff near the training length. A more practical measurement order is: use NIAH to check basic arbitrary-position retrieval, then use RULER to separate retrieve / track / aggregate, then use realistic tasks such as LongBench v2, BABILong, and Loong to verify whether reasoning still holds. [Loong2024][Goldman2024RetrievalOnly]c:T777,[LostMiddle2023] establishes a robust U-shape: evidence at the beginning and end is used more reliably than evidence in the middle. But attributing all positional degradation to positional encoding is inaccurate. [RoFormer2021] and [RoPEScaling2023] show that RoPE extrapolation has real limits; phase error accumulates beyond the training length, so a cliff often appears near or beyond the trained range. [EffectiveLongContext2023] and [DataEngineering128K2024] further show that changing PE alone, without long-sequence training and the right data distribution, often yields only “can accept longer input,” not “can use longer input.” This failure looks like a train-length cliff. A different failure is U-shape: it looks more like a priority-allocation problem than a pure length-boundary problem. [StreamingLLM2023] finds that the first few tokens naturally become attention sinks, with many heads assigning part of their probability mass to these anchors at most positions; this puts middle evidence at a disadvantage when competing for attention budget. [SinkEmergence2024] further shows that sink emergence depends on training and architecture, so at least part of lost-in-the-middle is anchor bias rather than a pure PE artifact. A third failure is uniform decay: as length grows, tracking or aggregation degrades smoothly, without a strong positional U-shape. This looks more like limited pattern capacity: the model cannot sustain enough independent paths, and as distractors grow, those paths compete for budget. [RULER2024][SameTaskMoreTokens2024] A steadier diagnostic order is therefore: first check for a cliff near the training length, then check for a middle-specific U-shape, and only then diagnose smooth capacity-limited decay. #   A: attention probabilities, shape (n_layers, n_heads, L, L)
#   reported per (layer, head), then aggregated; what tells us
#   which surrogate matters is correlating against RULER subtasks.

def per_head_entropy(A_lh):           # capacity (per query)
    p = A_lh + 1e-12
    H = -(p * p.log()).sum(-1)        # (L,)
    return H.mean()

def effective_rank(A_l):              # capacity (cross-head)
    M = A_l.reshape(A_l.shape[0], -1) # (H, L*L)
    s = svd(M, compute_uv=False)
    p = s / s.sum()
    return exp(-(p * p.log()).sum())  # entropy of singular distribution

def topk_jaccard_diversity(A_l, K=8): # diversity
    sets = topk_keys(A_l, K)          # (H, L, K)
    D = 0.0
    for i in range(H):
        for j in range(i+1, H):
            D += jaccard_distance(sets[i], sets[j])
    return D / (H * (H-1) / 2)

def specialization_score(A_lh, ref_pattern):  # diversity per archetype
    return cosine(flatten(A_lh), flatten(ref_pattern))

11:T766,Two engineering misreads are common. First, treating a “claimed 1M window” as equivalent to “any task within 1M tokens should be placed directly into the window.” [RetrievalMeetsLongContext2023], [Atlas2022], [kNNLM2019], and [RetrievalPretrain2023] all suggest that if the task is mainly sparse evidence lookup, external retrieval is often cheaper and more stable than forcing the whole document into the window. Second, treating compression, sparse attention, and KV reduction as necessarily damaging long-context ability. [StreamingLLM2023] already shows that aggressive eviction can still support stable generation if sink tokens are preserved; [ActivationBeacon2024] shows that compression can reduce cost without fully sacrificing performance if it preserves summary state useful for later retrieval; [LandmarkAttention2023] shows that better access structure can substitute for full visibility. This does not conflict with [Wu2024RetrievalHead]: the danger is not compression itself, but indiscriminately damaging the small subset of heads and tokens responsible for retrieval or anchoring. Conversely, when the task requires cross-span aggregation, comparison, or multi-hop reasoning, RAG is not the default answer either. [Goldman2024RetrievalOnly] argues that many benchmarks are retrieval in disguise; [LongBenchV22024], [BABILong2024], and [LooGLE2023] provide the counterpoint: after evidence is found, the model still needs to maintain multiple paths and compose them within the same context. A more practical engineering framing is: use long windows to preserve interaction structure, use RAG to shrink the search space, and use compression or sparsification to cut cost without harming critical paths. # Decision rules synthesized from Wu 2024 (retrieval heads),
# Xiao 2023 (sinks), Olsson 2022 (induction heads), and the
# NSA / MoBA / DSA papers.

def sparse_attn_safe(
    routing,                      # callable: (q, K) -> selected key indices
    head_class,                   # 'retrieval' | 'induction' | 'sink' | 'mover'
    sink_window: int = 4,         # always-keep first N tokens
    local_window: int = 256,      # always-keep recency window
) -> bool:
    # Rule 1 (sink): the first `sink_window` tokens MUST stay reachable
    # for every head class — they are the global anchor and aggressive
    # eviction here is the single biggest streaming-LM regression.
    if not preserves_first_k(routing, sink_window):
        return False

    # Rule 2 (retrieval): retrieval heads need to reach a small set of
    # remote keys; routing must be CONTENT-AWARE for this class, not
    # purely position-aware. NSA / MoBA satisfy this via top-K block
    # selection; pure local + sink (StreamingLLM) does not.
    if head_class == 'retrieval' and routing.is_position_only():
        return False

    # Rule 3 (induction): induction heads need (i-1, i-2) keys plus the
    # earlier copy point; local window covers (i-1, i-2), but the copy
    # point can be far. content-aware routing handles it.
    if head_class == 'induction' and routing.is_position_only():
        return False

    # Rule 4 (mover): densest working set; degrades first under aggressive
    # sparsity. Recommend: keep top-K with K large enough that mid-context
    # blocks have non-zero hit probability for ≥ ~30% of mover queries.
    if head_class == 'mover' and routing.expected_hit_rate() < 0.3:
        return False

    return True
