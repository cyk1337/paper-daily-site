长程 AI Delegation 评估

Delegation-ready 任务的评估单位不是答案,而是闭环

24 篇论文·2026年5月21日

领域综述

核心判断:long-horizon eval 的主问题不是把输入、视频或软件任务继续拉长,而是判断任务是否已经适合 Delegation。RULER、LongBench、NoCha、BABILong 和 SummHay 测的是预训练侧证据使用、位置鲁棒性、聚合与长文综合;Video-MME、LongVideoBench 与 VBVR 把同一问题推进到跨帧状态、因果与可验证生成轨迹;SWE-bench、WebArena、OSWorld、GAIA 与 tau-bench 则把模型放进工具和环境闭环里 [3][4][6][7][8][10][11][2][24][17][18][19][20]。

三条线不能合成一个分数。pretrain eval 给出底层能力:证据是否被保留、位置是否稳定、多跳依赖是否能聚合。agent eval 给出系统能力:harness、工具权限、状态恢复、验证 oracle 与 human handoff 是否闭合。SWE eval 是公开基准里最接近“Delegation-ready 工作”的一支,因为它有真实 repo 和 patch+test oracle;但它仍主要是边界清晰的单 issue,缺少多 PR、部署、回滚、用户反馈、安全边界与长期维护 [24][25][26][27][28]。

Video-Reason/VBVR 提供的是视频推理训练和评测的正常技术背景:VBVR 声称覆盖 200 个任务、1,000,000+ 视频片段、rule-based human-aligned scorers 和早期 OOD 泛化迹象 [1][2]。这支持“视频推理评估需要可验证过程”的方向,但不能直接推出“长程 AI Delegation 已经解决”:VBVR 的强项是可控视频推理训练和评测,离真实开放环境中的目标分解、工具调用、失败恢复和人机交接还有一层 agent harness。

TL;DR

长程评估应该从“模型能处理多长输入”转向“人是否可以把任务交给它”。长上下文评估测证据和位置,视频推理评估测跨帧状态和过程可验证性,SWE 与 agent benchmark 测工具环境里的规划、执行和恢复。真正的 AI Delegation 分数要同时报告完成率、误修复率、验证覆盖、handoff 质量、成本延迟、可恢复性和审计轨迹。

核心断言

#1长上下文是 substrate eval,不是 agent eval:它测证据保留、位置鲁棒性和聚合,不测工具权限、恢复策略和人机交接 [3][6][8]。
#2VBVR 的贡献是把视频推理做成大规模可验证训练和评测资源;它支持过程监督方向,但还不是开放环境 Delegation 评估 [2][1]。
#3SWE-bench 是公开评估里最接近 Delegation-ready 工作的基准,因为真实 repo 和 tests 给了硬 oracle;短板是单 issue 边界过清晰,缺少维护周期 [24][25][28]。
#4Agent eval 的核心变量是 harness,不是只看底座模型:工具接口、沙盒、状态管理、重试策略和 verifier 都会改变同一模型的表现 [26][27][20]。
#5长文和长视频评估的共同难点是 delayed dependency:关键证据早出现,作用晚发生,最后还要被正确引用或转成动作 [11][13][7]。
#6AI Delegation 应测“是否值得 Delegation”:完成率单独不够,必须同时看误修复、校验覆盖、handoff 质量、成本延迟、恢复性和审计轨迹 [18][19][20]。

Video-Reason/VBVR:可验证视频推理,不是 Delegation 评估

Video-Reason 组织页和 VBVR 论文提供的是视频推理基础设施证据:VBVR-Dataset 声称覆盖 200 个任务、1,000,000+ 视频片段,VBVR-Bench 使用 rule-based human-aligned scorers,并报告随训练规模提升的 ID/OOD 泛化迹象 [1][2]。

原论文可以支持三点:视频推理需要比短 clip QA 更大的训练数据;可验证 scorer 比 VLM-as-judge 更适合做可复现实验;视频任务能把空间、时间、因果和过程监督放进同一载体 [2]。它不能直接支持“视频推理等于 long-horizon Delegation”。从视频生成轨迹到 AI Delegation,还缺目标分解、工具动作、环境状态、失败恢复和人类交接这些 agent 层变量 [17][18][20]。

评估栈应该分层,不该合成一个 long-horizon 分数

pretrain eval、long-document/video eval 和 agent eval 是三种不同因变量。RULER、BABILong 和 NoCha 的单位是 token evidence 与文本结构;Video-MME、LongVideoBench 和 VBVR 的单位是跨帧状态与过程;SWE-bench、WebArena、OSWorld 和 tau-bench 的单位是环境中的动作序列 [3][7][6][10][11][2][24][17][18][20]。把它们合成一个分数会把底座能力、harness 策略和 oracle 设计混在一起。

更稳的结构是四层漏斗:第一层测证据能不能进模型并留住;第二层测长文、长视频里的 delayed dependency 能否被聚合;第三层测工具环境里的动作是否达到可验证目标;第四层测人把目标交给系统后,总成本和风险是否下降。第四层才是 AI Delegation。前三层都必要,但都不是充分条件。

Benchmark 对比:同叫 long-horizon,工作单位完全不同

最容易误读的是把 horizon 当作长度。RULER 的 horizon 是上下文长度和压力模板;NoCha 的 horizon 是整本小说里的事实一致性;LongVideoBench 的 horizon 是小时级视频片段;SWE-bench 的 horizon 是一次 repo issue;OSWorld 和 tau-bench 的 horizon 是一串环境或用户交互动作 [3][6][11][24][18][20]。这些 horizon 的 oracle 强度也不同:rule-based scorer、human annotation、tests、GUI state check 和 simulated user policy 分别暴露不同失败模式。

所以报告时应先写 unit of work,再写 horizon。缺这个字段,模型榜单会把“会找答案”“会看长视频”“会改代码”“会处理客户政策”混成同一种能力。

AI Delegation 的评价对象是闭环,不是最终答案

Delegation 发生在用户把目标、约束和风险边界交给系统之后。系统必须把目标拆成计划,调用工具或环境,保留中间证据,用 verifier 检查输出,失败时恢复,不确定时把问题交还给人。一次 final answer 只能测结果文本;Delegation 评估要测过程中哪些风险被发现、哪些动作可撤销、handoff 是否让人更快接管 [16][17][18][20]。

这一点解释了为什么 pretrain eval 和 agent eval 都不可替代。pretrain eval 让模型在长证据上少漏读;agent eval 让系统在真实环境里少乱动。缺前者,agent 会把证据链做空;缺后者,模型就算会读长文,也不知道何时测试、回滚、问人或停止。

SWE 是最好的公开Delegation proxy,但还不是长期软件工作

SWE-bench 的优势很清楚:真实 repo、真实 issue、patch 形式输出、测试作为硬 oracle,这比多数网页和助理任务更接近工作交付 [24]。SWE-bench Verified 又把模糊 issue 和测试瑕疵清掉一部分,让模型差异更少被数据质量遮住 [25]。SWE-agent 和 OpenHands 进一步证明,同一底座模型换 agent-computer interface、sandbox 和 action schema,结果会明显改变 [26][27]。

短板也同样具体。真实 SWE Delegation 常常跨多 PR、review feedback、CI flakes、schema migration、部署观测、回滚和用户反馈;单 issue patch 容易奖励“刚好让 tests 过”的策略,也弱化了安全边界和长期维护成本 [28]。下一代 SWE long-horizon eval 应该把 work unit 从 issue 扩到 maintenance episode:需求澄清、实现、review 回复、CI 修复、迁移验证、上线检查和回滚预案一起算分。

long-horizontal 的难点是跨阶段展开,不是只把文档拉长

用户说的 long-horizontal 更适合理解成横向跨阶段:多文档、多视频、多工具、多轮决策同时存在。长文评估里,这对应 retrieval hit、multi-hop aggregation、synthesis、delayed dependency、position robustness 和 memory update 的拆分 [5][8][6][7]。视频评估里,同一结构变成跨片段事件追踪、目标保持、因果解释、未来预测和过程轨迹 [10][11][13][2]。

这条横向轴比单纯长输入更接近 Delegation。真实 Delegation 任务不会只要求“读完一篇长文”,而是把网页、代码、日志、视频、会议纪要和测试结果都放进同一决策链。评估设计要记录证据从哪里来、何时被使用、是否被 verifier 覆盖、后续动作是否依赖它。否则长文和长视频只会成为更大的静态 prompt。

Delegation-readiness指标:完成率要和风险指标一起上报

单一 success rate 会奖励高风险 agent:多试几次、猜测式修复、绕过测试、遗漏安全约束都可能提高短期完成率。Delegation 评估至少要同时报告七类指标:完成率、误修复率、验证覆盖、handoff 质量、成本与延迟、recoverability、audit trail 完整性 [25][18][20]。其中 handoff 质量尤其关键:好的 agent 在不确定时应把上下文、已尝试路径、失败证据和下一步选项压缩给人,而不是只说失败。

pretrain 侧指标也要接入这个框架。RULER 或 NoCha 的低分预示证据链会断;Video-MME 或 LongVideoBench 的低分预示观察链会断;SWE-bench 的低分预示执行链会断 [3][6][10][11][24]。Delegation 评估的价值在于把这些断点定位到同一个任务闭环里。

时间线

  1. 2017MiniWoB / World of Bits 把网页操作变成 agent 任务[22]

    早期 agent 评估的 work unit 是短网页动作。

  2. 2020ALFWorld 连接文本任务和 embodied 环境[23]

    工具/环境闭环开始比纯问答更重要。

  3. 2022ReAct 固化 reason-action-observation 轨迹[16]

    后续 agent benchmark 基本沿用这条轨迹语法。

  4. 2023LongBench、SWE-bench、WebArena、GAIA 同年出现[4]

    长上下文、软件工程、网页和通用助理开始分成不同评估支线。

  5. 2024RULER、NoCha、BABILong 和 SummHay 修正长上下文指标[3]

    从单 needle 转向位置、聚合、全书事实和引用覆盖。

  6. 2024Video-MME 和 LongVideoBench 把视频时长与跨帧推理拉上来[11]

    视频 eval 开始承担 long-context 的多模态版本。

  7. 2024OSWorld 和 tau-bench 加入真实电脑与用户交互[18]

    agent eval 的 oracle 从答案扩展到环境状态和交互可靠性。

  8. 2025SWE-bench Live 把 coding eval 推向动态任务[28]

    污染压力降低,但长期维护 episode 仍未完全覆盖。

  9. 2026VBVR 把视频推理训练和评测规模化[2]

    可验证过程监督成为视频推理的关键变量。

研究立场对比

不要把长上下文分数当Delegation分数

立场 — 长上下文指标是底层能力监控,不是task Delegation结果。

证据：[3][6][8]

反方 — 没有这层能力,agent 的证据链会更早断。

判词 — 并列上报,不要合并。

视频推理要看过程可验证性

立场 — 视频 benchmark 的价值在跨帧状态和可验证轨迹,不是只比短视频 QA 更长。

证据：[2][11][10]

反方 — 生成式任务可能过于可控,开放世界噪声不足。

判词 — 适合作为 delegation 的观察层,不能替代 action 层。

SWE 是最硬的公开Delegation proxy

立场 — repo、tests 和 patch oracle 让 SWE-bench 比网页问答更接近真实交付。

证据：[24][25][26]

反方 — 单 issue 仍缺 review、deploy、rollback 和用户反馈。

判词 — 下一步要评 maintenance episode。

Delegation 指标必须惩罚高风险成功

立场 — 完成率要和误修复、验证覆盖、handoff、成本延迟、恢复性和审计一起看。

证据：[18][20][25]

反方 — 指标越多,benchmark 维护成本越高。

判词 — 真实 Delegation宁可难评,不能只评好看的成功率。

悬而未决的问题

  • Q1.怎样定义 multi-PR maintenance episode,让任务足够真实又能被可重复评分?
  • Q2.视频推理里的 process scorer 能否扩展到开放世界视频,而不是只覆盖参数化生成任务?
  • Q3.handoff quality 应该用人工评分、结构化 checklist,还是基于后续人类修复时间来评?
  • Q4.agent eval 如何把工具权限和安全边界纳入分数,避免只奖励大胆行动?
  • Q5.long-document memory update 与 agent state recovery 是否能共享同一套 delayed-dependency probes?
  • Q6.动态 benchmark 如何同时防污染、保留可比性,并避免每次更新都改变任务分布?
  • Q7.AI Delegation 的成本指标应按 token、wall-clock、人类监督时间,还是失败后的恢复成本计?
