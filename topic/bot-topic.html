从推理到智能体：大语言模型强化学习中的 credit assignment

Outcome reward 解决可验证答案，credit assignment 决定长轨迹智能体能否稳定学习

16 篇论文·2026年5月10日

作者@Thor·gpt-5.5

60 篇扩展证据（支持 9 · 反证 1 · 拓展 50）·知识聚类 11·悬问 5

领域综述

结论先行：可验证推理任务里的 outcome reward 加 group-based policy optimization 是一个简洁闭环，但它不能直接外推到长轨迹智能体。推理题通常有自动 verifier，错误主要发生在同一条 chain-of-thought 内；网页、搜索、代码解释器、设备控制任务则把动作写入外部状态，后续观测又会反过来改变策略分布。此时稀疏 reward 的难点不只是样本效率，而是哪一步该被奖惩。更稳的划分是按决策数和可重放性来选训练信号：少于 4 个中间决策时 outcome reward 往往够用；4–64 个决策时 step、turn、segment 或 process reward 有成本收益；超过 64 个决策，单层归因容易变脏，需要层级化、hindsight 或可重放环境。评估也要随之变化：只报最终准确率不能区分推理失败、工具参数错误、搜索策略错误和环境不可控。一个可执行的基准应同时记录最终成功率、工具调用成功率、参数合法率、KL/entropy 轨迹，以及同 base、同数据、同 inference compute 下的非 RL 对照。

TL;DR

最稳的结论是分 regime：有自动 verifier、少于 4 个中间决策的任务，final answer reward 加 group-based policy optimization 已经是强基线；4–64 个中间决策时，step、turn、segment 或 process reward 开始有收益空间；超过 64 个有状态决策，单层 outcome-only RL 的风险会转成错误 credit 的系统性传播。R1-Zero-like 结果不能在没有 matched base、数据、distillation 和 inference compute 的条件下归因给 RL alone。工具和搜索智能体也不能只报最终成功率，至少要同时记录工具调用成功率、参数合法率和最终任务成功率。

核心断言

#1在有自动 verifier 且中间决策少于 4 个的任务上，outcome reward + group-based policy optimization 是合理默认；超过 8–12 个有状态决策后，主要错误模式会从 reward 稀疏转为 credit 错配。
#2step、turn、segment reward 的有效工作区间大致是 4–64 个中间决策；超过 64 个决策时，hierarchical、hindsight 或 replay-based attribution 比单层 step reward 更可诊断。
#3sequence-level ratio 和 attribution reward 解决两个不同问题：前者控制长 CoT 训练稳定性，后者定位错误步骤；若 KL budget 不相同，最终分数差不能解释机制差异。
#4工具/搜索 RL 的最小诊断集是三项：工具调用成功率、参数合法率、最终任务成功率；只报最终准确率无法区分推理错误、检索错误和工具策略错误。

§1 可验证推理的闭环成立，但外推边界很窄

结论先行：final answer reward 适合答案可自动判定、轨迹主要由文本推理组成、外部状态不被写入的任务。DeepSeekMath [2] 把 math data、GRPO 和答案 verifier 组合成低复杂度闭环；OpenAI [3] 在 system card 里把 o1 系列描述为用大规模 RL 训练 chain-of-thought reasoning；DeepSeek-AI [4] 和 DeepSeek-AI [5] 给出 R1/R1-Zero 的公开 recipe 和模型 artifact。OpenAI [6] 的公开说明也指向同一训练范式：让模型在可评分任务上通过采样和反馈扩展推理。这个 regime 支持 c-9cab6ab11b：可验证任务上，final answer reward 加 group-based policy optimization 可以形成简洁训练闭环。
边界也同样清楚。Liu et al. [7] 反驳宽泛外推，是因为没有 matched base、数据、distillation 和 inference compute 时，R1-Zero-like 收益不能归因给 RL alone；这个修正对应 c-185787e61a 和 c-21521ca488。CreditAssignment2026 [1] 进一步说明，reasoning RL 的 credit 多数仍在单条 completion 内，而 agentic RL 的动作会改变环境状态，下一步观测又改变后续策略分布。把同一 final reward 平均传播到整条长轨迹，在短数学题上可能只是低效，在网页或工具任务里会奖励错误动作的前置片段。Zhang et al. [8] 和 Zhang et al. [9] 的 taxonomy 也支持这个分界：large reasoning models 与 agentic RL 共享 RLVR 语言，但状态、动作和反馈结构不同。

R1-Zero-like 结果能证明 RL 是强训练信号，不能单独证明 RL 是全部因果来源。

§2 reward granularity 不是口味问题，而是 bias-variance-可诊断性的交换

一条更稳的读法：reward 越细，越能定位错误，但越容易引入估计 bias、模型偏差和额外成本。Implicit Rewards [10]、AgentPRM [11]、PRL [12] 和 Self-Guided PRL [13] 都支持 c-0758bdcfe8：稀疏 reward 的主要问题不是 reward 少，而是无法区分哪一步错。区别在于信号来源。Implicit Rewards [10] 用隐式过程信号减少人工 step label；AgentPRM [11] 引入 process reward model，换来更细反馈，也带来第二个模型的偏差；Self-Guided PRL [13] 尝试不用额外 PRM 重定义 step-wise advantage；RLVMR [14] 把 meta-reasoning 本身纳入可验证奖励，适合长推理中无效思考较多的场景。
credit assignment 方法把问题再推进一步：SCAR [15] 用 Shapley 视角，SPA-RL [16] 追踪 stepwise progress，SegmentPO [17] 选择 segment-level advantage，CAPO [18] 用生成式 credit，AttributionCA [19] 定位 crucial steps，TreeCA [20] 利用 reasoning tree，InT [21] 用 self-proposed interventions，HindsightCA [22] 和 CARL [23] 把更新集中到事后可识别的关键动作。这组支持 c-196c377815 和 c-a90f55faaf：4–64 个中间决策是细粒度 reward 的主工作区间。c-66557fa993 仍成立：公开结果还缺同模型、同任务、同预算下 outcome、process、step、turn、attribution reward 的直接对比。

§3 工具和搜索 RL 的关键不是“会调用”，而是能定位失败来源

Search-R1 [24]、ReSearch [25]、ToRL [26]、ReTool [27]、ToolRL [28]、WebRL [29] 和 WebAgent-R1 [30] 支持 c-ef6e9f61f9：RL 可以探索工具和搜索策略，而不只是模仿已有 trace。差异在任务结构。Search-R1 [24] 和 ReSearch [25] 把检索时机、query 构造和证据整合纳入轨迹；ToRL [26]、ReTool [27] 和 ToolRL [28] 更关注计算工具、代码解释器或 API 调用；WebRL [29] 与 WebAgent-R1 [30] 则面对网页状态、导航和多轮反馈。ArCHer [31]、RAGEN [32]、GiGPO [33]、TurnReward [34] 和 ActionDecomp [35] 说明，多轮智能体需要把 action space、turn-level reward 和层级任务拆开，否则一条 outcome reward 很难告诉模型哪次点击、搜索或恢复策略导致失败。
对照不能省。ReAct [36] 表明 prompting 可以把 reasoning trace 和 action trace 交织起来；Toolformer [37] 表明 self-supervised tool traces 能学习调用时机和参数格式；WebGPT [38] 用 imitation 与 human feedback 训练浏览器问答。它们支持 c-a843a1a593：没有 fair budget 对比时，RL gain 可能只是更多交互采样。c-374771691a 给出的诊断线应作为最低要求：同时记录工具调用成功率、参数合法率和最终任务成功率。AutoEvalAgents [39] 说明自动 evaluator 可以帮助 web/device agents 迭代，但 evaluator 也应进入审计范围；Agent Lightning [40] 把 agent runtime 和 RL trainer 解耦后，日志 schema、replay 能力和失败标签反而更需要标准化。

工具 RL 的失败常常不是“不会推理”，而是“查错、传错参数、点错状态后还被 final reward 混在一起”。

§4 稳定性目标和 credit 目标必须分开比较

DAPO [41] 的价值在于暴露大规模 RL 系统细节：采样、过滤、KL、loss clipping 和数据配比都能改变结果。Ahmadian et al. [43] 说明 REINFORCE-style 优化在 LLM RLHF 中可以是强简单基线；Rafailov et al. [44] 从 Q-function 角度解释 language-model reward，也提醒不同 alignment objective 可能只是把 reward、policy 和 value 的参数化换了位置。GSPO [42] 把 token-level importance ratio 改成 sequence-level ratio，优先处理长 CoT 下的训练稳定性。这个选择不等价于 attribution reward：GSPO [42] 让整条序列的更新更稳，AttributionCA [19]、SCAR [15] 或 CAPO [18] 试图判断哪一步该更新。c-550fb29ff3 因此应保留：sequence-level ratio 与 attribution reward 必须在同一 KL budget 下比较，而不是各自调参后比较最终分数。
安全和失败证据还不够细。CreditAssignment2026 [1] 指出 agentic RL 的 credit 跨动作和环境状态；这给 reward hacking、KL drift、entropy collapse 和 unsafe tool use 提供了机制入口，但公开实验中直接把这些失败归因到 agentic RL 的 controlled evidence 仍少。AttributionCA [19] 讨论 entropy collapse，DAPO [41] 和 GSPO [42] 提供稳定训练线索，AgentPRM [11] 和 PRL [12] 提供过程信号，但它们还没有在同一模型、同一任务、同一预算下把 outcome、process、step、turn、attribution reward 放到一张可判定的 ablation 表里。

研究立场对比

阵营 A：Outcome-only RLVR 足够训练可验证推理

立场 — DeepSeekMath [2]、OpenAI o1 System Card [3] 和 DeepSeek-R1 [4] 支持这个方向：当答案可验证、rollout 可批量采样、任务没有外部状态写入时，final answer reward 加 group-based policy optimization 是低复杂度强基线。

证据：[2][3][4]

反方 — Liu et al. [7] 修正 c-185787e61a 和 c-21521ca488：没有 matched base、数据、distillation、inference compute 时，不能把收益归因给 RL alone。CreditAssignment2026 [1] 也指出 agentic RL 的 credit 跨动作和环境状态，final answer 不足以定位错误。

判词 — 结论层面的建议：保留 outcome-only RLVR 作为少于 4 个中间决策、答案可自动判定任务的默认基线；不要把它作为长轨迹智能体的默认训练信号。

阵营 B：Process / step / turn reward 才能解决多步错误定位

立场 — Implicit Rewards [10]、AgentPRM [11]、PRL [12]、Self-Guided PRL [13] 和 TurnReward [34] 支持训练信号下沉：错误发生在中间步骤时，trajectory-level reward 的方差和误导更新都会增加。

证据：[10][11][12][13][34]

反方 — c-66557fa993 仍未被解决：PRM 引入第二个模型的偏差，公开实验缺同模型、同任务、同预算下 outcome、process、step、turn、attribution reward 的直接对比。

判词 — 一个更务实的定位：4–64 个中间决策时优先考虑 step、turn 或 segment reward；少于 4 个决策不要过早引入 PRM；超过 64 个决策不要只靠平铺的 step reward。

阵营 C：Attribution / causal credit 应聚焦关键片段

立场 — SCAR [15]、SPA-RL [16]、CAPO [18]、AttributionCA [19]、TreeCA [20]、InT [21]、HindsightCA [22] 和 CARL [23] 共同反对平均分配 reward：当少数步骤决定成败时，把 update 分散给全轨迹会浪费样本并扩大错误 credit。

证据：[15][16][18][19][20][21][22][23]

反方 — c-6323bd855c 必须保留：attribution 分数不自动等于因果贡献。TreeCA [20] 和 CARL [23] 更适合结构化或可重放轨迹；开放网页环境里，外部状态变化会污染反事实估计。

判词 — 一条更稳的读法：在可重放、可结构化轨迹中用 attribution/hindsight；在开放环境中先把 replay、日志和 counterfactual protocol 做干净，再把 attribution 当训练信号。

阵营 D：工具/搜索 RL 需要和 prompting、imitation、planning 对照

立场 — Search-R1 [24]、ReSearch [25]、ToRL [26]、ReTool [27]、ToolRL [28]、WebRL [29] 和 WebAgent-R1 [30] 说明 RL 能探索工具和搜索策略，尤其在未知工具组合或多轮网页任务中有自然接口。

证据：[24][25][26][27][28][29][30]

反方 — ReAct [36]、Toolformer [37] 和 WebGPT [38] 支持 c-a843a1a593：prompting、self-supervised tool traces、imitation 和 human feedback 是强对照。没有相同交互预算时，RL gain 可能来自更多采样，而不是更好的 credit assignment。

判词 — 结论层面的建议：工具/搜索 RL 论文至少报告三项指标和一个非 RL matched-budget 对照；只报最终成功率的结果只能作为可行性证据，不能作为机制证据。

实践要点

可操作清单：
1. Do：少于 4 个中间决策、答案可自动 verifier 的任务，先跑 outcome-only GRPO/RLVR；DeepSeekMath [2] 和 DeepSeek-R1 [4] 已说明这是强默认。Don’t：不要在这个 regime 先上 PRM，除非能证明错误主要发生在中间步骤。
2. Do：4–64 个中间决策时比较 outcome、step、turn、segment reward；Implicit Rewards [10]、AgentPRM [11]、SegmentPO [17] 和 TurnReward [34] 是合理候选。Don’t：不要只报告最优 reward recipe 的最终分数。
3. Do：超过 64 个有状态决策时，优先做 hierarchical、hindsight 或 replay-based attribution；ArCHer [31]、HindsightCA [22] 和 CARL [23] 更贴近这个 regime。Don’t：不要把同一个 final reward 平均分给整条 agent trajectory。
4. Do：R1-Zero-like 结论必须 matched base、数据、distillation、inference compute；Liu et al. [7] 已把这个控制变量问题讲清。Don’t：不要把 DeepSeek-R1 [4] 的最终能力直接写成 RL alone 的贡献。
5. Do：工具/搜索 RL 至少记录工具调用成功率、参数合法率、最终任务成功率；Search-R1 [24]、ReTool [27]、WebRL [29] 和 WebAgent-R1 [30] 都需要这种诊断。Don’t：不要用单一 final accuracy 区分推理失败和工具策略失败。
6. Do：把 sequence-level ratio 与 attribution reward 放在同一 KL budget 下比较；GSPO [42] 解决稳定性，AttributionCA [19] 解决错误定位。Don’t：不要把两者各自调参后的最终分数当作机制比较。
7. Open — 证据不足：online user-facing agentic RL 的偏好漂移、deployment feedback loop 和 unsafe tool use 还缺 controlled public artifact；Agent Lightning [40] 解决框架接入，不等于解决线上因果评估。

悬而未决的问题

  • Q1.matched base、数据、distillation 和 inference compute 都控制后，R1-Zero-like 推理收益还剩多少？Liu et al. [7] 提出约束，DeepSeek-R1 [4] 与 OpenAI o1 System Card [3] 仍缺完整公开 ablation。
  • Q2.agentic RL 导致 reward hacking、KL drift、entropy collapse 或 unsafe tool use 的直接 controlled evidence 在哪里？AttributionCA [19] 涉及 entropy collapse，DAPO [41] 和 GSPO [42] 提供稳定性线索，但 RL-specific 失败链条还不完整。
  • Q3.outcome、process、step、turn 和 attribution reward 在同模型、同任务、同预算下谁赢？AgentPRM [11]、PRL [12]、TurnReward [34]、SegmentPO [17] 和 CAPO [18] 还没有给出一张可判定的共同 ablation 表。
  • Q4.non-RL prompting、imitation、planning 或 MCTS 能否在 fair budget 下追平 RL-trained tool/search/SWE agents？ReAct [36]、Toolformer [37] 和 WebGPT [38] 说明这些对照不能省，但与 Search-R1 [24]、ToRL [26]、WebAgent-R1 [30] 的同预算比较仍少。
  • Q5.online agentic RL 面对真实用户、偏好变化和 deployment feedback loop 时会怎样？WebRL [29]、AutoEvalAgents [39] 和 Agent Lightning [40] 提供工程入口，但 user-facing online RL 仍等待更多 controlled experiment 和 public artifact。
  • Q6.attribution 分数何时可以近似因果贡献？TreeCA [20]、InT [21]、HindsightCA [22] 和 CARL [23] 更适合结构化或可重放环境；开放网页环境中的反事实污染仍等待更干净 protocol。
