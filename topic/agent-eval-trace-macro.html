Agent Eval：从单条 Trace 判分到 Macro Eval

先固定单条 trace 的判分合同，再用切片和 macro eval 找系统性失败

15 篇论文·2026年6月10日

领域综述

核心判断：agent eval 的主问题不是再发明一个总分，而是把“可复跑的判分面”做成优化梯度。单条 trace 先要可信：能用代码判断的格式、工具参数、数值计算、权限边界和最终状态，应该写成断言或环境 oracle；不能写死的证据选择、推理依据、风险升级和整条决策路径，再交给校准过的 LLM judge，并把 judge 理由结构化保存。OpenAI macro eval cookbook 的关键不是“聚类 trace”，而是先把每条 trace 压成包含 case_type、run_outcome、eval_finding、behavior_pattern 候选信号的结构化摘要，再在已打过分的群体上发现复发模式。[1] Anthropic 的 agent 设计建议也指向同一约束：agent 只有在开放步骤、工具反馈和错误恢复不可预先写死时才值得上，工具接口与沙盒必须透明，否则评测测到的是框架雾而不是能力。[3]

更实用的分层是三层：trace 级 eval 判断“这一条是否可信”；slice 级 eval 按场景、工具、难度、agent 版本、模型版本、prompt 版本和预算切开，回答“哪里变差”；macro eval 在已打标 trace 上做无监督聚类与影响力排序，回答“哪类失败值得先修”。这三层不能倒过来：直接把原始长 trace 扔进聚类，会让工具 payload、重复状态日志和文本长度主导距离；直接让 LLM judge 看所有内容，又会把可验证的格式/计算错误变成昂贵且不稳定的主观判断。更稳的管线是 deterministic checks 优先，LLM judge 只处理语义和决策路径，再把每条 trace 变成可比较的摘要文档。[2][5]

pretrain eval for agent 和 posttrain eval 的差别在于控制变量。pretrain 侧应测底座可被 agent harness 使用的原子能力：指令保真、代码/工具 schema 理解、长上下文证据保持、执行语义、函数调用参数约束和低成本 likelihood/BPB 辅助信号；它不应宣称“会代理完成任务”。posttrain / harness 侧才测闭环：任务分解、工具选择、观察反馈利用、错误恢复、human handoff、成本和安全边界。Karpathy 的 autoresearch 设置给了一个朴素但重要的实验纪律：`prepare.py` 和 `evaluate_bpb` 是不可改的 ground-truth metric，优化只发生在 `train.py`；agent eval 也需要这样的冻结计分面，否则优化目标会在实验中漂移。[4]

TL;DR

agent eval 应该被设计成优化梯度，而不是赛后解释。第一层是单条 trace：schema、工具参数、权限、数值计算、最终状态和环境副作用能写断言就写断言；LLM judge 只判证据支持、风险升级、推理依据和决策路径。[3][2] 第二层是切片：同一总分下，按场景、工具、难度、agent 版本、模型版本、prompt 版本、预算和数据时间切开，才能知道问题是在工具 schema、路由、长上下文证据、恢复策略还是模型底座。[8][9][12] 第三层才是 macro eval：不要直接聚类原始 trace，先把每条 trace 压成结构化摘要，带上 case_type、run_outcome、eval_finding 和关键行为信号，再在已打分 trace 上做无监督聚类，并按影响力而不是频率排序。[1][13] pretrain eval 只应声称底座原子能力，如执行语义、repo 结构、工具 schema 理解和证据保持；posttrain eval 才测闭环系统，如任务分解、工具调用、错误恢复、human handoff、成本和安全。[10][11][7]

核心断言

#1能代码判断的失败不应交给 LLM judge：JSON schema、工具参数、权限、数值计算和最终状态是 eval contract，不是裁判意见。[3][2]
#2raw trace 不是 macro eval 的好输入；结构化摘要的字段选择决定聚类能看见什么，比 UMAP/HDBSCAN 的小参数更重要。[1][13]
#3macro eval 的优先级应按影响力排，而不是按频率排：低频但会造成错误提交、越权调用或错误升级的模式，要高于高频低害的格式瑕疵。[1][5]
#4pretrain eval for agent 测的是可被 harness 调用的底座原子能力；posttrain eval 测的是模型、工具、权限、状态和恢复策略组成的闭环系统。[10][11][7]

§1 单条 trace 先可信：deterministic checks 是第一层裁判

agent eval 的最低门槛不是“judge 写得像不像专家”，而是同一条 trace 的基本事实能否被复核。Anthropic 的 prompt chaining 和 routing pattern 都把 programmatic gate 放在中间步骤：只要某一步有明确格式、阈值、工具输出或环境状态，就应该用代码挡住错误。[3] 这条原则在 agent 上更强，因为 trace 里有大量非语言证据：tool name、arguments、return code、stdout/stderr、文件 diff、浏览器状态、API 响应、权限审批、最终数据库状态。让 LLM judge 去判断这些，等于把低方差 oracle 换成高方差文本裁判。

更稳的 trace contract 至少包含四类断言。第一，format assertions：工具调用是否符合 schema、字段是否缺失、单位是否一致。第二，tool assertions：该任务是否调用了必须调用的工具，是否调用了禁止工具，参数是否落在授权范围内。第三，state assertions：最终文件、数据库、网页或工单状态是否满足 oracle；SWE-bench 的 patch+test 就是这个层面的强例子。[7] 第四，numeric assertions：金额、日期、token budget、retry count、置信区间和汇总数是否能重算。OpenAI 的 agent improvement loop 把 trace 反馈转成可复跑 eval，价值就在这里：每一次失败都要沉淀成下一次能自动跑的检查，而不是一次性的人工意见。[2]

LLM judge 不是第一层裁判；它是 deterministic oracle 覆盖不到的语义层裁判。

§2 LLM judge 判路径，不判机器能算的事实

LLM judge 的价值在语义空隙：证据是否足以支持结论，工具 observation 是否被正确吸收，风险是否该升级，人类交接是否过早或过晚，整条决策路径是否避免了局部正确但全局错误。ReAct 之后，agent trace 不再只是最终答案，而是 reason、act、observe 的交替链。[6] 因此 judge rubric 应该围绕路径写，而不是围绕单句回答写。一个好的 rubric 会问：这一轮计划是否引用了可见证据；工具返回与下一步动作之间是否有因果关系；失败后是否使用新信息重试；是否在权限或不确定性超过阈值时暂停。

这也解释了为什么 judge 输入不能是原始 trace 全量文本。长 trace 中有重复状态、工具 payload、日志噪声和无关上下文，LLM judge 会把注意力浪费在可编程过滤的材料上。更好的输入是结构化 judge packet：任务目标、场景类型、关键工具步骤、deterministic check 结果、最终状态、候选风险点和少量原文证据。OpenAI macro eval cookbook 的 case_type/run_outcome/eval_finding 标签栈给了一个实用格式；它先把 lower-level eval 变成局部症状，再让 macro 层看这些症状如何复发。[1] judge 的输出也要结构化：score、failed_dimension、evidence_span、recommended_regression_check，而不是只给“好/坏”。

§3 切片比总分重要：切多细，就看见多细的问题

agent 系统的 aggregate 分数经常把根因压平。同样是失败，可能是 browser tool 在长页面上定位错、shell tool 超时、检索工具返回过时上下文、planner 过早停止、critic 过宽、模型版本不懂 schema、或者 prompt 版本把风险升级阈值写低。SWE-agent 和 OpenHands 的共同教训是 harness 不是实现细节；ACI、typed actions、Docker runtime、编辑原语和 benchmark hooks 都会改变结果。[8][9] 因而每个 eval run 至少要记录：agent_version、model_version、prompt_version、toolset_version、sandbox_version、budget、temperature、max_turns、retry_policy、scenario_type、difficulty、data_time。

切片的目的不是报更多表，而是把修复动作从“提升模型”改成“改哪一层”。按场景切，可以看 clarification、compliance、coding、web、data-analysis 是否是不同问题；按工具切，可以看同一模型在 browser、shell、retrieval、spreadsheet 上是否各自掉分；按难度切，可以区分 easy case 的格式回归和 hard case 的推理瓶颈；按版本切，才能把模型更新、prompt 更新和 harness 更新解耦。LiveCodeBench 把时间窗口显式化，提醒 agent eval 也必须记录任务发布时间与模型 cutoff；否则新版本提升可能只是数据时间不同。[12] 一个团队能切多细，就能看见多细的问题；看不见的维度，最后都会被归因到“模型不够强”。

§4 Macro eval：在已打分 trace 上聚类，按影响力排修复队列

macro eval 的常见误用是把它当日志聚类：攒够 trace 后直接 embedding，然后给几个 cluster 命名。这个流程通常会得到漂亮但不可行动的主题，因为原始 trace 的距离受日志长度、工具 payload、重复状态更新和模板化输出影响。OpenAI cookbook 更值得借鉴的地方，是先做 lower-level eval，再把每条 trace 转成结构化摘要文档：case_type 是输入场景，run_outcome 是终局，eval_finding 是低层症状，behavior_pattern 才是群体层发现。[1] 摘要字段不是清洗细节，而是 macro eval 的感受野；字段里没有工具版本，就发现不了工具版本回归；字段里没有风险升级，就发现不了 escalation 模式。

聚类之后也不能按频率拍板。agent 失败的产品损失常常是长尾：越权写操作、错误退款、错误提交代码、错误发邮件、错误关闭告警，频率低但损失高。OpenAI cookbook 用 impact_score 将 prevalence 和 severity 合起来排队，[1] 方向是对的；实际系统还应加入业务权重、可恢复性、自动检测率和人工介入成本。AgentTrace 补上了下一步：高影响力模式出现后，用 causal graph 从 failure node 回溯，优先检查近邻 tool call、handoff、shared memory 和异常传播，而不是默认重写总 prompt。[5] macro eval 的输出应是一张修复队列：模式名、影响力、代表 trace、疑似 owner、建议新增的 regression eval。

§5 Pretrain eval for agent：只测底座原子能力；闭环留给 posttrain

pretrain eval for agent 容易被高估，因为 agent 最终表现看起来像一个统一能力。但训练前后的控制变量不同：pretrain 侧没有固定 agent policy、工具权限、错误恢复、human handoff 和 verifier，因此它只能测底座是否具备可被 harness 调用的原子能力。代码方向上，CRUXEval 测执行语义，RepoBench 测跨文件上下文，二者都比单纯 code likelihood 更接近 agent 可用能力，但仍不能推出“会修 issue”。[10][11] 长上下文方向上，RULER/LongBench 类指标能测证据保持和位置鲁棒性；工具方向上，可以用 schema following、函数参数约束、JSON repair、API doc grounding 和模拟 tool-use 任务做轻量筛选。这些是 pretrain 的可扩展体检，不是部署结论。

posttrain / harness eval 才能测闭环：agent 是否能把目标拆成步骤，是否选对工具，是否从 observation 中改变计划，是否在失败后恢复，是否在不确定或高风险时交给人。SWE-bench、WebArena、OSWorld、GAIA、tau-bench 等公共基准各自覆盖一部分闭环，但都受 harness 设定影响；因此每个结果都要同时报告 model 与 harness 参数。[7][8] Karpathy 的 autoresearch 程序把 `prepare.py` 和 `evaluate_bpb` 冻结，把修改空间限定在 `train.py`，这个纪律对 agent eval 更重要：benchmark 一旦在优化中被改写，就不再提供方向信号，而会变成被系统适配的移动目标。[4] eval 是成本，但更是护城河；能把 trace 变成稳定梯度的团队，迭代会比只看榜单的团队快。

研究立场对比

阵营 A：一个端到端 benchmark 分数足够

立场 — 真实任务最终只关心是否完成；用 SWE-bench、WebArena、OSWorld 或内部 gold set 排名即可，trace 判分和 macro eval 只是诊断工具。

证据：[7]

反方 — 端到端分数是必要锚点，但无法区分模型、工具、权限、重试、budget 和 judge 的贡献；当分数接近或上线回归时，不看 trace 与 slice 就没有可行动根因。[8][1]

判词 — 保留端到端锚点，但不得单独使用；每个锚点都应配 trace-level checks、slice board 和 macro failure queue。

阵营 B：LLM judge 可以统一处理全部评测

立场 — agent 行为复杂，规则写不完；让强模型读 trace 并按 rubric 打分，比维护一堆断言更灵活。

证据：[1]

反方 — LLM judge 应处理语义和路径，但格式、参数、权限、数值和最终状态是低方差 oracle；把这些交给 judge 会增加成本和不稳定性，也让失败消息不可复跑。[3][2]

判词 — 采用分工：deterministic checks 先跑，LLM judge 只接收结构化 packet 和明确 rubric。

阵营 C：macro eval 可以直接聚类 raw trace

立场 — trace 越完整，embedding 能看到的信息越多；直接聚类避免人为摘要丢信息。

证据：[13]

反方 — raw trace 的距离常被长度、payload、重复日志和模板语言主导；OpenAI cookbook 的关键步骤是先构造 doc_structured_summary，让聚类看见 case、outcome、finding 和行为模式，而不是日志形状。[1]

判词 — 摘要构造是 macro eval 的主要设计变量；先决定摘要字段，再调聚类算法。

实践要点

可执行清单：
1) 给每个 agent run 生成 trace packet：goal、scenario、tool steps、deterministic check results、final state、risk flags、version metadata。
2) 把能代码判断的项目全部写成断言：schema、tool permission、argument range、numeric calculation、timeout、final state。失败消息要能直接变成 regression case。
3) LLM judge 只判四类：evidence support、reasoning groundedness、decision path、handoff/escalation timing。judge 输出必须有 failed_dimension、evidence_span、confidence 和 suggested_regression。
4) 每个分数至少按八个维度切：scenario、tool、difficulty、agent_version、model_version、prompt_version、toolset_version、budget。版本字段缺失的 trace 不应进入发布比较。
5) macro eval 不吃 raw trace；先生成结构化摘要，再在已打分 trace 上聚类。聚类结果按 impact 排，不按频率排。
6) 高影响力模式必须落到 owner：model、prompt、tool schema、sandbox、retrieval、planner、verifier、policy 或数据时间。没有 owner 的 cluster 只是可视化，不是 eval。
7) pretrain eval 只声明原子能力：执行语义、repo 结构、工具 schema、长上下文证据保持、格式遵循。posttrain eval 才声明闭环 agent 能力。
8) eval harness 要像 Karpathy autoresearch 的 `prepare.py` 一样冻结；实验中允许改 agent，不允许改计分面。计分面一改，历史趋势要重算。

悬而未决的问题

  • Q1.trace-level deterministic checks 与 LLM judge 的最佳预算分配是多少？需要在同一批生产 trace 上报告成本、稳定性、人类一致率和 bug catch rate。
  • Q2.结构化 trace 摘要的字段怎样选择才最稳？需要 ablation：去掉 tool version、risk flags、eval_finding、budget 后，macro cluster 的可行动性下降多少。
  • Q3.pretrain 原子能力与 posttrain 闭环分数之间哪些相关性稳定？CRUXEval、RepoBench、long-context probes、schema following 与 SWE/Web/OS agent 成功率之间仍缺受控 model ladder。
  • Q4.impact_score 应如何纳入真实业务损失？频率、严重度、可恢复性、自动检测率和人工介入成本的权重需要按产品类别重新标定。

LLM judge 应接手的是证据是否支撑、风险是否升级、推理是否有依据、整条决策路径是否合理；输入要是结构化 trace 摘要和裁判 rubric。
