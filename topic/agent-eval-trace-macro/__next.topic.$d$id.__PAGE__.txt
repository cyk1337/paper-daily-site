9:T9cb,核心判断：agent eval 的主问题不是再发明一个总分，而是把“可复跑的判分面”做成优化梯度。单条 trace 先要可信：能用代码判断的格式、工具参数、数值计算、权限边界和最终状态，应该写成断言或环境 oracle；不能写死的证据选择、推理依据、风险升级和整条决策路径，再交给校准过的 LLM judge，并把 judge 理由结构化保存。OpenAI macro eval cookbook 的关键不是“聚类 trace”，而是先把每条 trace 压成包含 case_type、run_outcome、eval_finding、behavior_pattern 候选信号的结构化摘要，再在已打过分的群体上发现复发模式。[OpenAIMacroEvals2026] Anthropic 的 agent 设计建议也指向同一约束：agent 只有在开放步骤、工具反馈和错误恢复不可预先写死时才值得上，工具接口与沙盒必须透明，否则评测测到的是框架雾而不是能力。[AnthropicAgents2024]

更实用的分层是三层：trace 级 eval 判断“这一条是否可信”；slice 级 eval 按场景、工具、难度、agent 版本、模型版本、prompt 版本和预算切开，回答“哪里变差”；macro eval 在已打标 trace 上做无监督聚类与影响力排序，回答“哪类失败值得先修”。这三层不能倒过来：直接把原始长 trace 扔进聚类，会让工具 payload、重复状态日志和文本长度主导距离；直接让 LLM judge 看所有内容，又会把可验证的格式/计算错误变成昂贵且不稳定的主观判断。更稳的管线是 deterministic checks 优先，LLM judge 只处理语义和决策路径，再把每条 trace 变成可比较的摘要文档。[AgentImprovementLoop2026][AgentTrace2026]

pretrain eval for agent 和 posttrain eval 的差别在于控制变量。pretrain 侧应测底座可被 agent harness 使用的原子能力：指令保真、代码/工具 schema 理解、长上下文证据保持、执行语义、函数调用参数约束和低成本 likelihood/BPB 辅助信号；它不应宣称“会代理完成任务”。posttrain / harness 侧才测闭环：任务分解、工具选择、观察反馈利用、错误恢复、human handoff、成本和安全边界。Karpathy 的 autoresearch 设置给了一个朴素但重要的实验纪律：`prepare.py` 和 `evaluate_bpb` 是不可改的 ground-truth metric，优化只发生在 `train.py`；agent eval 也需要这样的冻结计分面，否则优化目标会在实验中漂移。[KarpathyAutoresearch2025]a:Tb10,The central claim is that agent evaluation should not chase another aggregate score; it should turn rerunnable scoring surfaces into the optimization gradient. A single trace must be trustworthy first: format, tool arguments, numeric computation, permissions, and final state should be checked by code or environment oracles whenever possible. The parts that cannot be hard-coded—evidence use, reasoning support, risk escalation, and whole-trajectory decision quality—should go to calibrated LLM judges, with structured judge rationales saved. The key move in OpenAI's macro-evals cookbook is not “cluster raw traces”; it first compresses each trace into a structured document carrying case_type, run_outcome, eval_finding, and candidate behavior signals, then discovers recurring patterns over the already-scored population.[OpenAIMacroEvals2026] Anthropic's guidance points to the same constraint: use agents only when open-ended steps, tool feedback, and recovery cannot be pre-scripted, and keep tool interfaces and sandboxes transparent, otherwise the eval measures framework fog rather than capability.[AnthropicAgents2024]

A practical stack has three layers: trace-level eval asks whether this run is trustworthy; slice-level eval cuts by scenario, tool, difficulty, agent version, model version, prompt version, and budget to ask where behavior changed; macro eval clusters already-labeled traces and ranks patterns by impact to ask what to fix first. Reversing the order is brittle: clustering raw long traces lets tool payloads, repeated status logs, and text length dominate distance; asking an LLM judge to inspect everything turns verifiable format and arithmetic bugs into expensive subjective judgments. The stronger pipeline runs deterministic checks first, reserves LLM judging for semantics and decision paths, and then converts each trace into a comparable summary document.[AgentImprovementLoop2026][AgentTrace2026]

Pretrain eval for agents and posttrain eval differ in controlled variables. Pretraining-side eval should measure atomic capabilities that a harness can exploit: instruction fidelity, code/tool-schema understanding, long-context evidence retention, execution semantics, function-call argument constraints, and low-cost likelihood/BPB auxiliary signals. It should not claim the model can delegate work end to end. Posttrain and harness eval should measure the closed loop: task decomposition, tool choice, use of observations, recovery, human handoff, cost, and safety boundaries. Karpathy's autoresearch setup gives a useful experimental discipline: `prepare.py` and `evaluate_bpb` are the immutable ground-truth metric, while optimization happens only in `train.py`; agent eval needs the same frozen scoring surface, or the target drifts during the experiment.[KarpathyAutoresearch2025]b:T54a,Agent eval should be designed as an optimization gradient, not as post-hoc commentary. Layer one is the single trace: write assertions for schema, tool arguments, permissions, arithmetic, final state, and environment side effects whenever possible; reserve LLM judges for evidence support, risk escalation, grounded reasoning, and decision-path quality.[AnthropicAgents2024][AgentImprovementLoop2026] Layer two is slicing: under the same aggregate score, cut by scenario, tool, difficulty, agent version, model version, prompt version, budget, and data time to locate whether the problem lives in tool schema, routing, long-context evidence, recovery policy, or the base model.[SWEAgent2024][OpenHands2024][LiveCodeBench2024] Layer three is macro eval: do not cluster raw traces. First compress each trace into a structured summary with case_type, run_outcome, eval_finding, and behavior signals; then run unsupervised discovery over already-scored traces and rank by impact rather than frequency.[OpenAIMacroEvals2026][BERTopic2022] Pretraining eval should only claim substrate skills such as execution semantics, repo structure, tool-schema understanding, and evidence retention; posttraining eval should measure the closed-loop system: task decomposition, tool use, recovery, human handoff, cost, and safety.[CRUXEval2024][RepoBench2023][SWEBench2023]c:T608,The minimum bar for agent eval is not whether the judge sounds expert; it is whether the basic facts of the same trace are auditable. Anthropic's prompt-chaining and routing patterns put programmatic gates between steps: whenever a step has a clear format, threshold, tool output, or environment state, code should block the error.[AnthropicAgents2024] This principle is stronger for agents because traces contain large amounts of non-language evidence: tool names, arguments, return codes, stdout/stderr, file diffs, browser state, API responses, permission approvals, and final database state. Asking an LLM judge to evaluate these swaps a low-variance oracle for a high-variance text judge.

A stronger trace contract has at least four assertion families. First, format assertions: whether tool calls satisfy schemas, whether fields are missing, and whether units agree. Second, tool assertions: whether mandatory tools were used, forbidden tools were avoided, and arguments stayed within authorization. Third, state assertions: whether final files, databases, pages, or tickets satisfy the oracle; SWE-bench's patch+test setup is a strong example at this layer.[SWEBench2023] Fourth, numeric assertions: whether money, dates, token budgets, retry counts, confidence intervals, and aggregates can be recomputed. The value of OpenAI's agent improvement loop is exactly this conversion from trace feedback into rerunnable evals: each failure should become a check that can run next time, not a one-off review comment.[AgentImprovementLoop2026]d:T5e0,LLM judges are useful in semantic gaps: whether evidence supports the conclusion, whether tool observations were absorbed correctly, whether risk should have escalated, whether human handoff was too early or too late, and whether the decision path avoided local correctness with global failure. After ReAct, an agent trace is not just a final answer; it is an alternating chain of reason, act, and observe.[ReAct2022] Judge rubrics should therefore be written around paths rather than single responses. A good rubric asks whether the plan cites visible evidence, whether tool returns causally affect the next action, whether retries use new information, and whether the agent pauses when permission or uncertainty crosses a threshold.

This is also why judge input should not be the full raw trace. Long traces contain repeated status, tool payloads, log noise, and irrelevant context; an LLM judge will spend attention on material that code could filter. The better input is a structured judge packet: task goal, scenario type, key tool steps, deterministic-check results, final state, candidate risk points, and a few raw evidence spans. OpenAI's macro-eval cookbook gives a practical label stack in case_type/run_outcome/eval_finding; it first turns lower-level evals into local symptoms, then lets the macro layer see how those symptoms recur.[OpenAIMacroEvals2026] Judge output should also be structured: score, failed_dimension, evidence_span, recommended_regression_check, not just “good/bad”.e:T665,Aggregate scores often flatten root causes in agent systems. The same failure could come from a browser tool mislocating content on long pages, a shell timeout, stale retrieval context, premature planner stop, loose critic behavior, a model version that misunderstands schema, or a prompt version that lowered risk-escalation thresholds. The shared lesson from SWE-agent and OpenHands is that the harness is not an implementation detail; ACI, typed actions, Docker runtime, edit primitives, and benchmark hooks all change outcomes.[SWEAgent2024][OpenHands2024] Every eval run should therefore record at least agent_version, model_version, prompt_version, toolset_version, sandbox_version, budget, temperature, max_turns, retry_policy, scenario_type, difficulty, and data_time.

The purpose of slicing is not to report more tables; it is to turn “improve the model” into “fix this layer”. Slicing by scenario separates clarification, compliance, coding, web, and data-analysis failures. Slicing by tool shows whether the same model fails differently on browser, shell, retrieval, and spreadsheet tools. Slicing by difficulty separates easy-case format regressions from hard-case reasoning bottlenecks. Slicing by version decouples model updates, prompt updates, and harness updates. LiveCodeBench makes time windows explicit, reminding agent evals to record task release time and model cutoff; otherwise a version improvement may simply reflect different data time.[LiveCodeBench2024] A team sees failures only as finely as it slices them; invisible dimensions eventually get misattributed to “the model is not strong enough”.f:T6a4,A common macro-eval misuse is treating it as log clustering: collect enough traces, embed them directly, then name a few clusters. This often produces attractive but unactionable topics because raw-trace distance is dominated by log length, tool payloads, repeated status updates, and templated outputs. The OpenAI cookbook's more important move is to run lower-level evals first, then convert each trace into a structured document: case_type is the setup, run_outcome is the ending, eval_finding is the local symptom, and behavior_pattern is the population-level discovery.[OpenAIMacroEvals2026] Summary fields are not cleanup details; they define the macro eval's field of view. Without tool version, tool-version regressions cannot be discovered; without risk escalation, escalation patterns cannot be discovered.

After clustering, priority should not be frequency alone. Agent failures often have long-tail product loss: unauthorized writes, wrong refunds, bad commits, mistaken emails, or closed alerts can be rare but severe. The OpenAI cookbook's impact_score combines prevalence and severity,[OpenAIMacroEvals2026] which is the right direction; production systems should also add business weight, recoverability, automatic-detection rate, and human-intervention cost. AgentTrace adds the next step: once a high-impact pattern appears, use a causal graph to walk backward from the failure node and inspect nearby tool calls, handoffs, shared memory, and exception propagation, rather than defaulting to rewriting the global prompt.[AgentTrace2026] The output of macro eval should be a repair queue: pattern name, impact, representative traces, suspected owner, and the regression eval to add.10:T73b,Pretrain eval for agents is easy to overclaim because the final agent behavior looks like one unified capability. But controlled variables differ across training stages: pretraining-side eval has no fixed agent policy, tool permissions, recovery loop, human handoff, or verifier. It can only measure atomic substrate skills a harness can exploit. For code, CRUXEval measures execution semantics and RepoBench measures cross-file context; both are closer to agent-usable ability than code likelihood alone, but neither proves the model can fix issues.[CRUXEval2024][RepoBench2023] For long context, RULER/LongBench-style metrics measure evidence retention and positional robustness; for tools, schema following, argument constraints, JSON repair, API-doc grounding, and simulated tool-use tasks can provide cheap screening. These are scalable pretraining checkups, not deployment conclusions.

Posttraining and harness eval are where the closed loop is measured: whether the agent decomposes goals, selects tools, changes plans from observations, recovers from failure, and hands off to humans under uncertainty or risk. SWE-bench, WebArena, OSWorld, GAIA, tau-bench, and related public benchmarks each cover part of that loop, but all are sensitive to harness choices; every result should therefore report both model and harness parameters.[SWEBench2023][SWEAgent2024] Karpathy's autoresearch program freezes `prepare.py` and `evaluate_bpb` while restricting optimization to `train.py`; that discipline is even more important for agent eval. Once the benchmark is modified during optimization, it no longer provides a directional signal and becomes a moving target adapted by the system.[KarpathyAutoresearch2025] Eval is a cost, but also a moat: teams that turn traces into stable gradients will iterate faster than teams that only read leaderboards.11:T647,Executable checklist:
1) Produce a trace packet for every agent run: goal, scenario, tool steps, deterministic-check results, final state, risk flags, and version metadata.
2) Turn everything code can judge into assertions: schema, tool permissions, argument ranges, numeric calculations, timeouts, and final state. Failure messages should directly become regression cases.
3) LLM judges should score only four families: evidence support, reasoning groundedness, decision path, and handoff/escalation timing. Judge output must include failed_dimension, evidence_span, confidence, and suggested_regression.
4) Slice every score by at least eight dimensions: scenario, tool, difficulty, agent_version, model_version, prompt_version, toolset_version, and budget. Traces missing version fields should not enter release comparisons.
5) Macro eval should not consume raw traces; generate structured summaries first, then cluster already-scored traces. Rank clusters by impact, not frequency.
6) Every high-impact pattern must map to an owner: model, prompt, tool schema, sandbox, retrieval, planner, verifier, policy, or data time. A cluster without an owner is visualization, not eval.
7) Pretrain eval should claim only atomic skills: execution semantics, repo structure, tool schema, long-context evidence retention, and format following. Posttrain eval is where closed-loop agent capability is claimed.
8) Freeze the eval harness like Karpathy autoresearch freezes `prepare.py`; experiments may change the agent, not the scoring surface.
