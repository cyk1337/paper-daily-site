Agent harness 设计：tool 协议 × 执行沙盒 × Skills × Constitution

同一 base model 下，coding agent 的差距由 tool 协议、sandbox、edit、context、skills 与 constitution 共同决定。

16 篇论文·2026年6月1日

作者@Thor·gpt-5.5

60 篇扩展证据（支持 6 · 反证 4 · 拓展 48 · 切线 2）·知识聚类 9·悬问 5

领域综述

同一档 base model 上，coding agent 的可见差距主要来自 harness。更准确的拆法是四层：tool 协议决定 agent 能看见和调用什么；执行沙盒决定失败、越权和恢复成本；edit 原语决定代码修改是否可审计；Skills 与 Constitution 把“怎么做”和“不能做什么”从 system prompt 中拆成可版本化的 plug-in。ReAct 给出 reasoning/action 交替轨迹，SWE-agent 用 ACI 证明 tool 形式本身能改变 SWE-bench 结果，OpenHands 把 typed action、Docker runtime 和 benchmark hook 做成可复现实验平台。Aider、Cline、Cursor、Claude Code、Codex CLI 则把这些机制推到产品侧：git/test recovery、IDE editor-as-runtime、host shell permission、MCP 接入、sub-agent dispatch、context compaction。Claude Code 内部细节只应按二手证据处理，shareAI-lab 与 Yuyz0112 的反混淆和 runtime monkey-patch 可以互相校验，但不能替代官方说明。一个可落地的评估框架不应只比较 tool-call JSON，而要按 9 条轴打分：tool protocol、edit primitive、planning、context、sandbox、sub-agent、stop/recovery、skills、constitution。

TL;DR

结论很直接：2025–2026 的 coding agent 不应按“用了哪个模型”排序，而应先看 harness。SWE-agent 把 ACI 当主变量，给出同一类 base model 下 resolve rate 可翻倍的开源证据；OpenHands 说明 typed actions + Docker + benchmark hook 才能做可复现实验；Aider、Cline、Cursor、Claude Code、Codex CLI 说明产品差距落在 edit 原语、权限确认、context 压缩、sub-agent 和恢复闭环。Skills 与 Constitution 是一对 plug-in：前者描述“怎么做”，后者约束“不能做什么”。MCP 使 tool 供给从 harness 二进制中解耦，但是否成为稳定标准还取决于鉴权、版本、审计和企业部署。

核心断言

#1在 SWE-agent 的 ablation 中，换 ACI 而不是换 base model，就能把 SWE-bench resolve rate 从个位数基线推到约 12% 档位；这使 harness 成为可测主变量 [3][17]。
#2MCP 的可检验断言不是“tool call 格式更优”，而是“tool discovery 不再 hardcode 到 harness”：到 2025 年，Cursor、Cline、OpenHands、Continue、Sourcegraph、Zed 都公开接入或支持 MCP [5][11][12][4]。
#3Agent Skills 的三层 progressive disclosure 将启动 context 从“全量常驻”改成“metadata 常驻、procedure 命中加载、resources 按需加载”；这与把所有规则塞进 system prompt 的方案可直接用 token 占用和命中率比较 [2][50]。
#4Claude Code 的 nO/I2A/h2A/wU2、92% compaction、Sonnet-4 主 + Haiku-3.5 辅等命名只能按 [reverse-engineered] 二手证据处理；shareAI-lab 的静态反混淆与 Yuyz0112 的 runtime patch 互相支持，但都不是官方 API 契约 [7][8][1]。
#5只报告 model name 的 SWE-bench 数字不可复现：至少还要报告 tool schema、sandbox 类型、test 可见性、retry budget、context compaction、human approval 和 patch submission 规则 7 项 [17][3][4]。

§1 Tool 协议不是格式细节，而是能力边界

结论先说：tool 协议决定 agent 的可组合性上限。ReAct 把 reasoning 与 acting 放进同一 trajectory，使模型可以在 observation 后更新计划 [6]。但 ReAct 的 action 仍接近自然语言命令，错误边界较软；SWE-agent 把 open/search/edit/submit 做成 typed registry，Yang et al. [3] 用 SWE-bench 说明 ACI 本身能改变 resolve rate，而不是只改变输出样式。OpenHands 进一步把 bash、file ops、browser、IPython 等 typed actions 接到 Docker runtime 与 benchmark hook，Wang et al. [4] 给出可复现的 harness 形态。

这条线与早期 tool-learning 文献的差别在主变量。Toolformer 用自监督插入 API call，目标是让模型学会何时调用工具 [23]；ART 把 multi-step reasoning 与 tool call 交替起来 [24]；Gorilla、ToolLLM、RestGPT 关注 API retrieval、调用准确率和真实 REST 接口 [26][28][27]；Tool Learning survey 和 Augmented LM survey 把这些能力归到工具增强模型 [25][22]。coding harness 的工程分界更硬：tool 不是训练样本里的函数名，而是带权限、状态、错误码、审计日志的外部契约。MCP 把这个契约拆成 client-server discovery 与 invocation，Anthropic [5] 反驳了“每个 harness hardcode 一组工具就够”的做法，因为工具供给侧会比 harness 发布节奏更快。OpenAgents 证明开放平台可以承载多类工具 [29]，但 MCP 的额外约束是协议层互通，而不是单个平台内互通。

把 tool 写成 JSON schema 只是第一步；真正的边界是 discovery、权限、错误恢复和审计。

§2 产品分化落在 edit、runtime、permission 与 recovery

同样是 coding agent，产品差距很少来自“能不能生成 patch”，更多来自 patch 如何进入仓库、命令如何执行、失败如何回滚。Aider 把工作流压到 git diff、commit、test、undo，Gauthier [10] 的取舍是少做 runtime 抽象，多依赖开发者已经信任的 git。Cline 把 VS Code editor-as-runtime、每次写入确认、terminal command approval 和 MCP 放在一起 [11]；Cursor 把相近机制产品化到 IDE agent、rules、background context 和 project-level setting [12]。Claude Code 的公开面是 CLI + Edit/Write/Bash/Task/MCP/CLAUDE.md [1]，Codex CLI 则把 terminal coding loop 接到 OpenAI 模型与本地 patch 流程 [13]。

OpenHands 与这些产品形成研究侧对照：Docker sandbox 是默认 runtime，typed action 和 benchmark hook 都可替换 [4]。CodeAct 走另一条路线，把 code 本身作为 action，让 agent 用可执行代码表达操作 [16]；这对灵活性有利，但权限边界必须更清楚。ar2r/openclaude 说明 harness 抽象可以与 backbone 解耦 [9]，Hermes function-calling 说明模型侧也在适配 structured tools [14]，OpenAI ChatGPT Agent 则把 browsing、terminal、connectors 放进托管环境 [15]。一条更稳的读法：CLI、IDE、Docker、托管 agent 不是同一问题的皮肤，它们对应四种不同状态位置和信任模型。

§3 Planning、context、sub-agent 与 Skills 解决的是状态分配

中层机械的分歧可以压成一个问题：状态放在哪里。ReAct 把状态留在单一轨迹里 [6]；AutoGen 把角色、tool、human-in-loop 拆成 conversable agents [44]；ChatDev 把软件开发拆成角色对话 [47]；CAMEL 与 BOLAA 分别强调 role-playing coordination 与 agent orchestration [49][48]；Language Agents as Optimizable Graphs 把 planner、executor、critic、memory 显式成图节点 [46]。Wang et al. 的 autonomous-agent survey 把 profile、memory、planning、action 分开 [45]，这套分解与产品 harness 的实际模块基本对齐。

Claude Code 的 Task/sub-agent、short-term memory 和 compaction 只能用社区证据描述。shareAI-lab [7] 静态读出 nO、I2A、h2A、wU2 等命名，Yuyz0112 [8] 用 runtime monkey-patch 记录 prompts/tools，并给出 Sonnet-4 主、Haiku-3.5 辅的二手观察；两者交叉支持“存在主 agent + sub-agent + compaction + per-tool prompt”的结构，但不能把具体类名当成 Anthropic API。Skills 是状态分配的另一面：Anthropic [2] 用 name/when_to_use、procedure、resources 做三层 progressive disclosure；Voyager 把经验保存为可执行 skill library [50]；CRAFT 与 CREATOR 分别强调 specialized toolset 检索和 tool creation [51][52]；Web-agent self-improvement 则把行为经验转成后续策略 [53]。一条更实用的定位：skill 是 tool 的操作手册，不是 tool；sub-agent 是状态隔离手段，不是自动变强的同义词。

§4 Evaluation 与 Constitution 必须绑定到 harness 版本

只看 benchmark 分数会误判 coding agent。SWE-bench 要求 repo-level patch 通过测试，Jimenez et al. [17] 给出比函数补全更接近真实 issue 的任务；但同一个模型在不同 tool schema、sandbox、test 可见性、retry budget 下会得到不同数字。AgentBench、GAIA、ML-Bench、API-Bank、MINT 分别覆盖多环境交互、通用助手、多文件 ML repo、tool calling 与多轮反馈 [30][31][32][33][34]。Reflexion、Self-Debug、Self-Refine、Autonomous Evaluation and Refinement 说明反馈能驱动修复，但反馈源从 verbal reflection 到 compiler/test/evaluator 不同，不能混成一个“self-improvement”标签 [35][36][37][38]。WebArena、WebVoyager、AutoWebGLM、Structured Reflection、Screen-only agents 则提醒 GUI/web action 的 observation 与 coding CLI 不同，评测迁移要重新定义 action space [39][40][41][42][43]。

Constitution 是同一问题的规范侧接口。Bai et al. [18] 把原则列表用于 critique/revision；Claude's Constitution、Collective Constitutional AI 与 Anthropic AUP 把原则、公众偏好和产品使用边界分成三条轨道 [19][20][21]。Lee et al. [57] 说明 AI feedback 可扩展偏好训练，Tang et al. [58] 则提醒 autonomous scientist 类系统应优先做 safeguard。反方也有合理部分：SayCan 把 affordance model 放在 LLM 外部 [54]，Gato 与 Lemur 把交互能力更多推向模型内部 [55][56]。结论层面的建议：coding-agent 评测应同时发布 harness manifest 与 constitution manifest，否则分数和安全边界都不可审计。

SWE-bench 分数如果没有 harness manifest，只能说明某个封闭配置在某天跑出了一个数。

研究立场对比

阵营 A：Harness-first，先改 ACI、runtime、edit 和 recovery

立场 — SWE-agent、OpenHands、Aider、Cline、Claude Code 的共同判断是：在同一档 base model 下，tool schema、sandbox、edit primitive、test loop 能直接改变任务完成率和事故半径 [3][4][10][11][1]。

证据：[3][4][10][11][1]

反方 — 反方认为交互层应更多进入模型。Gato 把多模态多任务 action policy 放进一个 generalist model [55]，Lemur 通过调优使模型更适合 natural language + code agent [56]，SayCan 把 action feasibility 交给外部 affordance model [54]。

判词 — 一条更稳的读法：短期 coding agent 应先按 harness-first 做。模型内化 action policy 适合长期研究，但 repo 写入、shell 执行、权限审计、企业工具接入都需要外部契约。

阵营 B：Docker sandbox 优先，而不是 host shell + allowlist 足够

立场 — OpenHands 和 SWE-agent 把执行环境放进 container，评测和复现成本更低，失败也更容易清理 [4][3]。AgentBench 与 WebArena 的多环境设定也支持“环境是评测对象的一部分” [30][39]。

证据：[4][3][30][39]

反方 — Cline、Cursor、Aider、Claude Code、Codex CLI 更接近 host workspace：它们用 human approval、visible diff、git undo、command confirmation 控制风险 [11][12][10][1][13]。这类设计对真实开发更顺手，但默认信任边界更宽。

判词 — 一个更务实的定位：benchmark、CI、untrusted repo 默认 Docker；个人本地开发可以 host shell，但必须有 per-command approval、git checkpoint、denylist/allowlist 和一键回滚。

阵营 C：Structured Edit 优先，而不是 whole-file rewrite

立场 — SWE-agent 的 edit registry、Claude Code 的 Edit/Write、Aider 的 diff-first workflow、Cline/Cursor 的 visible editor patch 都把修改变成可审计增量 [3][1][10][11][12]。

证据：[3][1][10][11][12]

反方 — CodeAct 与一些 tool-learning 方案倾向让模型生成可执行代码或完整操作脚本，灵活性更高 [16][24][26]。代价是审计粒度变粗，错误可能在执行后才暴露。

判词 — 结论层面的建议：repo 修改默认 structured Edit + diff review；whole-file rewrite 只用于生成新文件、机械迁移、格式化，且单次 patch 不超过可人工 review 的范围。

阵营 D：公开 constitution manifest，而不是只给封闭 policy

立场 — Constitutional AI、Claude's Constitution、Collective Constitutional AI、AUP 说明原则、公众偏好、产品边界可以分层公开 [18][19][20][21]。对 open-source harness，至少应公开可审计的 norm 文件。

证据：[18][19][20][21]

反方 — Tang et al. [58] 提醒 autonomous scientist 类系统存在 misuse 与 over-autonomy 风险；完整公开 guard 细节可能帮助规避。Lee et al. [57] 也说明许多偏好信号来自训练流程，不一定能完整映射成产品规则。

判词 — 一条更稳的做法：公开 high-level constitution、tool permission policy、拒绝类目和 appeal 机制；不公开 exploit-level guard prompt。开放不是裸露所有防线，而是让用户知道系统按什么原则拒绝、暂停和升级给人类。

实践要点

实操要点：
1. Do：先写 harness manifest，再报 benchmark。manifest 至少包含 model、tool schema、runtime/sandbox、test visibility、retry budget、context compaction、human approval、patch submission 8 项；否则 SWE-bench 数字不可比 [17][3][4]。
2. Do：tool 协议优先选可发现、可版本化、可审计的 client-server 形态。MCP 是当前最强候选，但要额外记录 server version、auth scope、log retention；不要把工具静态 hardcode 到 agent binary [5][29][28]。
3. Do：repo 修改默认 structured Edit + diff review。单个 patch 超过约 300–500 行、跨 10 个以上文件、或包含 generated file 时，应强制分批或请求人工确认 [3][10][11][12]。
4. Do：untrusted repo、benchmark、CI 默认 Docker sandbox；host shell 只给 trusted workspace，并要求 per-command approval、network policy、git checkpoint、undo path [4][11][13]。
5. Do：把 Skills 当 tool manual。启动 context 只放 metadata，procedure 命中后加载，资源按需加载；不要把 20 页团队规范常驻 system prompt [2][50][51]。
6. Do：sub-agent 只在状态隔离有收益时使用，例如 parallel search、large-repo exploration、independent verification；不要把每个步骤都拆成 agent conversation，否则延迟、cost、trace debugging 会失控 [44][46][7][8]。
7. Don’t：不要把 [reverse-engineered] 的 Claude Code 类名、92% compaction、模型分工写成官方事实。它们适合作为设计线索，不适合作为产品依赖 [7][8][1]。
8. Open：sandbox vs host-shell 的直接 controlled experiment 仍不足。可执行实验是同一任务、同一模型、同一 tool schema，只替换 Docker / host approval，比较 resolve rate、误删文件率、平均恢复步数和人工介入次数 [4][11][10]。

悬而未决的问题

  • Q1.SWE-agent、OpenHands、CodeAct 已给出 ACI、typed actions、Docker sandbox 和 SWE-bench 证据，但还缺少同一 base model、同一 benchmark、只替换 ACI/runtime 的多系统公开 ablation [3][4][16]。
  • Q2.Aider、Cline、Cursor、Codex CLI、Claude Code 的 edit primitive、per-write permission、git/test recovery 和 context handling 文档仍不对称；需要一份可复现实验，把这些字段统一记录到 harness manifest [10][11][12][13][1]。
  • Q3.MCP 是否会成为事实 tool 协议，仍取决于 rival REST/OpenAPI/function-calling 生态能否在鉴权、版本、审计、enterprise deployment 上给出同等互通性 [5][27][26][14]。
  • Q4.Agent Skills、Constitutional AI、Claude's Constitution、Collective CAI、AUP 已给出 skill/norm artifacts，但 open-source harness 如何公开 constitution 而不暴露 exploit-level guard prompt 仍需要产品样例 [2][18][19][20][21]。
  • Q5.Claude Code Task/sub-agent dispatch、compaction threshold、tool guards、prompt/tool traces 目前依赖 shareAI-lab 与 Yuyz0112 的 [reverse-engineered] 证据；等待官方 artifact 或可重复 runtime logging protocol [7][8][1]。

ReAct 把 reasoning 与 acting 放进同一条 trajectory，形成后续 agent harness 的语法原点。它不是 typed tool 系统，但给出一个稳固 invariant：模型在同一 context 中交替生成计划、调用环境、读取 observation。

SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering

OpenHands: An Open Platform for AI Software Developers as Generalist Agents

Aider: AI Pair Programming in Your Terminal
