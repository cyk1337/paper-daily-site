Critical Batch Size:从 gradient noise scale 到 token-optimal pretraining batch

临界 batch 是动态统计效率边界,不是集群越大越该乘的固定数

22 篇论文·2026年5月14日

领域综述

Critical batch size 的工程含义不是一个固定阈值,而是某个训练状态下“再扩大 token batch 还值不值”的局部判据。McCandlish 把它接到 gradient noise scale:当 batch 远小于噪声尺度时,更多样本主要降低梯度方差,step 数近似按 batch 反比下降;当 batch 远大于它时,新增 token 的边际信号迅速变低,wall-clock 并行收益开始以 token efficiency 为代价 [7][8]。这个尺度随 loss、训练时长、数据混合、optimizer、LR schedule 和参数化变化,不能拿一次小实验的绝对 batch 当全程常数 [18][19]。

真正要分清的是 compute-optimal batch 和 token-optimal batch。Kaplan 与 Chinchilla 约束的是模型规模 N、训练 token D 和 compute 的配比,没有直接给 optimizer step 数;batch 决定同样 D 个 token 被多少次参数更新消化,所以它是 scaling law 到 optimizer trajectory 的桥 [12][15]。如果目标是固定 FLOPs 或固定 token budget 到最低 loss,过大 batch 会减少更新次数并浪费 token signal;如果目标是固定日历时间或集群吞吐,更大 batch 仍可能合理,但必须用 warmup、LR scaling、gradient accumulation、packing/length 控制和 data order 把早期低 CBS 阶段兜住 [3][9][19]。

LR scaling 也不是 linear scaling rule 的永久许可证。Goyal 的 ResNet 和 LARS/LAMB 的 BERT 经验说明 warmup + linear/sqrt scaling 能把一部分大 batch 推进临界区,Smith & Le 则把“降 LR”换成“增 batch”,本质是在调 SGD noise 而不是免费扩大 batch [3][4][6][5][9]。LLM 预训练里 AdamW、token batch、sequence packing、梯度裁剪和 cooldown 共同定标;超过临界区后,正确动作常常不是继续乘 batch,而是重配 LR schedule 或把并行资源转向 model/data parallelism [10][11][13]。

2024/2025 的新证据把老理论拉回 LLM 训练现实。Zhang et al. 在 C4 上训练 85M 到 1.2B autoregressive LM,发现 Chinchilla 联合放大时 CBS 会升,但控制 token 数后它主要随数据量/训练时长而不是模型大小增长 [18]。Merrill et al. 在 OLMo 1B/7B 上直接测 CBS,报告 CBS 初始接近 0、早期快速上升后平台化,并用 batch-size warmup 在 OLMo 1B 上以 43% 更少 gradient steps 达到略好 loss;这支持“动态 batch schedule”,但仍应按 source-reported 证据处理 [19][17]。

TL;DR

CBS 是动态统计效率边界:从 gradient noise scale 推出的量纲随 loss、训练时长、optimizer 与 LR schedule 移动;B << CBS 时增 batch 主要省 step,B >> CBS 时新增 token 多数变成冗余平均。Compute-optimal 与 token-optimal batch 会在临界区后分叉,固定 FLOPs 偏吞吐,固定 token/loss 偏 update 密度 [7][15][19]。

核心断言

#1CBS 是动态函数,不是配置常数;loss、data duration、optimizer 和 LR schedule 改变梯度噪声与均值梯度的比值,临界点随之移动 [7][19]。
#2模型变大不自动要求等比例更大 batch;Zhang et al. 控制 token 后发现 CBS 对 data/training duration 更敏感 [18]。
#3Token-optimal batch 关心每个 token 是否带来有效 update;compute-optimal batch 关心集群时间和并行效率,两者在超过 CBS 后会分叉 [12][15]。
#4Linear LR scaling 只在低于或接近临界区时近似成立;超过临界区后,LR 继续线性放大会放大 schedule 风险而不是恢复 token signal [3][10]。
#5Smith 的增 batch 代替降 LR 是噪声退火坐标;它建议联合调 LR 和 batch,不是把 batch 当免费吞吐旋钮 [4][6]。
#6大 batch 泛化 gap 不是单因果;训练步数、epoch、LR 和目标 loss 控制后,Keskar 的 sharp-minima 叙事需要收窄 [1][2][8]。
#7Contrastive 大 batch 的任务收益不能直接迁移到 causal LM;CLIP 从 in-batch negatives 获益,LM batch 主要改变梯度估计和 update 数 [14]。

GNS 给量纲,不给常数

Critical batch size 应读成局部效率边界:同一个模型、同一个数据混合,在不同 loss 和不同 LR schedule 下都可能有不同临界点。McCandlish 的经验模型把 GNS 写成梯度方差与均值梯度平方的比值,解释了 batch 从小到大时 step efficiency 的弯折;Shallue 的系统测量则提醒这个弯折依赖目标 loss、optimizer 和调参预算 [7][8]。所以 CBS 的单位最好是 token batch,不是“样本数”;sequence packing、长度分布和 gradient accumulation 都会改变同一个全局 batch 的有效统计量。

早期争议容易误导训练决策。Keskar 把大 batch 和 sharp minima 绑定,Hoffer 说明许多 generalization gap 来自大 batch 下 update 数/训练时间不足,Smith 的 Bayesian/noise-scale 视角则把泛化和 SGD noise 连起来 [1][2][6]。对 LLM 训练团队,更稳的判断是先问“这个 batch 在当前 loss 区间是否还降低 step 数”,再问“这个 noise level 是否服务最终泛化”。

2024/2025 证据把 CBS 拉回 pretraining

Zhang et al. 的关键贡献是把 Chinchilla 联合放大拆开:在 85M 到 1.2B C4 autoregressive LM 上,CBS 随 N 和 D 一起放大会升高;但固定 D 后,模型变大几乎不带来同等 CBS 增长 [18]。这比“更大模型要更大 batch”的粗规则更有用,因为训练团队真正控制的是目标 token 数、数据重复、warmup 和并行策略。

Merrill et al. 的贡献是把 GNS proxy 改成 direct branched measurement:在 OLMo 1B/7B 上,source-reported CBS 初始接近 0,早期快速上升后平台化,并能用 batch-size warmup 让 OLMo 1B 少走 43% gradient steps 且 loss 略好 [19][17]。这不证明所有 LLM 都该动态加 batch;它证明“全程固定大 batch”会在最早期撞上最低 CBS,而小规模可审计 run 可以给大规模 run 提供 batch schedule 的形状。

Compute-optimal 与 token-optimal batch 不是同一个问题

Kaplan 和 Chinchilla 解决的是“给定 compute 应该买多少参数和 token”,不是“这些 token 应该分成多少次 update” [12][15]。Batch 介入的位置很具体:同样 D 个 token,global batch 越大,optimizer steps 越少;如果还在线性收益区,这只是并行化;如果超过 CBS,它会改变轨迹并损失 token efficiency。Besiroglu 和 Porian 对 Chinchilla 复现/差异的讨论也说明,token budget 与 optimization adequacy 的细节足以改变 scaling-law 读数 [21][20]。

因此 compute-optimal batch 常偏向吞吐和集群利用率,token-optimal batch 常偏向更多有效 update。GPT-3 把 GNS 作为 batch 选择依据,说明大模型训练早就需要这个桥;Megatron-LM 则提醒,超过 data-parallel batch 的统计边界后,更好的 wall-clock 方案可能是 tensor/model/pipeline parallelism,不是继续扩大 token batch [13][11]。

LR scaling 是联合定标,不是线性规则外推

Goyal 的 linear scaling + warmup 能成立,是因为 batch 扩大后用 LR 把单 token 更新幅度拉回相近轨迹;这个直觉在 ResNet/ImageNet 上很干净,迁到 AdamW 预训练时必须重新估计临界区 [3][10]。You 的 LARS/LAMB 说明 layer-wise trust ratio 可以稳定超大 batch BERT,但它解决的是 layer 尺度不均和 optimizer stability,不保证同样 token budget 的最优 loss [5][9]。

Smith & Le 的方案经常被误读成“batch 替代 LR 衰减”。更准确的读法是:LR 和 batch 共同控制 SGD noise,训练后期降噪可以通过降 LR 或增 batch 实现,但一旦 batch 超过局部 CBS,继续增 batch 会同时牺牲 token efficiency [4][6]。LLM recipe 里的 warmup、cosine/cooldown、gradient clipping、weight decay 和 accumulation 应该一起扫;单独扫 batch 会把 schedule failure 误判成 batch law。

训练策略应围绕动态 CBS 建约束

可执行策略是把 batch schedule 当成 optimizer schedule 的一部分。早期 loss 高、CBS 低时,小 token batch 或 batch warmup 保留 update 密度;中期 CBS 上升后,扩大 data-parallel batch 换 wall-clock;后期如果 loss 改善主要靠精细 annealing,继续扩 batch 往往不如调 cooldown、数据混合或并行形态 [19][18]。Adaptive batch schedule 的分布式训练论文把同一个判断扩展到 data/model parallel 约束:batch 是调度变量,不是单次启动参数 [22]。

任务差异也要进入判断。CLIP 这类 contrastive objective 的大 batch 直接增加 in-batch negatives,收益机制和 LM next-token loss 不同;BERT 的 LAMB 大 batch 是 optimizer 工程成就,也不等于 causal LM token-optimal batch [14][9]。对 GPT-era/Chinchilla-era 训练,最小可落地规则是:用 token batch 表达 global batch,记录每个阶段的 effective sequence length/packing/accumulation,同时汇报 token-to-loss 和 wall-clock-to-loss 两条曲线。

研究立场对比

Do not set one global max batch from a GNS estimate and keep it fixed.

立场 — 反对

判词 — The estimate is local; early low-CBS phases and later plateau behavior make fixed-large-batch runs token-inefficient [19].

Report both token-to-loss and wall-clock-to-loss for batch sweeps.

立场 — 支持

判词 — Compute-optimal and token-optimal objectives can disagree; a single throughput number hides wasted token signal [15][18].

Treat linear LR scaling as a warm-start heuristic, not a law.

立场 — 支持

判词 — It works in specific regimes with warmup, but AdamW/LAMB and late-stage noise annealing require joint tuning [3][9].

Use batch-size warmup only when direct small-run diagnostics show a rising CBS.

立场 — 有条件支持

判词 — Merrill et al. give source-reported OLMo evidence, but data mixture, optimizer, and packing can shift the shape [19][17].

悬而未决的问题

  • Q1.How stable is a small-model CBS schedule when transferred to a much larger model with different sequence length, tokenizer, and data mixture? — Zhang et al. suggest weaker model-size dependence after controlling D, but production recipes also change packing and optimizer details [18].
  • Q2.Can online GNS/CBS estimators be cheap enough for trillion-token runs without disrupting pipeline throughput? — Direct branched measurement is cleaner than GNS proxy, but expensive; practical schedules need a low-overhead signal [7][19].
  • Q3.Where is the boundary between data-parallel batch growth and model-parallel/system optimization? — Past CBS, data-parallel batch sacrifices token efficiency; systems work may deliver wall-clock wins without changing optimizer trajectory [11].
  • Q4.How should CBS be defined for packed variable-length sequences and mixed objectives? — Token batch, sample batch, and effective loss terms diverge when examples have different lengths or modalities [14].
  • Q5.Does late-training cooldown prefer smaller batch, lower LR, or both? — Smith-style noise annealing gives two knobs, but LLM pretraining rarely publishes enough ablations to separate them [4][10].
