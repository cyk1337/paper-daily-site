#1已起草2026-05-01-looped-lmlooped-language-modeling

Looped Language Modeling：depth-recurrence 作为 pretrain FLOPs 与 inference compute 之间的第三根旋钮

Looped Language Modeling: Depth-Recurrence as a Third Knob Between Pretrain FLOPs and Inference Compute

» Looped / recursive transformer 不是 'Universal Transformer 情怀向复辟',也不是 'ALBERT 的参数压缩小把戏'——需要回答的真正命题有两条:(i) 固定参数量下,把算力花在更深的 depth-loop 上,收益斜率与 '同 FLOPs 增加参数量' 这条 baseline 的实际差距是多少;(ii) 'loop' 到底应该发生在哪里——weight-shared 层栈循环(Huginn/MoR/UT 路线)还是 latent-state 连续循环(Coconut/CoCoMix 路线)?Geiping et al. [Geiping2025Huginn] 用 3.5B × r=8 × 800B token 的第一手 pretrain 证据把前一条推到了可落地的规模,Bae et al. [Bae2025MoR] 把 loop count 做成 token-adaptive router 的决策,Yang et al. [Yang2025LoopedLatentThoughts] 直接画出了 looped transformer 在 GSM8K / MATH 上的 loop-count vs accuracy ladder;另一侧 Hao et al. [Hao2024Coconut] 和 Tack et al. [Tack2025CoCoMix] 论证的是 'loop 不是 iterative depth,而是 latent-continuous thought 的连续态 mixing',对照组从 'dense scaling + MoE' 切换为 'o1/R1 式 explicit CoT'——两派问题框架不一样,放在一起看会看清楚 depth-loop 和 latent-loop 的边界.

触发：三件事在 2024 底到 2025 中同时发生,使 looped LM 从 '架构小品' 升级为能与 depth-scaling / MoE 并列讨论的坐标轴:(a) Huginn 是第一次有人把 latent-recurrent-depth 推到 3.5B × 800B token 的 pretrain 规模,loop 化不再是小模型实验 [Geiping2025Huginn].(b) Relaxed Recursive Transformer [Bae2024RRT] 给出了把既有 Llama-3/Gemma-2 蒸馏为 loop 形态的 retrofit 路径,把讨论从 '从头预训' 转向 '改既有 checkpoint'——和 Transformer→SSM 的 migration 叙事是平行逻辑.(c) 2025-02 Yang et al. 的 'Reasoning with Latent Thoughts' 直接把 looped transformer 的 test-time compute 渲染成可验证的 scaling ladder,把 loop 放到与 o1/R1 CoT 的同一个坐标系下对照 [Yang2025LoopedLatentThoughts].同时 MoR [Bae2025MoR] 和 BLT [Meta2024BLT] 扩大了 'loop 可以是什么' 的操作定义:loop 既可以发生在 Transformer 层栈(MoR),也可以发生在 patch/byte latent encoder 里(BLT).这一年 'loop' 这个词从模糊概念变成了有 scaling ladder、有 retrofit recipe、有 adaptive-depth 实现的复合族系.

锚点论文

  • 2502.05171Scaling up Test-Time Compute with Latent Reasoning: A Recurrent Depth Approach (Huginn)— The 3.5B x r=8 x 800B-token pretrain result that makes depth-loop credible at production scale. First public evidence that a latent-recurrent-depth model can absorb 8T pretrain tokens without collapsing; Figure 5 / Table 3 of this paper is the closest published 'compute-ladder for looped pretrain' we have. Anchor for the pretrain-time-loop camp and the scaling-law section.
  • 2507.10524Mixture-of-Recursions: Learning Dynamic Recursive Depths for Adaptive Token-Level Computation— Turns loop count into a token-adaptive router decision — different tokens get different recursion depths, the natural extension of Universal-Transformer's ACT halting into the modern Transformer. Anchor for the 'fixed vs adaptive loop count' axis and for the cross-paper claim that MoR's ~20% param reduction at matched FLOPs is a different cost-curve slope than Huginn's.
  • 2410.20672Relaxed Recursive Transformers: Effective Parameter Sharing with Layer-wise LoRA— The distillation / retrofit story: take a pretrained Gemma-2 / Llama-3 checkpoint and uptrain it into a looped form with layer-wise LoRA on top of the shared weights. The only paper in this set treating looping as a deployment knob rather than a pretrain decision — necessary anchor for the retrofit-vs-from-scratch position axis.
  • 1807.03819Universal Transformers— The canonical depth-recurrence + adaptive-computation-time ancestor. Necessary to frame MoR as 'UT + modern routing' rather than new-from-scratch design, and to surface the prior — widely believed in 2018-2020 — that shared-weight recurrence interacts badly with long sequences. Huginn and MoR had to design around this prior; anchoring it explicitly prevents the report from treating looping as a 2025 invention.
  • 1909.11942ALBERT: A Lite BERT for Self-supervised Learning of Language Representations— Parameter-sharing at BERT scale, pre-dating the 'loop' framing. Useful as the negative control in the architecture section — ALBERT's 12-layer-shared-12x recipe compressed params 18x but measurably hurt downstream GLUE vs non-shared BERT. Understanding why that didn't generalise is the implicit question Huginn / MoR are answering a decade later, and anchoring it prevents the report from over-claiming that 'parameter sharing is free'.

对立阵营

  • · Explicit depth-loop (weight-shared layer stack iterated N times — Huginn / MoR / Universal Transformer / ALBERT) vs latent-state loop (hidden state fed back as next input — Coconut / CoCoMix / BLT patch encoder)
  • · Pretrain-time looping (Huginn r=8 × 800B pretrain; CoCoMix mixes concept vectors into pretrain) vs test-time-only looping (Coconut post-hoc finetune; distill existing dense into loop at inference only)
  • · Fixed loop count (ALBERT 12-layer × 12; Looped Transformer classic K-iteration) vs token-adaptive depth (MoR router picks per-token recursion depth; Huginn randomises r at training time)
  • · From-scratch looped pretrain (Huginn, Universal Transformer, CoCoMix) vs retrofit / distill from existing dense checkpoint (Relaxed Recursive Transformer with layer-wise LoRA on Llama/Gemma)

品味：一条更稳的读法:depth-loop 在 `固定参数量 × 增加 loop count` 这条 ladder 上的收益是真实的,但斜率显著低于 '同 FLOPs 下增加参数量' 的 dense 基线——Huginn 在 3.5B × r=8 时接近 7B dense 但没有打平 [Geiping2025Huginn];MoR 在 matched FLOPs 下比 dense 小 ~20% 参数仍对齐 ppl [Bae2025MoR];这些都是 1.1-1.3× compute 换 1× 参数等效的量级,不是质变.loop 的真正卖点不在 pretrain 替代 dense,而在两个更细的场景:(1) **inference-time 的第二旋钮**:同一份权重, loop count 越多 reasoning 越好, 这条曲线在 GSM8K / MATH / BBH 上单调 [Yang2025LoopedLatentThoughts];把它和 o1/R1 的 'think longer' 放同一个坐标系,loop 是 '在参数里 think longer',CoT 是 '在 context token 里 think longer',互不替代.(2) **retrofit 既有 dense checkpoint**:RRT-LoRA 把 loop 变成 deployment-time knob, 无需重新预训 [Bae2024RRT].latent-CoT 派(Coconut / CoCoMix / BLT)解决的是完全不同的问题——把 reasoning 内化到 representation 而不是 token,对照组是 explicit CoT,不是 dense scaling,把两派混为一谈会让架构选型混乱.开放的硬问题:(a) Huginn 用 randomised r 训练,MoR 用 token-adaptive router,但两者的 scaling ladder 斜率并没有系统性对比;(b) ALBERT 的 downstream 回退(同参数共享 12 次但 GLUE 掉点)与 Huginn / Looped Transformer 的 scaling 成功之间究竟差在哪?是数据规模、LN 位置、位置编码设计,还是 loop 粒度(encoder-shared vs decoder-only layer-shared)?目前没有控制实验能回答.(c) loop 与 SSM / Mamba 的 hybrid 混合是 open question——两者都是 'subquadratic 换 depth 或 state',放一起会不会重复计费还没有 ablation.

#2已起草2026-04-27-long-context-capacitylong-context-capacity-and-decay

长文能力的本质：从「窗口长度」到「pattern capacity × 衰减斜率」

The Essence of Long-Context Capability: From “Window Size” to “Pattern Capacity × Decay Slope”

» 2024–2025 这一年长文模型从 128K 一路堆到 10M，但同期评测端的共识是『标称窗口和有效上下文之间系统性偏离 2–4 倍』。把『长文能力』当作一个标量（窗口能塞多长）几乎注定推理出错。这份报告的立场是把长文能力拆成三个可测度的维度：(1) attention pattern 的 capacity——同一时间段内能维持几条独立的 retrieve / track / aggregate 路径；(2) attention pattern 的 diversity——retrieval / induction / sink 等专家化 head 的密度与覆盖；(3) 衰减斜率——perf 随 length / position 衰减的形状学（uniform / U-shape / cliff）。围绕这三个维度，把测量端（NIAH → RULER → LongBench v2 → Loong）与机制端（retrieval heads, induction heads, attention sinks, mover heads）合并到一个叙事里：『perf 衰减为什么是这样衰退的』和『attention pattern 的内部结构』本来就是一件事的两个端口，2024 年以前因为没人能同时测两端，所以这两条研究线一直平行；2024 年 Wu 等的 retrieval-head 因果实验把它们焊在了一起，本报告就以这个焊点为中心展开。

触发：三件事在 2024–2025 同时发生，使这一刻成为做这份分析的最佳窗口：(a) **测量端拐点**：RULER (2024) 把 NIAH 的『单针 retrieve』扩展为 multi-key + variable-tracking + aggregation 多压力项，第一次把『检索』『跟踪』『聚合』三种长文能力解耦在同一框架里；LongBench v2 (2024 末) 把多任务长文评估升级到 ≥10K token 的 64 个真实任务；Loong / LV-Eval / BABILong 把『长文 reasoning』拉出 retrieval baseline。这意味着今天可以在同一组任务上对比 100+ 模型的衰减曲线形状学。(b) **机制端拐点**：Wu et al. (2024) 在 LLaMA-2 / Mistral / Yi 上识别出『retrieval heads』并通过 head-mask ablation 给出因果证据：mask top-5% retrieval heads 直接把 NIAH 打回随机基线；StreamingLLM (2023) 已经把 attention sinks 作为系统级 streaming 的依赖；Anthropic 的 induction heads / function vectors 把 ICL 的相变机制坐实。这三条线在 2024 已经收敛到『attention pattern 的稀疏专家化』这一个核心解释。(c) **工程端拐点**：MLA / GQA / MQA 把 KV 压到 5–10% 的同时不破坏 retrieval head 的工作，意味着大幅压缩之后机制端依然在工作；DeepSeek V3.2 引入的 sequence-level sparse attention（与 NSA / MoBA 风格类似）等于直接利用『大多数 head 在大多数位置上是稀疏的』这一事实。这一年里如果不把测量、机制、工程三端合起来读，长文方向几乎只能踩坑。

锚点论文

  • 2404.06654RULER: What's the Real Context Size of Your Long-Context Language Models?— The standard 2024 measurement framework. Extends NIAH from single-needle retrieval to multi-key, variable-tracking, and aggregation pressures, decoupling retrieve / track / aggregate in one harness. Required as the report's measurement spine.
  • 2307.03172Lost in the Middle: How Language Models Use Long Contexts— Foundational position-decay paper. Establishes the U-shape (high recall at start and end, drop in the middle) as a robust empirical phenomenon across model families. The report's §3 (decay shape-ology) builds on this directly.
  • 2308.14508LongBench: A Bilingual, Multitask Benchmark for Long Context Understanding— Pre-RULER multi-task long-context benchmark; still cited because it pins down task-level performance vs claimed window. Necessary baseline before LongBench v2.
  • 2412.15204LongBench v2: Towards Deeper Understanding and Reasoning on Realistic Long-Context Multitasks— The 2024 update that pushes evaluation to ≥10K-token real-world tasks across 64 categories. Where retrieval-only models lose to reasoning-aware models.
  • 2404.15574Retrieval Head Mechanistically Explains Long-Context Factuality— Causal pivot of the report. Identifies retrieval heads on LLaMA-2 / Mistral / Yi, shows masking the top-5% collapses NIAH to a random baseline, and ties the decay-curve story to the attention-pattern story. Without this paper the two halves of the report don't connect.

对立阵营

  • · 测量框架: NIAH 单针 (饱和) → RULER 多压力 (检索/跟踪/聚合解耦) → LongBench v2 (多任务真实长文) → Loong / LV-Eval / BABILong (长文推理) — 评估的层级化
  • · 衰减形态学: uniform decay (capacity 受限) vs U-shape (lost-in-middle 位置偏置) vs cliff (训练长度末端) — 不同失败形状对应不同 root cause
  • · claim vs effective: 标称 128K–1M vs 实测 effective 32–64K — 系统性 2–4× 缺口的来源拆解
  • · retrieval heads: 散布在所有 head 里只有 ~5% (5–20 个) 承担 NIAH 主任务；mask 它们能因果验证 long-context-factuality

品味：读完应能回答下面 7 个钉死的问题：(1) **NIAH 还能做 long-context 主指标吗？** 给出 NIAH 在 32K+ 下为何普遍饱和、用 RULER 的哪几个子任务可以把已饱和的模型拉开 30+ 分差；明确 LongBench v2 与 NIAH 在『retrieve』和『aggregate』两轴上的相关性差异。(2) **lost-in-the-middle 是 PE 问题、训练分布问题还是 sink 问题？** 给出 Liu et al. (2023) 的 U-shape 与 Xiao et al. StreamingLLM 的 sink 现象、Press et al. ALiBi、Chen et al. PI 的位置插值之间的 disentangle 实验；指出在哪种情形下 U-shape 主要由训练长度截断引起、哪种情形下由 attention sink 的优先级偏置引起。(3) **retrieval heads 是不是 transferable？** Wu et al. 在 LLaMA-2 / Mistral 验证了，但跨族系（Qwen / Yi / DeepSeek）的 retrieval-head 数量、位置、起点是否一致？不一致时如何判定？这关系到 distill-to-dense / pruning 的安全边界。(4) **attention sink 在 MoE / MLA 下还成立吗？** MLA 把 K/V 共同压到 latent，重建出的 K/V 是否保留 sink 行为？给出在 V2 / V3 上的实测证据或合理推测。(5) **capacity 的可测度量** 怎么定义？per-token entropy、跨 head Jaccard、effective rank、entropy budget 中哪个对 RULER 任务的相关性最强？给出 ranked correlation 表。(6) **diversity 的相变** 与 ICL 突现相变的关系：Olsson et al. (induction heads) 给出 ICL 的相变；retrieval-heads 的相变在哪？两条相变是否在同一 compute 范围出现？(7) **稀疏 attention（NSA / MoBA / DSA / Sparse Attention）会不会重写本报告**：如果大多数 head 在大多数位置上 attention prob ≈ 0，那 capacity 是不是被严重高估？给出在 V3 / V3.2 / NSA 这一年的最新证据下的看法。和 `long-context-rope-ntk`（PE 机制）、`length-scaling-pretraining`（数据 + 系统）、`context-scaling-pretrain`（三轴：数据/packing/induction）、`packing-masking-length`（packing 工程）互补：那四个守『如何把模型训得到/扩展到长上下文』，本篇守『当模型已经名义上拥有长上下文之后，能力到底是什么、怎么测、为什么会衰退』——评估为先、机制为骨、工程为收尾。

#3已起草2026-04-27-downstream-predictionscaling-laws-downstream-tasks

下游任务的缩放律：从『涌现是惊喜』到可预测性工程化

Scaling Laws for Downstream Tasks: From 'Emergence Is a Surprise' to Operational Predictability

» 把下游任务表现预测从『直觉』升级为『流程』。Wei 2022 的『涌现 = 不可预测』直觉在 2023–2024 已被两步拆解：(1) Schaeffer 把『跳变』归因到离散度量（exact-match）的非线性，把 metric 换成连续 surrogate（如 token-level Brier / BPB-of-correct-completion）后，绝大多数曲线变单调。(2) Du 进一步把 x 轴从 compute 换成 pretraining loss，统一了 dense/sparse、不同架构、不同 token 预算下的下游表现轨迹。剩下的工程缺口由 Bhagia 的 model ladder 和 Ruan 的 observational scaling 补齐：用 sub-1B 的小模型梯子或公开模型回归就能在主训前回答『5 个 mix / 2 种 arch / 3 种 mid-train 谁赢』。真问题因此从『能不能预测』转移到『预测的不确定性带宽要多窄才支撑 ship/no-ship 决策』、『post-training（SFT/RLHF/distill/o1-style RL）之后这条曲线还成立吗』、以及『何时该退回去诚实地承认 broken / 多相位曲线（Caballero）』。下游缩放律已经从理论问题变成了 pretrain 团队的『预算 + 验收』工艺。

触发：三条证据链在 2024–2025 同时成熟，把下游预测从研究话题挤进生产 SOP：(a) **重新解释涌现**：Schaeffer 2023 + Du 2024 把『discrete-metric jump』和『compute-axis 错觉』剥离，留下一条以 pretraining loss 为主轴的连续曲线。这一步消除了『反正没法预测』的工程懒惰借口。(b) **可负担的预测工具**：Bhagia 2024 的 model ladder（小模型梯子 → 任务幂律）+ Ruan 2024 的 observational scaling（公开模型 → 低维 capability manifold）共同把单次预测的边际成本压到 sub-1% 主训预算。(c) **规模团队真在用**：DataComp-LM、OLMo、MAP-Neo、DeepSeek-LLM/V3 的技术报告都把预测曲线作为决策附录而非事后注释；Pythia/Cerebras-GPT 等 scaling-suite 进一步把『多 size × 多 ckpt』作为开放数据集，让 observational 和 ladder 都有了无成本的训练数据。下一年的差异化不是『有没有缩放律』，而是『预测带宽多窄、对什么任务族失效、以及 post-training 之后还守不守』。

锚点论文

  • 2206.07682Emergent Abilities of Large Language Models— The orthodox 'downstream is unpredictable' position. Establishes the canonical exhibit (BIG-Bench tasks with apparent threshold jumps) that motivates the rest of the literature. Necessary as the position the report negotiates against.
  • 2304.15004Are Emergent Abilities of Large Language Models a Mirage?— The metric-artifact rebuttal. Replacing exact-match with continuous surrogates collapses most 'emergent' jumps to smooth curves — the foundation of the report's claim that emergence is largely an evaluation choice, not a scaling property.
  • 2403.15796Understanding Emergent Abilities of Language Models from the Loss Perspective— Switches the x-axis from compute to pretraining loss and shows downstream curves unify across architectures and token budgets. The bridge from 'is emergence real' (Schaeffer) to 'what's the right axis to predict on' — load-bearing for the entire prediction toolkit.
  • 2403.08540Language Models Scale Reliably With Over-Training and on Downstream Tasks— DataComp-LM-style operational paper. Demonstrates that downstream task performance can be predicted from compute even in the over-trained regime, and supplies the 'small-scale ablation → 7B verdict' workflow that the report's senior-taste decision tree builds on.
  • 2412.04403Establishing Task Scaling Laws via Compute-Efficient Model Ladders— Compute-efficient model ladder: train a few small (sub-1B) models, fit per-task power laws, predict large-model task accuracy. The most concrete published recipe for cheap, repeatable, in-house downstream prediction — anchor for the 'how to actually do it before the main pretrain' section.

对立阵营

  • · x-axis = compute $C$ (Kaplan/Chinchilla) vs x-axis = pretraining loss $\mathcal{L}$ (Du) vs x-axis = low-d capability index $\phi(M)$ (Ruan)
  • · Single power law $y = aC^{-\alpha} + b$ vs smoothly-broken / piecewise / sigmoid (Caballero) — when one fit suffices and when it lies
  • · Per-task fit (one law per benchmark) vs universal capability manifold (PCA on benchmark vector) — granularity vs transfer
  • · Train a model ladder $\{N_i, D_i\}$ (Bhagia) vs observational regression on public models (Ruan) — when each is cheaper

DeepSeek 谱系工程考古：tokenizer / 数据 / 注意力 / MoE / 训练栈 / 对齐的版本演进

Engineering Archaeology of the DeepSeek Lineage: Tokenizer, Data Organization, Attention, MoE, Training Stack, and Alignment Across Versions

» DeepSeek 是 2024–2025 唯一一支把『前沿能力 + 完整技术报告 + 开源权重』连续做了 6 个版本的实验室——LLM/MoE/V2/V3/R1/V3.1——其每一次版本号跳变背后都对应一个具体的工程取舍，而不是一次单点优化。把它当成『又一篇 V3 解读』会丢掉 80% 的信号；把它读成一条『dense → fine-grained MoE → MLA + DeepSeekMoE → 671B + MTP + FP8 + aux-loss-free → R1 风 RL → 混合思考』的演化谱系，就能看清楚每一项决策的代价、收益和反例。这份报告分两层：第一层是『谁继承谁、关键技术在哪一版被引入、哪一版被替换』的版本树；第二层是『tokenizer / 数据组织 / 注意力 / MoE 拓扑 / 平衡损失 / pipeline / 数值精度 / 对齐配方』八条工程子轴上每一版的实际配置——可拷贝、可对照、可被自家训练栈直接借鉴的那种细节。读完应该能回答：哪些是『DeepSeek 真正发明的』、哪些是『他们第一个把 paper 写清楚的工程默认值』、哪些是『后续版本悄悄回退的』。

触发：三件事在 2025 上半年同时发生，让 DeepSeek 谱系成为最值得做考古的开源对象：(a) **R1 把 RL 路径打开**：R1-Zero 用纯 RL（GRPO）在数学/代码上撞出与 SFT-then-RL 可比的曲线，把 DeepSeekMath（GRPO 起源）→ V3 base → R1 这条 RL 流水线变成行业默认基线之一；后续 Qwen3、Llama4-reasoning、各家 RFT 配方多多少少在它的脚手架上做。(b) **V3 的工程账本被全行业反复对照**：MLA 把 KV 压到 ≈4–7%、aux-loss-free 把 router balance 损失搬出 loss、FP8 per-block 让 671B × 14.8T 训练首次进入『十亿美元以下 token cost』区间——这些数字成为接下来一年别家 paper 的『参照线』，也意味着读者要看懂别家工作就必须先把 V3 这本账本读熟。(c) **V3.1 引入混合思考**：在保持非思考接口兼容的前提下叠加 thinking mode，与 GPT-5、Qwen3 同时把『同一个 base 同时服务普通对话和长思考』的产品形态固定下来；这条线和 R1 的纯思考模型一起，形成了 DeepSeek 在 post-training 阶段的两条并行答案，必须画清楚。这一年里 70% 的开源高质量 LLM 工程默认值——MLA、fine-grained MoE、shared expert、FP8 per-block、GRPO、cold-start RL、distillation-to-dense——都能在 DeepSeek 谱系里找到一手出处或第一份成熟实现，等于一份『2024–2025 开源 LLM 工程默认值 changelog』。

锚点论文

  • 2402.03300DeepSeekMath: Pushing the Limits of Mathematical Reasoning in Open Language Models— Origin of GRPO. Required to make the post-training section honest — most readers know GRPO via R1, not via this earlier and clearer source.
  • 2401.14196DeepSeek-Coder: When the Large Language Model Meets Programming — The Rise of Code Intelligence— Establishes the repo-level FIM data pipeline, the dependency-graph-aware document construction, and the code-mixture upweighting that influences the rest of the lineage's data axis. 品味：读完应回答六个钉死的问题：(1) **MLA 是 'GQA 的下一代' 还是 '只在长上下文且 batch 较小时才划算'?** 给出 KV 压缩比、attention FLOPs、以及 prefill / decode 在不同 (B, L) 网格下的实测临界点；明确指出当 B 很大且 L 较短时 MLA 相对 GQA 的相对收益缩小到什么程度，附上 V2 paper 里 [DeepSeekAI2024V2] 的具体数字。(2) **fine-grained MoE 的 expert 粒度与 shared expert 数量到底敏不敏感？** 把 DeepSeekMoE [Dai2024DeepSeekMoE] 的 ablation 与 V2 / V3 的实际取值并列：『拆得更细 + 1–2 个 shared』几乎是默认安全选项，但 shared 比例过大会回退到 dense，过小会丢稳定性——给出推荐区间。(3) **aux-loss-free 真的是 free 吗？** 它把 balance 信号从 loss 移到一个 per-expert bias 的滑动更新里，理论上不再扰动语言建模 loss，但代价是 (a) 训练动力学变得更难复现、(b) 需要保留一个轻量 sequence-level 平衡项作为兜底——给出 V3 [DeepSeekAI2024V3] 的两条 ablation 与一条退化案例的判别条件。(4) **FP8 per-block 的边界**：哪些算子留 BF16 是 'numerically must'，哪些留 BF16 是 'we didn't bother'？哪些 epoch 段会出现 stability spike？V3 报告给的 fix（fine-grained scaling、accumulation in BF16、关键 GEMM 落 BF16）在更小模型上是不是 over-engineering？(5) **GRPO vs PPO 的真差异**：DeepSeekMath [DeepSeekMath2024] 提出 GRPO 主要是为了去掉 critic、用 group baseline 替代 advantage 估计；R1 [DeepSeekR12025] 把它从数学扩展到通用推理。给出在 'reward sparse / dense'、'每条 prompt 采样数 G'、'KL 系数' 三个维度上 GRPO 与 PPO 的偏差与方差曲线，并标出 GRPO 已知会失稳的区域（极小 G、reward 稀疏到只剩格式 reward）。(6) **R1 → V3.1 的混合思考是『后训练阶段的 architecture 决策』**：同一个 base 怎么同时承载 'fast chat' 与 'long thinking' 两套 KV 行为？是用 prompt-level switch、用 LoRA 子模型、还是直接共享权重让两种模式在采样时分开？给出 V3.1 [DeepSeekV31] 的实际配置和它与 R1 distill-to-dense 路线的取舍。和 `transformer-arch-improvements`、`moe-landscape`、`scaling-laws-llm`、`scaling-laws-downstream-tasks` 互补：那几个守『某条工程子轴上的趋势』，本篇守『一条具体血脉里这八条子轴怎么共同演化』，是给工程读者准备的 cross-section。
