5:T5cb,The contribution is benchmark construction, not a new agent architecture. SWE-Bench ProMax contains 170 refactoring instances mined from real commits in actively maintained GitHub repositories, spanning seven languages: Python, Java, TypeScript, Go, C, C++, and Rust. The task is explicitly behavior-preserving refactoring rather than bug fixing or feature addition.

The construction pipeline emphasizes three things. First, difficulty filtering: the authors remove tasks with limited complexity, too little cross-file scope, or too few changed lines, leaving instances that average 11.4 modified files and 261.6 lines of code. Second, evaluation quality: issue descriptions are rewritten from scratch to be precise and sufficient, and test suites are manually reviewed to remove overly narrow and overly broad checks. Third, multilingual coverage: the benchmark is intentionally not Python-centric, and includes languages with very different constraints such as Rust ownership, C memory management, and C++ header and build-system complexity.

The examples make the intended difficulty clear. One highlighted instance from NASA F’Prime requires migrating a monolithic header to a new unified entry point across 244 files, touching code generators, drivers, OS layers, services, and build configuration while preserving behavior. That kind of task stresses retrieval, planning, dependency tracking, and consistency maintenance much more than standard single-file patch generation.6:T497,The main results are dataset statistics and baseline benchmark outcomes. The benchmark has 170 instances across seven languages, with an average of 11.4 modified files and 261.6 changed lines. Thirty percent of instances modify more than 10 files, and 32% require more than 200 lines of code. The contrast with SWE-bench Verified is sharp: the paper notes that 86% of Verified instances modify only a single file.

On the evaluation side, the best model reaches only 41.2% resolve rate, far below the 75%+ numbers now seen on SWE-bench Verified. That suggests the benchmark is materially harder and not yet saturated. The abstract also notes that higher cost does not translate into proportionally better performance, which is an important signal: on long-horizon refactoring tasks, simply spending more inference budget is not enough.

The paper also cites prior audits of SWE-bench Verified showing that nearly 60% of unsolved instances contain flawed tests, including 35.5% with narrow tests and 18.8% with broad tests. Those numbers are not results on ProMax itself, but they explain why specification rewriting and manual test review are central to the benchmark design.7:T6cd,The work is a controlled benchmark. The design holds model, harness, task, evaluator, and execution environment fixed within paired blocks, changing only the user prompt. It evaluates six 500B-class reasoning models served through one provider: DeepSeek-V4-Pro, Kimi-K2.6, Kimi-K2.7-Code, Nemotron-3-Ultra-550B-A55B, Inkling, and GLM-5.2. Two real agent harnesses are used: PI.DEV through OpenAI-style chat completions, and Claude Code through an Anthropic-to-chat-completions translation gateway. The task set contains 24 deterministic coding tasks across Python, JavaScript, and Go, with visible tests plus hidden deterministic evaluators that are never placed in the workspace. Prompt variants are frozen templates. The primary variants preserve the objective, acceptance criteria, and test command while changing framing: precise baseline, deep thinking, exhaustive exploration, multiple approaches, maximum certainty, adjacent cleanup, no-questions autonomy, bounded efficiency, and related forms. Stress variants intentionally break semantic equivalence through ambiguity, conflicting constraints, irrelevant context, misleading hints, or multi-turn restatement. The main statistic is a paired reasoning ratio against the median baseline for the same model-harness-task block.
