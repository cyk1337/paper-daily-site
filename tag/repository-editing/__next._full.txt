18:T70f,The central construction is 'tasks built by subtraction.' Starting from a released research repository, the benchmark builders identify the code that implements the paper’s contribution, delete it, and leave the rest of the repository intact. The deleted code becomes a private human reference held by the judge. The agent receives the modified repository, where the missing functions are still declared and called, and is allowed to edit only the files that originally contained the contribution. This gives each task a natural oracle reference without requiring benchmark authors to manually recreate a gold solution.

The judge design is equally important. The agent and the judge run in separate sandboxes. The agent has no network access beyond a driver that forwards model calls and patch submissions, preventing trivial recovery of the original code. The judge holds the evaluator, the held-out final suite, and the private reference patch. During the run, the agent may submit patches multiple times and receives only development-suite feedback: simplified scores and threshold counts, not raw evaluator outputs or reference scores. At the end, the agent must choose one final patch, and only that patch is evaluated on the held-out suite. A run passes only if the final patch beats the reference threshold on every metric and every held-out workload. This setup makes patch selection part of the task and reduces direct overfitting to the final evaluation.

The paper also introduces the FrontierCS Capabilities Index (FCI) together with a task difficulty index. While the provided text does not include the full fitting details, the intent is clear: estimate agent capability and task difficulty jointly on a single latent scale, rather than treating benchmark performance as a flat leaderboard.19:T5f1,The benchmark contains 48 tasks across 13 domains and evaluates 12 model-plus-agent-harness combinations, with one run per task. The best-performing setup, Claude Opus 5.5 with Claude Code, passes 58% of runs. Every other agent passes fewer than half. An especially informative result is that no agent passes 16 of the tasks. That suggests the benchmark is not merely separating agents with a few outlier tasks; there is a substantial subset of research-style tasks that current top agents broadly fail.

The pass criterion is intentionally strict. Success is not defined by a single scalar score but by meeting thresholds on every metric and every held-out workload. In the SVG-EAR example described in the text, latency must be at most 0.96 times the reference latency while PSNR, SSIM, and LPIPS must remain within specified tolerances of the reference. This better reflects real systems research, where improvements usually have to satisfy multiple constraints simultaneously.

The paper also studies how the leading agent changes with the cost budget per run, which makes the benchmark useful for scaling analyses rather than only one-shot ranking. The provided excerpt does not include the full result tables or exact FCI values, so it would be inappropriate to invent finer-grained rankings. Then read the judge section carefully, especially the separation between agent and judge, the role of the development suite versus the held-out final suite, and the fact that the agent must choose its own final patch.
