18:T579,The method is a two-stage loop: idea discovery and idea control. (1) Formalization: evolutionary discovery is cast as a POMDP with a hidden mechanism θ_sci; proposing a program yields a score from an evaluator. An “idea” is defined as a high-level mechanistic property of programs that causally drives score differences. The theory section argues that without identifying such ideas, programs are effectively unrelated and search degenerates toward exhaustive exploration; conversely, identifying ideas requires deliberate contrastive exploration (programs with/without an idea). (2) Idea-factor extraction: built on COAT, the system searches for high-level factors that explain score differences by training/using a pairwise comparator over archived programs—given (p_i, p_j), predict which scores higher. Factors that improve this pairwise ordering are admitted as reusable idea factors. The key design choice is pairwise ranking (difference-explaining) rather than raw score regression. (3) Idea-level control: each admitted idea factor becomes an arm in a multi-armed bandit that selects which idea to emphasize when generating new candidates. The algorithm reserves capacity for random exploration and triggers idea-guided exploration on plateaus, explicitly pushing the LLM toward underrepresented ideas in top programs to maintain the contrasts needed for reliable factor identification.19:T404,Retrieval Program Learning lets the policy write short executable programs instead of invoking one monolithic retrieval tool. These programs run in a sandbox and can use local state and control flow to combine search primitives such as dense retrieval, sparse retrieval, candidate filtering, deduplication, fusion, reranking, and evidence selection. The main training issue is sparse-reward exploration: useful programs may require several coordinated structural choices before answer correctness improves. The proposed solution is program mutation. Starting from suboptimal RL rollouts, a typed grammar generates nearby program variants while preserving the original queries. Mutations can change the retriever, increase retrieval breadth, merge result sets, or add reranking. Verified successful variants are converted into synthetic trajectories, briefly used for fine-tuning, and then RL resumes. This gives the policy structured experience with useful retrieval programs that pure on-policy exploration may rarely discover.1a:T620,NCE has three core components. First, it organizes the running context into addressable blocks. Each block is named by dedicated address tokens, and some blocks such as system prompts or tool declarations can be locked. Second, it defines an executable editing grammar inside the model vocabulary. The grammar includes address tokens plus operator tokens such as drop, rewrite, and append, together with composition rules for forming valid edits. A task-agnostic runtime maps each well-formed edit to exactly one context-state transition. This is the key design choice: edit semantics are not explained in the prompt or delegated to external tool schemas, but anchored in the model vocabulary and a fixed executor. Third, it builds supervision with a two-teacher pipeline. An offline teacher reads the full trajectory and assigns each block a release point, meaning the earliest turn after which the block can be safely edited because its role in the task has ended. An online teacher only sees the current context plus those release annotations and decides when and how to edit. The crucial training detail is evolving-context distillation: after an edit is generated at the end of a turn, the runtime executes it before constructing the next turn’s input and labels. This avoids conditioning future supervision on text that the model has already deleted or rewritten. First, it formalizes tool-call histories as first-order logic facts using predicates for calls, parameters, and returns. To prevent the SMT solver from inventing unsupported facts, it adds closed-world assumptions: each timestep has a unique call, and past parameters and return values are fixed and complete. Second, it mines candidate constraints from API documentation. An initializer agent focuses on one target API at a time, retrieves related tool definitions, and proposes executable rules covering provenance constraints, temporal dependencies, domain restrictions, and observable-state preconditions. The model outputs both a natural-language description and a corresponding Z3 expression. Third, it refines those rules using execution traces. This matters because documentation alone tends to produce overly strict rules and miss environment-specific dependencies. A refiner agent removes bad rules and adds missing ones based on observed successful and failed interactions. Fourth, it performs runtime intervention. At each tool call, the current history facts and the mined rules are checked with an SMT solver. If the conjunction becomes UNSAT, the current call violates at least one constraint. The system uses an unsat core for approximate attribution and intervenes only when the current call participates in the contradiction. Interventions come in two forms: natural-language warnings that ask the agent to retry, and automatic repair via MaxSMT when a unique valid replacement can be inferred. The design choice is deliberate: the verifier does not replace the agent’s planner, but guards the tool boundary where structural errors are easiest to formalize.1d:T41f,SpecAgent separates tool actions into read-only actions and state-changing actions. The weak model is allowed to execute read-only calls while drafting, because these calls do not modify the environment and can be removed from the history if they are wrong. When the weak model reaches the first state-changing action, such as submitting an answer or modifying a record, execution is paused. The strong model then reviews the drafted segment in one prefill pass, commits the longest semantically valid prefix, and repairs the first rejected step.
