Increasing simulator-side compute from M=1 to M=4 yields gains ranging from about 1.2 to 24.1 points depending on benchmark and backbone.19:T579,The method is a two-stage loop: idea discovery and idea control. (1) Formalization: evolutionary discovery is cast as a POMDP with a hidden mechanism θ_sci; proposing a program yields a score from an evaluator. An “idea” is defined as a high-level mechanistic property of programs that causally drives score differences. The theory section argues that without identifying such ideas, programs are effectively unrelated and search degenerates toward exhaustive exploration; conversely, identifying ideas requires deliberate contrastive exploration (programs with/without an idea). (2) Idea-factor extraction: built on COAT, the system searches for high-level factors that explain score differences by training/using a pairwise comparator over archived programs—given (p_i, p_j), predict which scores higher. Factors that improve this pairwise ordering are admitted as reusable idea factors. The key design choice is pairwise ranking (difference-explaining) rather than raw score regression. (3) Idea-level control: each admitted idea factor becomes an arm in a multi-armed bandit that selects which idea to emphasize when generating new candidates. The algorithm reserves capacity for random exploration and triggers idea-guided exploration on plateaus, explicitly pushing the LLM toward underrepresented ideas in top programs to maintain the contrasts needed for reliable factor identification.1a:T404,Retrieval Program Learning lets the policy write short executable programs instead of invoking one monolithic retrieval tool. These programs run in a sandbox and can use local state and control flow to combine search primitives such as dense retrieval, sparse retrieval, candidate filtering, deduplication, fusion, reranking, and evidence selection. The main training issue is sparse-reward exploration: useful programs may require several coordinated structural choices before answer correctness improves. The proposed solution is program mutation. Starting from suboptimal RL rollouts, a typed grammar generates nearby program variants while preserving the original queries. Mutations can change the retriever, increase retrieval breadth, merge result sets, or add reranking. Verified successful variants are converted into synthetic trajectories, briefly used for fine-tuning, and then RL resumes. This gives the policy structured experience with useful retrieval programs that pure on-policy exploration may rarely discover.1b:T620,NCE has three core components. First, it organizes the running context into addressable blocks. Each block is named by dedicated address tokens, and some blocks such as system prompts or tool declarations can be locked. Second, it defines an executable editing grammar inside the model vocabulary. The grammar includes address tokens plus operator tokens such as drop, rewrite, and append, together with composition rules for forming valid edits. A task-agnostic runtime maps each well-formed edit to exactly one context-state transition. This is the key design choice: edit semantics are not explained in the prompt or delegated to external tool schemas, but anchored in the model vocabulary and a fixed executor. Third, it builds supervision with a two-teacher pipeline. An offline teacher reads the full trajectory and assigns each block a release point, meaning the earliest turn after which the block can be safely edited because its role in the task has ended. An online teacher only sees the current context plus those release annotations and decides when and how to edit. The crucial training detail is evolving-context distillation: after an edit is generated at the end of a turn, the runtime executes it before constructing the next turn’s input and labels. This avoids conditioning future supervision on text that the model has already deleted or rewritten.
