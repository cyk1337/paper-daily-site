a:T5e2,The central object is a blueprint: a dependency graph whose nodes are formal definitions and lemmas, and whose edges encode proof dependencies leading to the target theorem. The pipeline has three stages. First, blueprint generation: given the target theorem statement, optionally with a natural-language proof, the architect model emits a Lean file containing formally stated intermediate nodes and declared dependencies. Second, node proving: a tool-using Lean prover attempts to close open lemma nodes, using the declared dependencies and retrieval over Mathlib. These node-level proof attempts can run in parallel, which is important because the graph exposes independent subproblems. Third, global refinement: failed nodes are not handled only by deeper local decomposition. Instead, failure information is sent back to the architect, which can rewrite the blueprint globally by changing intermediate lemmas, adding or removing definitions, or restructuring dependencies.

This differs from recursive decomposition pipelines, where an early bad split can trap the system in an unproductive subtree. It also differs from Draft-Sketch-Prove style approaches. There, the informal proof becomes a flat sketch with placeholders. Here, the optional natural-language proof is converted into a graph of named sublemmas, which is easier to revise and recombine. In system terms, the paper separates high-level strategy formation from low-level proof discharge, and uses the graph as the interface between them.b:T58e,The most notable result is the performance-cost tradeoff rather than a single benchmark number. The paper claims a new Pareto point for its compute class using the open-weight DeepSeek-V4-Flash backbone, with roughly $0.44 per problem, versus about $244 per problem for the next-best open pipeline reported in the comparison table. The introduction also positions the method against the broader landscape: open one-shot provers remain weak on Putnam-class problems, while systems above the 50% range typically depend on closed models, closed pipelines, or very high API spend.

The experiments to pay attention to are likely in three groups. First, benchmark results on MiniF2F, PutnamBench, and possibly newer Putnam-style sets, with separate comparisons against open one-shot provers, open agentic systems, and closed frontier pipelines. Second, ablations on the blueprint mechanism: whether global refinement helps over no refinement, whether graph-based planning beats recursive decomposition, and whether natural-language proof seeds improve difficult problems. Third, cost accounting: number of architect/prover calls, token usage, and retry overhead. For a systems paper like this, those details matter as much as pass rate.
