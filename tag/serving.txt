18:T91b,方法由三部分组成，分别对应作者提出的三个瓶颈。

第一部分是 path-aware tile routing。DFlash 原生实现对 prefill 和 verify 复用同一套 attention tile 选择逻辑，但两者 query length 分布完全不同：prefill 往往很长，verify 只有短 candidate block。沿用 prefill 的 tile 会让 verify 阶段出现大量无效 padding。DScale 为不同执行路径选择预编译 tile，使 verify 使用更贴合短序列 workload 的 tile 形状，同时保留 prefill 的复用收益。这里的关键不是新 attention 算法，而是把“prefill 和 verify 是两种不同 kernel workload”显式编码进图选择逻辑。

第二部分是 dynamic verify-length, DVL。作者不去缩短 drafter 的生成长度，而是在验证前决定每个请求实际送多少 candidate prefix 进入 target verify graph。为此训练了一个很小的 predictor，参数量只有 112K，针对 target–drafter pair 学一次即可。它不做概率校准，也不需要硬件 profile，只输出用于排序/分配的分数。系统在共享预算下给不同请求分配不同 verify-length，并把总 candidate-slot 容量压到 native verify graph 的一半左右。这样做的动机很清楚：真正值得 target 花算力验证的，是更可能形成长 accepted prefix 的请求；对低潜力请求，保留完整 draft 但少送一些位置去 verify，比一刀切截断所有请求更划算。

第三部分是 fixed-address compact workspace。DVL 之后，每个请求的 prefix 边界会动态变化，这与 CUDA graph 偏好的 fixed-shape 接口冲突。DScale 用固定地址工作区来承载压缩后的 token、边界和前缀信息，让 decision graph、verify graph 和 acceptance 逻辑共享这些动态边界，同时继续复用 captured graphs，而不需要 CPU 侧重新切片。论文里 flat-pack compaction 是这里的配套机制：把各请求选中的 prefix 紧凑排布进共享验证预算，尽量保留长前缀，减少 padding 和空槽。

整体上，DScale 的思路不是改 acceptance rule，也不是训练更强 drafter，而是把 verify 当成一个受预算约束的 packing 和调度问题。相比 DSpark 这类依赖 confidence calibration 和硬件曲线的方法，它更轻量，也更容易迁移到已有 DFlash 部署上。19:T9d9,The method has three main components, each tied to one of the identified bottlenecks.

First, path-aware tile routing. Native DFlash uses the same attention-tile selection logic for prefill and verification, even though the workloads are structurally different: prefill has long query lengths, while verification operates on short candidate blocks. Reusing prefill-oriented tiles in verification leaves many inactive positions and wastes work. DScale introduces path-specific routing over precompiled tiles so that verification uses tile shapes better matched to short-query execution, while prefill still benefits from its own optimized path. This is not a new attention algorithm; it is a workload-aware graph-selection strategy.

Second, dynamic verify-length allocation (DVL). Instead of shortening the drafter’s output, DScale decides how many candidate positions from each request should actually enter the target verification graph. A tiny predictor—112K parameters, trained once per target–drafter pair—produces scores for allocation. The predictor does not require confidence calibration and does not depend on hardware speed-curve preparation. Under a shared verification budget, requests with higher expected acceptance potential receive longer verified prefixes, while lower-value prefixes are trimmed. The total candidate-slot budget is reduced to roughly half of the native verification capacity. The point is to spend target-model verification on prefixes likely to yield longer accepted runs, rather than uniformly truncating every request.

Third, a fixed-address compact workspace. DVL makes request boundaries dynamic, which conflicts with fixed-shape graph replay. DScale introduces a compact workspace that stores packed tokens, boundaries, and prefix metadata at fixed addresses, allowing the decision graph, verification graph, and acceptance logic to share changing boundaries while still reusing captured graphs. Flat-pack compaction is the associated packing mechanism: selected prefixes from different requests are laid out densely under the shared budget, preserving long useful prefixes and reducing padding without CPU-side re-slicing.

Overall, DScale treats verification as a budgeted packing and scheduling problem. It does not modify the acceptance rule and does not depend on a stronger drafter. Compared with approaches such as DSpark that rely on confidence calibration and hardware profiling, it is lighter-weight and easier to layer onto an existing DFlash-style deployment.1a:T60e,The evaluation spans four datasets, two target models, and concurrency levels from 8 to 32 on A100-40GB with tensor parallelism 1. Relative to DFlash, DScale improves geometric-mean throughput by 43.9% to 48.8% and reduces aggregate mean end-to-end latency by 31.4% to 33.1%. On GSM8K, GPU profiling shows 30.8% to 52.5% shorter complete decode steps.

A particularly informative intermediate metric is accepted-token retention. If verification capacity is reduced without a good allocation policy, only about 71% of accepted tokens are retained. With budget adjustment, retention rises to above 91%. That result matters because it shows the gain is not simply from verifying fewer tokens; it comes from verifying fewer low-value tokens while preserving most generation progress.

The ablations are the strongest part of the empirical section. The paper presents cumulative ablations showing that path-aware tiles, predictor scoring, budget allocation, and packing/workspace each add incremental benefit rather than one trick dominating the outcome. Runtime overhead is also small: prediction, budget allocation, and packing together account for only 3.08% to 4.08% of step time in GPU execution at concurrency 8. The motivation section provides the key baseline profile: for Qwen3-8B with an approximately 1B, five-layer DFlash drafter on GSM8K at concurrency 16, 83.3% of summed GPU-kernel time is spent in the target verification graph, versus 10.9% in the draft graph. That profile explains why verification-side optimization is the right target.1b:T4b7,Read this as a systems paper about where block-diffusion decoding actually spends time. Start with the introduction and background, especially the native DFlash profile showing that verification dominates GPU kernel time. Without that profile, the rest of the design can look like engineering detail; with it, the design choices become well motivated.

Then follow the three challenges and their paired mechanisms. For path-aware tile routing, the key question is why prefill and verification should not share the same tile policy. For token t, the MoE output is y_t = sum_{u in R_t} w_{t,u} E_u(z_t). If some experts are not loaded at the batch level, the layer output changes. The paper writes the resulting squared error as a sum of individual removal terms plus cross terms between experts omitted together. The key claim is that selection is robust to dropping the cross terms, which makes it possible to score experts independently and keep the highest-scoring ones under a fixed budget.

The score is a predicted removal error. For a token-expert pair, the removal cost is tied to the squared router weight and the expert output energy ||E_u(z_t)||^2. The difficulty is that the true expert output is unavailable before the expert is fetched and executed, while selection must happen beforehand. BASE addresses this by training a lightweight linear predictor for each expert during calibration. At inference time, it predicts the expert’s output energy from the current token representation, combines that with router weights, aggregates the resulting costs across the batch, and selects the experts with the largest predicted batch-level impact.

The paper also handles the practical case where a token routes to an expert that was not loaded. It uses a backfill mechanism, replacing the missing expert with an available routed alternative. Compared with methods such as SERE and OEA, which build the batch active set more directly from token routing decisions, BASE asks a stronger question: how much does this expert matter to the current batch output?
