18:T6d0,The contribution is a benchmark, not a new agent algorithm. EvoHarnessBench defines the harness as the set of tools an agent can call, the procedural skills it can reuse, and the specialist agents it can coordinate with. Each harness stream is a sequence of cumulative stages H1 ⊆ H2 ⊆ ... ⊆ HT, so later stages only add capabilities and never remove old ones. Streams are built along three axes: tools, skills, and agents.

Two design choices matter. First, each task is assigned to the earliest stage at which it becomes solvable, and it must require at least one newly introduced capability. This helps separate adaptation to new capabilities from retention of old ones. Second, capabilities are released from common core capabilities toward the long tail, which is meant to mimic real harness growth in deployed systems.

The benchmark supports two evaluation modes. In deployment evaluation, no experience is carried across stages; each harness version is evaluated independently. This isolates the direct effect of harness expansion: does a larger capability pool help, or does it mostly distract? In self-evolving adaptation evaluation, persistent artifacts such as memory, prompts, or learned skills can be updated within each stage and then carried forward, while the underlying model weights remain fixed. This tests whether accumulated experience helps or hinders adaptation under a growing harness.

The benchmark is reasonably large: 17 controlled harness streams, each with 3 to 6 cumulative stages, 802 unique tasks, 1,510 axis-specific evaluation examples, 520 executable tools, 42 latent reference skills, and 62 specialist agents. The paper evaluates representative single-agent and multi-agent systems under both modes.19:T540,The empirical message is mostly diagnostic. First, harness expansion is not free. Agents can lose competence on tasks they previously solved even though the underlying model is unchanged and the required capabilities are still present. That is the benchmark’s evidence for harness-induced forgetting. Second, self-evolving adaptation is inconsistent. Gains vary substantially across stages, axes, and environments, which suggests that simply accumulating memory or prompts is not a reliable answer to harness evolution. Third, retention and adaptation often pull in opposite directions: methods that preserve earlier competence better can be worse at exploiting newly introduced capabilities, while methods that adapt aggressively can sacrifice old-task performance.

The main concrete numbers visible from the full text excerpt are benchmark-scale statistics: 17 streams, 802 tasks, 1,510 evaluation examples, 520 tools, 42 skills, and 62 specialist agents. The paper evaluates representative SAS and MAS systems, but the excerpt provided here does not include the full per-system score tables. That makes this paper more useful as a benchmark-design read than as a leaderboard read. The most informative results are the performance trajectories over harness stages and the contrast between deployment mode and self-evolving adaptation mode.1a:T4b7,For a quick pass, read the benchmark definition and the two evaluation modes first. For foundation-model work, the deeper takeaway is the systems view behind the benchmark: many failures are not because the model lacks knowledge, but because retrieval, selection, and invocation degrade as the interface grows. That connects naturally to long-context retrieval, tool-use policy learning, and contamination of external memory.1b:T404,Boundary-Calibrated Intervention Transfer, or BCIT, stores each update as a state-bound record: the source context, the observed source evidence, prespecified applicability conditions and named hard conflicts, and provenance links for the model, data, configuration, and evaluation artifacts. The decision is made for a pair consisting of one candidate and the current context. A non-compensable conflict leads to rejection. Insufficient or unresolved evidence triggers a bounded validation run from the current parent. Only candidates satisfying a frozen authorization rule receive the full training budget. A fully trained child is still subject to a separate promote-or-rollback rule. The system may generate a small number of new atomic proposals when progress stalls, but those proposals have no fabricated source evidence and cannot skip validation. The main distinction from simple experience replay is that an update is not labeled globally as good or bad; its evidence remains tied to the context where it was observed.1c:T4b8,The proposed framework is Adaptive Functional Metaplasticity, or AFM. At each protected update, AFM first computes the endpoint that the same learner would have accepted from the exact same pre-update state without any retention constraint. This endpoint is used only as a counterfactual reference and is not installed. AFM then identifies the component of that update that is compatible with protected functional behavior and stores only an accepted fraction in the ordinary parameters. A key distinction is made between persistent adaptation, finite deployed protection, and population behavior: matching protected outputs on a finite set does not imply that the unrestricted learning has been stored, nor that behavior is preserved on unseen inputs.
