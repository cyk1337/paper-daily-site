9:T53c,The core contribution is DDBench plus a two-condition evaluation protocol. The benchmark contains 60 historical bugs mined from 13 open-source distributed systems, partitioned into three difficulty tiers, with tier-1 being the hardest and containing 31 cases. Each case is independently reproduced, sanitized for leakage, and reviewed by distributed-systems researchers, so the emphasis is on fidelity and evaluability rather than raw scale. The evaluation runs each case under two conditions: symptom-only and context-augmented. In symptom-only, the agent receives the bug symptom and codebase, similar to standard SWE-style repair. In context-augmented, it also receives curated debugging context such as logs, traces, or diagnostic notes. This design cleanly separates model-internal reasoning from externally supplied evidence. The authors use mini-swe-agent as a unified harness and evaluate 10 proprietary and open-weight models, tracking pass rate, token consumption, and steps to completion, with bootstrap tests for significance. An important nuance is that the paper does not assume more context is always better. It explicitly studies cases where faithful but causally distant observations mislead strong models, which makes the benchmark relevant not only for evaluation but also for context construction and evidence selection.a:T555,The main empirical findings are sharp. First, DDBench creates much stronger model separation than conventional coding benchmarks. On tier-1 under the symptom-only condition, the 10 evaluated models span 61 percentage points in pass rate. Among six models with publicly reported SWE-bench Verified scores, the same set spans only 7 points on SWE-bench but 58 points on DDBench tier-1. Pairwise bootstrap tests on the 31 tier-1 cases distinguish 9 of 15 top-tier model pairs at p<0.05, suggesting the separation is statistically meaningful rather than noise. Second, curated debugging context improves success and consistently reduces cost, but the gains are uneven across models. Aggregate pass rate rises from 32.6% to 50.6%, a gain of 18.1 points. First, data construction. The authors collect paper–repository pairs from major ML conferences, then mine GitHub issues from the linked repositories. They filter for issues that correspond to reproducibility blockers rather than generic feature requests or discussion. To avoid leaking the answer to the agent, they reconstruct repository snapshots aligned with issue timing and fix timing, such as issue-time snapshots, pre-fix snapshots, and post-fix snapshots. This turns naturally occurring historical failures into hidden evaluation targets.

Second, the task setup. Agents are given the paper and a fixed repository snapshot, but they do not execute code. The setting is intentionally compute-light and limited to static inspection. This is a practical design choice: many modern ML repositories require GPUs, large datasets, and external APIs, so full execution is expensive and hard to standardize. The benchmark therefore asks a narrower but still meaningful question: how many real reproducibility blockers can an agent surface from static inspection alone?

Third, the evaluation protocol. Agent findings are compared against human-reported issues using both exact match and semantic match. Metrics are reported at both the issue level and the paper level, along with cost. This layered evaluation is important because reproducibility failures are often described differently by different people. Exact match alone would understate capability, while semantic match alone would overstate localization quality. The paper also distinguishes visible failures from less visible ones, which helps characterize what current agents are actually good at.

Relative to prior work, the novelty is less about task format and more about supervision source and scale. Instead of expert-authored tasks, it uses naturally occurring GitHub issues. Instead of tens of papers, it covers 1,149 papers and 7,553 human-reported blockers. The trade-off is noisier supervision, but the snapshot design and multi-granularity metrics help manage that noise.f:T537,The scale of the evaluation is the main result. The benchmark covers 1,149 papers from three major ML conferences and 7,553 human-reported reproducibility blockers. The more important finding, however, is the gap between semantic coverage and exact localization. Agents are often able to identify the right semantic region of failure, especially for visible problems such as missing imports, broken scripts, dependency mismatches, or obvious setup issues. But they are much weaker at pinning down the exact source of the problem and at identifying less visible failure types. The paper also reports relatively low false positive rates, which suggests the agents are not simply generating broad generic warnings to inflate recall.
