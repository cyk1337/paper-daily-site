9:T402,Repo2Skill-Evo is built as:
1) A fixed V1 skill set produced by Repo2Skill via staged distillation plus expert refinement. Each skill is packaged (e.g., SKILL.md, optional scripts/references) and augmented with provenance metadata (source paths/symbols) to enable traceability.
2) A maintenance task: given the official V1→V2 release patch, a maintenance agent must delete or revise patch-verified obsolete skill lines while preserving still-valid content. The design intentionally emphasizes minimal, selective edits rather than full regeneration.
3) Evaluation: a strict patch-grounded headline metric that rewards correct edits on verified obsolete lines and penalizes edits elsewhere, plus a rubric-based NL judge with five dimensions for overall quality.
The analysis frames two complementary bottlenecks: incomplete localization of affected skill files (coverage) and imperfect edit selection (precision/within-file evidence tracing). An oracle localization experiment tests how much of the gap is purely localization.a:T66b,The core contribution is a conservative benchmark construction pipeline rather than a new model. The benchmark is mined from open-source, license-permissive Java Maven repositories. The pipeline has three stages.

First, candidate test-code change pairs are mined by walking adjacent commits that pass compilation and execution checks. Instead of relying only on static dependency analysis, the authors use lightweight dynamic instrumentation to collect test-code dependencies. This matters because static signals can over-approximate relationships and include many irrelevant files, while dynamic dependencies better reflect what the test actually exercises.

Second, the candidates are cleaned aggressively. Pairs with weak semantic linkage, unstable execution environments, or poor reproducibility are removed. This is an important design choice: many software-engineering benchmarks fail less because the task is hard and more because the labels are noisy or the environment is brittle.

Third, the benchmark tasks are packaged and labeled using cross-revision execution checks. The task type is determined by behavior across old and new code versions, not just by reading diffs. This is the key methodological point. A generated or updated test is meaningful only if it reflects the changed behavior under execution.

The evaluation protocol is also execution-centered. Metrics include success rate, pass rate, coverage, and mutation score. The most informative metric is success rate, defined so that the produced test should pass on the new version and not pass on the old version. That prevents trivial or weak tests from scoring well.b:T50c,The experiments mainly establish benchmark usability and measure the current frontier for test-evolution agents.
