19:T8d0,核心方法是 bilevel optimization。外层优化 workflow sketch，内层优化固定 sketch 下每个 LLM call 的 prompt。workflow 被表示成一串文本化的高层调用描述 a1 到 aK，每个调用对应一个更细的 prompt θi。高层 sketch 只描述“这一步做什么”，低层 prompt 决定“具体怎么做、用什么工具、如何措辞”。这种分离很重要，因为如果直接在完整 prompt 空间里同时搜索结构和参数，搜索空间会过大且难以稳定。

内层优化采用 layer-wise textual backpropagation。作者把 workflow 看成模块堆叠：输入 x0 经过第 i 个调用得到 xi。先做一次前向执行，得到所有中间输出。然后对最后一层，用一个专门的 LLM 根据最终输出、参考答案和损失，生成针对最后一个模块的 textual gradient。这个 gradient 不是数值向量，而是一段自然语言反馈，描述该模块应该如何调整输出行为。对中间层，则再用另一个 LLM，根据当前层输入、当前层输出以及下一层传回的 textual gradient，生成当前层的 textual gradient。这样就形成了从后往前的语言版误差信号传播。最后，再用优化器 LLM 汇总一个 batch 上的 textual gradients，改写对应模块的 prompt。

外层优化则修改 workflow sketch 本身。作者同样使用 textual gradients，但对象从 prompt 变成结构描述：可以删除已有调用、插入新调用、调整调用顺序或职责分工。这里的设计借鉴 NAS，但没有把结构离散化成固定算子集合，而是直接在文本空间里编辑 workflow 描述。优点是表达能力强，能自然容纳 retrieval、planning、verification、tool use 等异构步骤；代价是搜索稳定性更依赖底层 LLM 的判断质量。

和已有 prompt optimization 方法相比，FlowBot 的区别在于它不假设 workflow 结构固定。和自动 workflow generation 方法相比，它又不是一次性生成后就结束，而是通过内外两层交替更新，让结构和节点提示共同演化。作者还强调 modular optimization：每个模块的更新要显式条件于下游模块的错误，这比独立优化单步 prompt 更接近真正的组合系统调优。1a:T893,The method is a bilevel optimization framework. The outer loop optimizes a workflow sketch, while the inner loop optimizes the prompts of individual LLM calls under a fixed sketch. A workflow is represented as a sequence of high-level textual call descriptions a1 to aK, and each call has an associated detailed prompt theta_i. The sketch specifies what each step is supposed to do, while the prompt specifies how it should do it, including instructions and tool access. This separation keeps the search space manageable.

The inner loop performs layer-wise textual backpropagation. The workflow is treated like a stack of modules: x0 is the input, and each call maps x_{i-1} to x_i. After a forward pass, the final module receives a textual gradient generated by another LLM conditioned on the final output, the gold answer, and the task loss. This gradient is not numeric; it is natural-language feedback describing how the module should change its behavior. For intermediate modules, another LLM generates a textual gradient based on the current module’s input, output, and the downstream gradient. In this way, error information is propagated backward through the workflow in language form. A separate optimizer LLM then aggregates gradients over a batch and rewrites the module prompt.

The outer loop edits the workflow sketch itself. It uses textual feedback to add calls, delete calls, and revise the decomposition of responsibilities across steps. This is inspired by neural architecture search, but instead of searching over a fixed operator library, it edits workflow descriptions directly in text space. That makes the method expressive enough to represent retrieval, planning, verification, and tool use in a unified way, though it also makes optimization more dependent on the quality of the underlying LLM.

Compared with prior prompt-optimization methods, FlowBot does not assume a fixed workflow. Compared with one-shot workflow generation methods, it alternates between structure updates and module-level prompt updates, allowing both to co-evolve. The modular optimization aspect is important: each module is updated in light of downstream failures rather than in isolation.1b:T539,The empirical study compares FlowBot against two classes of baselines: prompt-optimization methods on human-crafted workflows, such as GEPA, and automated workflow-generation methods, such as AFlow. The main result is that FlowBot is competitive across multiple tasks and tends to discover sensible workflow decompositions rather than arbitrary chains of calls.

The ablations carry most of the weight. Removing the outer-loop structural search and keeping only prompt optimization under a fixed workflow hurts performance, which shows that structure search matters. Removing the inner-loop modular textual backprop and replacing it with coarser updates also hurts, which supports the claim that layer-wise textual gradients provide more targeted optimization signals. The paper also includes qualitative evidence that induced workflows often separate responsibilities in a meaningful way, for example decomposing a task into planning, retrieval or tool use, and final synthesis or verification.
