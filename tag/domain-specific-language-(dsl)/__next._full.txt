18:T581,The method has two key components. First, the model never emits raw SQL. It operates over a typed DSL with 15 relational operations: 12 relation-building operators and 3 read-only probing operators. Intermediate states are represented as immutable Relation handles, and later operations can only reference existing handles. This matters because many errors are caught at compile time rather than after SQL execution: unknown tables, unknown columns, references to columns removed by earlier projections, and malformed parameters all trigger typed errors from the DSL engine. Second, the system runs a standard think-act-observe ReAct loop. At each turn, the model reasons in a <think> block, then emits a JSON array of tool calls. The engine executes them sequentially and returns observations such as new handles, available columns, row counts, and result previews. If a call fails, the rest of the batch is skipped and the next reasoning step sees the diagnostic. Grounding is handled through iterative probing: the model can inspect candidate tables, sample values, verify join keys, and only then commit to joins, filters, or aggregations. An answer-shaping stage converts the final trace into the benchmark’s canonical answer format.
