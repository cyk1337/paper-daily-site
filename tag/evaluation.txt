从方法取舍看，这篇工作的关键不是发明新的 verifier，而是把形式方法嵌入真实软件工程 benchmark，并用环境 axiomatization + adversarial audit 让它可落地。相比传统 hidden tests，它牺牲了构造成本，换来更强的 correctness oracle；相比端到端全仓库验证，它牺牲了全局完备性，换来可扩展性。1a:T92a,The core method is Benchproofer, a pipeline that converts a coding task with a known correct patch into a formally verified benchmark instance. The design is built around two practical constraints: full-repository verification is infeasible, and mechanical verification alone is not enough if the specification itself is wrong.

First, Benchproofer uses local modeling. It formally specifies and verifies only the new or modified code. Calls into unchanged functions are handled through axioms: over-approximate summaries of the properties the patch relies on. This is the key scalability move. Without it, one would need to verify the entire transitive closure of dependencies, which is unrealistic for SWE-bench-scale tasks.

Second, the benchmark supports three verification backends: Nagini for statically typed Python verification, Velvet as an imperative-style verification DSL in Lean, and pure Lean where proof obligations are discharged by proof writing rather than an SMT solver. This is useful because it separates different sources of difficulty: specification quality, program verification, and proof search.

Third, the construction pipeline uses both mechanical and adversarial admission gates. A candidate instance is admitted only if the spec, implementation, and proof check mechanically in the target backend, and if adversarial LLM auditors judge the specification to be faithful to the original task. This is an important design choice. Formal verification only guarantees conformance to the spec, not that the spec captures the intended behavior. The paper identifies faithfulness failures as the dominant issue: a spec constrains part of the required behavior while leaving critical semantics unconstrained.

Fourth, the evaluation protocol disentangles patch generation from specification generation. The paper compares several settings: solving from the natural-language issue alone, adding a structured natural-language specification, asking the model to synthesize a specification and verify against it, and supplying the correct formal specification. This makes it possible to localize the real bottleneck.

The contribution is therefore not a new verifier. It is a practical recipe for embedding formal methods into realistic software-engineering benchmarks using environment axiomatization plus adversarial auditing.1b:T608,SWE-Proof covers all 500 instances of SWE-bench Verified and extends to the Python fragment of SWE-bench Pro. Each instance includes a ground-truth formal specification, implementation, and proof, under three verification backends. For realistic repository-level verified coding tasks, this is a substantial benchmark asset.

The evaluation uses Claude Opus 4.8 and GPT-5.5. The main findings are sharp. First, passing all hidden tests is not a reliable correctness signal: roughly 25% to 50% of such patches are still flawed. Second, adding a structured natural-language “specification” does not close that gap, which shows that informal constraints remain too weak. This design matters because a fixed-rubric benchmark would be vulnerable to memorization and would not truly test rubric generation quality. By keeping environments and certificates, the benchmark can evaluate newly generated rubrics from arbitrary models. The evaluation protocol is adversarial but structured. A rubric generator first produces a rubric from the task and evidence. A fixed attacker then writes an answer intended to score highly under that rubric, regardless of whether it remains faithful to the evidence. An honest baseline answer is also prepared. A literal judge scores both answers using the generated rubric, while the oracle certificate independently checks for violations. Exploitation is defined when the attacker scores above the honest baseline under the rubric judge while failing the oracle certificate. This turns rubric exploitability into a measurable event rather than an anecdotal concern. The paper also reports multiple robustness analyses to isolate whether failures come from the judge, the oracle, the attacker, or the rubric generator itself.
