18:T7c0,This is a measurement study, not a new agent method. The authors fix a ReAct-style coding-agent harness on a multi-tool aggregation task and evaluate protocol fidelity rather than task success. The design has three important pieces.

First, it separates channel from prompt. “Channel” means tool schemas are passed through the native tools= field and then rendered and parsed by the server. “Prompt” means the tool list and JSON call format are written directly into the textual prompt. The paper compares three settings: native, which uses tools= only; native+hint, which still uses tools= but also injects a plain-text tool list and strict JSON format instructions; and text-tools, which removes tools= entirely and parses calls from text. This isolates server-side protocol handling from the model’s ability to follow tool instructions.

Second, it refines the label space. Each assistant turn is categorized as valid in-schema call, hallucinated call, unparseable text, no-call prose, or non-response. The non-response category is crucial. In Ollama, some models trigger HTTP 400 request rejection before inference; the harness retries, gives up, and writes a generic error string into the trajectory. If that error is not preserved as structured metadata, downstream analysis can count it as a model non-call. The paper therefore excludes non-responses from the fidelity denominator and reports them separately.

Third, it performs a multi-stack comparison. The same weights and the same request behave differently under Ollama, llama.cpp, vLLM, and SGLang: some stacks reject tools=, some accept it but return calls as plain text, and some require explicit parser configuration before a call is recognized. The point is not to rank stacks, but to show that the measured outcome is stack-dependent. The constrained-decoding baseline adds another useful negative result: forcing valid call syntax can simply move the failure mode from malformed calls to endless looping.19:T668,The experiments cover small local models including Qwen2.5-Coder 0.5B/1.5B/3B, Llama-3.2, Phi-3, and Gemma-3. Results are reported over 8 seeds using both turn-pooled rates and per-seed means, with seed-level bootstrap 95% confidence intervals. Four findings stand out. First, under Ollama’s default native function-calling path, Qwen2.5-Coder models accept tools= but return calls as text, Llama-3.2 returns native tool_calls, and Phi-3 and Gemma-3 are rejected with HTTP 400 before inference. Without structured error logging, those rejected models can be falsely reported at 0% fidelity. Second, for models whose requests are accepted, native+hint often recovers much of the fidelity, which suggests that some failures come from protocol rendering rather than inability to use tools. But Llama-3.2 degrades under a uniform text-only protocol, so the best setup is model-dependent. Third, the same weights behave differently across four serving stacks: models rejected by Ollama can run on llama.cpp, vLLM rejects similar requests by default, and SGLang accepts them but returns text calls. That directly shows the benchmark outcome is partly a serving-stack property. Fourth, turn-pooled and per-seed metrics can differ by roughly 55 points because a single looping episode can dominate the pooled denominator. This makes aggregation choice a major source of instability.

The paper also includes a useful negative result: at this measurement precision, the authors do not support broader claims about scale, model family, or reasoning ability and explicitly avoid making them. That restraint is one of the stronger parts of the study.1a:T418,For a skim, start with the introduction and the method section explaining the OpenAI-compatible tool-calling pipeline. The key point is that tools= is not passed directly to the model; it is mediated by server-side template rendering and output parsing. Then read the comparison among native, native+hint, and text-tools, plus the four-stack behavior table or figure. Those sections make the confound concrete. Finally, look at how non-response is defined and removed from the fidelity denominator. That detail determines whether a reported 0% is meaningful or simply an artifact.

If you only have 20 minutes, that is enough to get the main lesson. If you are building your own evaluation stack, the practical checklist is worth extracting: log HTTP and serving failures explicitly, separate request rejection from model non-calls, report both pooled and per-seed metrics, and document parser/template configuration. It is not a methods paper, but it is a useful guardrail for anyone evaluating local agents or constructing tool-use training data.1b:T43b,The evaluation covers preference ranking, evidence-grounded factuality, final-answer adjudication, and simple style or format checks. The data include 400 RewardBench pairs, 350 JudgeBench GPT-4o pairs, 240 HaluEval evidence-grounded judgments, 150 saved multi-turn answer-consistency replies, 108 GSM8K challenge-conversation final replies, and 64 synthetic evidence judgments, for 1,312 items in total. A 642-item pilot was frozen before inference and split 40/60 into selection and test subsets; a 670-item extension was frozen before inspecting pilot accuracy. JEV comes within about three percentage points of the strongest LLM comparator on ordinary preference and evidence-grounded factuality while costing about 0.36% of that comparator’s measured fee. Larger gaps appear on tasks that require checking derivations or resisting fluent but incorrect answers. Confidence analysis shows that many of JEV’s misses are concentrated in low-confidence regions, which makes selective escalation viable, but the paper also reports failures of threshold transfer on some workloads.1c:T518,EvalMem abstracts heterogeneous memory systems into an encoding–retrieval–generation pipeline. The tested system first runs natively: it processes dialogue history, updates its memory store, retrieves context, and generates an answer. EvalMem then diagnoses the completed run using benchmark annotations. The Encoding Examiner checks whether the target fact is present in the memory store. The Retrieval Examiner checks whether the system’s native retriever returns usable evidence. The Generation Examiner tests whether the model can answer when given oracle evidence. An Attribution Agent merges these decisions into an 11-code multi-label defect set, allowing coupled failures while avoiding retrieval blame when the source fact is absent from the store. The framework also separates POS queries, where the system should remember and retrieve a fact, from NEG queries, where the correct behavior is refusal due to insufficient evidence. To make store-level diagnosis more reliable, the Encoding Examiner uses a recall-first agentic RAG routine that searches the original memory store with both the query and the source evidence. The paper also introduces DynaMem-Bench for on-policy dynamic evaluation and MemWiki, a search-friendly auxiliary structure built from a system’s own memory export.1d:T493,The benchmark defines three knowledge-work personas: Morgan, a startup CEO; Alex, an infrastructure engineer; and Riley, a product manager. Each persona has a multi-year simulated history with 3,400 to 5,128 user messages, around 500k user-message tokens. Evaluation is action-based rather than QA-based. For example, if a user asks the agent to order a small latte without naming a cafe, the agent has to recover an earlier preference and place the order at the right shop. Tools and apps such as Notion, Gmail, GitHub, calendars, CRM systems, and deployment tools are simulated for reproducible action grading.

The data is built hierarchically. The authors first define the persona, relationships, and tools, then draft multi-year narratives, quarterly plans, weekly events, and conversations. Each test is verified with an oracle-memory procedure: an agent given the relevant history must be able to complete the task, while the same agent without that history must fail. This addresses common defects in synthetic benchmarks, such as incorrect labels, mislabeled evidence, or unanswerable tasks. Every submission must report accuracy, total cost, and median latency.1e:T6ef,The paper has three methodological layers.

First, it measures shared errors directly. Across multiple preference datasets, the authors collect decisions from both open-weight and frontier judges, compute pairwise error correlations, and summarize the amount of independent information using effective sample size. They use the design-effect approximation: once average correlation is nonzero, a bank of n judges behaves like a much smaller number of independent judges in variance terms. The paper is careful to note that this does not mean 10 judges can literally be replaced by 3.5 judges; it means the consensus contains only that much independent statistical information.
