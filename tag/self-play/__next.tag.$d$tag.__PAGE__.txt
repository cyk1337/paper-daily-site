9:T4d0,SESA (Self-Evolving Skill-Augmented Agent) integrates tool-augmented search self-play with an evolving skill memory.
- Two policies: a challenger/proposer generates problems with verifiable targets; a solver uses a search tool to answer. Parameters are separated.
- Skill memory B: a bounded, non-parametric bank of human-readable skills. Each entry stores a description, trigger conditions, avoidance cues (common confusions/anti-patterns), reusable query templates, and usage statistics (retrieval/helpful/hurt counts) for maintenance.
- Asymmetric access: only the solver can retrieve skills; the challenger cannot, preventing strategy leakage that would collapse the self-play game.
- Four-stage loop: (1) memory priming with a small initial set; (2) asymmetric self-play where retrieval is active during training rollouts; (3) frontier shaping to keep generated problems near the solver’s competence boundary; (4) failure distillation that converts informative failed rollouts into deduplicated skills written back to memory.
- Attribution design: compare SSP baseline, SESA-Off (trained with the loop but memory disabled at inference to measure parametric carryover), and SESA-On (memory enabled to include retrieval gains).a:T6bd,The method has three main ingredients. The first is an agentic red-teaming harness. Instead of asking the attacker for a single-shot jailbreak prompt, the system gives it a stateful defender_model tool so it can probe, observe, revise, and retry. This matters because realistic prompt injection often depends on multi-turn interaction, tool outputs, file edits, and context-specific weaknesses that a one-pass generator will miss. The second ingredient is environment construction. Existing capability tasks are converted into adversarial RL environments under a realistic threat model: during the defender’s rollout, the attacker may be allowed to edit a designated tool response, a local file region, or another controlled insertion point. This keeps the attack surface close to real agent deployments while making the environment family extensible as production tasks expand. The third ingredient is large-scale self-play RL. The base game rewards the attacker for inducing valid failures and rewards the defender for resisting the attack while still completing its original task. Crucially, training is not limited to a single attacker-defender pair. The attacker is trained against a diverse, simultaneously trained population of strong defenders. That design is meant to prevent overfitting to one defender’s quirks and instead teach the attacker to identify model-specific weaknesses. The paper also frames scaling along three axes: inference-time compute through iterative search in the harness, environment diversity through many red-teaming scenarios and goals, and training compute through a very large RL run. The resulting GPT-Red is therefore a search-based adaptive attacker, not a prompt-template library.b:T51b,The main empirical message is that GPT-Red finds more working attacks, transfers better, and keeps improving with additional test-time compute. Another important result is longitudinal rather than benchmark-specific: progressively stronger internal red-team models were used over roughly six months in the training of each production model since GPT-5.2, culminating in GPT-5.6 achieving the strongest robustness profile in their internal evaluation suites. The public text does not fully disclose all run details such as parameter counts, RL steps, or complete absolute metrics, but several experimental signals are especially informative. Test-time scaling is strong, which suggests the attacker is using search and adaptation rather than memorized attack strings. Training against a defender population improves generalization, indicating that the attacker is learning broader attack principles rather than exploiting one model’s idiosyncrasies. The method has three main components.

The first is a two-level group-relative update. On the Solver side, the update is close to GRPO, but replaces standard-deviation normalization with mean normalization so that the gradient better matches the MLRL weighted-pass@k objective. This gives rare successful trajectories larger weight. On the Proposer side, advantages are defined over candidate specifications based on the distribution of Solver outcomes, with the aim of generating tasks near the Solver’s competence frontier rather than trivially easy or impossible ones.

The second is iterative self-distilled SFT. The authors argue that sparse-reward exploration alone causes the Proposer to drift away from the valid-output manifold. They therefore repeatedly project the model back onto a region that reliably produces valid specifications and solutions before full RL. This is presented as a stabilizing requirement, not a minor warm-start trick.

The third is a UCB-guided Curriculum DAG. Newly proposed tasks are admitted only if they pass strict filtering, novelty checks, and Solver verification. UCB is used to select seeds from the existing DAG, balancing exploration and exploitation while preventing curriculum poisoning.

Compared with standard self-improvement setups, the novelty is not the verifier itself but the closed-loop coupling of proposer learning, solver learning, manifold preservation, and controlled curriculum expansion.10:T4d2,POP (Post-trains LLMs on Open domains with Pretraining text) uses one model in three roles, but ties all roles to a sampled document d from a relevant corpus D.
- Proposer: sample d (min length constraint; truncate), then generate a question x and a reference answer y_ref. For tasks with factual grounding (health QA), x is constrained so the answer is derivable from d; for creative writing / instruction following, the response must build on d.
- Solver: sample multiple candidate answers {y_j} to x.
- Verifier: conditioned on (d, x, y_ref, {y_j}), generate a query-specific rubric (criteria + descriptions + optional gold labels + weights), then grade each candidate.
Stability / anti-hacking mechanisms:
1) Privileged access: the verifier sees d (and more context) while the solver only sees x, creating a generation–verification gap via information asymmetry.
2) Preference learning instead of scalar RL: select only the top- and bottom-scored answers and train with DPO, which is less sensitive to score calibration noise.
3) Diversity via corpus grounding: sampling diverse d helps prevent query mode collapse.
Operationally, the framework is a reusable pipeline where changing D and prompts adapts to new open-ended tasks.11:T7e3,The method, Self-Guided Self-Play (SGS), uses three roles, all initialized from the same base model: a Solver, a Conjecturer, and a Guide. The Solver attempts problems, the Conjecturer generates synthetic problems, and the Guide scores whether those synthetic problems are actually useful for solving the corresponding target problems. Two design choices are central.

First, the Conjecturer is not asked to generate arbitrary training problems. For each unsolved target problem x, it is conditioned to generate a related synthetic problem x-tilde that should be easier but still meaningfully connected. This anchors the synthetic distribution near the frontier of unsolved targets and prevents drift toward detached “fake hard” problems. Second, the Guide scores each synthetic problem for at least relevance and formulation quality. A problem must not only look related, but also be cleanly posed and structurally useful; messy, bloated, or pathological constructions are downweighted.

During training, the Solver attempts both original and synthetic problems, with rewards coming from a verifiable environment; in Lean4, the verifier is the compiler. The Conjecturer’s reward is no longer based only on whether the Solver passes. It depends on whether the Solver makes progress on the generated problems and whether the Guide judges them to be high quality. This writes both learnability and target relevance into the generator objective, which is the mechanism used to suppress reward hacking.

The paper also stresses the Solver objective. If the Solver’s RL objective causes entropy to collapse too quickly, its policy distribution narrows early, the Conjecturer receives weaker feedback, and the whole self-play loop loses exploratory capacity. So SGS is not just “add a judge to the generator.” It addresses two coupled failures at once: generator degeneration and solver entropy collapse. The novelty lies in making data generation, quality evaluation, and solver exploration a stable closed loop.12:T7a9,Experiments are conducted on Lean4 theorem proving, with the goal of maximizing cumulative solve rate on a fixed training set of hard problems. The authors deliberately run training much longer than prior work: the main self-play run produces more than 6 billion tokens and epochs over the target set more than 230 times. This is important because the paper is about long-run dynamics, not short-run gains. Evaluation includes both direct solve rate and scaling-law fits to cumulative solve rate, which are used to compare asymptotic behavior across methods.

The main result is that SGS outperforms pure RL and parallel sampling baselines, improving asymptotic solve rate by 7% over RL alone. With enough compute, DeepSeek-Prover-V2-7B trained with SGS surpasses the pass@4 of the much larger DeepSeek-Prover-V2-671B. The implication is that in some regimes, controlling the quality of long-run self-generated data matters more than simply increasing parameter count.

The ablations are especially important. Removing conditioning on unsolved target problems causes the synthetic distribution to degrade. Removing the Guide also leads the Conjecturer to collapse toward pathological problems that do not help learning. Freezing the Conjecturer is also suboptimal, because the Solver quickly saturates the fixed synthetic distribution. On the Solver side, the objective ablation shows that rapid entropy collapse weakens the training signal available to the Conjecturer, so self-play failure is not a one-sided issue; both distributions can degenerate together.

For a pretraining-oriented reader, the most useful part is not the exact Lean score. It is the evaluation methodology: how the paper defines plateauing, and how long-run training plus asymptotic fitting can separate methods that look good early from methods that remain productive late.
