a:T4e0,The core idea is response-level speculative decoding. Instead of drafting k tokens and verifying them with token-level acceptance, a cheap model drafts an entire response and a stronger model decides whether to accept it, enhance it, or be skipped entirely. This makes the method deployable across providers and architectures through standard HTTP APIs.

The system has three main components. First, a proxy layer intercepts Anthropic-format API calls, so the client can remain unchanged. Second, a rule-based complexity router sends tool-selection requests directly to Opus, because smaller models are unreliable at producing schema-valid tool JSON; simple text-generation requests are sent directly to DeepSeek; more complex text requests go through draft→verify. Third, the verifier performs response-level judgment in natural language rather than token-level acceptance.

Relative to prior work, this is neither standard speculative decoding nor pure request-level routing. It sits between them: both models can participate on the same request, but only through API-level orchestration. The trade-off is clear. It loses the lossless guarantee of token-level speculative decoding, but gains deployability across heterogeneous black-box models.b:T45b,The evaluation is built around a real agentic coding workload using Claude Code. DeepSeek-V4-Pro serves as the draft model and Claude Opus 4.8 as the verifier. On 125 production requests, the paper reports an 88.8% draft-use rate and a 45.8% API cost reduction relative to a direct Opus baseline.

Latency also improves: median response time drops from 3698 ms to 2026 ms, a 1.83x speedup at p50. The reason is not that verification is intrinsically faster, but that the SKIPPED path dominates the workload, with roughly 64–70% of requests handled by the cheap model alone.

For quality, the paper reports 100% pass rate on a 20-task benchmark versus 95% for the direct Opus baseline. This is directionally interesting but should be treated cautiously because the benchmark is small and may not fully cover routing mistakes, verifier failures, or edge cases in tool use.

One operational detail matters a lot: tool-selection turns account for roughly 70–80% of production turns, while speculative handling only applies to the remaining text-generation turns. That explains why the tool-bypass rule is essential.c:T457,Paradigms:
- PA: predict the judge score for the would-be response, then answer/act (or route).
- RPRA: add a reasoning step before prediction and another before answering, aiming to improve both score prediction and final output.

Implementation regimes: zero-shot, in-context learning, and supervised fine-tuning.
