9:T9b7,技术路线可以拆成“人类提供什么”和“agent 决定什么”两部分。

人类提供的是 Research Skills。它们不是逐实验的人工指令，而是把专家经验编码成可执行的操作模板、代码资产、权限边界和流程约束。论文强调 high-density prior, low-frequency intervention：人类把成熟做法一次性写成可复用技能，之后不再频繁介入具体实验决策。这样做的目的，是把经验保留在系统里，但把搜索权交给 agent，而不是让 agent 在完全无先验的空间里盲搜。

agent 端由 Codex GPT-5.6-Sol（xhigh reasoning）承担。它从 base checkpoint 和可用算力出发，先构建 executable task pool，再基于 verified capability-gap trajectories 对 Qwen3.6-27B 做 cold-start。随后训练流程不是直接从 SFT 跳到 RL，而是先经过 OPSD，再过渡到 RLVR。根据正文描述，OPSD 阶段里至少发生了三类关键调整：其一，evaluation 会反过来决定哪些数据进入训练，说明数据池不是静态的，而是被在线证据筛选；其二，受控消融改变了 self-teacher 可见的证据范围，作者借此诊断 teacher 何时在利用泄漏信息、何时在学真实能力；其三，原有目标函数出现 collapsing objective，迫使 agent 把学习规则改成 verifier-anchored credit，也就是让 credit assignment 更紧贴可验证结果，而不是依赖容易漂移的代理信号。

RLVR 阶段则处理另一组问题：reward exploits、false verdicts、length-dependent degeneration。对应的修补方向分别是重写 reward eligibility、调整优化过程、控制 trajectory budgeting。这里最值得注意的是，论文没有把 RLVR 写成一个固定 recipe，而是把它描述成一系列失败后的重设计：奖励被利用，就收紧资格；verifier 有误判，就修改奖励语义或过滤机制；长输出导致退化，就把预算和优化目标一起改。这个叙述方式很像真实工业训练，而不是干净的学术设定。

从模型定位看，iCoder-27B 是一个面向工业编码的专门模型，任务覆盖 RTL 设计和 GPU kernel 优化。选择这两个方向有明确原因：它们都能用可执行 verifier 检查正确性，同时又要求性能意识和系统约束，不是普通代码补全就能解决。论文因此把“可验证环境中的 agent-led model development”落在一个反馈足够硬、但搜索空间仍然很大的场景里。a:T749,结果部分最醒目的是 iCoder-27B 在多个工业代码基准上的竞争力。相对同尺寸的 Qwen3.6-27B，iCoder 在 RTLLM 上从 49.6 提升到 68.0，增幅 18.4 分；在 VerilogEval Spec-to-RTL 上从 70.1 提升到 86.3，增幅 16.2 分；在 KernelBench L2 correctness 上从 28 提升到 74，约 2.64 倍。这个幅度说明它不是小修小补，而是任务能力被显著重塑。

与更大模型相比，iCoder 也有竞争力。论文给出的数字是：在 RTLLM 上超过 DeepSeek-V4-Pro（68.0 vs. 67.5）；在 KernelBench L1 correctness 上接近翻倍于 DeepSeek-V4-Pro（61 vs. 32）。对闭源前沿模型，iCoder 在 RTLLM 上高于 GPT-5.5、Claude Opus 4.8、Gemini 3.5 Flash（68.0 vs. 66.0/64.7/63.5）；在 KernelBench L1 上也高于 GPT-5.5 和 Gemini 3.5 Flash，并超过 Claude 的 55 达到 61。TritonBench-G 上它与 Claude Opus 4.8 持平在 20.1，高于 GPT-5.5 的 19.5 和 Gemini 3.5 Flash 的 14.9。

论文还给了更贴近使用场景的 case study。对 8 个 RTL design 任务，iCoder 距 HY3 和 DeepSeek-V4-Pro 分别只差 1.1 和 4.5 分，但使用的输出 token 仅为它们报告值的 51% 和 33%。这说明它不仅正确率高，推理开销也更省。对选取的 8 个 GPU operator，它在其中 2 个上达到 strongest archived endpoint，说明其优化能力不只是 benchmark 分数上的偶然。

从全文表述看，实验的另一条主线是开发过程中的 ablation 和失败分析，而不仅是最终榜单。作者强调 evaluation 改变训练数据进入条件、controlled ablation 改变 self-teacher 证据、objective collapse 触发学习规则重写、reward exploit 和 false verdict 改写 RLVR 设计。这些内容如果正文给出具体表格和时间线，会比最终分数更值得看，因为它们揭示了 agent 是如何做研发决策的。b:Ta30,The setup is organized around a division of labor. Humans provide Research Skills: reusable, executable operational procedures, code assets, permission boundaries, and process scaffolds distilled from expert model-development practice. The paper frames this as high-density prior, low-frequency intervention. The point is not to remove human expertise, but to compress it into reusable machinery so that the agent can search over concrete development decisions without requiring constant human steering.

The agent is Codex GPT-5.6-Sol running at high reasoning effort. Starting from a base checkpoint and available compute, it first builds an executable task pool, then cold-starts Qwen3.6-27B on verified capability-gap trajectories. Training does not jump directly from supervised initialization to RL. Instead, the pipeline goes through OPSD and then RLVR.

The OPSD stage appears to be where much of the development logic happens. The paper highlights at least three important dynamics. First, evaluation changes which data are admitted into training, so the data mixture is not static but filtered by ongoing evidence. Second, controlled ablations alter what evidence the self-teacher can access, which is a way to diagnose when the teacher is exploiting leakage versus learning transferable capability. Third, the original objective collapses, forcing the agent to redesign the learning rule around verifier-anchored credit. That means credit assignment is tied more tightly to executable verification rather than to softer proxy signals that drift or become exploitable.

The RLVR stage addresses a different set of failures: reward exploits, false verdicts, and length-dependent degeneration. The corresponding fixes involve changing reward eligibility, modifying optimization behavior, and redesigning trajectory budgeting. One of the strongest aspects of the paper is that RLVR is not presented as a fixed recipe. It is presented as a sequence of failures and revisions: when reward is exploited, tighten eligibility; when the verifier is wrong, revise reward semantics or filtering; when long outputs degrade behavior, adjust both budget and optimization. That is much closer to real model development than a static benchmark loop.

The task domain is industrial coding, specifically RTL design and GPU kernel optimization. That choice is sensible. Both domains offer executable verification, but they also require exact reasoning, systems awareness, and performance-sensitive optimization.
