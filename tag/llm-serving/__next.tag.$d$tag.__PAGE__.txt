First, the paper builds a trace-level accounting identity for decode work. In each decode iteration, dense weights are shared across all useful outputs, while each output token attends to its own KV history. Let Mw be the dense-weight footprint in bytes, Beff the realized mean number of useful outputs per iteration, KKV the combined key-value bytes per cached token across layers, and L̄token the useful-token-weighted mean attended history length. Then the logical read demand per useful output token is Atoken = Mw/Beff + KKV·L̄token. If one also accounts for writing one new KV record per generated token, the read-write demand becomes Atoken_rw = Mw/Beff + KKV·(L̄token + 1). The key idea is structural: batch size and context length affect different terms, rather than entering the model as interchangeable scalar knobs.

Second, the authors convert this accounting into regression coordinates for energy. They define q_w = Mw/(10^9·Beff) for shared dense-weight bytes and q_KV = KKV·(L̄token + 1)/10^9 for KV read-write bytes, both in decimal GB, and introduce realized decode time per token, τ, computed from total decode duration divided by useful output tokens. Token energy is then modeled with a common affine form over q_w, q_KV, τ, and a constant term. This is an important design choice: bytes alone are not enough, because the same logical byte demand can be realized with different occupancy, kernel efficiency, communication overhead, and stall behavior.

Third, the paper connects logical accounting to physical memory behavior. Active bytes are explicitly defined as the principal logical account of dense-weight and KV accesses, not all resident memory and not all operator traffic. Embedding and positional accesses sit outside the main account and require separate treatment. The authors then use HBM measurements to test how these logical coordinates map to actual physical traffic, and calibrate coefficients per model and hardware platform. Taliesin stores and restores the KV state produced by prefilling a block of text. Blaise stores the text itself in sectioned form and selects a relevant section on the CPU so the model reads only that section rather than the full corpus. Taliesin removes repeated computation; Blaise removes unnecessary reading.

Taliesin is built around byte-exact memory. After a runtime computes KV state for a prompt block, the system stores that state under a fingerprint defined by the exact input bytes, the model fingerprint, and the tenant identity. If a later request contains the same byte block, the runtime loads the saved KV state instead of recomputing it. The design goal is exactness: restored state must yield bit-identical logits to a fresh prefill. To enforce this, the system validates stored records on load and falls back to normal computation on any failure. The guiding rule is explicit: serve without memory rather than serve with wrong memory. This differs from approximate cache reuse or ordinary GPU prefix caching, where the emphasis is often hit rate rather than strict equivalence.

Blaise is retrieval-like, but the returned unit is byte-exact text rather than an approximate semantic chunk assembled from embeddings. The paper does not disclose the internal section-selection method. It reports only the first operating mode, where the CPU selects one section and passes its exact text to the model. A second mode is mentioned, where the model reads Blaise’s index and Taliesin amortizes that reading too, but that mode is not evaluated here.

It requires tenant identity and model fingerprinting to prevent cross-model or cross-tenant misuse, supports integrity checks and encryption at rest, and explains why reuse must happen at block granularity with exact token-position alignment.
