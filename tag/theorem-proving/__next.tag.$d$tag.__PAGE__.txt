9:T437,The central object is the conditional proof-difficulty function V(T|P), the difficulty of proving a target theorem T given an available premise set P. Lean 4 and mathlib provide the formal environment, and proof difficulty is operationalized through formal proof length or proof cost. Using the dependency structure in mathlib, the authors post-train a 27B model to predict V(T|P) before the proof is actually constructed. They then define intrinsic interestingness as proof length divided by statement length. The intended signal is high information density: a theorem that is short to state but hard to prove is more interesting. They also define utility as the amount by which adding a theorem to the mathematical context compresses later proofs. Utility captures reusable abstraction, while interestingness is easier to estimate locally. The paper reports a strong correlation between the two, which motivates using interestingness as a practical reward. The metric is then used both for post-training theorem generation and for inference-time pruning in recursive discovery.a:T41a,The framework has three main components. First, it decomposes each natural-language reasoning step into premises, explanations, and conclusions, making the dependency structure explicit. Second, it auto-formalizes these components into symbolic representations and uses automated theorem provers to check whether the conclusion follows from the premises. Third, it defines Solver-Based Backtracking Reward, or SBR, which combines solver verification with premise fidelity. This matters because a model could otherwise obtain a formally valid proof by changing or misusing the original premises. At inference time, if a step’s SBR falls below a threshold, the system backtracks and regenerates from that point. Compared with post-hoc methods such as LogicReward and VeriCoT, LogicTrack verifies during generation rather than after the full trajectory is completed. The paper also extends the framework to supervised fine-tuning by pairing real flawed model trajectories with solver-verified corrections and introducing a dedicated <backtrack> token.b:T4ed,This is not a new model paper. It is a detailed expert-review case study. The authors used Claude Code, given a human-written theorem statement and a PDF proof sketch from Hartshorne, to semi-autonomously formalize Grothendieck’s vanishing theorem in Lean. The first fully compiling version is called state A. An expert Lean/mathlib review then identified substantial issues in definitions, theorem statements, API design, and file organization. Those review comments were converted into a checklist, and Claude plus Codex iterated until the checklist was addressed, producing state B.

The paper’s main contribution is the evaluation frame. It separates “kernel acceptance” from “library quality” and documents the difference with before/after expert review. One especially informative episode is the heartbeat debugging story. When typeclass search and proof checking became too expensive, the agent’s first move was to raise maxHeartbeats repeatedly. The durable fix was different: cache instances with inferInstanceAs, split large proofs into named lemmas, and restructure the development. That is a concrete example of the broader pattern: the agent follows locally executable fixes more readily than it recognizes structural design problems.c:T43a,The evidence is a project-level reconstruction rather than a benchmark table. The development is around 5,000 lines of Lean code and targets a graduate-level algebraic geometry theorem, not a short contest-style proof. State A already reaches zero sorries and follows the intended mathematical proof structure, which is a strong sign that current models can handle substantial local proof completion when the route is fixed. The weaknesses appear under expert review: poor definitions, insufficient theorem generality, awkward namespace and file structure, and APIs that are hard to build on.

After the review-driven refactor, state B is substantially better as a library artifact. The paper does not reduce this to a single scalar metric. Instead it presents process evidence: the sorry curve, commit history, token usage, loop modes, and the evolution of expert-review findings. That is exactly the point. If one only measures “does it compile?”, state A already looks successful.
