17:T4ed,This is not a new model paper. It is a detailed expert-review case study. The authors used Claude Code, given a human-written theorem statement and a PDF proof sketch from Hartshorne, to semi-autonomously formalize Grothendieck’s vanishing theorem in Lean. The first fully compiling version is called state A. An expert Lean/mathlib review then identified substantial issues in definitions, theorem statements, API design, and file organization. Those review comments were converted into a checklist, and Claude plus Codex iterated until the checklist was addressed, producing state B.

The paper’s main contribution is the evaluation frame. It separates “kernel acceptance” from “library quality” and documents the difference with before/after expert review. One especially informative episode is the heartbeat debugging story. When typeclass search and proof checking became too expensive, the agent’s first move was to raise maxHeartbeats repeatedly. The durable fix was different: cache instances with inferInstanceAs, split large proofs into named lemmas, and restructure the development. That is a concrete example of the broader pattern: the agent follows locally executable fixes more readily than it recognizes structural design problems.18:T43a,The evidence is a project-level reconstruction rather than a benchmark table. The development is around 5,000 lines of Lean code and targets a graduate-level algebraic geometry theorem, not a short contest-style proof. State A already reaches zero sorries and follows the intended mathematical proof structure, which is a strong sign that current models can handle substantial local proof completion when the route is fixed. The weaknesses appear under expert review: poor definitions, insufficient theorem generality, awkward namespace and file structure, and APIs that are hard to build on.

After the review-driven refactor, state B is substantially better as a library artifact. The paper does not reduce this to a single scalar metric. Instead it presents process evidence: the sorry curve, commit history, token usage, loop modes, and the evolution of expert-review findings. That is exactly the point. If one only measures “does it compile?”, state A already looks successful. If one measures “is this a good mathlib contribution?”, state A and state B are far apart.19:T5e2,The central object is a blueprint: a dependency graph whose nodes are formal definitions and lemmas, and whose edges encode proof dependencies leading to the target theorem. The pipeline has three stages. First, blueprint generation: given the target theorem statement, optionally with a natural-language proof, the architect model emits a Lean file containing formally stated intermediate nodes and declared dependencies. Second, node proving: a tool-using Lean prover attempts to close open lemma nodes, using the declared dependencies and retrieval over Mathlib. These node-level proof attempts can run in parallel, which is important because the graph exposes independent subproblems. Third, global refinement: failed nodes are not handled only by deeper local decomposition. Instead, failure information is sent back to the architect, which can rewrite the blueprint globally by changing intermediate lemmas, adding or removing definitions, or restructuring dependencies.

This differs from recursive decomposition pipelines, where an early bad split can trap the system in an unproductive subtree. It also differs from Draft-Sketch-Prove style approaches. There, the informal proof becomes a flat sketch with placeholders. Here, the optional natural-language proof is converted into a graph of named sublemmas, which is easier to revise and recombine. In system terms, the paper separates high-level strategy formation from low-level proof discharge, and uses the graph as the interface between them.1a:T58e,The most notable result is the performance-cost tradeoff rather than a single benchmark number. The paper claims a new Pareto point for its compute class using the open-weight DeepSeek-V4-Flash backbone, with roughly $0.44 per problem, versus about $244 per problem for the next-best open pipeline reported in the comparison table. The introduction also positions the method against the broader landscape: open one-shot provers remain weak on Putnam-class problems, while systems above the 50% range typically depend on closed models, closed pipelines, or very high API spend.

The experiments to pay attention to are likely in three groups. First, benchmark results on MiniF2F, PutnamBench, and possibly newer Putnam-style sets, with separate comparisons against open one-shot provers, open agentic systems, and closed frontier pipelines. Second, ablations on the blueprint mechanism: whether global refinement helps over no refinement, whether graph-based planning beats recursive decomposition, and whether natural-language proof seeds improve difficult problems. Third, cost accounting: number of architect/prover calls, token usage, and retry overhead. For a systems paper like this, those details matter as much as pass rate.

The provided full-text excerpt does not include the complete result tables, so precise solve-rate numbers should not be inferred beyond what the paper explicitly states in the introduction.1b:T5b1,The method, Feedback Distillation, maintains a student and a teacher with the same architecture, both initialized from the same pretrained LM. For a problem x, the student first samples an attempted proof y. The teacher is then conditioned not only on x but also on textual feedback F(y), which is generated from the attempt and, in this setting, can incorporate verifier output. The feedback may come from a frozen copy of the same model or from a stronger external LLM. Training minimizes the per-token KL divergence between the teacher and student distributions along trajectories sampled from the student. Since gradients do not flow through the teacher distribution, this is equivalent in practice to token-level cross-entropy from the teacher to the student on the student's own rollouts. The teacher weights are updated by EMA every five gradient steps, using μ ← αμ + (1-α)θ, and the paper emphasizes that α is critical for stability. To reduce cost, the KL is approximated using only the teacher's top-K tokens, with K=25 in the reported experiments. Compared with GRPO, the method differs in three important ways. It does not rely on ranking multiple sampled trajectories by reward. It provides learning signal even when all sampled attempts fail. And it can be viewed as on-policy knowledge transfer: the model learns what it would do if it had access to richer feedback at generation time, then absorbs that behavior into its parameters.1c:T487,Experiments are conducted on Lean 4 theorem proving using LeanWorkbook. The main empirical result is twofold. First, Feedback Distillation alone maintains higher policy entropy than GRPO and shows better pass@k scaling, indicating a broader and more diverse proof distribution rather than collapse onto a small set of high-reward modes. Second, the method combines well with GRPO instead of replacing it. On the LeanWorkbook test split, Qwen3.5-9B reaches 59% pass@1 with GRPO alone, while Feedback Distillation followed by GRPO reaches 75% pass@1. That is a large gain, and it suggests the distillation stage is doing more than providing a mild warm start. It appears to improve exploration and local credit assignment before reward optimization takes over. The paper also studies different feedback sources and training stability. A notable practical point is that the EMA coefficient α strongly affects both performance and stability, so the method is promising but not yet a plug-and-play recipe. The diversity findings also align with recent critiques that GRPO often sharpens pre-existing successful modes rather than expanding the search distribution.1d:T812,DreamProver is built around an iterative wake-sleep cycle.

In the wake stage, the system attempts to prove training theorems using the current lemma library. Two mechanisms are central. The first is learnable theorem identification. Under a fixed budget of proof attempts and error-correction attempts, the LLM is prompted to prove a target theorem using the current library. If it succeeds within budget, the theorem is treated as learnable at the current knowledge level and may imply a more advanced reusable lemma built on top of existing ones. The second is intermediate theorem discovery. When a theorem is too hard to prove directly, the system recursively decomposes it into more tractable intermediate theorems. These intermediate theorems become the raw material for later lemma induction.

In the sleep stage, the system does not simply append all discovered lemmas to the library. Instead, it performs structured lemma evolution. Based on the method description, this includes clustering, pruning, abstraction, and validation: semantically similar candidate lemmas are grouped and deduplicated; each cluster is abstracted into a more general and reusable lemma; the resulting abstractions are formally validated; and the library is updated with a compact set of accepted lemmas. The design trade-off is important. If the system optimizes only for coverage, the library becomes a bag of local tricks. If it optimizes only for abstraction, it risks producing overly general or unverifiable lemmas. DreamProver tries to balance provability, compactness, and transferability.

At test time, the learned lemma library is used explicitly to prove unseen theorems. So the learned artifact is not just an updated model state, but an externalized, compressed set of formal skills. This distinguishes it from methods that repeatedly synthesize fresh intermediate lemmas online.

Relative to prior work, DreamProver is neither fixed-library retrieval nor per-problem lemma synthesis. Its novelty is the closed loop of discovery, abstraction, validation, and reuse.1e:T6ee,The experiments span multiple formal math domains, including inequality, number theory, combinatorics, plane geometry, and machine learning theory. The headline result reported by the authors is a 61% improvement in proving success rate when using the learned lemma library, along with a 50% reduction in proof length and a 48% reduction in token usage. This suggests the gains are not only about solving more problems, but also about finding shorter and cheaper proof trajectories.

From the available full-text content, the most informative experimental dimensions appear to be the following. First, cross-domain effectiveness: the method is evaluated on several mathematical domains rather than a single narrow benchmark, which supports the claim that the learned lemmas are transferable rather than purely local heuristics. Second, library-quality analysis: the paper emphasizes that the resulting library is compact, so the experiments likely include statistics on library size, reuse frequency, and the effect of clustering/abstraction. Third, compute efficiency: the reductions in proof length and token usage indicate that the learned lemmas improve search structure rather than merely benefiting from larger sampling budgets.
