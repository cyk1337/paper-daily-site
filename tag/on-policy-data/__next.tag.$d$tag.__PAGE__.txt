9:T5ce,The interaction pattern is locate-correct-continue. An annotator reads a model response and marks the first inappropriate token. onPanda shows the model's top-k candidate tokens and probabilities at that position, with k defaulting to 20. If a suitable replacement is available, the annotator selects it; otherwise, the annotator writes a free-form replacement. The system truncates all later text and continues generation from the corrected prefix. The process repeats until the response is acceptable.

This differs from standard post-editing because the annotator does not repair a completed response after the model has already drifted. The continuation is re-rolled from the corrected prefix, so most final tokens remain model-generated. Each correction also creates a local supervision record: the bad token, the replacement, the prefix, and the model's candidate distribution. These records can be converted into SFT data, DPO pairs, reward-model data, or process-level supervision. Implementation-wise, onPanda is a componentized front-end library. It can run as a static web app or be embedded in an existing annotation platform. It requires an inference API that can continue from an assistant-message prefix and return token logprobs. A full annotation session is serialized into a single .panda.json file. 1) Pair construction with controlled contrastiveness: for each prompt, sample K responses from the current policy (on-policy). Score each response with an external reward model R. Choose a high-reward completion as y_c. Instead of picking the minimum-reward completion as y_r, pick the response whose reward is closest to μ-2σ of the per-prompt reward distribution. This targets a “moderately bad” rejection, aiming for an informative but not trivial reward gap.

2) Multilingual data generation: start from an English instruction set, translate prompts into multiple target languages, then generate K candidates conditioned on each target-language prompt. Importantly, scoring is done within each language’s candidate set.

3) Reward model transfer: use a reward model trained on English preferences but built on a multilingual base encoder/LM, and rely on within-language ranking rather than absolute reward comparability across languages.

4) Training regimes: compare monolingual DPO (per-language tuning) vs multilingual DPO (joint training on the union of all language datasets). The paper also contrasts against SFT and prior multilingual preference-tuning baselines.
