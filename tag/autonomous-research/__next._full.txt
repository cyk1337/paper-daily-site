18:T974,核心做法是构建一个 agent-native 的研究环境 Athanor，而不是只给 agent 一个 shell 和若干脚本。系统把 post-training 研究拆成少数高频原子操作：提交训练作业（athanor job）、请求评测（athanor eval）、引入公开数据（athanor data）、保存/拉取/提交工件（athanor artifact）。agent 在自己的 sandbox 中写代码、读日志、分析结果，但真正的训练执行、评测、数据去污染、工件持久化由环境统一管理。这样做有两个直接好处：一是 agent 不必反复搭建训练基础设施，研究迭代速度更高；二是所有动作都被记录，便于追踪 lineage 和防止评测泄漏。

系统设计里有几个关键点。其一，研究状态外化。作者明确认为长周期研究不能依赖 agent 的上下文窗口，因此把 job history、evaluation results、notes、checkpoint lineage、workspace git commit、journal entry 等都持久化，agent 和队友可以读取这些记录继续工作。这相当于给 agent 提供了一个“外部研究记忆”。其二，评测隔离。开发集由冻结 evaluator 执行，最终 held-out suite 对 agent 完全不可见，只在 campaign 结束后由 operator 打分，避免 agent 通过反复 probing 过拟合最终测试。其三，数据入口控制。新数据只能通过 athanor data 引入，并经过 decontamination 后进入共享 data pool，减少训练数据污染评测的风险。其四，并行与异步执行。每个 researcher agent 占用一个 8-GPU node，在共享 GPU 池上并行发起训练和评测任务，允许多个假设同时推进，而不是串行试错。其五，团队协作。agent 可以读队友的 notes 和 results，也可以抓取队友 checkpoint 继续做增量实验，形成研究分工和 checkpoint lineage。

从研究范式上看，这篇工作强调的不是某个 RL 算法或某个数据合成技巧，而是“把研究流程编程化”。作者的设计判断是：如果没有受管控的执行层，agent 会把大量时间耗在调环境、查故障、重复造轮子上；而一旦把训练、评测、数据接入、artifact 管理做成稳定 API，agent 才能把能力真正用在假设生成、证据分析和实验决策上。这和很多只评估 agent 是否会写训练脚本的工作不同，后者往往忽略了真实研发里最耗时的部分正是执行与验证。19:T420,The paper is not mainly about finding a better post-training recipe. It asks a harder question: how to turn post-training research itself into a process that an agent can execute autonomously, over long horizons, on real GPUs, under clean evaluation constraints. The task is framed as AutoPostTrain: starting from a raw base model, public data, and a sealed held-out evaluation, with no external teacher models, can an agent run the full research loop by itself? That loop includes diagnosing weaknesses, importing and cleaning data, writing and modifying training code, changing objectives or algorithms, tuning hyperparameters, analyzing results, and deciding what to try next. The target is a single generalist checkpoint that improves multiple capabilities at once, not a collection of benchmark-specific specialists. The real difficulty is therefore not one training run, but long-running asynchronous experimentation, state persistence, evaluation isolation, decontamination, failure recovery, and evidence-based iteration under engineering friction.1a:T9cd,The central contribution is Athanor, an agent-native research environment rather than a loose collection of scripts. The system exposes a small set of high-frequency atomic operations for post-training research: launch a training job (athanor job), request evaluation (athanor eval), import public data (athanor data), and save/fetch/submit artifacts (athanor artifact). Agents work inside their own sandboxes, where they can write code, inspect logs, analyze checkpoints, and keep notes. But the actual execution layer is managed by the environment: training runs, evaluation, decontamination, artifact persistence, and record keeping are all handled centrally. This reduces repeated infrastructure work and makes the full research process auditable.

Several design choices are doing most of the work. First, research state is externalized. The paper explicitly treats long-horizon research as something that cannot live inside the agent context window. Job histories, evaluation results, notes, checkpoint lineage, git commits, and journal entries are persisted so that agents, or teammates, can resume from prior evidence. This is effectively an external research memory. Second, evaluation is isolated. Development evaluations are run by a frozen evaluator, while the final held-out suite is never exposed to the agents and is only scored after the campaign. This prevents direct overfitting to the final test. Third, data ingress is controlled. New datasets enter through a dedicated interface and are decontaminated before joining the shared pool, reducing leakage into evaluation. Fourth, the system supports asynchronous parallel execution. Each researcher agent has access to an 8-GPU node, and multiple training and evaluation jobs can overlap across shared nodes. Fifth, collaboration is built in. Agents can read teammates’ notes and results, fetch their checkpoints, and continue from existing lineages.

The deeper methodological point is that the paper treats research as a programmable process. The claim is not that agents lack ideas, but that without a managed execution substrate they waste time on setup, debugging, and rebuilding the same machinery. By turning training, evaluation, data ingestion, and artifact management into stable APIs, the system lets agents spend more of their capability on hypothesis generation, evidence interpretation, and experimental decision-making.
