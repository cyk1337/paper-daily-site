在 vLLM 上跑 DeepSeek V4 Flash 时，作者对比了官方 checkpoint 与 Canada-Quant 的量化/混合精度 checkpoint，发现后者在该拓扑的 batch=1 单流 decode 明显更快。作者给出的机制解释不是“目录更小”，而是“热路径上哪些张量以什么格式被访问、触发了哪些 vLLM kernel 路径”：Canada-Quant 采用混合布局（路由专家权重 W4 packed、注意力投影 FP8、部分敏感张量保留 BF16/FP32），在单流 decode 下减少了活跃专家权重带宽压力，并可能更容易走到更合适的 vLLM kernel。

MTP 部分的核心是修复 checkpoint/运行时契约不一致：Canada-Quant 的 MTP block 里存在 BF16 未量化张量（如 mtp.0.*），而 vLLM 的 DeepSeek V4 NVIDIA O-projection 路径假设该投影有 FP8 scale 元数据（适用于全 FP8 路径）。结果是主模型能 load，但 MTP draft 启动失败。作者讨论两条路：
1）工件侧：把 MTP 张量也量化进 compressed-tensors 格式（更“干净”，但需要额外量化流程与可能的校准数据）；
2）运行时侧：在 vLLM 增加 BF16 fallback——检测 wo_a 是否存在 FP8 scale；有则走 FP8 kernel，无则用 BF16 做 inverse RoPE、reshape grouped 权重、grouped matmul，再接 wo_b。

The practical implication is simple: for batch=1 decode, you want the hot path to stream weights from local HBM and avoid designs that induce frequent cross-GPU transfers.

On top of that, the author benchmarks DeepSeek V4 Flash in vLLM using two artifacts: the official checkpoint and a Canada-Quant mixed-format checkpoint. The key observation is that the quantized artifact is much faster on this topology even though it is not smaller on disk. The proposed mechanism is “hot-path tensor traffic and kernel selection,” not directory size: Canada-Quant uses W4-packed routed expert weights, FP8 attention projections, and keeps some sensitive tensors in BF16/FP32. That can reduce active expert-weight bandwidth and steer vLLM into more favorable kernel paths for single-stream decode.

For MTP, the core issue is a checkpoint/runtime mismatch. The Canada-Quant artifact leaves MTP block tensors (e.g., mtp.0.*) in BF16/unquantized form, while vLLM’s DeepSeek V4 NVIDIA O-projection path expects FP8 scale metadata for wo_a (valid for a fully-FP8 pipeline). Result: the main model loads, but MTP draft initialization/execution fails.

Two fixes are discussed:
- Artifact-side: quantize MTP tensors into the same compressed-tensors format (cleaner, but requires an actual quantization pass and possibly calibration data).
- Runtime-side: add a BF16 fallback in vLLM’s O-proj op—check if wo_a has FP8 scale metadata; if yes, use the FP8 path; if not, run inverse RoPE in BF16, reshape grouped weights, do grouped matmul, then continue through wo_b.

The author also highlights three adjacent “contract” issues that must all be correct for stock end-to-end MTP: artifact metadata must match vLLM runtime module names (not just safetensors names); vLLM must propagate prefix= when constructing MTP e_proj/h_proj so compressed-tensors can match layer names; and the O-proj execution path needs the BF16 fallback for unquantized wo_a.
