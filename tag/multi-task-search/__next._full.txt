17:T903,方法上，作者把优化对象统一表示为字符串 artifact，系统输入包括 seed artifact 或自然语言目标、一个 evaluator、可选数据集，以及可选 side information。evaluator 返回标量分数和一个 SI 字典；SI 可以是文本、结构化指标、报错、profile、图像等。系统的 proposer LLM 读取当前候选、历史轨迹和 SI，生成改进候选。关键不在“让模型写文本”，而在候选选择与搜索组织。

核心搜索机制继承并扩展了 GEPA 一类的 Pareto-based search。作者不是只按单一 aggregate score 排序，而是按 per-example 或 per-metric 的 Pareto dominance 保留候选。这样做的原因很直接：不同候选往往在不同子样本、不同指标上各有优势，如果过早压成单一平均分，搜索会丢掉互补结构，后续反思也会失去素材。这个设计原先主要用于 prompt optimization，这里被推广到任意文本 artifact。

论文统一了三种模式。第一是 single-task：对单个问题迭代搜索。第二是 multi-task：把一批相关问题放在一起搜索，让候选在任务间迁移模式，例如 CUDA kernel 优化中，不同 kernel 的局部技巧可以互相借用。第三是 generalization：在训练集样本上优化 artifact，但目标是对未见输入也有效，这一点从 prompt 扩展到了 agent architecture 和 scheduling policy。

另一个技术重点是 side information 的一等公民化。以往很多系统也会把报错或日志塞进 prompt，但通常是 ad hoc 的。这里作者把 SI 变成统一 API 契约，使 proposer 可以系统地消费 stack trace、性能 profile、图像渲染结果、子指标等反馈。论文的消融表明，这不是锦上添花，而是决定收敛速度和最终质量的关键变量。

从系统设计看，这套方法更接近“LLM-guided black-box search with structured feedback”，而不是梯度学习。它依赖 evaluator 的可执行性和反馈质量，也依赖 proposer 对反馈的解释能力。与 AlphaEvolve 这类偏代码进化系统相比，它的区别在于 artifact 类型更广、支持多任务和泛化模式、并把诊断反馈接口标准化；与 GEPA 相比，区别在于不再局限 prompt，并补上单任务和多任务搜索。18:T7ed,实验覆盖六个主域，目的是证明统一性而不是只打一个点。文中给出的代表性结果包括：

1. Agent architecture / ARC-AGI：演化出的 agent 架构把 Gemini Flash 的 ARC-AGI 准确率从 32.5% 提到 89.5%。这个数字很显眼，但阅读时要注意它衡量的是“在给定模型和 evaluator 下搜索出的 agent scaffold”，不是模型本体能力提升。

2. Cloud scheduling：搜索得到的调度算法可将云成本降低最多 40%。这里更值得看 evaluator 和 side information 如何定义，因为这决定了 LLM 能否稳定改写策略代码。

3. CUDA kernels / KernelBench：生成的 kernel 中，87% 能达到或超过 PyTorch baseline。更关键的是 multi-task mode 在等价 per-problem budget 下优于独立 single-task 优化，说明跨任务迁移不是口号，而是能在相近 kernel 家族中带来真实收益。

4. Prompt optimization：把 GPT-4.1-mini 在 AIME-2025 上的准确率从 46.67% 提到 60.00%。这部分更多是验证系统能覆盖 GEPA 类场景，而不是新结果本身。

5. Circle packing：优于 AlphaEvolve 公布的 n=26 解，并且作者做了 matched-condition rerun against OpenEvolve，试图排除预算和实现差异带来的干扰。

6. 数值优化 / solver code：文中声称定制 solver code 可匹配并超过 Optuna；摘要截断后细节不全，但从定位看，重点是证明 artifact 不必是 prompt 或通用代码，也可以是面向数值搜索的程序化策略。

消融方面，最重要的是 side information 和 multi-task 两组。作者在 prompt optimization、circle packing、CUDA kernels 三个域上报告：有 actionable SI 时，收敛速度提升约 4–6 倍，最终性能也明显更高；只给 score 的版本会慢很多，也更容易停在局部模式。multi-task 的收益则随相关任务数量增加而扩大，这支持“共享搜索记忆”这一设定。论文还强调 Pareto 选择优于简单 aggregate 排序，因为它能保留互补候选。19:T9e7,The method represents every candidate solution as a string artifact. The user provides a seed artifact or a natural-language objective, an evaluator, an optional dataset, and optional side information. The evaluator returns a scalar score and an SI dictionary. SI may contain free-form text, structured metrics, stack traces, profiler outputs, rendered images, or other diagnostics. A proposer LLM then reads the current candidate, search history, and SI, and proposes revisions.

The key algorithmic choice is candidate selection. Instead of ranking candidates only by a single aggregate score, the system extends Pareto-based search from prior prompt-optimization work to arbitrary text artifacts. Candidates are retained based on per-example or per-metric Pareto dominance. The motivation is practical: different candidates are often strong on different subsets of examples or metrics, and collapsing them too early into one average score destroys complementary structure that could be exploited in later iterations.

The framework supports three modes under one API. Single-task mode iteratively improves one artifact for one problem. Multi-task mode jointly searches over a batch of related problems, allowing useful patterns discovered in one task to transfer to others; CUDA kernels are the main example. Generalization mode optimizes an artifact on a dataset with the goal of performing well on unseen inputs; the paper extends this beyond prompts to agent architectures and scheduling policies.

A second major design choice is making side information a first-class contract rather than an ad hoc prompt addition. Many earlier systems can pass logs or errors to the model, but here SI is standardized at the API level. This lets the proposer systematically consume stack traces, performance profiles, rendered outputs, and sub-metrics. The ablations suggest that this is not cosmetic: actionable diagnostics materially change both convergence speed and final quality.

Conceptually, the system is closer to LLM-guided black-box search with structured feedback than to gradient-based learning. It depends on evaluator quality, on the informativeness of side information, and on the proposer’s ability to interpret that feedback. Relative to AlphaEvolve-style code evolution, the main differences are broader artifact coverage, support for multi-task and generalization modes, and a standardized diagnostic interface. Relative to GEPA, the main step is generalizing beyond prompts and adding single-task and multi-task search.1a:T7b6,The evaluation spans six primary domains to demonstrate breadth rather than depth on one benchmark. The headline results reported in the paper include:

1. Agent architectures for ARC-AGI: evolved scaffolds raise Gemini Flash accuracy from 32.5% to 89.5%. This is a search-over-scaffolds result, not a claim about intrinsic model capability.

2. Cloud scheduling: discovered scheduling algorithms reduce cloud costs by up to 40%. The interesting part here is how the evaluator and diagnostics are defined so that policy code can be improved reliably.

3. CUDA kernels on KernelBench: 87% of generated kernels match or beat PyTorch baselines. More importantly, multi-task search outperforms independent single-task optimization under matched per-problem budget, which is the strongest evidence that cross-task transfer is real rather than rhetorical.

4. Prompt optimization: GPT-4.1-mini on AIME-2025 improves from 46.67% to 60.00%. This mainly shows that the framework subsumes GEPA-like settings.

5. Circle packing: the system beats AlphaEvolve’s published n=26 solution, and the authors also rerun against OpenEvolve under controlled conditions to reduce confounding from budget or implementation differences.

6. Numerical optimization / solver code: the paper claims custom solver code can match or outperform Optuna. The exact details are less visible in the provided excerpt, but the point is to show that the artifact need not be a prompt or generic code snippet.

The most informative ablations concern side information and multi-task search. Across prompt optimization, circle packing, and CUDA kernels, actionable SI yields roughly 4–6x faster convergence and substantially better final performance than score-only feedback. Multi-task gains grow with the number of related tasks, supporting the idea of shared search memory. The paper also argues that Pareto selection is preferable to simple aggregate ranking because it preserves complementary candidates.1b:T595,This is a skim paper. Do not spend most of your time on every task-specific result table. Focus on three parts.

First, read the introduction and API section carefully. The important question is not the syntax of the interface, but how the paper factors the problem into artifact, evaluator, dataset, and side information. That abstraction determines whether the framework can transfer to your own optimization setting.

Second, read the search method section, especially Pareto candidate selection and the unification of single-task, multi-task, and generalization modes. The key questions are why Pareto retention helps open-ended search, why multi-task search can beat isolated optimization on related tasks, and what assumptions are required for that to happen.

Third, prioritize the ablations over the headline numbers. The side-information ablation and the multi-task scaling plots are the most revealing parts of the paper. They explain why the system works. If you only read the ARC-AGI or CUDA headline numbers, you may misread the contribution as a domain-specific trick.

A good reading order is: Introduction → API/method → side-information ablation → multi-task results → one domain case study you understand well.
