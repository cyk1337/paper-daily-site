a:T6bd,The design is organized around five principles. First, reuse existing Python abstractions. In NOOA, a class defines the agent, fields hold explicit model-visible state, methods define capabilities, type annotations specify contracts, exceptions handle failures, and asyncio handles concurrency. Second, treat agentic loops as ordinary method calls. If a method has a normal body, it runs as deterministic Python; if the body is just an ellipsis (...), the runtime interprets it as an LLM-driven agentic method. That means the application sees a typed function call rather than an unstructured text exchange.

Third, deterministic work should be moved out of the agent loop. Parsing, arithmetic, state transitions, and rule-based logic should live in ordinary methods that the model can call. Fourth, leverage the model's existing Python knowledge. Instead of constraining the model to a narrow tool-calling DSL, NOOA allows CodeAct-style methods to write and execute ordinary Python using loops, conditionals, imports, libraries, async code, and external clients. Fifth, expose the harness through explicit APIs. Context construction, event history, and state rendering are not hidden framework internals; they are surfaced as Pythonic interfaces available to both developers and the model.

The central idea is to collapse several layers of agent specification into one class definition: source code, prompt surface, tool interface, state boundary, and type contract. The paper also emphasizes that inputs need not be serialized into text only; live Python objects and even images can be passed by reference, with the harness rendering bounded previews for the model while preserving executable object access for code paths.b:T41f,The empirical section is mostly capability validation rather than training-oriented measurement. The paper evaluates whether current models can operate effectively through this native Python interface on SWE-bench Verified, Terminal-Bench 2.0, and ARC-AGI-3. The provided text does not include the full result tables, so it would be unsafe to invent exact numbers. What is clear is that the authors are trying to show that the interface is usable on nontrivial agent tasks, not just toy examples.

There is also a framework comparison section covering fourteen other agent frameworks or harnesses against six interface capabilities. That comparison is meant to position NOOA as a more unified programming model, especially around typed contracts, state, prompt surface, and runtime extensibility. It is more of a design-space comparison than a strict benchmark.
