18:T6ef,DPara 的关键做法是把 DSpark-style drafter 拆成“重的 diffusion backbone”和“轻的 autoregressive head”。在 target model 正在 verify 当前 draft 时，DPara 不去猜最终 accepted prefix 和 bonus token，而是让 diffusion backbone 为所有可能的 acceptance boundary 预先计算 draft representations，并且暂时不绑定 bonus token。等 verification 结果返回后，真实的 accepted boundary 和 bonus token 已经确定，再由轻量 AR head 把这些信息接进去生成下一轮可用 draft。这样，概率性错误不再导致 backbone fallback；只要 backbone 能在 target verification window 内跑完，backbone 延迟就被完全隐藏，关键路径上只剩 AR head。

标准 DFlash 并不能直接满足这个使用方式，因为它通常依赖单个带有上下文 feature 的 anchor，而 DPara 需要同时覆盖多个 acceptance boundary，并从 feature-less anchors 预测。论文因此提出 M-DFlash：从公开 DSpark checkpoint 初始化，只 finetune diffusion backbone，让它适配 multiple-anchor、feature-less 的输入 regime；AR head 保持冻结，不引入新的可训练参数。这一点很重要，因为它说明 DPara 不是重新训练一个完整 drafter，而是用较小代价把已有 DSpark-style drafter 改造成适合并行排程的版本。

与 SSD/PEARL 这类方法相比，DPara 的差别不在于“更会猜 outcome”，而是不再把 overlap 建立在猜测 outcome 上。与普通 DSpark 相比，DPara 保留了 parallel drafter 的 acceptance 能力，同时把最重的 backbone 从串行 draft-verify 路径里拿掉。代价是需要为多个 boundary 准备 backbone 输出，并要求额外 drafting 设备或足够的同机资源来保证 overlap window。19:T68a,DPara exploits the internal structure of a DSpark-style drafter: a heavy diffusion backbone followed by a lightweight autoregressive head. While the target model verifies the current speculative block, DPara runs the diffusion backbone ahead of time for every possible acceptance boundary and leaves the bonus token unspecified. Once verification completes, the true accepted boundary and bonus token are known; the lightweight AR head then conditions on that outcome and produces the next draft tokens. As long as the backbone finishes within the target verification window, the dominant part of drafting latency is hidden, and only the AR head remains on the critical path.

A standard DFlash backbone is not directly suitable for this schedule. In the serial setting, it anchors prediction on a single token after a fully featured prefix. DPara needs predictions from multiple feature-less anchors, one for each possible acceptance boundary. The paper introduces M-DFlash by initializing from a published DSpark checkpoint and finetuning only the diffusion backbone for this multiple-anchor, feature-less regime. The AR head is kept frozen, and no new trainable parameters are added.

The key difference from SSD or PEARL is that DPara does not try to make a better guess about the accepted prefix or bonus token. It removes the need for that guess. The key difference from serial DSpark is that DPara keeps the strong parallel drafter but moves the expensive backbone computation out of the serial draft-verify path. The cost is extra boundary coverage work and a requirement that drafting resources be provisioned well enough to complete inside the verification window.1a:T4d5,The evaluation uses Qwen3-8B and Qwen3-14B on math, coding, and chat benchmarks. DPara outperforms the baselines on every model-dataset pair. Average speedups over autoregressive decoding are 3.21× for Qwen3-8B and 3.52× for Qwen3-14B, with a maximum reported speedup of 4.53×. Compared with DSpark, the strongest serial drafter, average gains are 11.1% and 5.1%. On Qwen3-14B, DPara improves average speedup over PEARL and SSD by 31% and 64%, respectively.

The batching results are central. DPara remains ahead of DSpark from batch size 1 to 16 and keeps more than 2× AR throughput at batch size 16. Outcome-dependent methods such as SSD degrade more sharply as batch size increases because a mismatch in any request can push the batch back to serial execution.

The resource studies are also informative. DPara-A10 preserves 98% of DPara's speedup while reducing drafting-device cost by about 90%. DPara-single preserves roughly 90%–95% of the speedup at small batch sizes. An ablation shows that finetuning only the diffusion backbone increases average acceptance length by 30.7%, which supports the claim that the multiple-anchor feature-less regime needs adaptation rather than a direct reuse of the original DFlash backbone.1b:T47e,Read the introduction and Figures 1–2 first. They clarify the difference between serial speculative decoding, SSD-style parallel speculative decoding, and DPara's outcome-independent overlap. The main point is the critical path, not the acceptance-rejection math.

The DPara design section deserves close reading. Focus on why bonus-token conditioning is deferred to the AR head, and why the system covers all acceptance boundaries instead of predicting a single likely boundary. The M-DFlash section is the other technical core: the distribution shift from standard DFlash to multiple feature-less anchors explains why finetuning the backbone is necessary.

For experiments, prioritize Section 4.2 for speedups and batch scaling, then Section 4.3 for heterogeneous drafting and single-GPU colocation. Appendix A and Appendix B are worth checking because they quantify the 24%–32% draft latency share and the high SSD fallback rate at batch size 16. Good follow-up questions are compute redundancy across boundaries, memory pressure, overlap conditions for different target/drafter size ratios, and interaction with production serving schedulers.1c:T4ba,TreeSpark builds on DSpark. A small bidirectional backbone runs once over a block of masked positions and emits hidden states and base logits U_d for each draft depth. DSpark also has a low-rank Markov head B(x,v)=<W1[x],W2[v]> that adds a transition bias from parent token x to candidate token v. TreeSpark uses this existing Markov head to construct parent-conditioned child distributions for every concrete tree node. Evaluating another parent requires only an embedding lookup and a rank-r matrix-vector product, not another backbone pass. Raw proposal probability q0 is then calibrated with target-verification labels using a two-parameter map p_hat = sigmoid(a logit(q0)+b), fitted only on edges whose ancestors were accepted. Nodes are prioritized by the product of calibrated edge probabilities along the path, and expansion stops when the best remaining path survival score falls below a threshold theta. The runtime selects theta from a load-dependent ladder. For nonzero-temperature decoding, TreeSpark samples siblings without replacement from the residual q_T and reconstructs the proposal during recursive rejection sampling. This avoids the bias introduced by deterministic top-k tree expansion.1d:T57b,Experiments use Claude Code with Claude Sonnet and Codex with GPT-5 on real repositories such as textual, jinja2, werkzeug, rich, httpx, and tox. On correctness, the authors first identify a representation bug. LMCache’s handling of packed-page attention blocks recognized rank-5 attention tensors but missed the rank-4 packed representation used in the evaluated deployment. That caused an incorrect byte view during transfer. They adopt an existing upstream packed-subpage patch to repair this representation issue. In the reported 27B setup, a 1,568-token logical block spans 49 pages of 32 tokens. This fixes the question of which bytes should be transferred.

However, after the representation fix, cross-replica reuse still produced wrong outputs. The authors then isolate a second issue: the evaluated image lacks the LMCache CUDA-ops extension and falls back to a PyTorch path. In that path, the raw-pointer lmcache_memcpy_async branch uses cudaMemcpy with cudaMemcpyDefault but without dependence on the current CUDA stream. Because the stream pool uses cudaStreamNonBlocking, the copy does not inherit the producer-consumer ordering of the preceding gather/scatter work. As a result, host or device consumers can observe stale data or overwritten data.

The paper validates this with controlled byte-level probes. In a device-to-host test, a delayed GPU write of byte value 37 is scheduled before the fallback copy, yet host memory still receives the old value 0. In a host-to-device test, a GPU read of old value 0 is scheduled before the fallback overwrites the host buffer with 53, and the consumer ends up reading 53. In both cases, all 1,048,576 bytes in a 1 MiB object mismatch. That rules out floating-point noise or sampling variance and pins the problem on ordering.

The authors then run a stronger control suite: fixed pinned host and GPU buffers, only the ordering mechanism varies, object sizes of 4 KiB, 1 MiB, and 16 MiB, both transfer directions, with and without 10^8 CUDA sleep cycles. The raw fallback fails all 120 delayed checks and passes all 120 undelayed checks. Three alternatives that restore ordering—waiting for prior stream work, using cudaMemcpyAsync on the current stream, and same-stream tensor copy—pass all 720 checks. This is a clean isolation of the mechanism.

They also connect the diagnosis back to deployment behavior. In helper-level probes, the lazy allocator path fails, while the mixed allocator path passes on both GPUs. The practical workaround is therefore to force the mixed allocator path with --no-l1-use-lazy, bypassing the raw-pointer fallback.

A final systems issue concerns large pinned-memory allocation. The first 256 GiB service allocation falls back to pageable memory. The authors trace this to PyTorch host allocator power-of-two rounding, which may inflate a 256 GiB + 4096 B request to 512 GiB. Setting PYTORCH_CUDA_ALLOC_CONF=pinned_max_round_threshold_mb:128 constrains large-allocation rounding and restores full-pool pinned allocation checks.
