a:T471,ClosureBench is built around “logic primitives + executable semantics + controlled instance generation.”
- Task space: 26 categories derived from explicit graph-relational primitives such as reachability/transitive closure, degree, set operations, connectivity (e.g., SCC-related queries), and aggregation over reachable sets.
- Exact labels: each query is implemented as a short program whose execution yields the reference answer. The paper mentions implementations in Ein (tensor-contraction style graph ops) and an equivalent Python/NetworkX version.
- Constructive generator: instances are produced on demand with separate structural and surface seeds, allowing independent control of graph structure and linguistic realization.
- Difficulty control: three orthogonal axes—number of nodes, edge density, and query depth/compositional level—so evaluators can hold two fixed and sweep the third to localize failure modes.

The first is lifecycle decomposition. The authors organize harness risk into six operational phases: Harness Configuration, Capability Extension, Runtime Operation, State Persistence, Action Control, and Incident Recovery. This is useful because it re-groups agent failures by harness responsibility. Configuration covers connectors, credentials, gateways, and policy templates; capability extension covers plugin selection, installation, updates, and permissions; runtime operation covers adversarial content in emails, webpages, documents, and tool outputs; state persistence covers whether transient malicious content gets written into durable memory or policy state; action control covers high-impact actions such as payments, deployments, deletions, OAuth grants, and outbound communication; incident recovery covers rollback, credential rotation, state repair, and evidence preservation. The second idea is the benchmark protocol itself. HarnessRisk contains 128 sandboxed cases spanning those six phases. Each case combines a benign user goal with an adversarial instruction embedded in an untrusted workflow artifact. The agent operates through a three-turn owner workflow with case-specific files, tools, persistent state, and mock services. Every run starts from a fresh environment and real network access is disabled. Evaluation is split into Utility, Attack Success Rate, Persistence, and Detection. That separation is important because it allows the benchmark to show that successful task completion and safe execution are not the same thing. Second, the stack is highly heterogeneous: a single application may combine GPU-bound LLMs, memory-bound vector databases, CPU-bound sandboxes, and network-bound external services.
