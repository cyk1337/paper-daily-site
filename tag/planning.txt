The paper defines a mobile planner as the high-level decision core of an on-device assistant: it interprets user intent, retrieves long-term memory, invokes structured business APIs, loads reusable composite skills, and delegates specialized subtasks to GUI sub-agents when direct tool use is insufficient. Around this setup, the benchmark is organized into four capability dimensions. Basic Tool Use covers utility calls, multimodal input handling, strict execution order, permission boundaries, and OS feedback. Sub-agent Collaboration measures whether the planner can decompose tasks and hand them off to downstream specialists with valid context transfer. Memory Usage tests whether the agent can retrieve persistent user context—preferences, credentials, prior state—to resolve underspecified requests before planning. Skill Usage evaluates whether the planner can invoke packaged multi-step skills instead of replanning every primitive action, reducing long-horizon error accumulation.

Operationally, MobilePA-Bench runs in an executable sandbox with live application databases and structured feedback. The key design choice is to decouple central planning from low-level visual parsing. In other words, the benchmark is intentionally not centered on pixel understanding; it is centered on deciding when to call an API, when to query memory, when to invoke a composite skill, and when to fall back to a GUI sub-agent. This keeps the evaluation focused on planner quality rather than visual noise, while still preserving realistic friction such as call dependencies, permission blocks, and dynamic state mutations.

The benchmark itself contains 1,705 real-world tasks across 13 domains and 212 tools. If you want to reuse ideas for agent training environments or RL-style evaluation loops, revisit the task schema and feedback interface more carefully.1b:T698,DART-SD has three main components. First, it builds an Interaction-State Transition Graph from teacher rollouts. Nodes are not single actions; they are cumulative interaction states, defined by the task-relevant information acquired so far. To make this possible, the method introduces information atom abstraction: tool outputs are canonicalized, semantically equivalent responses are mapped to the same atom, and non-informative outputs such as status-only or empty responses are collapsed away. This lets trajectories with different action orders but the same acquired information land on the same node, which naturally captures the diamond topology induced by order-independent sub-goals. Second, for a failed student rollout, the method performs success-reachable projection and identifies the Critical Topological Breakpoint. Instead of cutting by timestep, it asks whether each cumulative student state still lies in the region from which success is reachable in the empirical graph. The CTB is the point where the rollout leaves that success-supported region. Third, starting from a recovery anchor near the CTB, the method retrieves a success-supported continuation from the ISTG and applies localized supervision only to the recovery segment, while preserving the valid prefix. Training is progressive self-distillation: the student rolls out, exposes its current capability boundary, receives CTB-guided local correction, and gradually extends the length of valid interaction prefixes. Compared with vanilla SFT, supervision is localized. Compared with RL, the method does not rely on sparse reward propagation; it uses explicit graph structure extracted from teacher behavior.1c:T47e,The study evaluates on five benchmarks and two model scales. The main empirical claim is consistent improvement over supervised and RL baselines, along with fewer redundant tool calls and longer valid interaction prefixes. The pipeline has three stages. First, blueprint generation: given the target theorem statement, optionally with a natural-language proof, the architect model emits a Lean file containing formally stated intermediate nodes and declared dependencies.
