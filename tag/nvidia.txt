19:T6bd,The design is organized around five principles. First, reuse existing Python abstractions. In NOOA, a class defines the agent, fields hold explicit model-visible state, methods define capabilities, type annotations specify contracts, exceptions handle failures, and asyncio handles concurrency. Second, treat agentic loops as ordinary method calls. If a method has a normal body, it runs as deterministic Python; if the body is just an ellipsis (...), the runtime interprets it as an LLM-driven agentic method. That means the application sees a typed function call rather than an unstructured text exchange.

Third, deterministic work should be moved out of the agent loop. Parsing, arithmetic, state transitions, and rule-based logic should live in ordinary methods that the model can call. Fourth, leverage the model's existing Python knowledge. Instead of constraining the model to a narrow tool-calling DSL, NOOA allows CodeAct-style methods to write and execute ordinary Python using loops, conditionals, imports, libraries, async code, and external clients. Fifth, expose the harness through explicit APIs. Context construction, event history, and state rendering are not hidden framework internals; they are surfaced as Pythonic interfaces available to both developers and the model.

The central idea is to collapse several layers of agent specification into one class definition: source code, prompt surface, tool interface, state boundary, and type contract. The paper also emphasizes that inputs need not be serialized into text only; live Python objects and even images can be passed by reference, with the harness rendering bounded previews for the model while preserving executable object access for code paths.1a:T41f,The empirical section is mostly capability validation rather than training-oriented measurement. The paper evaluates whether current models can operate effectively through this native Python interface on SWE-bench Verified, Terminal-Bench 2.0, and ARC-AGI-3. The provided text does not include the full result tables, so it would be unsafe to invent exact numbers. What is clear is that the authors are trying to show that the interface is usable on nontrivial agent tasks, not just toy examples.

There is also a framework comparison section covering fourteen other agent frameworks or harnesses against six interface capabilities. That comparison is meant to position NOOA as a more unified programming model, especially around typed contracts, state, prompt surface, and runtime extensibility. It is more of a design-space comparison than a strict benchmark.

So the right reading of the experiments is modest: they support feasibility and usability of the interface, but they do not establish a strong performance advantage over other agent paradigms.1b:T4c5,The method has two stages: structural compression followed by capability recovery. The structural stage uses Iterative Puzzle, a sequential version of the Puzzle framework. Instead of compressing the model in one large step, it alternates hardware-aware structural compression with short knowledge-distillation recovery phases. This allows each compression step to account for representation drift and inter-layer dependencies introduced by earlier steps. The compressed dimensions include heterogeneous channel pruning of routed MoE experts, heterogeneous reduction of active experts, and pruning of the SSM state size in Mamba layers. The main design choice is non-uniform capacity allocation across depth: sensitive regions keep more capacity, while more redundant regions are compressed harder. The recovery stage combines medium- and long-context knowledge distillation, RL post-training for software-engineering and agentic reasoning tasks, mixed FP8/NVFP4 inference, and a Multi-Token Prediction head for speculative decoding. The novelty is in optimizing these components under explicit serving constraints rather than treating pruning, distillation, quantization, and decoding acceleration as independent tricks.1c:T481,The paper reports two central deployment results. In interactive serving on a single 8×B200 node, Puzzle-75B-A9B reaches roughly 2× the server throughput of Nemotron-3-Super at matched user-throughput constraints, with the target operating point set at at least 100 tokens per second per user. The evaluation covers both a prefill-heavy 50K/2K input/output regime and a decode-heavy 8K/64K regime. In ultra-long-context deployment on a single H100 GPU, the compressed model raises 1M-token concurrency from 1 request to 8 requests by reducing parameter memory, KV-cache pressure, and Mamba-state footprint. The model size changes from 120.7B total / 12.8B active to 75.3B total / 9.3B active.
