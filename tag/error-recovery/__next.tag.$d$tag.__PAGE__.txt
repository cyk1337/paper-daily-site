第一部分是 GUI-RobustEval。作者把 GUI agent 任务建模为 POMDP：任务指令和动作是语言空间，观测是 screenshot，状态和转移由 GUI 环境决定，策略由 VLM 实现。与普通成功率评测不同，这个 benchmark 不是从初始状态让 agent 从头做任务，而是先给定一段带错误的前缀轨迹，再把环境和 agent 重置到某个“错误深度”对应的状态，让模型从这个已经被带偏的中间状态接管任务。这里有两个关键定义：error type 是根因动作的类别；error horizon / error depth 则描述从根因动作发生到错误变得可识别，需要经过多少步。这个设计比简单注入随机噪声更贴近真实 agent failure，因为很多错误不是立刻显现，而是几步之后才暴露。

GUI-RobustEval 共包含 1216 个可执行测试用例，覆盖 11 类代表性错误和 4 个可控错误深度。指标也不是单一 success rate，而是拆成 Error-Awareness Rate 和 Post-Error Success Rate。前者测模型能否意识到当前状态已经不对，后者测它在意识到或未意识到的情况下，最终能否恢复并完成任务。这样的拆分很有意义，因为有些模型会“知道错了但不会救”，另一些则是“根本不知道已经走偏”。

第二部分是 RoTS，Robustness-driven Trajectory Synthesis。作者观察到现有训练数据有两个错配：error-coverage mismatch 和 error-horizon mismatch。前者指训练数据里的错误类型偏低级、偏人工常见，而真实 agent failure 更高层、更组合式；后者指训练样本多是短程错误，而真实恢复常常需要长程回溯。RoTS 用树状在线合成来同时补这两个缺口。

具体做法是：在 GUI 环境中迭代生长 trajectory tree。对成功分支，从脆弱状态继续分叉，主动探索新的失败模式，同时复用已有正确前缀，提升错误覆盖；对失败分支，则从错误状态回放并合成恢复 rollout，生成长程 failure-recovery 轨迹，提升恢复 horizon。这个设计比离线改写演示数据更自然，因为错误是由策略与环境交互真实诱发的，不是人工编造的局部反思句子。最终作者构建了 800k 规模的数据集，并在 Qwen2.5-VL 基座上训练 RoTS-7B 和 RoTS-32B。6:T978,The work has two main parts: a benchmark and a data synthesis pipeline.

The benchmark, GUI-RobustEval, models GUI interaction as a POMDP where instructions and actions are in language space, observations are screenshots, environment state and transitions come from the GUI, and the policy is a VLM. Unlike standard task-success evaluation, the benchmark does not always start from a clean initial state. Instead, each test case provides an erroneous prefix trajectory, then resets the environment and the agent to a targeted state at a chosen error depth, and asks the model to take over from there. Two definitions matter here. Error type is the category of the root-cause action. Error horizon or depth measures how many steps after the root cause are needed before the error becomes identifiable. This is more realistic than injecting random perturbations, because many GUI failures only become visible several steps later.

GUI-RobustEval contains 1,216 executable test cases spanning 11 representative error types and 4 controllable error depths. The evaluation uses two metrics: Error-Awareness Rate and Post-Error Success Rate. This split is important. Some agents can notice that something is wrong but still fail to recover; others do not even realize they are off track.

The second part is RoTS, Robustness-driven Trajectory Synthesis. The authors identify two mismatches in existing training data. Error-coverage mismatch means training sets overrepresent low-level or human-typical errors, while real agent failures are often higher-level and compositional. Error-horizon mismatch means training examples are usually short-horizon, while real recovery often requires long-horizon backtracking. RoTS addresses both with a tree-based online synthesis process.

The trajectory tree grows inside the GUI environment. On successful branches, the system branches out from fragile states to proactively discover new failure modes while reusing the correct prefix, improving error coverage. On failed branches, it replays from the error state and synthesizes recovery rollouts, producing long-horizon failure-recovery trajectories. This is more realistic than offline reflection rewriting because the failures are induced by actual policy-environment interaction rather than manually fabricated local corrections. First, asynchronous checking. Instead of forcing generation and checking to proceed in lockstep at token granularity, Hydra lets the checker validate code fragments at a more natural semantic granularity, such as complete statements or declarations. This matters because semantic checking is not naturally token-local. Token-level checking wastes work on the vast majority of tokens that are not problematic. By decoupling the checker from the generation loop, Hydra removes checker overhead from the critical path when the generated prefix is valid.

Second, checkpoint-and-rollback. Whenever the checker validates a prefix fragment, Hydra creates a checkpoint containing both the accepted prefix and the checker’s internal state. Saving checker state is the crucial part: rollback can then reuse prior parsing and semantic analysis instead of rechecking the same prefix from scratch. The paper emphasizes that production compilers are not built for this. Their state is often implicit, stack-resident, and oriented toward whole-program compilation. Hydra introduces an incremental-checking abstraction that can be retrofitted onto existing compilers. For Clang, the implementation reportedly requires about 500 modified lines plus a 1400-line shim, which is modest relative to a 1.2M-line frontend.

Third, policy-driven repair. Because checking is asynchronous, an error may be reported after generation has already advanced far beyond the actual fault. Hydra therefore manages a search tree over partially validated continuations rather than a single linear trajectory. A policy module decides which checkpoint to roll back to and where to spend regeneration budget. The paper implements a Bayesian root-cause estimation policy that tries to balance two failure modes: rolling back too little and missing the true cause, or rolling back too far and wasting already validated work. The interface is general enough to support other policies, including uncertainty-based ones from prior work.

Relative to constrained decoding, Hydra changes the repair unit from the current token to a validated prefix with reusable checker state. Relative to post-hoc repair, the gain is not only earlier error discovery but also avoiding repeated validation of known-good prefixes.
