9:T7f5,The method is an executable contract audit. Instead of starting from the benchmark paper’s informal description, the authors derive a contract from the surfaces visible to the agent and the evaluator: prompt templates, tool schemas, return-value semantics, task files, and grader code. Each contract clause is provenance-bound, meaning it cites the exact interface surface it operationalizes. This is an important design choice because it prevents the auditor from silently adding unstated assumptions.

The checker operates over tuples of (pre, post, args, result), one per probed call or call sequence from a fresh environment. The paper defines six executable defect classes as typed rules at the tool boundary. Two of them are especially notable. Phantom Effect captures the case where the tool reports success for an advertised effect that did not materialize in state. Partial Effect captures incomplete realization of a promised effect. The authors note that these classes are absent from surveyed benchmark-audit taxonomies. Another class, Ignored Argument, is deliberately defined as a state-based rule rather than a conjunctive state-plus-message rule, because some tools interpolate the argument into a success string while dropping it from state; a stricter textual condition would miss exactly the defect of interest.

The implementation combines static and dynamic checks through benchmark-specific adapters, with manual reading where no adapter is possible. The second key component is score-at-risk tracing. After identifying a defect, the audit follows the benchmark’s own evaluator code to determine which task verdicts depend on the defective state or return path, and whether the evaluator’s basis is state, result text, or another proxy. The validation protocol is stronger than a typical code audit: injected defects, negative controls with pre-specified expected verdicts, gold replays, and constructed trajectories showing that the shipped evaluator can reward the defect while failing to reward the repair.a:T516,The audit covers 34 mutating tools across four benchmarks. At pinned commits, the authors confirm seven tool defects and one evaluator property, with at least one benchmark-class, agent-visible finding per benchmark. They also run a blind audit on 12 additional AgentDojo tools and uncover one previously unflagged defect. With six held-out tools plus seven audited earlier, they complete the 25-tool surface for that benchmark and report that at least five tools diverge from their advertised contract.

The most informative result is not a single aggregate metric but the defect-to-score linkage. In the MedAgentBench case, the POST path returns an agent-visible message equivalent to “accepted and executed successfully,” yet the repository code does not perform the write. The benchmark’s write-task grader then treats that success path as evidence. The validation section further shows the checker’s operating boundary: some defects are missed by static inspection alone and require dynamic state comparison; some shipped evaluators positively reward defective behavior and fail to recognize repaired behavior on constructed trajectories. That moves the discussion from “mock environments are simplified” to “the benchmark’s observable contract and scoring basis are misaligned.”b:T472,Read this as a benchmark-audit methods paper, not as an agent-methods paper. Start with the introduction to understand the target of the audit: not realism in general, but consistency between advertised tool behavior, actual implementation, and scoring. Then go directly to the defect-class definitions around Table II. Phantom Effect, Partial Effect, and Ignored Argument are the conceptual center of the paper.

After that, focus on the three-step pipeline: contract construction, static/dynamic checking, and score-at-risk tracing. Pay attention to why the contracts are provenance-bound; that is what makes the audit reproducible rather than dependent on auditor intuition.

In the empirical section, the per-benchmark case studies matter more than the headline counts. The MedAgentBench write-path example is the clearest illustration of the paper’s claim. If time is limited, read one or two case studies and then the validation setup—especially injected defects, negative controls, and constructed trajectories. That is enough to judge whether the method is careful or merely anecdotal.
