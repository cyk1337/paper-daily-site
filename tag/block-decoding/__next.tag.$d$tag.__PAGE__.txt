9:T8c0,方法核心是 learnable block experts routing。作者的出发点有两个观察。第一，原始 token-level router 产生的 expert scores 本身已经包含了专家重要性信息，不一定需要重新设计一套完全不同的路由器。第二，不同 denoising step、不同 block 的专家分布集中度差异很大，因此压缩 unique experts 不能用固定阈值硬裁。

具体做法是先从 token-level expert scores 出发，聚合成 block-level expert scores。直观上，就是把一个 block 内多个 token 对各专家的偏好汇总，得到“这一整个 block 更值得保留哪些专家”的全局排序。然后再用这些 block-level scores 去约束原始 token-level routing：每个 token 仍然保留原来的 top-k 选择机制，但候选专家集合会被 block-level 结果裁剪，只允许在一个较小的共享专家池中选择。这样做的关键点是，它压缩的是一个前向步内的 unique expert count，而不是减少每个 token 的 active experts 数量，因此理论上更容易保住模型表达能力。

作者进一步引入 top-p 形式的动态控制，而不是固定保留前 m 个 block experts。原因是不同 denoising step 的路由熵不同：有些 step 专家偏好很集中，可以压得更狠；有些 step 更分散，需要保留更多候选。top-p 让保留的专家数随 block-level score 分布自适应变化。

训练上采用 self-distillation。论文描述是，在 forward pass 中就使用与推理一致的 routing procedure，让模型在受限专家集合下学习恢复原模型行为。这一点很重要，因为如果只在推理时硬套 block-level 约束，分布偏移会更明显。自蒸馏的作用是把原始 token-level 路由下的能力尽量迁移到压缩后的执行路径上。

从方法定位看，dMoE 不是改 MoE 层结构，也不是做 expert merging / pruning 的离线压缩，而是一个运行时可调的 routing compression 机制。它与 EC-DLM、TEAM、DES 的区别在于：它直接针对“单步 unique experts 过多”这个 dLLM 特有瓶颈，用 block 级共享候选池来压缩激活集合，而不是主要从负载均衡、跨 step 复用或候选约束的其他角度切入。a:T95c,The core idea is a learnable block-level routing mechanism for MoE diffusion LLMs. The method is motivated by two observations. First, the original token-level router scores already contain useful information about expert importance, so one does not need to redesign routing from scratch. Second, expert concentration varies substantially across denoising steps and across blocks, so a fixed compression rule is too rigid.

Concretely, dMoE starts from token-level expert scores and aggregates them into block-level expert scores. Intuitively, it summarizes how strongly the tokens in a block collectively prefer each expert, producing a block-wise ranking over experts. These block-level scores are then used to constrain the original token-level routing. Each token still keeps its original top-k routing behavior, but the candidate expert set is restricted to a smaller shared pool selected at the block level. This is the key design choice: dMoE compresses the number of unique experts activated in one forward pass, rather than reducing the number of active experts per token. That makes it easier to preserve expressivity while improving efficiency.

The method further uses a top-p style dynamic control instead of keeping a fixed number of block experts. The reason is that routing entropy changes across denoising steps: some steps have highly concentrated expert preferences and can be compressed aggressively, while others require a broader candidate set. Top-p allows the number of retained experts to adapt to the score distribution.

Training uses self-distillation. The paper states that the same routing procedure is applied in the forward pass during training, so the model learns to operate under the compressed expert set rather than only facing that constraint at inference time. This matters because otherwise the routing restriction would introduce a larger train-test mismatch. Self-distillation helps transfer the behavior of the original token-level routing into the compressed execution path.

Positionally, dMoE is not an MoE-layer redesign and not an offline pruning or merging method. It is a runtime-adjustable routing compression mechanism. Compared with prior efficient MoE methods for diffusion LMs such as EC-DLM, TEAM, and DES, its focus is more direct: reduce the unique expert set within each denoising step by introducing a block-level shared candidate pool.b:T672,The base model is LLaDA2.0-mini, evaluated on MATH500, GSM8K, ARC-C, and MMLU. These are meaningful numbers because such memory and latency gains would be hard to obtain if expert activation were only reduced marginally.

The most important experimental view is the efficiency-quality curve rather than any single benchmark score. The paper emphasizes that dMoE is tunable, meaning the compression level can be adjusted through top-p to fit different deployment constraints. That boundary reveals how much representational flexibility is lost when routing is forced into a shared block-level candidate pool.

Another critical part is latency profiling. The introduction says Section 3 shows that MoE latency scales linearly with the number of unique experts and dominates end-to-end inference. That profiling is the foundation of the paper. If it is done carefully, then dMoE is not just an empirical trick but a direct intervention on the actual bottleneck.
