18:T81e,ReproRepo has three core pieces.

First, data construction. The authors collect paper–repository pairs from major ML conferences, then mine GitHub issues from the linked repositories. They filter for issues that correspond to reproducibility blockers rather than generic feature requests or discussion. To avoid leaking the answer to the agent, they reconstruct repository snapshots aligned with issue timing and fix timing, such as issue-time snapshots, pre-fix snapshots, and post-fix snapshots. This turns naturally occurring historical failures into hidden evaluation targets.

Second, the task setup. Agents are given the paper and a fixed repository snapshot, but they do not execute code. The setting is intentionally compute-light and limited to static inspection. This is a practical design choice: many modern ML repositories require GPUs, large datasets, and external APIs, so full execution is expensive and hard to standardize. The benchmark therefore asks a narrower but still meaningful question: how many real reproducibility blockers can an agent surface from static inspection alone?

Third, the evaluation protocol. Agent findings are compared against human-reported issues using both exact match and semantic match. Metrics are reported at both the issue level and the paper level, along with cost. This layered evaluation is important because reproducibility failures are often described differently by different people. Exact match alone would understate capability, while semantic match alone would overstate localization quality. The paper also distinguishes visible failures from less visible ones, which helps characterize what current agents are actually good at.

Relative to prior work, the novelty is less about task format and more about supervision source and scale. Instead of expert-authored tasks, it uses naturally occurring GitHub issues. Instead of tens of papers, it covers 1,149 papers and 7,553 human-reported blockers. The trade-off is noisier supervision, but the snapshot design and multi-granularity metrics help manage that noise.19:T537,The scale of the evaluation is the main result. The benchmark covers 1,149 papers from three major ML conferences and 7,553 human-reported reproducibility blockers. The authors evaluate Claude Code and Codex paired with four frontier LLMs. Under the static-inspection setting, the results are stronger than one might expect: Codex with GPT-5.5 finds at least one semantically related hidden issue for 93.3% of NeurIPS 2024 main-conference papers and 89.7% of ICLR 2026 papers.

The more important finding, however, is the gap between semantic coverage and exact localization. Agents are often able to identify the right semantic region of failure, especially for visible problems such as missing imports, broken scripts, dependency mismatches, or obvious setup issues. But they are much weaker at pinning down the exact source of the problem and at identifying less visible failure types. The paper also reports relatively low false positive rates, which suggests the agents are not simply generating broad generic warnings to inflate recall.

When reading the experiments, focus on four things: comparisons across agent/model combinations; the gap between exact match and semantic match; the stratified analysis of visible versus less visible failures; and the cost analysis, since scalability is one of the benchmark’s main claims.1a:T5ea,Read it in the order of data construction, evaluation protocol, then error analysis.

Start with Figure 1 and Table 1. They make the benchmark positioning clear relative to earlier reproducibility evaluations such as PaperBench, CORE-Bench, and REPRO-Bench. The key point is not the names, but why this benchmark scales: supervision comes from GitHub issues rather than expert-authored tasks.

Then read the data construction section carefully. Check how reproducibility-related issues are filtered, how repository snapshots are aligned with issue timing, and how pre-fix versus post-fix states are used. This determines whether the benchmark is really measuring reproducibility blockers rather than repository maintenance noise.

Next, read the metric definitions. Pay close attention to exact match versus semantic match, issue-level versus paper-level metrics, and how false positives are counted. In agent benchmarks, much of the real disagreement usually comes from the matching protocol.

Finally, spend time on the qualitative analysis. The most useful part is the failure analysis: why agents can often identify the right semantic area but fail to localize precisely; which failure types are inherently hard for static inspection; and whether some findings are inferred from the paper text without being grounded in the codebase.

If you only want the main ideas, read the introduction, Figure 1, Table 1, the main result table, and the qualitative error analysis.
