18:T734,TIRE has three modules: Physical Knowledge, Top-Down Formula Instantiation, and Teacher Distillation, all tied together by program-based verification.

The first module represents reusable physics knowledge as formula records. These records are not treated as plain text snippets; they encode the physical relation, variable semantics, and applicability conditions needed for downstream instantiation. The dataset is grounded in 3,051 such records extracted from PHYSICS and SciBench.

The second module is the core design choice: top-down instantiation. A formula is translated into an executable program, validated through Program Validation, then instantiated with concrete parameter values that satisfy the formula’s validity conditions. The program is executed to obtain a reference answer y*. This ordering matters. Instead of asking an LLM to jointly invent a scenario, choose a law, assign values, and solve it, TIRE first constructs a valid physical instance and only then verbalizes it as a natural-language problem. That sharply narrows the error surface.

The third module is teacher distillation. A teacher model generates reasoning traces, but those traces are not trusted by default. TIRE keeps only traces whose final answer matches the execution-derived reference via Answer Verification. This turns the teacher into a language explainer rather than the source of truth. That is a notable departure from many synthetic CoT pipelines, where the teacher’s full output is directly used as supervision.

The broader design logic is clear: separate semantic generation from numerical correctness, and let deterministic execution define the target whenever possible. The framework does not fully solve realism or coverage of complex multi-law physics problems, but it substantially improves controllability and label reliability.19:T556,The paper builds TIRE-19k, a dataset of 19,144 examples spanning 9 physics subfields, grounded in 3,051 formula records. Each example contains a natural-language question, an execution-derived reference answer, and an answer-verified teacher reasoning trace.

Empirically, the authors evaluate on 3 backbones and 4 benchmarks. Under equal training-data budgets, TIRE-19k outperforms existing physics reasoning datasets both in-domain and on out-of-domain generalization. The important point is that the gain is shown under matched data volume, which supports the claim that the improvement comes from data construction quality rather than simply more samples.

The ablations are the most informative part. They show that:
1. top-down formula instantiation is better than direct text-based generation;
2. reliable execution is critical, because removing the execution anchor increases supervision noise;
3. the framework works with multiple teachers, so the benefit is not tied to one specific teacher model;
4. GRPO after SFT yields additional gains, suggesting that execution-grounded data is also a good starting point for RL-style post-training.

The paper’s strongest experimental message is not a single benchmark number. It is the demonstration that when the answer is independently computed, the teacher should generate explanations, not define correctness.1a:T478,For a skim-level read, start with the problem framing in the introduction. The useful part is the distinction between physics and math data generation: physics requires consistency between scenario semantics, law applicability, and computation, not just symbolic derivation.

Then read the method overview and focus on three checkpoints: Program Validation, Instance Execution, and Answer Verification. These are the real backbone of the pipeline. The key question is what type of error each checkpoint removes.

In the experiments, prioritize:
- comparisons against prior datasets under equal data budgets;
- ablations removing execution grounding or replacing top-down instantiation with direct generation;
- teacher comparison;
- the SFT-to-GRPO extension.

A practical reading lens is to ask whether this pipeline can scale beyond single-formula or relatively clean textbook-style problems. If you care about reuse, the most important issues are the cost of building the formula library and whether the execution layer can support more complex multi-step physical modeling.
