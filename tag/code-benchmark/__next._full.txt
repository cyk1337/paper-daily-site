19:T59d,The paper has a structural part and an empirical part. Structurally, for an odd-numbered unweighted majority panel with k judges and a single replacement ballot, the panel prediction can change if and only if the original vote margin is one, m = |2s-k| = 1. This is a deterministic arithmetic fact about majority voting, not a statistical claim. It identifies the exact affected set for single-ballot substitution.

Empirically, the authors build multi-model judge panels for code-generation evaluation and introduce a verification signal from a different evidence source. They compare several replacement rules, including random replacement, fixed replacement, and replacing a vote on the majority side. They then report two diagnostics on the same data: the same effective-vote statistic used in prior work, and margin-stratified accuracy/error analyses. The key result is that these diagnostics answer different questions. Aggregate dependence can remain unchanged while conditional gains on pivotal examples are large and reliable.

The mechanism is simple. Most examples are structurally unaffected by single-ballot substitution, so averaging over the full population dilutes any verifier benefit. If the verifier is especially useful where the panel is near the decision boundary, the gain is real but localized. The paper also includes an exploratory analysis linking part of the pivotal-region error pattern to panel composition.1a:T552,The experiments cover three code benchmarks and four panel sizes, k in {3, 5, 7, 9}. The main setting uses seven LLM judges plus one verification signal. At larger scale, replacing one judge with the verifier changes the effective-vote count by about -0.04 with a 95% confidence interval of [-0.10, +0.02], so the aggregate metric shows no distinguishable improvement. Yet panel accuracy still increases.

The margin-stratified analysis explains why. For non-pivotal cases, such as at least 5–2 agreement in a 7-judge panel, single-ballot substitution cannot alter the majority outcome, so the accuracy gain is exactly 0. For 4–3 cases, the same verification signal improves accuracy by more than 10 percentage points. In the main setting, 199 of 569 panel errors occur in the pivotal region. So pivotal cases do not contain all errors, but they have higher error rates, and every decision change induced by single-ballot substitution is confined there.

The paper also evaluates margin gating. Once a substitution rule is fixed, verifier calls outside the pivotal region can be skipped without changing predictions. In their experiments, this reduces verifier-call frequency to 12%–27% while preserving the same outputs as universal substitution. Table 7 further shows that the replacement rule itself materially affects accuracy; gating only saves calls.1b:T614,PerfCodeBench is an executable benchmark for system-level code optimization. Each task provides a correct but slower baseline implementation and a human-expert or expert-inspired optimized reference. The model is asked to optimize the baseline while preserving semantics. The evaluation harness checks three things in a controlled way: compilation, task-specific correctness, and runtime performance. The dataset is built from public repositories, benchmark suites, and systems research artifacts, then filtered aggressively. A task is kept only if it compiles and runs, has an automatic correctness oracle, has a reference implementation that is genuinely faster than the baseline, and yields stable runtime measurements. The final benchmark contains 1,854 executable tasks across six programming languages and multiple systems domains, including GPU and accelerator benchmarks, CPU SIMD and cache-sensitive libraries, parallel and HPC workloads, SQL and data-processing systems, AI inference runtimes, and general systems libraries. The design has two major strengths. First, it turns performance optimization into an executable and quantitative objective rather than a subjective code-quality judgment. Second, it avoids the bias of algorithmic coding benchmarks, because many real bottlenecks come from memory access patterns, parallel scheduling, and hardware details rather than big-O improvements. There is no novel learning algorithm here; the contribution lies in task curation, the unified harness, and the baseline/reference evaluation protocol.1c:T434,The main experimental result is straightforward: current models often generate functionally correct code, but they still fall short of expert-level efficiency. Across a broad evaluation of frontier models, even the strongest model reaches or surpasses the expert reference on only 61.6% of comparable tasks. That means top models match or beat human-optimized implementations on only about three fifths of the benchmark. The gap is especially pronounced for parallel programs and GPU kernels, which suggests weaknesses in hardware-aware optimization, synchronization reasoning, and low-level execution behavior. In scale, the benchmark contains 1,854 executable tasks spanning six languages. The provided text does not include the full per-model tables or category-wise exact scores, so it would be unsafe to fabricate more detailed numbers.
