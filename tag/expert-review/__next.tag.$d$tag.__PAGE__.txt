9:T4ed,This is not a new model paper. It is a detailed expert-review case study. The authors used Claude Code, given a human-written theorem statement and a PDF proof sketch from Hartshorne, to semi-autonomously formalize Grothendieck’s vanishing theorem in Lean. The first fully compiling version is called state A. An expert Lean/mathlib review then identified substantial issues in definitions, theorem statements, API design, and file organization. Those review comments were converted into a checklist, and Claude plus Codex iterated until the checklist was addressed, producing state B.

The paper’s main contribution is the evaluation frame. It separates “kernel acceptance” from “library quality” and documents the difference with before/after expert review. One especially informative episode is the heartbeat debugging story. When typeclass search and proof checking became too expensive, the agent’s first move was to raise maxHeartbeats repeatedly. The durable fix was different: cache instances with inferInstanceAs, split large proofs into named lemmas, and restructure the development. That is a concrete example of the broader pattern: the agent follows locally executable fixes more readily than it recognizes structural design problems.a:T43a,The evidence is a project-level reconstruction rather than a benchmark table. The development is around 5,000 lines of Lean code and targets a graduate-level algebraic geometry theorem, not a short contest-style proof. State A already reaches zero sorries and follows the intended mathematical proof structure, which is a strong sign that current models can handle substantial local proof completion when the route is fixed. The weaknesses appear under expert review: poor definitions, insufficient theorem generality, awkward namespace and file structure, and APIs that are hard to build on.

After the review-driven refactor, state B is substantially better as a library artifact. The paper does not reduce this to a single scalar metric. Instead it presents process evidence: the sorry curve, commit history, token usage, loop modes, and the evolution of expert-review findings. That is exactly the point. If one only measures “does it compile?”, state A already looks successful.
