9:T597,The setup treats a benchmark as a fixed list of M questions. For each question, generated answers have a verifier score S and a correctness bit Y. At budget k, the selected answer is the one with the highest verifier score among k samples, and the curve reports the average correctness over the fixed question list. The audit may adaptively choose questions, extend answer paths, query correctness labels, and stop when it can return a simultaneous confidence band with half-width ε and failure probability δ. The analysis counts three resources: generated answers, correctness queries, and question visits. For a fixed list, the main cost law for certifying all budgets up to K is, up to logarithmic factors, K/ε + min(M, ε^{-2}) + s/ε^2. The three terms correspond to rare high-scoring answers at large budgets, the identity of the benchmark questions, and within-question variance accumulated along the curve. Matching lower bounds show that these terms are intrinsic. A key technical device is a coupling of nested winners on one answer path, which lets a single path serve all budgets. The practical algorithm is a paired audit: each round draws two fresh paths per question, uses an exponential inequality for paired Bernoulli draws to build anytime-valid simultaneous bands, and then applies a corrected exact-binomial final look to stop at a fixed round. Combined with a multilevel audit, it attains near-minimax cost.a:T45b,The empirical study uses 185 held-out score pools. The curves often plateau early: the median curve is within 1/32 of its best value by k=10, so small differences matter. On 100 MMLU-Pro questions, a fixed exact-binomial design needs 192,000 generated answers to certify all budgets up to K=64 within ±1/32 at 95% confidence. By contrast, one path of 64 answers per question uses only 6,400 answers and gives unbiased estimates of all points, but does not provide a sufficiently tight simultaneous guarantee. At budget 64, roughly three quarters of the variance in selected-answer correctness comes from between-question variation, which explains why balanced revisits to every fixed question can save cost. In experiments, the paired audit uses 0.74, 0.66, and 0.53 times the generated answers of the cheapest competing certified audit at K=64, 256, and 1024. It is cheaper on all eight generator-benchmark answer sets, misses none of 3,255 runs against exact curves, and its cost follows the three-term theory closely with R^2=0.995. A cost law fitted before a new study predicts that study’s bill within 0.6%.b:T5a8,Core represents a reasoning trajectory as a stack of decisions. Each decision has a stable identifier, dependencies, and a canonical key that preserves type, value, dependency context, and occurrence identity when needed. A proposer, which may be an LLM or a deterministic policy, returns a finite ordered list of candidates for the next decision. The verifier returns pass, fail(C), or unknown. A fail(C) output is only eligible for hard caching when C is a sound conflict core: no valid complete solution can contain all decision keys in C. The controller keeps a stack and a set of learned nogoods. Before verifying a candidate, it checks whether the resulting state contains a cached core; if so, the candidate is skipped without another verifier call. When a certified failure is found, Core optionally minimizes the core, inserts it into the cache, removes stored supersets, and backjumps to the latest decision contained in the core. Later decisions are discarded because they cannot repair a conflict that does not mention them. If all candidates at a level are exhausted, their explanations can be resolved into an exhaustion core. Unknown verifier outputs can extend the stack provisionally, but they cannot create hard constraints. The formal guarantees require sound verification, sound cores, finite branching and depth, and exhaustive proposals; under these assumptions, uncapped search is complete and does not prune valid solutions.c:T551,The method is simple, but the experimental control is strong. Mid-Harness keeps the generator, execution harness, and serving setup unchanged. It only inserts an intermediate wrapper: given the same interaction history, sample several candidate actions, apply a verifier, and forward only the selected action to the original harness. This makes it possible to separate two questions: whether the generator already contains useful alternatives, and whether a verifier can identify them before execution. In that regime, wider sampling helps little, which indicates that the bottleneck is discrimination rather than candidate diversity.
