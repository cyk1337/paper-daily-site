ProVe: Proposer-Verifier Decoding

这篇工作解决的是一个很具体但很关键的推理问题：当大模型已经能在一次前向里提出一个长度为 B 的候选 token block 时，推理加速里“由小模型起草、大模型验证”的传统 speculative decoding 分工是否还合理。作者的答案是否定的。论文把角色反过来：让大模型一次性提出整段候选，再用一次额外前向去判断这段里有多少前缀可以安全提交。核心矛盾不在于能不能提出 block，而在于提出之后如何决定提交长度。MARS 这类 block proposer 只靠 proposer 自己的置信度做提交，代价低，但会明显少提交通常其实已经与 AR greedy 一致的前缀；ProVe 关注的就是如何用一次验证 pass 把这部分“未被利用的可提交前缀”找回来，从而把 serial decoding 的步数真正降下来。

评反转了推测解码的常规设定，让大模型自己做 proposer 并通过微调实现 block prediction，思路清奇，值得关注其训练 recipe 和实际加速比。

BitMTP: When Multi-Token Prediction Meets Low-Bit Large Language Models

这篇工作解决的是：超低比特 LLM 与 multi-token prediction 直接拼接后，往往拿不到“更快且不掉质”的真实收益。问题不在于 MTP 能不能少走几步，而在于低比特场景下，每一步的 block 计算更宽，accepted prefix 长度又是动态的，KV materialization、replay 输入、verifier 调度都会跟着变化，最后把理论上的并行收益吃掉。作者把这个问题明确成 accepted-prefix dynamics，并进一步指出，若不同时处理训练目标、解码策略和 runtime 状态一致性，低比特 MTP 很容易在实际 GPU 上既不快也不稳。

评别把它当训练范式论文；当作“低比特+并行草稿”为何不加速的工程复盘更合适，重点看KV更新与验收策略是否真在端到端吞吐上赢。

Adaptive Multi-Token Prediction: How far should we go?

这篇工作解决的是 MTP speculative decoding 里的一个很具体但很实际的问题：在每一轮验证前，应该一次性 draft 多长的 token span。长度太短，target model 的验证开销摊不薄；长度太长，一旦前面早早被拒，后面整段草稿都白算。AR drafter 可以边生成边决定是否继续，但 MTP 的多个 head 是同一次前向一起出结果，所以 horizon 必须在 drafting 之前就定下来。作者把这件事形式化成一个在线控制问题：利用历史 verification feedback，动态预测当前上下文下不同 horizon 的吞吐收益，并在部分反馈条件下持续更新决策器。

评把“选多长草稿”从拍脑袋变成可学习的在线控制，适合直接塞进解码栈；先看 acceptance survival 的建模与对比是否算清总算力账。

ECHO: Efficient Causal Self-Recursion Beyond Auxiliary Multi-Token Prediction

这篇工作要解决的是：现有 multi-token prediction（MTP）虽然能给预训练提供更密的监督，也能服务 speculative decoding，但它通常只是挂在主干模型外面的辅助头。这样有两个直接问题。第一，多步未来 token 的监督大多被 horizon-specific 的辅助模块吸收，真正负责 next-token 生成的 backbone 只得到间接收益，所以长程规划能力提升有限。第二，想把监督深度做深，代价会线性上升：每多一个 horizon，就多一套模块和一轮计算，因此大规模训练里往往只敢做 depth-1 draft。ECHO 的目标，是把多步未来预测从“外挂辅助任务”改成“主干自身递归执行的训练方式”，让未来监督直接落到 backbone 上，同时把更深 horizon 的训练成本压到可接受范围内。

评这篇会直接影响你怎么看 MTP：如果监督真落在 backbone 比外挂 head 更有效，就该立刻做 internal ablation；先看 DDS 成本曲线和 reasoning/code 的饱和对比。
