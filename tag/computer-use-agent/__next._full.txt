18:T46d,LEASH formulates weak-to-strong escalation as a budget-constrained sequential stopping problem, where the weak model’s estimated failure risk acts as a proxy for the benefit of escalation. It builds a representation bank from a small set of held-out tasks by recording hidden states on prompt and action tokens and labeling them with task-level and subgoal-level outcomes. At test time, the current prompt or execution trace is scored by a Mahalanobis-distance criterion: the hidden state is uncertain if it lies closer to past failures than to past successes. This score drives two mechanisms. First, an initial gate decides whether to escalate at the start, while a runtime gate monitors the weak agent during execution. Second, after handoff, the weak model becomes a shadow observer for the strong model, checking the trajectory every three steps. If uncertainty is high, the pending action is rolled back and re-decided once with higher reasoning effort. The main difference from prior escalation schemes is that no additional monitor training, external knowledge base, reference model, or per-step multi-sampling is required.19:T4de,OS-Helix frames hybrid GUI/code computer use as end-to-end policy learning.
- Unified action space: the model emits either GUI atomic actions (mouse/keyboard) or code/shell execution actions under one policy.
- Environment/data foundation: application–artifact composition pairs versioned desktop applications with authentic file artifacts to instantiate diverse, reproducible Ubuntu states.
- Trajectory synthesis pipeline: an Exploration Agent briefly explores the initialized state to propose grounded instructions; a separate Evaluator Agent builds mostly rule-based evaluators to score/filter trajectories, enabling scalable collection of hybrid demonstrations.
- Training recipe: (i) SFT on filtered hybrid trajectories to internalize action semantics and modality routing; (ii) online RL in executable desktop environments to improve success.
- Optimization fix: early RL increases the fraction of code actions while degrading success; the paper attributes this to token-length asymmetry (short GUI actions vs long code blocks) causing token-based optimization signals to be dominated by code.
