18:T44c,AdaExploreBench models environment dynamics as latent rules mapping input fields to an intervention score.
- Setup: each case provides field values; the agent selects one of four ordered actions (increasing intervention strength).
- Latent rule: a subset of fields (factors) with directional effects determines a score s∈[-1,1]; a fixed utility function maps s to action utilities, enabling calibrated evaluation.
- Rule families: additive, conjunctive, disjunctive, and lexicographic dynamics, yielding diverse but controlled hypothesis structures.
- Protocol: in the default setting, the agent decides when/what/how many queries to make to gather evidence. Rule drift occurs without announcement during interaction.
- Sequential batching: evaluation cases are presented in small batches so agents can notice drift either via further probing or via degraded performance, producing an in-process performance curve.
- Scalable synthesis: an LLM-assisted pipeline generates a field catalog (semantics, ranges, sampling distributions) plus cross-field feasibility constraints and dynamics constraints.19:T623,The contribution is a benchmark design, not a new model. Each task simulates a customer engagement. The agent receives a sponsor instruction, a copy of the customer’s production system, documents and historical data, a staff directory, and a constrained runtime with Python and SQLite. General internet access is blocked. After the agent finishes, the contents of system/ are deployed without modification, and production still calls the original entry points. This forces real integration into an existing codebase rather than a side demo. Scoring is based on improvement in the customer’s business metric on held-out production data, minus stakeholder-contact cost. Three design choices matter. First, the anchors are explicit: the unchanged system scores 0, the expert reference solution scores 1, and literal compliance with the sponsor request is capped around 0.2. This sharply distinguishes “doing what was asked” from “solving the customer’s problem.” Second, the four instruction levels are a clean intervention. L0 fully specifies the problem; L1, L2, and L3 progressively remove constraints and true objectives until L3 is just the original sponsor request. Because the environment, stakeholders, and grader are fixed, score differences across levels isolate the cost of missing information and failed problem discovery. Third, stakeholder interaction is priced, but the agent is not told upfront which contacts are useful or wasteful. That means the benchmark evaluates information-gathering strategy, not just willingness to ask more questions.1a:T6c9,The benchmark contains 95 tasks from 20 customer scenarios spanning 18 sectors, adapted from real delivery projects by domain experts. The paper evaluates 13 model configurations from 7 providers. On L3, the setting closest to real sponsor requests, the best configuration is Claude Opus 5.5 with a mean score of 0.56 and only 14 of 95 tasks resolved. Five of the thirteen configurations resolve none. Even an oracle that picks the best model configuration per task reaches only 0.70 overall and resolves 30 tasks, still well below the expert reference. The most informative result is the bottleneck analysis. When relevant rules and constraints are provided, the top three models score 0.73–0.82. When they must discover those constraints themselves, scores drop to 0.39–0.62. That points to unstated-constraint discovery, not implementation, as the main failure mode. Another useful observation is that on the original tasks, L3 is at most 0.08 below L1, suggesting the sponsor request often contains partial clues; the hard part is turning scattered evidence into the right intervention. The paper also shows that leading models can obtain 72%–85% of key facts from stakeholders at L3, yet their delivered systems achieve only 0.60–0.70 of the reference improvement. Stakeholder-contact cost then removes another 0.14–0.22 from final scores. So information acquisition is not the same as effective delivery. Weak models are risky in deployment terms: Claude Haiku 4.5 scores below the do-nothing baseline on 79 of 95 tasks, and Mistral Small 4 is below that baseline on 51 tasks even before contact costs are deducted. Generalization across scenarios is also poor: in 5 of 20 scenarios, no model reaches a mean score of 0.5.1b:T4aa,This is best read as a benchmark and failure-analysis paper. Start with the introduction and the task anatomy to understand how it differs from SWE-bench, clarification benchmarks, and customer-service deployment benchmarks. Then focus on the four instruction levels, the scoring anchors, and the definition of stakeholder-contact cost. Those sections determine whether the benchmark is really measuring delivery rather than multi-turn coding. In the experiments, prioritize three views: the performance gap from L0 to L3, which separates implementation from problem discovery; the gap between key-fact retrieval and final business improvement, which shows where current agents lose traction; and the count of tasks below the do-nothing baseline, which is more deployment-relevant than mean score alone. If time is limited, 30 minutes is enough to extract the main message from the level-wise score tables, resolved-task counts, and scenario variance. The deeper questions are whether this benchmark can guide training-data construction for realistic enterprise delivery, and whether the metric may underweight long-horizon improvements that do not show up immediately in a single business KPI.1c:T7f5,The method is an executable contract audit. Instead of starting from the benchmark paper’s informal description, the authors derive a contract from the surfaces visible to the agent and the evaluator: prompt templates, tool schemas, return-value semantics, task files, and grader code. Each contract clause is provenance-bound, meaning it cites the exact interface surface it operationalizes. This is an important design choice because it prevents the auditor from silently adding unstated assumptions.

The checker operates over tuples of (pre, post, args, result), one per probed call or call sequence from a fresh environment. The paper defines six executable defect classes as typed rules at the tool boundary. Two of them are especially notable. Phantom Effect captures the case where the tool reports success for an advertised effect that did not materialize in state. Partial Effect captures incomplete realization of a promised effect. The authors note that these classes are absent from surveyed benchmark-audit taxonomies. Another class, Ignored Argument, is deliberately defined as a state-based rule rather than a conjunctive state-plus-message rule, because some tools interpolate the argument into a success string while dropping it from state; a stricter textual condition would miss exactly the defect of interest.

The implementation combines static and dynamic checks through benchmark-specific adapters, with manual reading where no adapter is possible. The second key component is score-at-risk tracing. After identifying a defect, the audit follows the benchmark’s own evaluator code to determine which task verdicts depend on the defective state or return path, and whether the evaluator’s basis is state, result text, or another proxy. The reliability framing is central. pass@k measures whether at least one of k attempts succeeds, which captures discovery capability. pass^k measures whether all k attempts succeed, which captures repeatable reliability.
