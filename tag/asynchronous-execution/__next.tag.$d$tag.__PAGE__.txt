a:T9af,AsyncFC replaces blocking value-based function interaction with future-based interaction while preserving the standard call-return shape that existing models expect. It does this without modifying the model or the underlying function implementations.

The mechanism has four parts.

First, automatic schema adaptation. The runtime rewrites synchronous function schemas into future-compatible ones so the model can accept and pass around future placeholders instead of only concrete resolved values. It also introduces a lightweight await_future function that lets the model explicitly request resolution when needed. The key idea is that the model does not need to learn a new concurrency language; unresolved results are exposed as symbolic objects it can continue to manipulate.

Second, asynchronous dispatch with immediate return. When the model emits a function call, the runtime submits the original synchronous function to an async executor and immediately returns a symbolic future identifier into the conversation. From the protocol's perspective, the function has already returned, so the model can keep decoding, issue more calls, or pass the future into downstream calls.

Third, event-driven result integration. Once the backend execution completes, the runtime injects the resolved result or an error message into the context at turn boundaries. The model still sees a call followed by a return, but the return is initially a future placeholder and only later becomes a concrete value.

Fourth, dependency-aware scheduling. To avoid unsafe parallel execution, AsyncFC is conservative by default and serializes calls unless the developer provides resource-interaction annotations. With those annotations, the scheduler can unlock dependency-safe inter-function parallelism. This yields two forms of concurrency: overlap between model decoding and function execution, and parallel execution among independent functions.

Compared with prior approaches, the paper deliberately avoids two common routes: changing the model so it explicitly manages fork/join behavior, or changing the function-calling protocol so the model itself bears more concurrency-management complexity. AsyncFC pushes concurrency management into the runtime. The upside is compatibility with existing models and tools; the downside is that gains depend on whether the model can naturally operate over future placeholders and whether the scheduler has sufficiently accurate dependency annotations.b:T653,The paper reports several end-to-end latency results. The clearest numbers are a 1.26x speedup on BFCL v4 Web Search workloads under realistic function latencies, and a 1.44x speedup on SWE-bench Lite when integrated with SWE-agent under scaled latencies intended to better reflect real-world conditions. It also extends the setup to multi-hop reasoning tasks such as HotpotQA, suggesting the mechanism is useful not only for API-heavy workflows but also for retrieval-and-wait reasoning patterns.

The reported gains come from two sources: overlap between decoding and function execution, and inter-function parallelism when dependencies allow it. Importantly, the paper claims these latency reductions do not come with an accuracy drop, meaning the asynchronous execution semantics preserve task quality reasonably well.

The evaluation appears to compare against both standard synchronous function calling and native parallel function-calling modes exposed by some models. The argument is that even when a model supports parallel FC, an execution-layer future-based runtime can still reduce latency further, because native parallel APIs often allow same-turn parallel issuance but do not remove decode-time blocking or define execution-order semantics clearly enough for stateful calls.
