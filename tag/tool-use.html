Do Agent Benchmarks Do What They Say? An Executable-Contract Audit of Tool-Using Agent Environments

这篇工作要解决的问题不是“agent 能不能用工具”，而是“agent benchmark 给出的分数，是否真的对应了环境里发生过的状态变化”。作者指出，很多工具使用型 benchmark 默认相信工具接口的成功返回值，认为只要 tool call 回了 success，就等于环境状态按接口承诺被正确修改了。但这个假设可能是错的：工具实现可能没有真正写入状态、只做了部分写入、忽略了参数，甚至 evaluator 还会把这种错误成功信号当成得分依据。论文把工具接口视为一种可执行契约，逐个检查接口宣称、实现代码、环境状态变化和评分逻辑之间是否一致，并进一步追踪哪些任务分数暴露在这些缺陷之下。

评做 tool-use 或 agent RL 的人该看：它提醒你 benchmark 分数可能是在给环境 bug 打分；读审计 taxonomy 和静态检查结果就够，方法本身还不够成熟。

RLTL;DR: Self-improvement by Internalizing Self-generated Feedback

这项工作处理的是 RLVR 在极稀疏成功信号下无法启动的问题。常规 GRPO/RLVR 会对同一个任务并行采样多条 rollout，然后用 verifier 给出的成功/失败奖励更新策略。问题在于，若任务难到当前 policy 在 128 次尝试内都很难成功，所有 rollout 都是负样本或零收益，优势估计没有有效区分度，训练循环会停在原地。更麻烦的是，在自我改进场景里没有更强 teacher，也没有标准解可蒸馏，模型只能从自己的失败尝试和 verifier 输出中提炼可迁移的信息。

评应立刻看方法和失败集构造；它把 RLVR 的“必须先成功”前提拆开了，但要警惕 verifier 反馈是否泄漏解题结构。

这篇论文要解决的是闭源 frontier model 的隐藏推理不可观测问题。许多模型不再暴露原始 CoT，只给最终答案、摘要式 reasoning 或粗粒度 reasoning control。这样只能知道模型答对了什么，难以比较不同模型的推理路径、token 使用效率和中间步骤质量。

评用 Tool Use 骗出闭源模型隐藏 CoT 的巧妙黑盒探测，其对不同模型推理结构的对比分析（token 效率、搜索策略）对做 reasoning distillation 和 RL 奖励设计非常有启发，值得细看实验分析部分。
