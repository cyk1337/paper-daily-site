5:T86b,The system starts from a merged PR and reconstructs the corresponding task condition on a healthy descendant revision of the same repository. The lifecycle is formalized as follows: a historical source patch P_s transforms V_pre into V_post; Change2Task starts from a healthy modern base H, applies a task patch D to create a task state C, and records a restoration patch G that returns C to a restored state H'. The goal is behavioral restoration, not textual identity.

The framework has four main stages. First, it extracts task evidence from the PR: description, implementation patch, and executable checks. From this it derives target checks, regression checks, and a source change profile. The source change profile later serves as a fidelity constraint, ensuring that the reconstructed task remains close to the original maintenance intent and edit footprint. Second, it selects a healthy modern base revision, preferring explicitly declared healthy or target revisions and otherwise resolving an accessible descendant in the repository lineage.

Third, it reconstructs the task using a three-level escalation strategy. Level 1, Patch Reversal, handles cases where the historical patch still maps cleanly to modern code. Level 2, Code Mapping, is used when files, symbols, or APIs have moved but correspondence can still be established. Level 3, Agent Reconstruction, is invoked when direct mapping is too weak and an agent must re-create the change in the modern repository. This staged design is sensible: use the cheapest and most deterministic reconstruction first, and escalate only when repository evolution breaks direct transfer.

Fourth, the system validates the full lifecycle. Healthy, task, and restored states must satisfy their respective checks, and the task is verified for provenance, behavior, scope, and restoration. Objectives are expressed through task adapters, which define the expected output, executable oracle, and edit scope for task types such as Bug Fix, Feature Addition, Test Generation, API Migration, and Security Repair. That adapter abstraction makes the framework broader than a bug-fix-only benchmark generator.6:T4f6,The evaluation focuses on reconstruction yield, fidelity, agreement with historical tasks, and environment-efficiency gains. From 1,130 eligible changes, the system finalizes 900 paired tasks, which is a strong yield given the validation requirements. On 621 matched Bug Fix candidates, Change2Task reconstructs 500 tasks, compared with 387 for SWE-smith PR Mirror, indicating better coverage when transferring historical changes to modern code.

For quality, the corpus reaches 0.894 task-weighted source change profile fidelity, measuring how well the reconstructed task preserves the original PR’s change scope and structure. More importantly, matched agent evaluation shows up to 98.0% outcome agreement between historical and reconstructed cases while preserving agent ranking. That means the reconstructed tasks are not merely superficially similar; they behave similarly enough to maintain comparative evaluation signals.

On efficiency, reusing 388 modern bases reduces environment time by 58.4%, storage by 71.2%, and end-to-end expenditure by 10.8%.
