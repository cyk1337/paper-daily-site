9:T588,The method is a staged verification pipeline. First, an LLM rewrites the original problem using strategies such as numerical reparameterization, logical restructuring, constraint modification, and contextual reconstruction. Importantly, the rewriter is instructed not to solve the rewritten problem, which helps separate problem generation from answer generation. Second, RePro performs conservative semantic screening. This stage filters out candidates that are ambiguous, under-specified, contradictory, unrealistic, or infeasible. The paper is careful about the notion of feasibility: it is not merely formal derivability, but semantic and constraint consistency of the rewritten problem. Third, the surviving candidates are translated into executable Lean specifications, and Lean-oriented neural ATPs such as Goedel-Prover and DeepSeek-Prover search for candidate proof scripts. A proof is accepted only if it passes Lean kernel-level verification.

This design differs from prior rewriting-based evaluation in three ways. It verifies answers through formal proof rather than heuristic checking. It evaluates reliability along three axes—well-definedness, feasibility, and answer correctness—rather than treating validity as a single vague notion. And it explicitly trades recall for precision by retaining only proof-verified instances. That trade-off is deliberate and sensible for benchmark construction.a:T4a3,The experiments are conducted on GSM8K and MATH. The headline result is straightforward: among the retained rewritten instances, RePro achieves 100% well-definedness, feasibility, and answer correctness, whereas prior rewriting methods still leave invalid questions or incorrect reference answers in the benchmark. This is the central empirical claim, and it supports the paper’s argument that formal verification changes the reliability ceiling of rewritten evaluation sets.

A second important result concerns reformulation sensitivity. Using proof-verified rewrites, the authors show that several models suffer noticeable accuracy drops when mathematically equivalent problems are restated in new forms. Because the rewritten items are verified, the drop is more plausibly attributed to sensitivity to formulation and possible memorization dependence, rather than to benchmark corruption. The paper also makes clear that not every rewrite survives the pipeline: the released benchmark is a retained subset of candidates that can be formalized and proved. That gives high precision, but limits coverage and may bias the benchmark toward problems that are easier to formalize in Lean.b:T519,For each intended theorem T, the authors construct a complete shadow set 𝒮={S1,...,Sn}. Each shadow theorem Si is chosen so that T implies Si, giving a forward checker. The set is complete only if the conjunction S1∧...∧Sn implies T, giving a backward checker. Both directions are encoded and mechanically verified in Lean, so completeness is not an informal annotation claim but a machine-checked property. During evaluation, the generated candidate theorem \hat{T} is appended with these checkers. It receives credit only if it type-checks and passes the implication tests induced by the shadow set. A notable design choice is the annotation workflow: experts do not write everything from scratch. LLMs first draft candidate shadows, experts revise them, and Lean verifies completeness. This keeps expert labor focused on correction and validation rather than blank-page authoring. The method is especially well suited to multi-conclusion theorems, bundled conditions, existence/uniqueness statements, and other structures where partial formalization can still compile. Compared with BEq+-style reference-based equivalence checks, SA-Pass is less tied to one canonical expression. Compared with compile rate, it explicitly tests whether the generated statement is neither too weak nor too strong.c:T51b,Three results matter most. In localization, the system decomposes coarse benchmark steps into finer EdgeUnits using a proof-state-tree representation. Each transition in this tree corresponds to a local reasoning responsibility, which makes the evaluation target much sharper than judging an entire paragraph-like step. In verification, the method extracts typed proof obligations from suspicious transitions. These obligations are not treated uniformly; they encode different kinds of reasoning responsibilities such as algebraic transformation, implication transfer, existence construction, boundary-condition handling, or case transitions. The system then gathers evidence through both lightweight checks and Lean-based validation. Lean is used as a structured evidence source rather than a direct judge. Lean evidence is only trusted when this alignment is high enough, preventing drifted or weakened targets from producing false reassurance. Beyond measurement, they run a factorial ablation over three intervention axes:
- Parametric drafting: the base model producing an initial Lean statement.
- Mathlib/context grounding: retrieving/providing relevant definitions and library context.
- Lean elaboration feedback: iterative repair using elaborator/compiler feedback.

The key design choice is to quantify which interventions primarily improve validity, which improve faithfulness, and which mainly reduce cost/iterations—rather than treating “verifier feedback helps” as a monolithic effect.10:T7f9,The central abstraction is the blueprint, an evolving Lean file that simultaneously serves as a formal proof skeleton, a natural-language proof graph, and the shared system of record for all agents. Each lemma or theorem node contains a Lean type, the corresponding LaTeX statement, and natural-language proof content. Dependency links between nodes form a proof DAG. A key design choice is that this DAG is not frozen at initialization. It can be split, repaired, and reorganized during the run, which matches the uncertainty of research-level formalization much better than a static decomposition.

On top of this shared artifact, the system uses four contract-scoped agents responsible for construction, auditing, proving, and repair. The contract-scoped part matters. Agents are restricted to bounded edit regions rather than given unrestricted write access to the whole development. This is a deliberate error-containment mechanism: the worst outcome of a bad action should be a rejected patch, not hidden corruption of distant proof state.

Coordination is handled by a two-stage orchestrator. The first stage stabilizes target fidelity through adversarial review, trying to lock down whether the current formal statements still correspond to the intended mathematical targets. The second stage discharges the proof DAG from dynamic leaves upward in parallel, with each round gated by CI-style verification. This separation is important. The system does not ask one monolithic agent to simultaneously infer the structure, prove subgoals, debug failures, and decide whether it is still proving the right theorem.

The paper’s design principles are also worth noting: dynamic DAG decomposition, external or deterministic verification, restricted tool scope, and continuous projection between informal reasoning and the blueprint. Compared with monolithic ReAct-style agents, this is much closer to a controlled collaborative software workflow.
