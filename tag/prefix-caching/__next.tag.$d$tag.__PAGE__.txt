a:T584,CacheRoute builds a periodically refreshed routing table that plans prefix affinity and expected load together, prioritizing cache stability over per-request reactive remapping.
- Inputs/abstraction: per-key arrival rates λ_b for business keys; R routable destinations (a destination is a model-server group; in the 70B setup, TP=2).
- Admission (warm set): admit the highest-rate keys into an affinity-managed warm set under a warm-prefix slot budget; non-admitted traffic falls back to cache-blind power-of-two choices.
- Load cap via replication: calibrate q_cap from a single destination’s latency/load knee. For each key, allocate enough destinations so the expected per-destination load contributed by that key is ≤ q_cap. Replication is primarily for load control (capping per-destination contribution), not for improving hit rate per se.
- Placement: assign admitted keys (and their replica counts) to destinations using LPT (longest-processing-time-first) list scheduling to reduce expected load imbalance.
- Control interval: keep the table fixed for a period to preserve cache warmth; avoid reactive spilling that would send the next request to a cold destination once a cap binds.
The novelty is not LPT or top-k admission individually, but the combined routing design and the empirical characterization of when planned affinity beats both cache-blind balancing and reactive cache-aware routing.b:T532,The central proposal is an agent runtime layer inserted between the framework and the engine. This layer owns the cross-cutting metadata neither neighbor has on its own. It exposes four policy-agnostic primitives: observe, to ingest events from either side; score, to return priorities for ranking decisions; predict, to forecast future agent activity; and act, to trigger off-critical-path side effects such as prefetching or warming. The paper frames these as an observe→score→predict→act loop, with agent identity as the shared key.

The main instantiation is CacheSage for KV caching. The idea is that multi-agent workloads often reuse a recurring system-plus-tools prefix across sessions, but reactive caches evict those blocks before the next relevant session arrives. CacheSage learns an online first-order Markov transition matrix over agents within a workload. That model is used in two ways: for score, it estimates survival probability to guide eviction; for predict plus act, it triggers cross-session prefetch when a future agent call is likely. The design keeps state bounded, at no more than 20 KB per workload, and falls back gracefully to LRU when the learned signal is weak.
