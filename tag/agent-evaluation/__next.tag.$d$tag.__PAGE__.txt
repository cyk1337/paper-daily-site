It has four parts. First, define the comparison target explicitly: which two configurations are being compared, and what quantity is the score intended to estimate—raw success on the observed benchmark mix, equal-repository weighting, expert-labeled success, deployment-style success, or cost-aware utility. Second, check common support under that target. If the two systems do not both cover the same support cells after stratification or reweighting, the target comparison is not identified from the released data. Third, estimate the supported gap and attach a stated uncertainty rule plus a practical margin. The paper stresses that uncertainty is not a cosmetic add-on: one must specify the sampling unit, clustering level, and whether simultaneous inference is needed. Fourth, return a decision label rather than forcing a total order. Labels include stable superiority, target-sensitive, verifier disagreement, insufficient precision, and missing support.

The paper also includes controlled checks. Simulations test whether these labels recover known finite-sample states. A known-target estimation exercise shows why target reweighting must be judged with uncertainty included; otherwise one overstates how often rankings “flip.” An AgentRewardBench permutation analysis provides a task-conditioned exchangeability reference for interpreting close gaps.

What distinguishes this from routine leaderboard commentary is the insistence that multiple metrics help only if each metric’s estimand is explicit. EvoHarnessBench defines the harness as the set of tools an agent can call, the procedural skills it can reuse, and the specialist agents it can coordinate with. Each harness stream is a sequence of cumulative stages H1 ⊆ H2 ⊆ ... ⊆ HT, so later stages only add capabilities and never remove old ones. Streams are built along three axes: tools, skills, and agents.

Two design choices matter. First, each task is assigned to the earliest stage at which it becomes solvable, and it must require at least one newly introduced capability. This helps separate adaptation to new capabilities from retention of old ones. Second, capabilities are released from common core capabilities toward the long tail, which is meant to mimic real harness growth in deployed systems.

The benchmark supports two evaluation modes. In deployment evaluation, no experience is carried across stages; each harness version is evaluated independently. This isolates the direct effect of harness expansion: does a larger capability pool help, or does it mostly distract? In self-evolving adaptation evaluation, persistent artifacts such as memory, prompts, or learned skills can be updated within each stage and then carried forward, while the underlying model weights remain fixed. This tests whether accumulated experience helps or hinders adaptation under a growing harness.

The benchmark is reasonably large: 17 controlled harness streams, each with 3 to 6 cumulative stages, 802 unique tasks, 1,510 axis-specific evaluation examples, 520 executable tools, 42 latent reference skills, and 62 specialist agents. The paper evaluates representative single-agent and multi-agent systems under both modes.11:T540,The empirical message is mostly diagnostic. First, harness expansion is not free.
