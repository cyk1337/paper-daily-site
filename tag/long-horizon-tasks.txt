19:T465,Its value is primarily as an evaluation asset and a diagnostic study. For foundation-model researchers, the benchmark matters because Office automation is a strong stress test for long-horizon tool use: it requires precise parameter settings, stateful multi-step execution, and cross-application workflows. Unlike many existing agent benchmarks, the tasks are not synthetic and the scoring is not based on subjective LLM judges. The benchmark inherits 7,118 machine-gradable criteria from a mature human exam system, which makes the signal much cleaner. The most useful finding is the gap between execution success and semantic correctness. Strong coding agents can get code to run at 98-99% success rates, yet still score poorly on the actual task rubric. That suggests the bottleneck is shifting from raw code generation or tool invocation toward domain-specific semantic understanding of Office object models, formatting rules, and task constraints. This is more of an eval paper than a pretraining paper, but it is highly relevant to post-training, tool-use data synthesis, and environment-grounded capability assessment.1a:T7ac,The main contribution is benchmark construction and evaluation protocol. OfficeEval is derived from the Level 1 and Level 2 MS Office practical exams in the NCRE. The benchmark contains 200 tasks spanning Word, Excel, and PowerPoint, and preserves the original rubric structure and point allocations. These are not short QA items. Each task requires a sequence of interdependent operations on real documents, spreadsheets, or presentations, such as formatting, formulas, pivot tables, chart customization, mail merge, animation settings, and layout edits. The full benchmark is decomposed into 7,118 machine-gradable criteria, and performance is reported as Score Rate (SR), the percentage of rubric points earned.

The evaluation compares two paradigms. The first is single-turn code generation, where the model receives the task and relevant files and outputs code in one shot. The second is an autonomous coding-agent setup, where the model can iteratively plan, write code, execute it, inspect outcomes, and revise. This distinction is important because it separates raw model competence from the recovery and iteration benefits provided by an agent scaffold.

Another strong design choice is the bilingual setup. Since the original tasks are in Chinese, the authors also construct English-translated versions of all tasks, documents, and scoring criteria. This allows them to test whether language understanding is the main bottleneck or whether the harder issue is Office-specific semantic execution.

The paper's most informative methodological addition is its error taxonomy. Instead of reporting only aggregate scores, it distinguishes execution crashes from logic or operation errors. Execution failures include code crashes and environment-level failures. Logic errors correspond to cases where code runs but the resulting Office artifact does not satisfy the rubric. This turns the benchmark into a diagnostic instrument rather than just a leaderboard.1b:T701,The headline results are straightforward. Under the single-turn code generation setting, no model reaches the 60-point reference threshold for the practical subset. The best model, Claude Opus 4.7, achieves only 36.6% SR. Under the autonomous coding-agent setting, performance improves substantially: Claude Code reaches 53.0% and Codex reaches 68.8%. Even then, models remain well below the 95.5% community-reference score used as a sanity-check upper baseline. Performance is also highly polarized across models, with some systems such as Grok-4.1-fast dropping to 2.8% SR, showing that frontier branding does not translate directly into Office competence.

The error breakdown is the most useful part of the study. In stronger coding-agent settings, execution success rises from below 50% to around 98-99%, but operation accuracy remains low. In other words, agent scaffolding and iterative repair solve much of the 'can the script run?' problem, but not the 'did it perform the correct Office operation?' problem. That is a meaningful diagnosis for future training work.

The benchmark also supports difficulty analysis through the NCRE Level 1/Level 2 split. Level 2 tasks are naturally harder because they involve more advanced spreadsheet logic, richer formatting constraints, and more complex PowerPoint operations. The Chinese-English comparison is used to test language sensitivity; the paper's overall conclusion is that language is not the dominant issue. The harder challenge is Office-specific semantics under long-horizon, multi-step execution. The per-application breakdown is also worth attention: Excel tends to stress formula and structural reasoning, Word stresses formatting and layout fidelity, and PowerPoint stresses object hierarchy and visual arrangement constraints.1c:T57b,Begin with the benchmark construction section. The key question is whether OfficeEval is merely a repackaged exam or a rigorous, reproducible benchmark. Pay attention to task sourcing, rubric extraction, machine grading, and the meaning of the two reference points: the 60-point threshold and the 95.5% community-reference score.

Next, read the main results table with two comparisons in mind: single-turn generation versus autonomous agents, and variance across models. The gap between those two paradigms is itself a major result. It shows that agent scaffolding helps a lot with execution, but does not close the semantic gap.

Then focus on the error taxonomy and the per-application analysis. Aggregate SR alone hides the most important distinction in the paper: running code is not the same as performing the correct Office operation. If your interests include post-training, tool-use supervision, or environment-grounded evaluation, this is the section to read carefully.

If time is limited, a good reading order is: introduction, benchmark construction and scoring protocol, main results, error analysis, and the language comparison.
