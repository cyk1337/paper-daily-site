18:T655,The design has three central pieces. First, the model uses a Causal Encoder-Decoder architecture. The encoder handles the causal prefill side, and decoder global KV is projected from the final encoder hidden states. This gives a cheaper prefill path and a stronger decode path, matching input-heavy agent workloads. Second, the paper introduces Compressed Sparse Attention 2, or CSA2. DeepSeek-V4 can be viewed as a sliding-window local-processing backbone plus compressed global context; V4.1-Flash keeps SWA in every layer but simplifies the global branch. CSA2 statically assigns layers to Full, Reindex, and Reuse modes. Full layers generate global KV and perform indexing. Reindex layers reuse global KV from a previous layer but use their own indexer Q to rescore shared indexer K and select fresh Top-K indices. Reuse layers reuse both global KV and Top-K indices. Each layer still keeps its own global Q and local SWA KV, so the method shares the expensive global cache components without collapsing all attention behavior into one shared layer. Third, the system combines FP4 global KV cache training with SWA Bounded Replay. FP4 global KV reduces runtime cache size with only small degradation. SWA Bounded Replay avoids persisting SWA KV to SSD by replaying only the most recent n_win tokens, rather than the L × n_win replay needed for exact reconstruction in the earlier design. Additional components include pure CSA2 instead of the previous CSA-HCA hybrid, Single-Pass mHC with a Mega-mHC kernel that halves activation memory traffic, the Engram conditional memory module, and DSpark speculative decoding.19:T529,The evaluation covers seven model/context settings, RULER-style tasks at 32k and 128k, and both the intended host-memory regime and GPU-HBM-resident settings. For Qwen3-8B, the paper reports 36 layers, 8 KV heads, 128 channels per head, and 4 query heads per KV head. At 32k tokens, dense attention reads about 4.8 GB of bf16 KV cache per step. With top-k sparse attention at k=512, the selected row fetch is around 200 MB and does not grow linearly with context, while a 136-bit scan used by Loki, Double Sparsity, or SparQ r=32 is about 160 MB at 32k and grows to roughly 5.1 GB at 1M tokens. In the host-memory regime, Fathom is 1.37x faster at 256k tokens and 1.67x faster at 1M tokens in GPU time compared with 136-bit scans, at equal or better accuracy. Against SparQ’s 68-bit read, it reads 18% fewer bytes in the same GPU time and reports 1.1x to 5.3x better accuracy. At equal error, it saves 1.8x to 2.9x bytes compared with Double Sparsity’s 136-bit scan. It maintains downstream parity with an exact top-k oracle on RULER-style tasks, and on real coding-agent sessions reaches the step agreement of the strongest 136-bit scan using about 92 bits. At the main budget K=32, all methods nearly saturate on direct cases, but derived cases separate the policies. An LLM-as-judge check labels 94.6% of clean-perturbed pairs as intent-preserving.1c:T4c0,Self-Indexing Attention builds a shared transform-domain sign-magnitude representation. A structured orthogonal transform (motivated by Hadamard-style transforms with random sign flips, LSH intuition, and transform-domain KV compression such as QJL/TurboQuant) is applied to Q/K/V. The per-coordinate sign of transformed keys is stored as a 1-bit, token-level index. Query–key similarity is approximated via sign agreement (a proxy for angular similarity).

Because sign bits are part of the compressed key payload, the same representation supports retrieval and compression without separate index metadata.

To make it work across inference stages:
- Prefill: group queries to amortize selection cost. Instead of average pooling (which can cancel signs), use absmax-sign pooling: for each coordinate, take the sign of the query with the largest absolute value, preserving evidence important to any query in the group.
- Decode: perform packed 1-bit sign-agreement scoring for fast candidate selection, then apply norm-weighted agreement to reintroduce magnitude information lost in sign-only matching.
- Implementation: GQA-aware sparse-attention kernels and bitwise operations for accelerator-friendly execution.1d:T42f,GVA starts from GQA grouping. Multiple query heads share grouped value heads, but the model no longer writes an independent content-key stream into the cache. For query head h, the content key is reconstructed as K_h = V_g(h) M_h, with a separate reconstruction map per query head. During decoding, the map can be folded into the query, since q·(V M_h) equals (q M_h^T)·V. This avoids materializing content keys in the intended decode path. A direct K=V design was tested and did not recover the GQA training loss, which suggests that the same vector should not be forced to both score and carry retrieved content. RoPE creates the main complication: standard RoPE is position-dependent on cached keys, so it cannot be absorbed into a fixed transformed query. Based on this principle, the paper introduces InplaceKVCache and a scheduling layer called WriteScope.

InplaceKVCache partitions KV storage along two axes. The first is device affinity, meaning whether a region is intended for CPU-side or GPU-side consumption. The second is access pattern, meaning whether the region is optimized for in-place compute or high-bandwidth loading. This yields four regions: on the CPU side, an unpinned compute region and a pinned load region; on the GPU side, a ping-pong compute region and a D-window offload region. CPU attention reads only the unpinned compute region in place. GPU attention streams only the pinned load region through ping-pong buffers. This removes the fallback path of temporary contiguous buffers, copies, and layout conversion.

Prefill KV is routed directly to its target region at write time. Decode KV is first staged in the GPU-side D-window and, once an eviction batch of size D is full, the batch is routed as a whole into either the pinned or unpinned CPU region. The key point is that future consumer and access mode are encoded into the write path itself. The scheduler no longer needs to reorganize data; it only decides how much future KV should go to each physical partition.

WriteScope performs the actual CPU/GPU split along the sequence dimension. It uses a portable roofline-style model to estimate the two costs: GPU-side transfer plus attention compute, and CPU-side in-place attention compute. Eviction batches are assigned so that cumulative placement stays near the balance point where the two engines finish at similar times. The choice of sequence-dimension partitioning is important. It matches the natural history-token access pattern of attention and preserves stable physical layouts on both sides better than finer-grained head- or page-level splitting.

Compared with prior systems, the distinction is clear. GPU-centric systems such as FlexGen and SolidAttention treat spilled KV mainly as data to reload, so PCIe becomes the bottleneck. CPU-centric systems such as NEO and ScoutAttention treat spilled KV mainly as data to compute over in place, so CPU compute becomes the bottleneck. On correctness, the authors first identify a representation bug. LMCache’s handling of packed-page attention blocks recognized rank-5 attention tensors but missed the rank-4 packed representation used in the evaluated deployment. That caused an incorrect byte view during transfer. They adopt an existing upstream packed-subpage patch to repair this representation issue. In the reported 27B setup, a 1,568-token logical block spans 49 pages of 32 tokens. This fixes the question of which bytes should be transferred.

However, after the representation fix, cross-replica reuse still produced wrong outputs. The authors then isolate a second issue: the evaluated image lacks the LMCache CUDA-ops extension and falls back to a PyTorch path. In that path, the raw-pointer lmcache_memcpy_async branch uses cudaMemcpy with cudaMemcpyDefault but without dependence on the current CUDA stream. Because the stream pool uses cudaStreamNonBlocking, the copy does not inherit the producer-consumer ordering of the preceding gather/scatter work.
