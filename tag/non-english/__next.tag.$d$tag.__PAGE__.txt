9:T691,RuBench 1.0 contains 25 repository-level bug-fix tasks drawn from five active open-source repositories: aiohttp, aiogram, Laravel, NestJS, and Fastify, spanning Python, PHP, TypeScript, and JavaScript. Each task comes from a real fix commit rather than a handcrafted puzzle. The task statement is then newly authored in Russian, in the style of a customer request to a contractor: symptoms, desired behavior, and compatibility constraints are described behaviorally, without translating or paraphrasing an English upstream issue.

The benchmark design has several strong protocol choices. First, the judge is the maintainer’s regression test suite, kept private and withheld from the released benchmark artifacts. Second, a freshness gate admits only tasks whose fix commits postdate the training cutoffs of all evaluated models, and this gate is enforced mechanically at import time. Third, the authors release full trajectories and diffs for every run, making outcomes auditable. Fourth, the unit of evaluation is a deployed product configuration—CLI agent plus model plus reasoning-effort setting—rather than a bare model, because the harness itself materially affects behavior.

A notable methodological detail is the validity audit. In a hors-concours setting with Claude Code + Fable 5, the authors found that an official safeguard silently substituted Opus 4.8 on a subset of tasks. From this they derive a practical validity rule: an evaluation cell is valid only if the executing model in the trajectory matches the requested model. This is especially relevant for benchmarking closed product agents where the visible configuration may not fully determine execution.a:T5e5,The benchmark is small, but the protocol is careful. The paper evaluates four product configurations, with three independent runs per configuration, for a total of 300 scored rollouts. It reports pass@1, task-level 95% confidence intervals, paired bootstrap comparisons, and per-task cost, token, and time accounting.

The headline numbers are straightforward: the best configuration, Claude Code + Opus 4.8, solves 78.7% of RuBench 1.0 tasks on average across three runs, while the weakest, Claude Code + Haiku 4.5, solves 53.3%, a spread of 25.4 points. The authors are careful not to overclaim statistical separation at N=25; they explicitly note that only gaps involving the weakest configuration are cleanly resolvable at this sample size.

The most interesting empirical finding is the trajectory audit. In the hors-concours Claude Code + Fable 5 setting, about 20% of tasks were silently executed by Opus 4.8 instead. This shows that benchmark validity can fail if one trusts product labels without checking execution traces.

On the construction side, every included task had to satisfy an import contract: the maintainer oracle must fail on the parent commit and pass on the fix commit in a reproducible environment. The paper also mentions a deliberately imported pre-cutoff task that was rejected by the freshness gate, serving as a sanity check for the machinery.
