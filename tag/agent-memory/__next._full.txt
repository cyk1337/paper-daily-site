18:T4d1,Task Advancement Memory (TAM) uses verified task progress as both online state and offline supervision.

1) Instruction compilation into a requirement graph 𝒬: an LLM-based compiler decomposes the instruction into requirements (info to acquire or outcomes to achieve), dependency edges, per-requirement evidence rules for verification from GUI observations, and optional branch conditions.

2) Task Advancement State (online): maintains each requirement’s status (unresolved/established), known values, evidence, and object bindings. When an observation satisfies an evidence rule, TAM records an advancement and updates the remaining-goal representation—what is done, what inputs are available, and which goals are ready next.

3) Advancement supervision (retrospective): each advancement marks candidate interaction segments; after the episode, TAM selects/abstracts segments that caused verified local results into persistent operations specified by required inputs at entry, the result to achieve, and how to verify it. This salvages useful skills from both successful and failed trajectories.

4) Plug-in design: TAM augments a fixed base policy by providing bounded memory context; it does not retrain the policy itself.19:T86e,结果可以分三层看。第一层是弱模型下 memory patch 的短期收益。用 GPT-4o-mini 时，Mem0 准确率最高，78%，高于 full context 的 74% 和 BM25 的 74%；Zep 只有 43%。此时 agent 表现较差：Pi 63%，Codex 28%，Claude Code 29%。作者解释得也合理：后两者很多时候甚至不打开对话文件，基本是在凭问题本身作答。也就是说，弱模型加弱 agent harness 时，预先抽取的 memory 还能帮忙。

第二层是模型变强后 memory 增益消失。GPT-6 Luna 下，full context 92%，BM25 82%，Mem0 80%，Zep 51%。Claude Opus 5.5 下，Mem0 和 full context 都是 95%，Zep 87%，而 agents 反而最好：Pi 99%，Codex 98%，Claude Code 97%。这说明当模型足够强时，压缩式记忆不再优于直接读原始记录，甚至会因为抽取损失而落后。

第三层是成本和 writer ceiling。Mem0 的 build 成本单独就高于 full context 的整次 rollout：GPT-4o-mini 下是 $0.56 对 $0.43，GPT-6 Luna 下是 $0.45 对 $0.29，Claude Opus 5.5 下是 $25.88 对 $17.84。虽然 Mem0 每题查询更便宜，但要在同一段历史上回答 372、545、596 个问题后，build 成本才回本；LoCoMo 这里只有 152 题，所以不划算。writer ceiling 的证据更直接：在 GPT-4o-mini 写出的 Zep graph 上，GPT-4o-mini、GPT-6 Luna、Claude Opus 5.5 读取后的准确率分别是 43%、43%、45%；如果 graph 由 Claude Opus 5.5 写出，则对应变成 66%、71%、87%。Mem0 也有同样趋势，只是差距较小：从 GPT-4o-mini 的 store 读取时三者为 78%、83%、84%，从 Claude Opus 5.5 的 store 读取时为 89%、91%、95%。这组结果很有说服力，说明抽取式记忆的瓶颈首先是写入阶段的信息保真度。

还有一个细节值得记住：Pi with Claude Opus 5.5 在 cost–accuracy frontier 上最好，99% 准确率，rollout 成本 $6.95，而同模型 full context 是 95%、$17.84。Pi 平均每题读约 1 万 input token，其中 7900 是 cached；full context 每题约 28900 token。它唯一一次“错误”还是 LoCoMo 标注本身有误，说明 frontier 优势不只是偶然波动。1a:T6e4,The setup is intentionally simple. The authors run 21 cells: 7 methods times 3 models, all on LoCoMo conversation conv-26. The methods split into two groups. The memory methods are full context, BM25, Mem0, and Zep. Mem0 and Zep first build a store, then answer each question using retrieved memory. The agent methods are Pi, Codex, and Claude Code. For each question, the agent starts a fresh session with the conversation provided as a file and uses its default tools to inspect the raw record.

The models range from GPT-4o-mini to GPT-6 Luna to Claude Opus 5.5, with high reasoning effort for the stronger two. Cost accounting is more complete than in many small empirical studies: they include build-time calls, question-time calls, agent-loop calls, and embedding calls at list price, excluding only the judge. The target is not just accuracy but the cost–accuracy frontier.

The most informative design choice is the writer–reader decoupling experiment. By default, Mem0 and Zep use the same model to write the store and later read from it. The authors additionally let different models answer from stores written by other models. This directly tests where the bottleneck lives. The result is clear: the quality of the writer sets the ceiling. A stronger reader can exploit a better store, but it cannot reconstruct facts omitted during memory construction. That is a more revealing test than a plain end-to-end comparison.

The paper does not settle that question, but it gives a useful failure mode.1d:T58f,REM (Reusable Experience Memory) introduces three explicit decisions, executed from within the agent’s loop:
1) What to store:
- Each completed run is a 55K–170K token trajectory with heavy exploration noise.
- REM consolidates it into a phase-structured document organized by four phases: localize, understand, fix, verify. This document is both the retrieval unit and the primary injected context, avoiding duplicated token spending.
- The design choice is deliberate: not raw trajectories (too noisy and context-hungry), not atomized factoids (lose solution structure).
2) When to recall:
- Two-tier read path: the phase document is injected at task start; a much costlier “implementation record” (fine-grained details closer to the original trace) is withheld.
- A struggle-gated in-loop node injects the implementation record only when the running agent appears stuck, leveraging the fact that the agent state is observable only inside the loop.
3) What to forget:
- The implementation record is evicted after a single exposure (one-shot eviction) to prevent persistent bias; the phase document remains for the whole run.

The server maintains a shared skill document d and a global experience document e. Each client has private train/validation splits and four LLM-based roles: an executor for task execution, a skill optimizer for local refinement, a sanitizer for privacy cleaning, and an auditor for private-value checking. Instead of uploading a rewritten full skill document, the client generates semantic commits: localized skill patches together with supporting experience summaries.

The pipeline has several stages. First, local skill evolution: the client executes tasks using the current global skill and global experience context, collects local successes and failures, and asks the optimizer to produce revisions. Second, two-stage privacy filtering: a sanitizer rewrites or removes sensitive content, and an auditor checks whether the commit still contains private values or environment-specific details. This is not formal differential privacy; it is semantic privacy filtering performed by LLM agents. Third, cross-round experience reuse: the server maintains a global experience document that accumulates reusable evidence over rounds and redistributes it to clients, reducing redundant rediscovery and making local optimization more informed. Fourth, experience-aware aggregation: the server uses a merge agent to combine commits with reference to the global experience document, rather than simply concatenating or voting over full documents. Fifth, version validation: a candidate updated skill is only published if it passes validation.

Relative to straightforward federated baselines, the key differences are the shift from document-level to commit-level updates, the inclusion of evidence alongside edits, and the explicit use of a shared experience memory.
