9:T7a1,FedSkillGit is explicitly inspired by Git-style incremental collaboration. The server maintains a shared skill document d and a global experience document e. Each client has private train/validation splits and four LLM-based roles: an executor for task execution, a skill optimizer for local refinement, a sanitizer for privacy cleaning, and an auditor for private-value checking. Instead of uploading a rewritten full skill document, the client generates semantic commits: localized skill patches together with supporting experience summaries.

The pipeline has several stages. First, local skill evolution: the client executes tasks using the current global skill and global experience context, collects local successes and failures, and asks the optimizer to produce revisions. Second, two-stage privacy filtering: a sanitizer rewrites or removes sensitive content, and an auditor checks whether the commit still contains private values or environment-specific details. This is not formal differential privacy; it is semantic privacy filtering performed by LLM agents. Third, cross-round experience reuse: the server maintains a global experience document that accumulates reusable evidence over rounds and redistributes it to clients, reducing redundant rediscovery and making local optimization more informed. Fourth, experience-aware aggregation: the server uses a merge agent to combine commits with reference to the global experience document, rather than simply concatenating or voting over full documents. Fifth, version validation: a candidate updated skill is only published if it passes validation.

Relative to straightforward federated baselines, the key differences are the shift from document-level to commit-level updates, the inclusion of evidence alongside edits, and the explicit use of a shared experience memory. That makes the system closer to collaborative knowledge editing with validation than to standard federated averaging.a:T63a,The paper reports experiments on three datasets and three LM families. The headline result is that FedSkillGit outperforms the strongest baseline by up to 22% and approaches centralized performance. From the provided full-text excerpt, the most reliable takeaways are as follows.

First, overall effectiveness: the gains appear across multiple datasets and backbones, suggesting that the improvement is not tied to a single model family or task distribution. The paper positions the method against federated baselines that evolve and aggregate full skill documents, and the reported gap indicates that the update representation itself matters.

Second, communication and privacy motivation: because the method transmits semantic commits rather than full documents, the communication cost should scale with newly acquired knowledge instead of accumulated skill length. When reading the full paper, the most important tables and plots to verify are communication curves, average commit size, and how document growth behaves over rounds.

Third, ablations: the architecture strongly suggests useful ablations around removing privacy filtering, removing the global experience document, disabling version validation, and replacing commit-level aggregation with full-document aggregation. FEB-30 contains 30 fact-evolution trajectories spanning 6 diagnostic categories and 3 difficulty levels. The categories are designed to isolate failure modes that extrinsic QA-based evaluation cannot disentangle:
1. C1, LLM Compensation: the memory state is wrong, but the model may still answer correctly.
2. C2, Retrieval Bottleneck: the memory state is correct, but retrieval fails because of lexical mismatch or abstraction mismatch.
3. C3, Classification Accuracy: whether the system correctly classifies observations as create, update, reinforce, or conflict.
4. C4, Synthesis Quality: whether evidence from multiple artifacts is merged into the right fact structure.
5. C5, Temporal Correctness: whether the memory state tracks temporal evolution, retraction, and drift correctly.
6. C6, Multi-Author Attribution: whether source identity is handled correctly in corroboration, conflict handling, and confidence updates.

Difficulty is controlled in a structured way. L1 is close to surface matching, with target claims appearing almost verbatim. L2 embeds claims in more realistic document context. L3 requires inference from multiple statements and includes substantial distractor content.

The most important design choice is what the authors call paradigm inversion. Instead of starting from documents and then annotating facts, they first define the exact atomic claims that should hold at each state of a trajectory, then generate documents from those trajectories. This makes the ground truth deterministic from the start. The pipeline also uses multi-model rotation and three-judge verification to reduce generator-specific artifacts and improve factual consistency.

Evaluation is split into intrinsic and extrinsic metrics. Intrinsic evaluation directly compares the memory store against the state-specific ground truth, using metrics such as claim coverage, update detection, and false update rate. Extrinsic evaluation keeps the usual QA accuracy. The point is not to replace end-to-end evaluation, but to complement it with a unit-test-like view of the memory component itself.d:T5bf,The central empirical result is straightforward: intrinsic and extrinsic evaluations diverge substantially. The paper reports an average gap of 16 percentage points, and 44% of trajectories show what the authors consider a meaningful divergence. By construction, C1 and C2 are the clearest demonstrations of the problem. C1 produces cases where systems answer correctly despite broken memory. C2 produces cases where memory is correct but the final answer is wrong because retrieval fails. Categories C3 through C6 are more diagnostic of internal memory-pipeline behavior, including update classification, synthesis, temporal consistency, and source attribution. Two systems with similar QA scores can therefore have very different internal memory quality.

The first is a persistent context graph. Instead of storing history as a flat sequence of messages, the system keeps messages, tool calls, and full tool results as persistent nodes, preserving chronology and references. This matters because omitted results are not destroyed; they remain recoverable later.

The second is Tool-Flow Analysis (TFA), which is the main technical idea. TFA tracks how values introduced by earlier tool results are reused in later model steps and tool calls. When a later operation uses a value that originated in an earlier result, the system records an execution dependency and treats it as observed reuse. This is different from standard retrieval memory: the signal is not only whether an old chunk looks relevant to the current query, but whether the execution trace has already shown that the old result supports later actions.

The third is the renderer. Before each model invocation, it selects which historical tool results to expose within a fixed token budget. Selection combines three signals: observed reuse, recency, and semantic relevance. Unselected results stay in the graph and can be restored later. This is a more conservative design than aggressive summarization, because summaries often discard details whose importance only becomes clear much later.

A notable design choice is that the paper does not rely on a learned memory controller or model-driven compression policy. It uses explicit structured state plus hand-designed signals. The upside is interpretability and recoverability.
