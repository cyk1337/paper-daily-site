18:T836,The system is built around an Explorer–Builder–Verifier loop, with explicit source evidence as the shared interface. The Explorer–Builder collects browser-observable evidence from a real site under a given scope and budget. The evidence includes page structure, computed styles, element geometry, screenshots, resource references, and before/after observations around interactions. A notable design choice is that different interaction states at the same URL are treated as distinct evidence units. That is necessary if the goal is to reconstruct state transitions rather than static snapshots.

The Builder converts this evidence into a local executable environment: routes, components, shared object relations, state transitions, fixed initial states, reset mechanisms, and task evaluators. The reconstruction target is intentionally bounded by a site contract. The system does not try to infer hidden backend logic beyond what the evidence supports. In that sense, it is closer to contract-bounded replayable reconstruction than to full website cloning.

The Verifier is the key differentiator. It runs independently on frozen candidates and checks them against source evidence and site contracts. When it finds a discrepancy, the system asks whether the available evidence is sufficient to support a concrete correction. If yes, the issue is treated as an implementation bug and sent to local repair. If not, the problem is treated as an evidence gap and triggers targeted recapture from the source site. The updated candidate is then frozen and reverified. This separation between evidence-supported repair and evidence-insufficient recapture is the central mechanism that distinguishes the work from one-shot generative reconstruction pipelines.

The broader design trade-off is clear. The paper avoids the high-quality but low-scale route of manual mirrors, and also avoids purely generative site synthesis that scales but may drift from the source. It chooses browser-evidence-driven reconstruction because the target is a training/evaluation environment, not an open-ended web simulator.19:T70b,The evaluation covers scale, fidelity, and downstream utility.

On scale, the resource pool contains 244 website artifacts across 14 domains and 53 categories. That is enough to show the system is not limited to a handful of showcase sites.

On environment quality, the paper compares against five matched WebHarbor sites and 14 historical states. WebAnything achieves better automated fidelity metrics and wins a blind overall-fidelity audit with 12 wins, 2 ties, and 0 losses. This is an important choice of evaluation target: the paper is trying to preserve source correspondence, so fidelity matters more than raw task success alone. Separate interaction tests are used to characterize functional coverage, which is also the right move because visual similarity does not guarantee executable behavior. The historical analysis identifies evidence-supported discrepancies in 39 pairs across 22 sites, and independently reverifies the resolution of 18 issue records across 6 sites. That part is especially useful because it validates the repair loop, not just the final outputs.

For downstream utility, the environments support 12,984 executed and accepted tasks. The resulting trajectories are used for SFT, improving Qwen3.5-9B on REAL, Odysseys-Easy, and WebArena-Verified Overall. The excerpt provided does not include the exact gains, so the main takeaway is qualitative but still meaningful: the automatically reconstructed environments are good enough to produce training data that transfers to agent performance.

The strongest evidence comes from the combination of three experiment types: fidelity against manually mirrored environments, discrepancy-to-repair records, and downstream SFT gains.
