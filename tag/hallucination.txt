Existing benchmark scores provide unstable diagnostics: upstream capability scores do not reliably predict hallucination, and even benchmarks assigned to the same stage can move in opposite directions. Replacing a length-matched random window with the oracle evidence span improves accuracy by about 17–18 points across all three architectures, roughly four times the effect of substantial frame corruption in the Watching stage. Deployed grounders recover only about one quarter of this available gain. 第二是代码 provenance tracing 工具。作者提出两种追踪方法。其一是基于 control-flow-graph block decomposition 加 git log -L 历史追踪，并处理 rename bridge，用来把代码块级别的变更追溯到具体来源事件。这里的来源不只是用户指令，也包括 AI 的自发发现和自我修正。其二是 session transcript mining，从工具调用日志中恢复那些在 session 内已经被修正、因此不会出现在 commit 历史里的代码生成错误。这个点很关键，因为只看 git history 会低估模型犯错率，尤其低估“先写错、再自救”的频率。

第三是三套 taxonomy。用户指令 taxonomy 扩展了 Tang 等人的 IDE-chat 分类，使其适用于多轮 CLI coding agent 场景，并新增 cross-session coordination 与 correction of AI conduct 两类。commit provenance taxonomy 则把传统软件工程里的 Perfective / Corrective / Adaptive maintenance 进一步拆开，区分“为什么改”和“怎么发现要改”。response reliability taxonomy 是这篇文章最有新意的部分之一：作者不只看代码结果，而是把 AI 对用户的陈述按 reporting / verification、mechanism explanation、root-cause diagnosis、design fix proposal 等类型分类，再用软件工件去核验这些陈述是否准确。

第四是基于上述工具和 taxonomy 的过程分析。作者把开发过程区分为 proactive 与 reactive 两类触发机制，前者是主动扩展、规划、实现，后者是对 bug、测试失败、异常现象的响应。这样做的目的，是理解 AI coding agent 到底是在“持续前进，偶尔修错”，还是“频繁出错，被动补洞”。全文结论偏向前者，但同时指出中间错误并不少。1a:T9c8,The work has four technical components. First is the Extractor dataset itself. The target project is a real reverse-engineering tool that recovers protobuf descriptors from Apple Objective-C / Mach-O binaries. It is not a toy repository. The project contains 21,000 lines of production Python code, a similarly sized test suite, 210 commits, 25 sessions, and 678 user instructions. All code, tests, and commits were authored by Claude models, with no human-written code. The value of this setup is completeness: it preserves the full development process rather than a thin slice of it.

Second are two provenance-tracing tools. One combines control-flow-graph block decomposition with git log -L history tracing, including rename bridging, to map code changes back to specific source events. Those events include user instructions, autonomous discoveries, and self-corrections. The other mines session transcripts and tool-use logs to recover code-generation errors that were fixed within a session and therefore never appear in commit history. This is a key methodological point. Commit-only analysis systematically underestimates how often the model first writes something wrong and then repairs it.

Third are three taxonomies. The instruction-intent taxonomy extends Tang et al.’s IDE-chat taxonomy to multi-turn CLI coding-agent interaction and adds categories such as cross-session coordination and correction of the AI’s own conduct. The commit-provenance taxonomy extends the standard Perfective/Corrective/Adaptive maintenance framing by separating why a change was needed from how that need was discovered. The response-reliability taxonomy is one of the more original parts of the paper. Instead of only checking code outcomes, the authors classify the agent’s user-facing claims into categories such as fact reporting, mechanism explanation, root-cause diagnosis, and design-fix proposal, then verify those claims against the software artifacts.

Fourth is the process analysis built on top of these tools. The authors distinguish proactive development from reactive development. Proactive work means planning, extending, and implementing ahead of failures. Reactive work means responding to bugs, failed tests, or observed problems. This framing helps answer whether the agent mostly advances the project and occasionally repairs mistakes, or whether it is mainly patching its own failures. The paper finds more of the former, but with a nontrivial amount of hidden intermediate error.1b:T716,The key results come from full-process annotation rather than final-repo statistics. On scale, the project contains 21k lines of production code, a roughly comparable test suite, 210 commits, 25 sessions, and 678 cleaned user instructions. On interaction patterns, CLI-based coding-agent instructions differ from prior IDE-chat datasets by putting more weight on comprehension, planning, and consultation rather than one-shot code requests. On development dynamics, 86–90% of commits and 89–90% of code blocks trace back to proactive triggers rather than reactive responses to bugs or failed tests. In this case study, development is mostly forward-moving rather than purely error-driven.

The most informative numbers are about hidden errors and conversational reliability. By mining transcripts rather than only commits, the authors estimate that 14.3% of AI code-generation events contain a real error that is later caught by the AI-authored test suite before any commit is made. Standard commit-based analysis would miss these errors entirely.
