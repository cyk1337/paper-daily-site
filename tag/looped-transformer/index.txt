18:T6cd,The model is a Parcae-style looped Transformer. Inputs pass through a Prelude, then the same Core blocks are applied recurrently multiple times, with the input representation injected at every iteration, and a Coda plus LM head produces next-token logits. During training, each sequence samples a forward depth T_i from max(1, Poisson(16)); evaluation mainly uses T_eval = 16. The control variable is the backward window k: gradients are retained only through the final min(k, T_i) iterations, while earlier iterations are executed in the forward pass and detached at the boundary. This keeps the forward computation and inference architecture fixed, changing only gradient depth and per-update training cost.

The main contribution is the experimental protocol rather than a new model. At each budget, the authors run two paired comparisons. Equal-token comparisons train different windows on the same amount of data, isolating per-token efficiency. Matched-time comparisons allocate approximately the same training time to each window, allowing the shorter window to take more updates because each update is cheaper. Paired runs share random seeds, and the forward-depth distribution, architecture, and inference iteration count are held fixed. This lets the paper separate the benefit of deeper backprop itself from the benefit of simply training longer.

The primary comparison is K4 versus K8, with additional K6 and FULL controls. An important detail is that “extended training” means a full recipe adjusted to the larger update count, including a rescaled learning-rate schedule, not just naively appending extra steps. That matters because in realistic pretraining, the value of extra updates depends strongly on schedule design.19:T650,There are two model scales. The main configuration has about 144M parameters with width 768 and a 2/2/2 Prelude/Core/Coda layout. A larger configuration has about 388M parameters, width 1024, and 4/4/4 blocks. Training uses a document-deduplicated FineWeb-Edu subset, sequence length 1024, and the main metric is test NLL, with downstream checks on CORE (22 tasks) and LAMBADA.

Four findings matter most. First, at the smaller training budget, K4 beats K8 in matched-time comparisons across all seeds: shallower backprop plus more updates is the better use of limited time. Second, when the budget is increased by 4x, the K4 advantage shrinks on every seed evaluated at both budgets. The paper presents this as a robust trend, not a one-off fluctuation, and reports the same direction under different learning rates and model configurations. Third, equal-token controls confirm that K8 is genuinely more efficient per token: if token count is fixed, deeper backprop learns more from the same data. Fourth, the shift in matched-time preference comes from both components getting smaller with scale, but extended-training gains shrink more than per-token-efficiency gains. In other words, as budget grows, “doing more updates” becomes less valuable faster than “learning more from each token,” making longer windows relatively more competitive.

The abstract excerpt does not expose the full numeric tables, but the body supports a clear conclusion: the best backward window is not budget-invariant. Choosing a recipe from a single-budget or fixed-token comparison can be misleading for larger-scale training.1a:T85e,方法由三个部件组成。第一，候选块构造。给定当前前缀 p，先用浅层或当前可读出的预测得到一个 head token h，然后在 p∥h 中做 suffix matching，寻找此前上下文里与末尾后缀最长匹配的位置；从该位置向后复制最多 K 个 token 作为 tail，形成候选块 B=(b0,...,bk)，其中 b0=h。若找不到匹配，就退化成单 token 块。这里借鉴了 prompt lookup decoding 的思路，但不是直接把复制结果当最终输出，而是把它当 speculative proposal。

第二，浅层筛查。候选块整体先推进到 screening depth ds，而不是直接跑满总深度 D。在 ds 处，用每个前驱位置的 shallow next-token prediction 去检查后继 copied token 是否一致。具体是找从 head 开始的最长连续通过前驱预测校验的前缀；通过的部分保留，后缀立即裁掉，并释放其 KV / hidden state。这个设计比最终深度才发现错误更省，因为错误复制通常会在较早位置暴露，没必要让整段错误 tail 继续消耗深层 recurrent 计算。

第三，连续调度与因果提交。保留下来的 token 继续向更深层推进，同时最近一个保留位置立刻作为下一块的起点，允许新块在旧块尚未 full-depth 验证完成时进入流水线。最终只有达到 full depth 的位置才按因果顺序提交输出。论文强调，真正的收益来自 shallow screening 和 continuous scheduling 的配合：如果只是筛查但不让新块提前进入，流水线填充不足；如果只连续推进但不筛查，错误复制会污染后续深层计算，浪费算力。

First, block construction. Given a prefix p, the model predicts a fresh head token h. Then CopyLoop performs suffix matching over p concatenated with h, looking for the longest matching suffix in earlier context, similar in spirit to prompt lookup decoding. From the matched location it copies up to K following tokens as a tail, producing a candidate block B=(b0,...,bk) with b0=h. If no useful match exists, it falls back to a single-token block.

Second, shallow screening. Instead of sending the whole candidate block directly through the full recurrent depth D, the block is advanced only to a screening depth ds<D. At that depth, each copied token is checked against the shallow next-token prediction of its immediate predecessor. The algorithm keeps the longest prefix of copied tokens that agrees with predecessor predictions and prunes the remaining suffix immediately, including its KV and hidden-state footprint. This is the key efficiency move: copied tails are cheap to propose, but many are partially wrong, so the method tries to detect disagreement before deep recurrent compute is spent.

Third, continuous scheduling with causal commitment. Tokens that survive screening continue toward full-depth verification, while the latest retained position immediately seeds the next candidate block. This allows newer blocks to enter the pipeline before earlier ones finish full verification. Final outputs are still committed only in causal order once they reach full depth. The paper argues that the gain comes from the interaction between shallow screening and continuous scheduling: screening alone saves some wasted deep compute, but scheduling is what turns that into latency reduction; scheduling alone would let many bad copied tails consume deeper passes.

Compared with prior self-speculative decoding, the differences are clear. Drafts are not generated token by token from intermediate passes; they are block proposals composed of one fresh head plus a copied tail. Verification is not only a final accept/reject step; there is an explicit shallow recurrent filter. And the execution pattern is a recurrent pipeline rather than a clean two-stage draft/verify setup.
