9:T7f3,ASIL is presented as an agent-native interaction layer rather than a single backend. The core design choice is to expose software through the deepest feasible access path available for each application. On the observation side, the agent receives a structured JSON object containing task metadata, application state, interactive elements, environment context, navigation structure, and a concise textual summary. On the action side, the agent emits a schema-constrained JSON action with explicit type, target, and parameters. The key shift is from “where to click” to “what to modify / invoke / export.”

The implementation is organized around three realization paths:
1. file-based access, where structured file formats are read and modified directly;
2. scripting-based access, where native scripting runtimes or automation APIs are used;
3. service-based access, where backend APIs or service endpoints expose semantic operations.

The paper emphasizes four design principles: completeness, semanticity, stability, and composability. Completeness addresses the partial observability of screenshots. Semanticity aligns actions with meaningful software operations. Stability avoids UI-dependent identifiers and layout drift. Composability allows complex tasks to be solved through a sequence of higher-level operations rather than long GUI event chains.

A notable systems contribution is the onboarding framework: reviewed interface profiles are compiled into validated adapter contracts. This makes ASIL more than a one-off wrapper. It resembles tool schemas or MCP-style interfaces, but with a stronger emphasis on state observability and action closure.

Importantly, ASIL is also treated as a trainable environment. The authors run small-scale SFT followed by resource- and time-limited on-policy RL. Because states and actions are structured and directly checkable, reward design and rollout efficiency become much cleaner than in screenshot-and-click settings. That is the part most relevant to agent training dynamics.a:T689,The evaluation has three layers. First, the environment and benchmark: ASIL is instantiated across 15 applications, with 300 single-application tasks and 80 multi-application tasks. The authors also render GUI snapshots from the underlying software state at every step, so ASIL and screenshot-driven agents can be compared under the same task definitions and validators. This is an important design choice because it controls for task specification while changing only the interaction interface.

Second, the interface comparison: the abstract reports that ASIL reaches above 80 with closed models on the benchmark. The paper also includes repaired GUI / 50max results, matched native-interface baselines such as LibreOffice UNO and draw.io MCP, and independent validity checks to bound the comparison. The main empirical message is not just higher end performance, but shorter and more stable trajectories. GUI agents pay a large step budget and are fragile to grounding, focus, timing, and layout errors. ASIL compresses many multi-step GUI procedures into one or a few semantic actions.

Third, the training results: the authors run small-scale SFT plus resource-limited, time-limited on-policy RL on Qwen3.5-2B and Qwen3.5-9B, and report double-digit gains. They further confirm the trend on a curated 80-task hard suite. There is also an ablation over realization patterns, comparing file, scripting, and service access routes.
