18:T624,SkillGym is built around a skill-to-task pipeline. The input is a registry of human-written skills spanning 12 major categories and 63 sub-categories. Each skill is first organized into a structured skill card containing descriptions, examples, pseudocode or scripts, and execution constraints. For each sub-category, the authors manually design reusable templates that instantiate concrete tasks from these reusable workflows, including input assets, interaction interfaces, target conditions, and code-based verifiers. This turns a static skill document into an executable environment.

A key design choice is contrastive validation. Under a reference agent configuration, the system runs tasks with and without the target skill and keeps tasks that show empirical skill dependence. This matters because many tasks associated with a skill document may still be solvable by generic capability alone. Without this filtering step, the resulting supervision would overstate the contribution of the skill itself.

Once environments are validated, the authors collect successful trajectories using multiple teacher models and harnesses. These trajectories can support supervised fine-tuning and outcome-based reinforcement learning. The paper mainly demonstrates the SFT path: verified long-horizon workflows are used to fine-tune Qwen3.5-35B-A3B into SkillGym-Agent. The novelty is less about a new RL algorithm and more about closing the loop from human workflow documents to instantiated tasks, verifiers, contrastive dependency checks, and high-quality interaction traces.19:T670,The scale of the resource is substantial: 2,756 environments across 12 major categories and 63 sub-categories, plus 8,364 successful trajectories. Each trajectory averages 49 tool calls and more than 60k logged text tokens, which indicates genuinely long-horizon, multi-tool interaction rather than short completion-style supervision.

On the model side, supervised fine-tuning of Qwen3.5-35B-A3B on these trajectories yields broad gains over the base model. The abstract reports, under Claude Code, +199 Elo on GDPval-AA v2, +19.10 percentage points on Terminal-Bench 2.1, and +28.13 / +12.38 points on SkillsBench v1.1 with and without skills, respectively. Another notable result is that on skill-assisted SkillsBench, the 35B model reaches 51.47%, exceeding the reported scores listed in the paper for Claude Sonnet 4.6, GPT-5.4 Mini, and DeepSeek V4 Pro (Preview). The more interesting claim is not the leaderboard comparison, but that the trained model still outperforms its skill-assisted base even when no inference-time skills are provided. That supports the paper’s central argument about internalization rather than better external skill usage.

When reading the full experiments, the most important checks are: (1) whether gains are consistent across harnesses, so the result is not an artifact of one execution stack; (2) how much improvement remains in the no-skill setting, which is the cleanest evidence of reusable procedural competence; and (3) ablations on environment filtering and teacher sampling, to verify that the benefit comes from skill-dependent verified trajectories rather than simply adding more long-form SFT data.1a:T51e,For a first pass, start with Figure 2 and the main SkillGym pipeline. Once you understand the five stages—skill cards, template instantiation, verifiers, contrastive skill-dependence filtering, and trajectory sampling—the method is mostly clear.

Then read the environment construction details. The most important parts are the template design and verifier implementation, because they determine whether the tasks are executable, scorable, and scalable. If your interest is data generation rather than benchmark ranking, this section matters more than the final headline numbers.

In experiments, prioritize Table 4 and the SkillsBench results. The key questions are not the absolute scores, but whether the model still improves without inference-time skills and whether the gains hold across different harnesses. Those two points are the strongest support for the internalization claim.

A 20-minute skim is enough to capture the main idea. If you work on agent post-training data pipelines, spend more time on the appendix examples, failure cases, and the teacher/harness combinations. For a pretraining-focused reader, the paper is best read as a case study in converting high-quality human procedural knowledge into verifiable training signals rather than as a directly transferable pretraining recipe.1b:T5ce,The interaction pattern is locate-correct-continue. An annotator reads a model response and marks the first inappropriate token. onPanda shows the model's top-k candidate tokens and probabilities at that position, with k defaulting to 20. If a suitable replacement is available, the annotator selects it; otherwise, the annotator writes a free-form replacement. The system truncates all later text and continues generation from the corrected prefix. The process repeats until the response is acceptable.

This differs from standard post-editing because the annotator does not repair a completed response after the model has already drifted. The continuation is re-rolled from the corrected prefix, so most final tokens remain model-generated. Each correction also creates a local supervision record: the bad token, the replacement, the prefix, and the model's candidate distribution. These records can be converted into SFT data, DPO pairs, reward-model data, or process-level supervision. Implementation-wise, onPanda is a componentized front-end library. It can run as a static web app or be embedded in an existing annotation platform. It requires an inference API that can continue from an assistant-message prefix and return token logprobs. A full annotation session is serialized into a single .panda.json file. For agents, it can access tools through MCP and connect to harnesses such as Claude Code, Codex, and OpenClaw, allowing corrected tool calls to be executed in the loop.1c:T4be,The study builds a controlled customer-support workflow setting. The dataset covers 130 workflows, each with a domain policy, tool schemas, and user goals. Two GPT-5 instances are used to generate multi-turn conversations, one acting as the user and the other as the workflow agent. From 1800 generated conversations, Claude-4.5-Opus and Gemini-2.5-Pro independently filter for logical consistency, missing steps, and policy compliance; 1027 conversations remain. Assistant decisions are converted into next-action examples. The training split contains 5834 examples, with 4093 text responses and 1741 tool calls; the validation split has 664 examples. The held-out evaluation split contains 84 conversations and 542 next-action examples, including 376 text decisions and 166 tool calls. The model comparison uses Qwen3 4B/14B and Gemma 3 4B/12B before and after full SFT with the same five-epoch recipe. The evaluation protocol separates text similarity, gold-history turn success judged by Gemini-2.5-Pro, tool behavior, and closed-loop autonomous execution. This separation is the main technical design choice: it makes the difference between local correctness and trajectory-level state maintenance observable.1d:T7bf,The method is deliberately simple but well targeted. The authors define two axes. Direct rate (DR) measures how often the model repeats its top answer over 30 samples of the original prompt at temperature 0.6. This captures concentration under one wording. Framed rate (FR) then asks whether that same direct top answer survives 30 matched scenario reframings of the underlying question. Importantly, FR is not the concentration of answers under reframing; it is the reappearance rate of the original direct top answer. That design choice is the core of the paper, because it measures persistence of a specific preference rather than generic consistency. The final bias depth score is π = DR × FR, which is high only when the model is both concentrated under direct prompting and robust to reframing.

The dataset construction is also central. They build 4,442 opinion prompt families, each grounded in a real Olmo-3-7B-SFT training example, and create matched everyday-scenario reframings for each family. Because the task is open-ended generation rather than multiple choice, answer normalization is necessary to merge semantically equivalent outputs and avoid contaminating FR with superficial phrasing variation. The contribution is therefore less about a new model and more about turning a causally meaningful question—does a preference survive paraphrastic and situational variation?—into a scalable evaluation protocol.
