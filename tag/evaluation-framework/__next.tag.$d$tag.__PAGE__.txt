a:T772,The technical contribution is an automated evaluation pipeline rather than a new agent architecture. The system has three main components. First, framework collection and isolation: the authors gather 51 Python ADKs and run each inside its own Docker environment to avoid dependency conflicts and cross-framework contamination. Second, an LLM-as-a-Developer loop: given a benchmark task and a target framework, the coding model studies the framework through documentation, source code, or both, writes agent code, and enters a validate-and-feedback repair cycle. Third, a three-level validation pipeline: basic import and syntax checks, framework-level execution checks, and finally execution on real benchmark tasks. This staged design separates “can the code run at all” from “does it solve the task,” which reduces noise from trivial failures.

A strong design choice is that the generation process itself is treated as a first-class evaluation signal. The system logs token usage, number of turns, repair attempts, failure types, and dollar cost. As a result, the output is not just a task score but a joint measure of performance and development effort. Another important component is the information-source ablation. The developer model is tested with docs only, source only, both, or neither. This is necessary because many popular frameworks are already partially memorized by frontier coding models. Without this ablation, it would be unclear whether the model is actually learning from the provided materials or simply recalling APIs from parametric memory.

The method does not remove every confound. Results still depend on the coding model, its search and repair behavior, context budget, and the benchmark mix. The paper’s stance is more practical than idealized: keep the developer and execution protocol fixed so that framework differences become the dominant source of variation.b:T8e9,The evaluation covers 51 frameworks and 4 benchmarks, for 204 framework-benchmark pairs. The benchmark suite spans software engineering, conversational tool use, multi-tool orchestration, and terminal interaction, which gives a broader view than a single micro-benchmark.

Three findings stand out. First, development cost varies widely. The cost to reach a working agent differs by about 5.6x across frameworks, roughly from $0.6 to $3.4 per agent. The paper interprets this as a combined signal of API complexity, documentation quality, and abstraction design. Frameworks such as LangGraph and OpenAI Agents are among the cheapest to target, while larger or less coherent frameworks are much more expensive. Second, final task performance is highly dispersed. The best single-benchmark ADK agents reach around 80% resolution, while the median framework is only around 32%, so there is no universally dominant framework. Third, the model that writes the agent matters more than the model that runs it. Agents authored by stronger coding models such as Opus resolve roughly twice as many tasks as GPT-authored agents on the same execution backbone. That is an important systems result: coding-time model quality has a persistent downstream effect through code structure, API usage, and error handling.

The information-source ablation is also informative. Documentation, source code, and parametric knowledge are not equivalent, but the gap is smaller than one might expect. Genuine framework usage success stays in roughly the 28% to 40% range, with raw source access performing best. Even with no reference material, about 33% of agents still pass. This suggests that many framework APIs are already partially internalized by coding models, and that source code often provides more actionable grounding than polished documentation because it exposes real call paths, signatures, and defaults.

A limitation is that the paper, at least from the provided content, does not fully unpack variance across repeated runs, sensitivity to developer-model settings, or confidence intervals per benchmark. Those details matter for ranking stability.
