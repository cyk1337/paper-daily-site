18:T41a,The paper introduces Approval Laundering as a taxonomy of approval–execution binding failures. It organizes the space into six failure modes: Scope, Argument, Temporal, Tool, Delegation, and Semantic laundering. The unifying idea is that a human approves action A under an explicit policy, but the harness executes A' without requesting renewed approval. The contribution is primarily formal and empirical rather than algorithmic. The authors define a falsifiable approval policy, distinguish it from subjective operator intent, and then design reproducible tests around different credential-binding surfaces. A key point is that many failures do not involve the model changing the literal command string at all. Instead, the mismatch arises from repository-local hooks, session-scoped grants, tool indirection, delegated execution, or UI/rendering mismatches that alter the downstream effect of an otherwise approved action. This makes the work different from prior benchmarks centered on command risk classification or over-broad scope inference.19:T551,The method is simple, but the experimental control is strong. Mid-Harness keeps the generator, execution harness, and serving setup unchanged. It only inserts an intermediate wrapper: given the same interaction history, sample several candidate actions, apply a verifier, and forward only the selected action to the original harness. This makes it possible to separate two questions: whether the generator already contains useful alternatives, and whether a verifier can identify them before execution. The paper varies candidate width, verification mechanism, and verifier capability. A key setting is self-verification, where the same model both generates and verifies. In that regime, wider sampling helps little, which indicates that the bottleneck is discrimination rather than candidate diversity. The paper compares pointwise and pairwise verification and finds pairwise comparison works best, likely because candidate actions differ in intent, semantics, and environmental fit in ways that are easier to judge relatively than absolutely. The authors then distill a verifier initialized from the generator using pairwise judgments from GPT-5.6 Sol, while leaving the action generator unchanged. This is a useful design because it separates the upper bound enabled by a strong verifier from the portion that can be recovered by a practical local verifier.1a:T555,The main experiments use a fixed TMAX-9B generator on TerminalBench-Lite. There are three key findings. First, with a strong verifier, GPT-5.6 Sol raises Pass@1 from 50.00% for the base agent to 68.03%, showing that the generator already produces many useful alternatives that the default pipeline fails to select reliably. Second, under self-verification, increasing candidate width yields only marginal gains, and pairwise verification is the best among the tested mechanisms. Third, distilling a verifier from GPT-5.6 Sol pairwise responses improves Pass@1 from 54.76% to 57.14% without changing the generator. The gain is smaller than using the frontier verifier directly, but it confirms that part of the opportunity can be recovered through verifier training alone. The disagreement analysis is also informative: the main remaining gaps are command semantics and execution feasibility, meaning the verifier still struggles to predict what a command will actually do and whether it will work in the current environment. The paper also shows compatibility with trajectory-level scaling. Mid-Harness improves both parallel scaling with Best-of-T trajectories and sequential scaling with Sequential Refine. In particular, TMAX-9B plus one round of Sequential Refine and Mid-Harness outperforms Best-of-T at T=7 while using less than half the estimated token cost.1b:T7f5,The method is an executable contract audit. Instead of starting from the benchmark paper’s informal description, the authors derive a contract from the surfaces visible to the agent and the evaluator: prompt templates, tool schemas, return-value semantics, task files, and grader code. Each contract clause is provenance-bound, meaning it cites the exact interface surface it operationalizes. This is an important design choice because it prevents the auditor from silently adding unstated assumptions.

The checker operates over tuples of (pre, post, args, result), one per probed call or call sequence from a fresh environment. The paper defines six executable defect classes as typed rules at the tool boundary. Two of them are especially notable. Phantom Effect captures the case where the tool reports success for an advertised effect that did not materialize in state. Partial Effect captures incomplete realization of a promised effect. The authors note that these classes are absent from surveyed benchmark-audit taxonomies. Another class, Ignored Argument, is deliberately defined as a state-based rule rather than a conjunctive state-plus-message rule, because some tools interpolate the argument into a success string while dropping it from state; a stricter textual condition would miss exactly the defect of interest.

The implementation combines static and dynamic checks through benchmark-specific adapters, with manual reading where no adapter is possible. The second key component is score-at-risk tracing. After identifying a defect, the audit follows the benchmark’s own evaluator code to determine which task verdicts depend on the defective state or return path, and whether the evaluator’s basis is state, result text, or another proxy. The validation protocol is stronger than a typical code audit: injected defects, negative controls with pre-specified expected verdicts, gold replays, and constructed trajectories showing that the shipped evaluator can reward the defect while failing to reward the repair.1c:T516,The audit covers 34 mutating tools across four benchmarks. At pinned commits, the authors confirm seven tool defects and one evaluator property, with at least one benchmark-class, agent-visible finding per benchmark. They also run a blind audit on 12 additional AgentDojo tools and uncover one previously unflagged defect. With six held-out tools plus seven audited earlier, they complete the 25-tool surface for that benchmark and report that at least five tools diverge from their advertised contract.

The most informative result is not a single aggregate metric but the defect-to-score linkage. In the MedAgentBench case, the POST path returns an agent-visible message equivalent to “accepted and executed successfully,” yet the repository code does not perform the write. The benchmark’s write-task grader then treats that success path as evidence. The validation section further shows the checker’s operating boundary: some defects are missed by static inspection alone and require dynamic state comparison; some shipped evaluators positively reward defective behavior and fail to recognize repaired behavior on constructed trajectories. That moves the discussion from “mock environments are simplified” to “the benchmark’s observable contract and scoring basis are misaligned.”1d:T472,Read this as a benchmark-audit methods paper, not as an agent-methods paper. Start with the introduction to understand the target of the audit: not realism in general, but consistency between advertised tool behavior, actual implementation, and scoring. Then go directly to the defect-class definitions around Table II. Phantom Effect, Partial Effect, and Ignored Argument are the conceptual center of the paper.

After that, focus on the three-step pipeline: contract construction, static/dynamic checking, and score-at-risk tracing. Pay attention to why the contracts are provenance-bound; that is what makes the audit reproducible rather than dependent on auditor intuition.

In the empirical section, the per-benchmark case studies matter more than the headline counts. The MedAgentBench write-path example is the clearest illustration of the paper’s claim. If time is limited, read one or two case studies and then the validation setup—especially injected defects, negative controls, and constructed trajectories. That is enough to judge whether the method is careful or merely anecdotal. Estimated reading time: 30–45 minutes.1e:T5de,RLTL;DR has two components. The first changes rollout collection. Instead of K independent parallel attempts, the agent solves the same task sequentially. After each failed attempt, the verifier is run and exposes error messages, failed assertions, tracebacks, or final-state checks. The same policy then reads the failed attempt and verifier output and writes a short TL;DR insight, such as a reminder to paginate search results. The next attempt is conditioned on the original task plus the accumulated insights. This converts some tasks from a zero-success sampling regime into a regime where at least one successful trajectory can be found.

The second component changes optimization. Sequential exploration alone does not solve test-time performance, because evaluation requires a first-attempt solution without any accumulated insights in context. The paper therefore enables backpropagation through the in-context insight tokens, about 17 tokens per insight. The first is a persistent context graph. Instead of storing history as a flat sequence of messages, the system keeps messages, tool calls, and full tool results as persistent nodes, preserving chronology and references. This matters because omitted results are not destroyed; they remain recoverable later.

The second is Tool-Flow Analysis (TFA), which is the main technical idea. TFA tracks how values introduced by earlier tool results are reused in later model steps and tool calls. When a later operation uses a value that originated in an earlier result, the system records an execution dependency and treats it as observed reuse. This is different from standard retrieval memory: the signal is not only whether an old chunk looks relevant to the current query, but whether the execution trace has already shown that the old result supports later actions.

The third is the renderer. Before each model invocation, it selects which historical tool results to expose within a fixed token budget. Selection combines three signals: observed reuse, recency, and semantic relevance. Unselected results stay in the graph and can be restored later. This is a more conservative design than aggressive summarization, because summaries often discard details whose importance only becomes clear much later.

A notable design choice is that the paper does not rely on a learned memory controller or model-driven compression policy. It uses explicit structured state plus hand-designed signals. The upside is interpretability and recoverability.
