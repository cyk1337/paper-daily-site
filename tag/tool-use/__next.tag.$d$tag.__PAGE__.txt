9:T4fc,The paper formalizes executable prefixes and defines a set of metrics.
- A rollout is a tool-invocation sequence τ̂=(a1,…,aT) executed over evolving environment states st.
- An action is executable if: the tool exists, arguments match the schema, explicit preconditions hold, cross-step data dependencies are satisfied (e.g., using an ID returned earlier), and the current environment state permits the action.
- Prefix executability checks whether each prefix (a1…ak) remains executable; aggregating over k yields a survival-style curve.
- Metrics:
  - PEC (Prefix Executability Curve): executability rate as a function of prefix length.
  - FED (First-Error Depth): the step index of the first non-executable action.
  - TER (Trajectory Executability Rate): fraction of fully executable trajectories.
  - Horizon-normalized AUC-PEC: area under PEC for length-normalized comparison.
  - RR (Recovery Rate): whether trajectories recover after entering a failure regime.
- A minimal Dual-Loop planner–verifier is used as a controlled probe (not the main contribution) to demonstrate that terminal-success rankings can diverge from prefix-executability rankings, and that pre-execution validation can improve executability metrics even when final success changes little.a:T6ba,The core artifact is MCP-Injector, a proxy-style middleware inserted between the agent and the MCP server. It does not require modifying the agent runtime, the MCP client, or the tool servers. Instead, it intercepts the call_tool boundary, which gives a clean experimental handle on semantic tool-call failures rather than lower-level deployment noise.

The fault model has three dimensions. The first is failure mode: timing failures versus content failures. Timing failures include delays, hangs, and missing responses; content failures include wrong values, malformed payloads, and schema/type violations. The second is persistence: permanent, transient, and intermittent faults. This is an important design choice because agent recovery behavior depends heavily on whether an error is persistent or bursty. The third is the injection schedule, which specifies when faults occur and is seedable for reproducibility.

A strong point is that the fault mix is calibrated rather than hand-crafted. The authors mine 57,240 issue and pull-request threads from 1,774 open-source MCP repositories and estimate the observed distribution over failure mode × persistence. The injected scenarios are therefore tied to reported ecosystem incidents instead of synthetic worst-case examples.

The evaluation is a full-factorial design: three agent stacks, two backbone sizes, three fault conditions, 25 tasks, and three seeds, for 1,350 experimental cells. The stacks include a custom multi-round plan-and-execute system, OpenAI Agents SDK, and another mainstream framework. This setup is meant to separate model scale effects from framework-level error-handling effects such as retries, exception propagation, and output validation.b:T448,Three findings matter most. First, under calibrated MCP faults, the 120B backbone does not show better fault tolerance than the 20B backbone. It does not retain a larger fraction of its fault-free score and descriptively completes fewer tasks. That is the paper’s central result and the reason for the title. Second, differences across agent stacks are substantial, suggesting that framework-level handling of tool failures matters more than backbone scale in this setting. Third, MCP-Injector itself appears to provide a reproducible and low-intrusion way to evaluate agent robustness under permanent, transient, and intermittent failures without modifying the tested systems.

The paper emphasizes retained share of fault-free performance, task completion counts, and degradation patterns under different fault conditions rather than a single average score. The 1,350-cell design gives the result some breadth.
