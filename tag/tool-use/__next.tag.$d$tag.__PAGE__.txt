9:T852,The method, State-Path Tool Menu, has three components: an encoder, a retriever, and a reranker. Each tool has documentation, required inputs, and produced outputs. A request exposes an initial state s0(q), containing the fields and constraints visible before any tool call. The system must construct an ordered menu of K=32 tools, and the online agent can only use tools from that menu during execution.

The central idea is the state path, a latent pre-execution route from the observable initial state to the desired outcome. Tools on this route are assigned one of four roles: entry tools can run immediately from the initial state, bridge tools create intermediate fields needed later, the target tool resolves the main request, and an optional terminal tool commits or delivers the result. This role decomposition is useful because it separates different notions that relevance-based retrieval conflates: immediate executability, intermediate utility, and final-task alignment.

The encoder learns relation-aware tool representations from the request state, tool schemas, and successful training trajectories. The excerpt explicitly mentions three directional signals: whether a tool can run now, whether it produces fields needed later, and how it depends on other tools in precedence order. So the representation is not just semantic similarity over tool descriptions; it is structured around state compatibility and dependency. The retriever then selects 32 tools that cover complementary path roles rather than simply maximizing top-k relevance. The reranker orders the selected tools so that producers appear before consumers, making the menu easier to execute under the same online loop and call budget.

Training supervision comes from successful trajectories. The retriever is trained with route membership, entry, and path-role targets, while the reranker is trained with slot and pairwise precedence targets. A notable design choice is that the paper keeps the online agent unchanged. The gains are meant to come from better pre-execution menu construction, not from modifying the planner or increasing the budget.a:T4b9,From the available text, the experiments compare State-Path menus against relevance-based menus under a fixed agent and a fixed 32-tool budget. The reported evaluation dimensions include end-task success, complete-chain coverage, and executable entry. The paper also claims comparisons across tool libraries, evaluators, and executor families, plus paired outcomes and controlled variants to isolate whether the gains come from route coverage and ordering.

EvoHarnessBench defines the harness as the set of tools an agent can call, the procedural skills it can reuse, and the specialist agents it can coordinate with. Each harness stream is a sequence of cumulative stages H1 ⊆ H2 ⊆ ... ⊆ HT, so later stages only add capabilities and never remove old ones. Streams are built along three axes: tools, skills, and agents.

Two design choices matter. First, each task is assigned to the earliest stage at which it becomes solvable, and it must require at least one newly introduced capability. This helps separate adaptation to new capabilities from retention of old ones. Second, capabilities are released from common core capabilities toward the long tail, which is meant to mimic real harness growth in deployed systems.

The benchmark supports two evaluation modes. In deployment evaluation, no experience is carried across stages; each harness version is evaluated independently. This isolates the direct effect of harness expansion: does a larger capability pool help, or does it mostly distract? In self-evolving adaptation evaluation, persistent artifacts such as memory, prompts, or learned skills can be updated within each stage and then carried forward, while the underlying model weights remain fixed. This tests whether accumulated experience helps or hinders adaptation under a growing harness.

The benchmark is reasonably large: 17 controlled harness streams, each with 3 to 6 cumulative stages, 802 unique tasks, 1,510 axis-specific evaluation examples, 520 executable tools, 42 latent reference skills, and 62 specialist agents. The paper evaluates representative single-agent and multi-agent systems under both modes.d:T540,The empirical message is mostly diagnostic. First, harness expansion is not free. That is the benchmark’s evidence for harness-induced forgetting. Second, self-evolving adaptation is inconsistent. Gains vary substantially across stages, axes, and environments, which suggests that simply accumulating memory or prompts is not a reliable answer to harness evolution. Third, retention and adaptation often pull in opposite directions: methods that preserve earlier competence better can be worse at exploiting newly introduced capabilities, while methods that adapt aggressively can sacrifice old-task performance.

PMR captures whether the agent keeps checking the dashboard; RAG@K captures whether stated plans are translated into execution.10:T8e7,APEx maintains two levels of experience. Instance-level memory stores summarized execution traces for concrete queries, preserving operational details that can later be retrieved. Category-level skills aggregate many experiences within a category-modality bucket and distill them into reusable procedural guidance. At inference time, a query q is routed to a bucket, relevant memories R_M(q) and the corresponding skill R_S(q) are retrieved, and both are packed into a structured context E(q). The Planner uses E(q) to generate a research plan. The Executor follows that plan through multi-turn tool interaction and produces a trajectory τ and a final answer. After execution, the trajectory is summarized into a new memory entry, and once enough fresh experience accumulates, the Distiller updates the category-level skill.

The key idea is not just hierarchical memory, but the Executor-Distiller-Planner loop. Planner converts retrieved experience into a task-specific plan, Executor interacts with tools, and Distiller abstracts new trajectories into procedural skills. These modules are trained with a three-stage alternating GRPO schedule rather than a single joint objective. The motivation is cross-module credit assignment: if everything is optimized end-to-end at once, it is difficult for final task reward to shape the quality of distilled skills in a stable way. Alternating optimization gives each module a cleaner relative-reward signal while the others are partially fixed. In that sense, skill distillation is treated as reward-guided policy learning, not prompt-based summarization.

Another notable component is skill-guided TTRL. During deployment, the Planner performs test-time reinforcement learning on unlabeled queries, while retrieved skills and memories act as procedural priors that regularize online adaptation. The model is therefore not exploring from scratch at test time; it adapts locally around previously distilled high-quality procedures. The resulting improved trajectories are then written back into memory and can later trigger skill updates. This is the main conceptual difference from standard memory-augmented retrieval: retrieval helps the current sample, but APEx is designed so that the current sample also improves future behavior.11:T64b,The headline result reported in the paper is an average score of 64.4% across deep research benchmarks. This is 14.7 points above GPT-5.4 and 3.0 points above the strongest memory-augmented baseline. For judging the method, the second comparison matters more, because it isolates the gain from experience organization and training rather than from a stronger base model.

The paper also highlights a context-efficiency result: a skill-only variant remains competitive while injecting fewer memory tokens. That supports the claim that category-level procedural skills are a more compact carrier of useful experience than flat trajectory retrieval. This matters for long-context agents, where the bottleneck is often not retrieval quality but context budget and retrieval noise.
