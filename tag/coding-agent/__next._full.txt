18:Ta58,核心方法是 Benchproofer，一条把已有 coding task 连同其已知正确 patch，转成 formally verified instance 的构造流程。它的设计抓住了两个现实约束：一是不能把整个仓库都形式化；二是不能只依赖机械验证，因为规格本身可能写错。

第一部分是局部建模。Benchproofer 只对新增或修改的代码建立形式规格和证明，而不是试图验证整个代码库。对于修复代码调用但未修改的现有函数，系统不去展开其实现，而是为这些 callee 写 axioms，也就是对调用方真正依赖的性质做过近似摘要。这样做的原因很直接：如果要求把所有依赖函数及其传递闭包都证明一遍，SWE-bench 级别任务几乎不可操作。axiomatization 把验证边界收缩到 patch 附近，使问题规模可控。

第二部分是多后端验证表示。SWE-Proof 为每个实例提供三种验证后端：Nagini（面向静态类型 Python 验证）、Velvet（Lean 上的命令式验证 DSL）和纯 Lean。这里不是简单换语言，而是覆盖了不同验证风格：SMT 驱动的程序验证，以及需要显式写 proof 的 theorem proving。这样能区分“代码逻辑是否容易规格化”和“证明搜索是否成为瓶颈”。

第三部分是 admission pipeline，也就是机械门和对抗门联合筛选。一个候选实例只有在多重 gate 都通过后才会被收入 benchmark。机械 gate 包括规格、实现和证明在对应后端上的可检查性；对抗 gate 则用 LLM 审计规格是否 faithful，是否遗漏需求、过度放宽、或允许错误实现通过。作者特别强调 dominant failure 是 faithfulness failure：规格只约束了部分行为，把剩余关键语义留空。这一点很重要，因为形式验证只能保证“满足规格”，不能保证“规格就是用户想要的东西”。

第四部分是评测协议。作者不仅评估模型直接修 patch，还比较了几种设置：只给自然语言 issue；给结构化自然语言 specification；让模型自己写 specification 再验证；以及直接提供正确 formal specification。这个设计把“patch synthesis”和“specification synthesis”两个子问题拆开，因而能定位真正瓶颈。

从方法取舍看，这篇工作的关键不是发明新的 verifier，而是把形式方法嵌入真实软件工程 benchmark，并用环境 axiomatization + adversarial audit 让它可落地。相比传统 hidden tests，它牺牲了构造成本，换来更强的 correctness oracle；相比端到端全仓库验证，它牺牲了全局完备性，换来可扩展性。19:T92a,The core method is Benchproofer, a pipeline that converts a coding task with a known correct patch into a formally verified benchmark instance. The design is built around two practical constraints: full-repository verification is infeasible, and mechanical verification alone is not enough if the specification itself is wrong.

First, Benchproofer uses local modeling. It formally specifies and verifies only the new or modified code. Calls into unchanged functions are handled through axioms: over-approximate summaries of the properties the patch relies on. This is the key scalability move. Without it, one would need to verify the entire transitive closure of dependencies, which is unrealistic for SWE-bench-scale tasks.

Second, the benchmark supports three verification backends: Nagini for statically typed Python verification, Velvet as an imperative-style verification DSL in Lean, and pure Lean where proof obligations are discharged by proof writing rather than an SMT solver. This is useful because it separates different sources of difficulty: specification quality, program verification, and proof search.

Third, the construction pipeline uses both mechanical and adversarial admission gates. A candidate instance is admitted only if the spec, implementation, and proof check mechanically in the target backend, and if adversarial LLM auditors judge the specification to be faithful to the original task. This is an important design choice. Formal verification only guarantees conformance to the spec, not that the spec captures the intended behavior. The paper identifies faithfulness failures as the dominant issue: a spec constrains part of the required behavior while leaving critical semantics unconstrained.

Fourth, the evaluation protocol disentangles patch generation from specification generation. The paper compares several settings: solving from the natural-language issue alone, adding a structured natural-language specification, asking the model to synthesize a specification and verify against it, and supplying the correct formal specification. This makes it possible to localize the real bottleneck.

The contribution is therefore not a new verifier. It is a practical recipe for embedding formal methods into realistic software-engineering benchmarks using environment axiomatization plus adversarial auditing.1a:T608,SWE-Proof covers all 500 instances of SWE-bench Verified and extends to the Python fragment of SWE-bench Pro. Each instance includes a ground-truth formal specification, implementation, and proof, under three verification backends. For realistic repository-level verified coding tasks, this is a substantial benchmark asset.

The evaluation uses Claude Opus 4.8 and GPT-5.5. The main findings are sharp. First, passing all hidden tests is not a reliable correctness signal: roughly 25% to 50% of such patches are still flawed. Second, adding a structured natural-language “specification” does not close that gap, which shows that informal constraints remain too weak. Third, asking the model to synthesize a specification and then verify against it does not improve over the unaided baseline. But when the correct formal specification is supplied, performance rises substantially: Opus 4.8 goes from 85.0% to 95.1%, and GPT-5.5 from 81.2% to 94.7%.

The most informative analysis concerns specification quality. Only 62% of synthesized specifications survive adversarial audit. The dominant failure mode is lack of faithfulness. The correlation with task success is strong: 89% of specifications from unresolved instances fail the audit, compared with 47% from resolved ones. This makes specification synthesis the central unresolved problem.

From a reward-design perspective, the paper also carries a warning: formal verification is only as good as the specification. A wrong spec can turn a seemingly strong oracle into a misleading one.1b:T58f,Although marked skim, this is worth reading a bit more carefully if you care about coding RL verifiers.
