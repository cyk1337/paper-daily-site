19:T85b,方法上有三个关键设计。其一是 extractive compression：模型不是重写代码和工具输出，而是从输入段落中选择要保留的 span，并配合一组固定的结构标记表示删除区域。这样做的目的很明确，不是追求语言自然，而是尽量保证 identifier、path、number、error string 这类 downstream edit 依赖的精确字符串不被改坏。文中对这一点做了审计，训练语料上 96.0% 的 identifier/path/number 来自输入拷贝，held-out SWE-bench Lite 上是 96.2%；如果排除作者刻意允许改写的一类对象，这个比例到 98.3%。

其二是 intent conditioning。每次压缩不是只看 segment 本身，而是同时输入当前任务 query，让模型优先保留 query 中点名的实体、文件、函数、报错线索。作者强调“什么重要”不是静态属性，而是相对当前 agent 目标定义的，这也是它和通用压缩器的主要区别。

其三是 pipeline 设计。系统先做 segmentation、kind classification 和 level labeling，再按 segment 单独压缩。压缩模型只看到 task + 单个 segment + kind/level tag，不直接接收数值 token budget；预算通过 system prompt 中的 level-to-ratio 表间接传达。作者原本设计了四级重要性标签 L0-L3，并希望不同 level 对应不同压缩率，但实验发现蒸馏后的 student 实际只学出了两个有效压缩带宽，四级设计没有按预期落地。这个负结果作者没有回避，反而是全文里比较有价值的部分。

数据方面，作者从 67,074 条 OpenHands 轨迹出发，经过五阶段流水线，构建出 45K segment distillation pool 和 40,606 条 teacher-validated compression examples，带有 intent-conditioned target、level label 和 must-keep annotation。训练上比较了三个匹配 backbone，最后选 4B；还尝试过对 drop supervision 加权，但结果适得其反，最终部署版本没有采用。更有意思的是，最终上线 checkpoint 不是训练 loss 最优，而是通过 OOD sweep 选出来的，说明这个任务里 loss 和真实可用性并不严格一致。1a:T89d,The method has three main pieces. First, it uses extractive compression. Instead of rewriting code and tool outputs, the model selects spans from the input and uses a fixed set of structural markers to denote removed regions. The reason is straightforward: downstream edits depend on exact strings, so identifiers, paths, numbers, and error messages should be copied, not paraphrased. The paper audits this claim explicitly: 96.0% of emitted identifier/path/number-like tokens are copied from the input on the training corpus, and 96.2% on held-out SWE-bench Lite outputs; excluding the one category intentionally rewritten by design, the rate reaches 98.3%.

Second, the compressor is intent-conditioned. Each compression call receives both the current task/query and a single segment, so the model can prioritize entities, files, functions, and error clues named in the live task. The paper argues that importance is not intrinsic to a segment; it is defined relative to what the agent is trying to do now.

Third, the system is built as a pipeline. A gateway performs segmentation, kind classification, and level labeling, and the model compresses one segment at a time. The compressor sees the task plus one segment with kind/level tags, but no explicit numeric token budget. Budget control is only indirectly encoded through a static level-to-ratio table in the system prompt. The authors originally designed four importance levels, L0-L3, but report that the distilled student effectively learned only two usable compression bands. That negative result is one of the more informative parts of the paper.

On data, they start from 67,074 raw OpenHands trajectories and build a five-stage pipeline that yields a 45K-segment distillation pool and 40,606 teacher-validated compression examples with intent-conditioned targets, level labels, and must-keep annotations. On training, they compare three matched backbones and choose 4B. They also tried drop-supervision weighting, found that it backfired, and shipped without it. Notably, the deployed checkpoint was selected by an out-of-distribution sweep rather than by training loss, which suggests that lower loss did not reliably predict real utility.1b:T53a,The evaluation has two layers. The intrinsic evaluation focuses on OOD holdout performance, including compression quality, must-keep retention, and identifier retention, with confidence intervals. One notable result is that at comparable budgets, the student does not underperform its own teacher on must-keep identifier retention, which suggests that distillation preserved the key exact-copy behavior.

The end-to-end evaluation plugs Paritok-4B into a coding-agent workflow under both raw-source and in-distribution line-numbered settings. The headline result is a 25.7% compression rate, meaning roughly one quarter of the original context is retained, while maintaining comparable single-shot solve quality. The paper describes this as roughly twice as aggressive as strong GPT-based compressors. Interestingly, the expected trade-off did not appear in the predicted form: instead of harder compression at equal quality, they observed slightly softer compression with higher quality, and no paired degradation was statistically resolvable over 300 instances.

That said, the scope is narrow. The conclusions are tied to coding-agent trajectories, the specific segmentation pipeline, and teacher-generated targets. The collapse from four intended levels to two effective bands also shows that fine-grained budget control remains weak.1c:T435,The system uses MCTS to organize repository exploration. It first parses the repository into a queryable representation, including directories, files, classes, functions, and code spans. At inference time, it builds a search tree where each node stores the current evidence and reasoning state. The action space covers semantic search, structural navigation, targeted code inspection, and stopping. Four agents operate in each iteration: a Perception Agent summarizes the current state and missing evidence; a Planning Agent proposes candidate actions; an Execution Agent runs the selected action over the indexed repository; and an Evaluation Agent scores the new state and propagates value estimates back through the tree. Compared with ReAct, the key difference is multi-trajectory exploration. ReAct follows one path and can accumulate early mistakes; DeepRepoQA keeps multiple branches alive and uses value estimates to balance exploration and exploitation. Its memory path from root to current node also makes the final answer easier to ground in explicit code citations.1d:T402,Repo2Skill-Evo is built as:
1) A fixed V1 skill set produced by Repo2Skill via staged distillation plus expert refinement. Each skill is packaged (e.g., SKILL.md, optional scripts/references) and augmented with provenance metadata (source paths/symbols) to enable traceability.
2) A maintenance task: given the official V1→V2 release patch, a maintenance agent must delete or revise patch-verified obsolete skill lines while preserving still-valid content. The design intentionally emphasizes minimal, selective edits rather than full regeneration.
3) Evaluation: a strict patch-grounded headline metric that rewards correct edits on verified obsolete lines and penalizes edits elsewhere, plus a rubric-based NL judge with five dimensions for overall quality.
The analysis frames two complementary bottlenecks: incomplete localization of affected skill files (coverage) and imperfect edit selection (precision/within-file evidence tracing). An oracle localization experiment tests how much of the gap is purely localization.1e:T4ab,The setup is clean and controlled. The authors define a fixed Task Management API with seven components, explicit communication rules, data ownership constraints, six hard architectural rules, 25 HTTP routes, three ADRs, and a prescribed file layout. They then encode the exact same system in five formats: natural-language prose, Mermaid diagrams with constraints and ADRs, OpenAPI, C4/Structurizr DSL, and TypeScript interface contracts with ArchUnit-style rules. Six models from three vendor families are asked to implement the system in a multi-turn coding-agent setting.
