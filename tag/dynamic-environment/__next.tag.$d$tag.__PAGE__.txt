9:T8a5,The core artifact is EnvOS, a framework for task construction, pre-run certification, and post-run auditing. It starts with a phenomenon, an application-independent class of environment changes. A concrete instance is implemented as an executable perturbation with four explicit components: a state operator, a triggering condition, an observation channel, and a single-execution guard. A candidate evaluation artifact then consists of a seeded world, the perturbation, endpoint criteria, and a verifier. Crucially, this artifact is not used immediately. It is admitted only after scoped certification tests.

From the full-text description, those tests cover at least five properties: whether the state transition actually occurs; whether observations are delivered consistently to the policy; whether the task remains feasible after the change; whether the checker discriminates correct from incorrect behavior; and whether the checker is robust to corrupted or abnormal records. This is the main methodological move: benchmark construction is tied to executable certification rather than assumed validity.

A second important design choice is to separate world-state change from information disclosure. In both clinic booking and insurance approval, the authoritative state changes in all principal comparisons. What varies is what the agent sees at review time. In the clinic setting, OFF-A gives no extra review information, CUE-A gives a reminder plus a link to the original source, and LIVE-A directly shows the updated location. In insurance, OFF-A is no extra policy exposure and ON-A re-exposes the current policy at approval time. This means the experiments estimate review-information effects within a dynamic environment, rather than conflating multiple factors in a static-vs-dynamic comparison.

The evaluation pipeline also includes preregistered counting rules, isolation between policy and evaluator data, and independent re-checking of verdicts from archived evidence. That last step is especially important: the grader is no longer a single trusted endpoint, but an auditable component. For RL settings with verifiable rewards, this is effectively an audit layer on top of the reward pipeline.a:T694,The available full-text excerpt provides mostly qualitative findings and relative comparisons rather than a complete numeric table, but the experimental structure is clear. EnvOS is instantiated in two applications: clinic booking, where a session location changes mid-task, and insurance-claim approval, where a policy limit changes before the agent computes an approval amount. In both cases, the environment-side change is present; the main comparison is how much updated information is shown at review time.

Three findings stand out. First, in clinic booking, directly showing the updated location in LIVE-A outperforms merely prompting the agent to verify via a source link in CUE-A, and this remains true after paper-wide multiplicity correction. That is an informative result: explicit re-exposure of the current authoritative value helps more than a generic verification cue. Second, in insurance approval, Opus 5 succeeds on the tested silent-change instances, while Sonnet 5 shows a local benefit from policy re-exposure that does not survive the retrospective paper-wide multiplicity adjustment. Third, the authors run archive challenges with deliberately corrupted records to test whether the same pipeline can detect evidence-chain failures. Misses are reported as qualifications on the claims rather than hidden.
