18:T7c0,This is a measurement study, not a new agent method. The authors fix a ReAct-style coding-agent harness on a multi-tool aggregation task and evaluate protocol fidelity rather than task success. The design has three important pieces.

First, it separates channel from prompt. “Channel” means tool schemas are passed through the native tools= field and then rendered and parsed by the server. “Prompt” means the tool list and JSON call format are written directly into the textual prompt. The paper compares three settings: native, which uses tools= only; native+hint, which still uses tools= but also injects a plain-text tool list and strict JSON format instructions; and text-tools, which removes tools= entirely and parses calls from text. This isolates server-side protocol handling from the model’s ability to follow tool instructions.

Second, it refines the label space. Each assistant turn is categorized as valid in-schema call, hallucinated call, unparseable text, no-call prose, or non-response. The non-response category is crucial. In Ollama, some models trigger HTTP 400 request rejection before inference; the harness retries, gives up, and writes a generic error string into the trajectory. If that error is not preserved as structured metadata, downstream analysis can count it as a model non-call. The paper therefore excludes non-responses from the fidelity denominator and reports them separately.

Third, it performs a multi-stack comparison. The same weights and the same request behave differently under Ollama, llama.cpp, vLLM, and SGLang: some stacks reject tools=, some accept it but return calls as plain text, and some require explicit parser configuration before a call is recognized. The point is not to rank stacks, but to show that the measured outcome is stack-dependent. The constrained-decoding baseline adds another useful negative result: forcing valid call syntax can simply move the failure mode from malformed calls to endless looping.19:T668,The experiments cover small local models including Qwen2.5-Coder 0.5B/1.5B/3B, Llama-3.2, Phi-3, and Gemma-3. Results are reported over 8 seeds using both turn-pooled rates and per-seed means, with seed-level bootstrap 95% confidence intervals. Four findings stand out. First, under Ollama’s default native function-calling path, Qwen2.5-Coder models accept tools= but return calls as text, Llama-3.2 returns native tool_calls, and Phi-3 and Gemma-3 are rejected with HTTP 400 before inference. Without structured error logging, those rejected models can be falsely reported at 0% fidelity. Second, for models whose requests are accepted, native+hint often recovers much of the fidelity, which suggests that some failures come from protocol rendering rather than inability to use tools. But Llama-3.2 degrades under a uniform text-only protocol, so the best setup is model-dependent. Third, the same weights behave differently across four serving stacks: models rejected by Ollama can run on llama.cpp, vLLM rejects similar requests by default, and SGLang accepts them but returns text calls. That directly shows the benchmark outcome is partly a serving-stack property. Fourth, turn-pooled and per-seed metrics can differ by roughly 55 points because a single looping episode can dominate the pooled denominator. This makes aggregation choice a major source of instability.

The paper also includes a useful negative result: at this measurement precision, the authors do not support broader claims about scale, model family, or reasoning ability and explicitly avoid making them. That restraint is one of the stronger parts of the study.1a:T418,For a skim, start with the introduction and the method section explaining the OpenAI-compatible tool-calling pipeline. The key point is that tools= is not passed directly to the model; it is mediated by server-side template rendering and output parsing. Then read the comparison among native, native+hint, and text-tools, plus the four-stack behavior table or figure. Those sections make the confound concrete. Finally, look at how non-response is defined and removed from the fidelity denominator. That detail determines whether a reported 0% is meaningful or simply an artifact.

If you only have 20 minutes, that is enough to get the main lesson. If you are building your own evaluation stack, the practical checklist is worth extracting: log HTTP and serving failures explicitly, separate request rejection from model non-calls, report both pooled and per-seed metrics, and document parser/template configuration. - Measurements: task score/pass rate, total tokens and estimated cost, tool-call counts/tokens, call success rate, repetition, plus domain breakdowns and failure analysis.1c:T852,The method, State-Path Tool Menu, has three components: an encoder, a retriever, and a reranker. Each tool has documentation, required inputs, and produced outputs. A request exposes an initial state s0(q), containing the fields and constraints visible before any tool call. The system must construct an ordered menu of K=32 tools, and the online agent can only use tools from that menu during execution.

The central idea is the state path, a latent pre-execution route from the observable initial state to the desired outcome. Tools on this route are assigned one of four roles: entry tools can run immediately from the initial state, bridge tools create intermediate fields needed later, the target tool resolves the main request, and an optional terminal tool commits or delivers the result. This role decomposition is useful because it separates different notions that relevance-based retrieval conflates: immediate executability, intermediate utility, and final-task alignment.

The encoder learns relation-aware tool representations from the request state, tool schemas, and successful training trajectories. The excerpt explicitly mentions three directional signals: whether a tool can run now, whether it produces fields needed later, and how it depends on other tools in precedence order. So the representation is not just semantic similarity over tool descriptions; it is structured around state compatibility and dependency. The retriever then selects 32 tools that cover complementary path roles rather than simply maximizing top-k relevance. The reranker orders the selected tools so that producers appear before consumers, making the menu easier to execute under the same online loop and call budget.

Training supervision comes from successful trajectories. The retriever is trained with route membership, entry, and path-role targets, while the reranker is trained with slot and pairwise precedence targets. A notable design choice is that the paper keeps the online agent unchanged. The gains are meant to come from better pre-execution menu construction, not from modifying the planner or increasing the budget.1d:T4b9,From the available text, the experiments compare State-Path menus against relevance-based menus under a fixed agent and a fixed 32-tool budget. The reported evaluation dimensions include end-task success, complete-chain coverage, and executable entry. The paper also claims comparisons across tool libraries, evaluators, and executor families, plus paired outcomes and controlled variants to isolate whether the gains come from route coverage and ordering.

The provided excerpt does not include the result tables, exact gains, dataset sizes, or training details, so it would be inappropriate to fabricate numbers. First, it uses an explicit pipeline. The motivation is straightforward: shortest path, matching, coloring, and related computations are deterministic; the real weakness of LLMs is the language-to-structure mapping.

Second, the method enforces structural invariance during training. The authors construct multiple isomorphic views of the same underlying graph: node identifiers may be random, semantic, aliased, or noisy, and the task description may range from standardized templates to more realistic narratives. The model is trained to recover the same intermediate graph despite these surface changes. This is more than ordinary augmentation, because the reward directly checks whether the predicted intermediate graph matches the ground-truth topology. That gives denser and more targeted feedback than final-answer supervision alone.

Third, GRAIN uses single-agent RL as a form of robustness distillation. The goal is not to build a multi-agent system, but to absorb into one model the robustness that would otherwise require repeated decomposition and verification across multiple agents. The RL objective jointly rewards correct structure recovery and correct tool invocation. The intended effect is to learn identifier-invariant and formulation-invariant parsing rules instead of memorizing templates.
