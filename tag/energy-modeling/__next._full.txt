18:T925,方法上有三层。第一层是 trace-level accounting。作者从 decode iteration 的共享结构出发，把每个有效输出 token 的逻辑字节需求写成两部分：共享的 dense weights 和私有的 KV history。定义 Mw 为一次迭代中需要参与计算的 dense weight footprint，Beff 为该迭代实际产生的有效输出数，KKV 为每个缓存 token 的 key+value 总字节数，L̄token 为按有效输出加权的平均注意历史长度。于是每 token 的逻辑读需求是 Atoken = Mw/Beff + KKV·L̄token；若把每生成一个 token 还要写入一条新的 KV 记录算进去，则读写需求变成 Atoken_rw = Mw/Beff + KKV·(L̄token+1)。这里最关键的不是公式本身，而是共享与私有两类工作被明确分开：batch 只摊薄前者，context 只放大后者。

第二层是把逻辑字节坐标转成可回归的能耗变量。作者把共享权重项写成 q_w = Mw/(10^9·Beff)，把 KV 读写项写成 q_KV = KKV·(L̄token+1)/10^9，再引入 realized time per token，记为 τ，即总 decode 时长除以有效输出 token 数。最终用一个 affine 形式去拟合 token energy，大意是把 q_w、q_KV、τ 以及常数项放进同一个线性响应模型。这样做的含义是：能耗既受“需要搬多少字节”影响，也受“这些工作在硬件上花了多久”影响；单独看 bytes 或单独看 time 都不够。

第三层是把逻辑 accounting 和物理实现联系起来。论文没有停留在符号推导，而是强调 active bytes 是 trace 的 principal account，不等于所有驻留显存，也不等于所有 operator 的全部访问。像 embedding lookup、positional access 这类不在主账本里的访问，需要单独处理。作者再用 HBM 测量去检验这些逻辑坐标与真实物理流量之间的关系，并按模型和硬件分别校准系数。这个设计比直接做黑盒回归更稳，因为变量有明确语义，也更容易解释为什么某些配置下能耗变化来自 batch 摊薄、某些来自 KV 增长、某些来自时间拉长。

从方法取舍看，这篇工作刻意没有把所有系统细节都塞进模型，而是保留一个小而可解释的主干。代价是覆盖面有限；好处是可以作为 dense decode 的一阶近似规律，用来做部署前估算和设计空间分析。19:T83f,The method has three layers.

First, the paper builds a trace-level accounting identity for decode work. In each decode iteration, dense weights are shared across all useful outputs, while each output token attends to its own KV history. Let Mw be the dense-weight footprint in bytes, Beff the realized mean number of useful outputs per iteration, KKV the combined key-value bytes per cached token across layers, and L̄token the useful-token-weighted mean attended history length. Then the logical read demand per useful output token is Atoken = Mw/Beff + KKV·L̄token. If one also accounts for writing one new KV record per generated token, the read-write demand becomes Atoken_rw = Mw/Beff + KKV·(L̄token + 1). The key idea is structural: batch size and context length affect different terms, rather than entering the model as interchangeable scalar knobs.

Second, the authors convert this accounting into regression coordinates for energy. They define q_w = Mw/(10^9·Beff) for shared dense-weight bytes and q_KV = KKV·(L̄token + 1)/10^9 for KV read-write bytes, both in decimal GB, and introduce realized decode time per token, τ, computed from total decode duration divided by useful output tokens. Token energy is then modeled with a common affine form over q_w, q_KV, τ, and a constant term. This is an important design choice: bytes alone are not enough, because the same logical byte demand can be realized with different occupancy, kernel efficiency, communication overhead, and stall behavior.

Third, the paper connects logical accounting to physical memory behavior. Active bytes are explicitly defined as the principal logical account of dense-weight and KV accesses, not all resident memory and not all operator traffic. Embedding and positional accesses sit outside the main account and require separate treatment. The authors then use HBM measurements to test how these logical coordinates map to actual physical traffic, and calibrate coefficients per model and hardware platform. Compared with a pure black-box fit, this gives the model clearer semantics and better diagnostic value.1a:T548,The provided full-text excerpt includes the introduction and the main modeling setup, but not the full experimental section, tables, or numerical results. So it would be unsafe to invent exact figures. From the paper’s setup, the experimental program appears to target three questions. First, whether the two active-byte coordinates—shared weight demand and private KV demand—can explain token-energy variation across batch size, context length, and model settings.
