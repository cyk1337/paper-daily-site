9:T4dd,The paper uses a roofline-style analysis to separate weight traffic from KV-cache traffic during decode. For a model with P parameters and weight width wp, a batch-one decode step performs roughly 2P FLOPs and reads P·wp bytes, giving about 1 FLOP/B for BF16 weights. An H100 SXM has a BF16 dense ridge point around 295 FLOP/B, so this regime is bandwidth-bound by a large margin. KV attention has the same structure: one query attending over s cached tokens costs about 4sdh FLOPs per head and reads 2sdh·wkv bytes, again about 1 FLOP/B in BF16. GQA improves reuse by the query-to-KV head group factor g, but even g=8 gives only about 8 FLOP/B, still far below the ridge point. The paper then explains why batching helps weight reads but not KV reads. Weight bytes can be amortized across requests; KV bytes cannot, because each sequence owns its cache. The techniques are organized into five mechanism classes: quantization reduces element width, token eviction reduces retained tokens, paging manages KV blocks and fragmentation, prefix caching shares common prompt prefixes, and memory tiering moves KV state across HBM, host DRAM, and storage.
