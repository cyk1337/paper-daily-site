a:T6ce,The work has two layers. The first is the Thinkingbox sandbox. A task is instantiated as a finite-horizon POMDP whose latent state includes backend state, simulated-user private state, evaluator-relevant event logs, and episode status. At each turn, the agent observes dialogue history and tool outputs, then either sends a user-facing message or issues a tool call with arguments. Tool calls execute inside isolated backend sessions. The system records side effects and runs hidden executable checks at the end. A key design choice is outcome-based evaluation: multiple trajectories may be valid as long as the final backend state, required side effects, and dialogue constraints are correct.

The second layer is Thinkingbox-bench, a 507-task benchmark spanning retail/e-commerce, travel/hospitality, auto insurance, neobank internal IT support, and consulting IT/HR support. Tasks are designed around recurring enterprise patterns: lookup-then-update flows, user clarification, confirmation before irreversible actions, policy-conditioned changes, and multi-tool coordination. Most tasks are graded through executable checks over terminal backend state. An additional subset of 30 tasks uses binary rubrics on the final response, covering required disclosures, confidentiality, and consistency between what the agent says and what it actually executed.

The reliability framing is central. pass@k measures whether at least one of k attempts succeeds, which captures discovery capability. pass^k measures whether all k attempts succeed, which captures repeatable reliability. That distinction is important because many agents can occasionally find a correct trajectory while remaining unstable under sampling noise or interaction variation.b:T56f,The main empirical result is a large discovery–reliability gap. The benchmark contains 507 tasks, and the authors evaluate 12 proprietary and open-weight models with 20 repeated trials per task. The strongest model reaches 65.36% pass@1, which is still far from dependable single-run performance. Its pass@20 rises to 91.12%, showing that many tasks are solvable at least once. But its pass^20 is only 25.25%, meaning only a quarter of tasks succeed in all 20 attempts. That gap is the central takeaway of the paper.

Because evaluation is tied to terminal backend state rather than a single final answer, the benchmark can expose failure modes that simpler tool-use benchmarks miss: updating the wrong entity, producing a convincing response while leaving the backend unchanged, missing a required side effect, introducing an extra side effect, executing high-impact actions before collecting confirmation, or generating a final message inconsistent with the actual execution outcome. The paper also includes evaluator ablations and failure analyses to show that fluent tool use is not the same as reliable work completion.
