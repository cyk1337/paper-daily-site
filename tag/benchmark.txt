1) Threat model: an attacker probes in English; if the model responds safely in English, the attacker translates the same intent into multiple low-resource languages and retries. Success is any harmful completion in any translated language—no jailbreak skill required.
2) Conditional bypass metric: compute translation-bypass rates conditioned on English safety, explicitly separating translation-induced failures from English failures.
3) Structured language analysis: evaluate 78 low-resource languages (plus English), grouped by resource level (Joshi et al.) and by language family (WALS). Formally test whether bypass risk concentrates at the family level. The authors discuss a key confound: translation degeneracy/quality differences can correlate with family-level ordering and must be accounted for in interpretation.
Prompts come from multiple public safety/jailbreak datasets (AdvBench, MultiJail, PHTest, HarmBench, DiaSafety, etc.) mapped into a shared safety taxonomy. To reduce misuse, the paper withholds prompt text and fine-grained per-language/category vulnerability maps.19:T7bf,The authors introduce reuF2F, a Lean 4 benchmark of 244 open conjectures drawn largely from undergraduate research projects, especially REUs. The source choice is deliberate: these are real research problems, but unlike famous conjectures they are less likely to attract concentrated attention or have solutions widely circulated online later. That makes them more suitable as a longer-lived held-out benchmark.

The evaluation protocol is designed around coding-agent workflows. Each task runs in an isolated sandbox where the agent can inspect and edit files, search Mathlib, run computations, and iterate using Lean feedback. Because an open conjecture may be true or false, each task includes both the original statement and its full logical negation, and the agent may pursue either direction. After submission, the code is checked in a separate evaluation container. Comparator is used to verify that the submission proves either the statement or its negation without altering definitions or introducing unproved assumptions. A task counts as solved only if the proof passes both Lean’s kernel and the independent nanoda checker. This makes formal correctness the sole success criterion and sharply reduces evaluator noise.

To reduce confounding from agent engineering, the paper also introduces Leanimum-agent, a lightweight adaptation of mini-SWE-agent for formal theorem proving. It standardizes instructions, shell access, context handling, and the interaction loop across models. That is an important design choice because many agent benchmarks mix model quality with toolchain differences. Here the benchmark tries to hold the harness fixed so that model comparisons are cleaner.

Methodologically, this is a benchmark and protocol paper rather than a new training algorithm. Its main contributions are the problem-source strategy, the bidirectional prove-or-disprove setup, the independent verification pipeline, and the alignment with modern coding-agent evaluation.1a:T506,From the provided full-text excerpt, the confirmed hard facts are: the benchmark contains 244 Lean 4 formalized open problems; evaluation uses isolated task sandboxes plus a separate verification container; and success requires proving either the original conjecture or its negation while passing both Lean’s kernel and nanoda. Even without the full numbers, the experimental design already establishes several useful properties. First, this is an agentic benchmark rather than a static theorem-proving dataset: models can search, edit, run, and iterate. Second, the prove-or-disprove formulation avoids turning false conjectures into impossible tasks. Third, the independent checker chain makes the benchmark suitable for RLVR-style settings and for tracking capability progress over time. To assess empirical strength, the most important missing details to inspect in the full paper are solve rates by model, budget sensitivity, tool-use traces, and performance variation across mathematical subfields.1b:T427,The benchmark is built by extending established datasets through professional human translation. MGSM is used for grade-school mathematical reasoning. A STEM subset of IndoMMLU is used for scientific reasoning across biology, chemistry, and physics. XQuAD provides extractive question answering. CrossSum evaluates abstractive summarization, with English source documents and target-language summaries. WMT shared-task data is used for English-to-target machine translation. For MGSM, XQuAD, WMT, and CrossSum, translations are produced from English into each target language. For IndoMMLU, which originates in Indonesian, the low-resource versions are translated from Indonesian. The translation protocol is deliberately conservative: translators are asked to translate only the designated fields, avoid adding explanations, preserve numeric forms, and keep punctuation, casing, and formatting as close as possible to the source. 2) TrekTrace (core method): a plug-and-play failure attribution framework that inspects the search trajectory to determine whether answer-bearing evidence was retrieved, then reruns the model with that evidence to test whether it can answer correctly. This separates failures into pre-retrieval (bad query), retrieval (missing evidence), and post-retrieval (evidence present but still wrong). Post-retrieval is further split into distraction (misled by conflicting/irrelevant context) versus interpretation (fails even on gold evidence alone). First, the benchmark builds three diagnostic settings that expose different failure modes. Parallel evidence requires preserving two parallel reasoning chains for ambiguous references. Conditional evidence requires keeping both the supporting statement and its qualifier, so the compressor cannot turn a conditional claim into an unconditional one. Imbalanced evidence tests whether minority-supported perspectives survive when most evidence points elsewhere. Second, for each query, the required evidence is extracted from the source context and decomposed into minimal self-contained propositions. Evaluation is then done proposition by proposition, based on whether each one is explicitly stated or unambiguously inferable from the compressed context alone. Third, the paper introduces All Proposition Recall (All-Rec), which only counts a case as correct if every required proposition is preserved. Criterion synthesis then proceeds in two independent passes:
- a PRD-only pass that extracts required behaviors and constraints from the request,
- a reference-diff-only pass that records what changed in the accepted implementation without inferring business intent.

These are reconciled to filter incidental edits and unsupported inferences, then refined into atomic Code Points. - L0 performs structural checks for explicit hard violations,
- L1 uses bounded call-graph search to gather candidate code and integration context,
- L2 applies a judge to each Code Point with cited evidence, while allowing semantically equivalent implementations rather than requiring the reference patch.
