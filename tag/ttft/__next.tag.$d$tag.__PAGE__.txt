For each incoming query, the router combines three signals: expected response quality, monetary cost, and predicted latency at a specific model instance. The difficult part is latency estimation. The paper proposes a Serving Framework Simulation (SFS) estimator that simulates the evolution of autoregressive token batches at each instance. It tracks active requests, separates prefill and decode work, and incorporates the batching/admission/scheduling behavior of the underlying serving framework.

This is a more structured approach than using prompt length, expected output length, or queue length alone. In modern continuous batching systems, prefill is typically compute-bound while decode is more memory-bandwidth-bound, and the mix of the two phases strongly affects how much delay a new request will see. The estimator therefore models not just how long a query is, but what kind of workload is already occupying the instance.

A notable design choice is that latency is not treated as a pure black-box regression target. For each chunk, the scheduler decides whether it should be streamed from the cloud or recomputed on the device, subject to causal and layer-wise dependencies, with the objective of minimizing end-to-end TTFT.

The second component is an overhead model. The paper uses a lightweight MLP to predict per-chunk local computation latency from features such as attention sparsity. This matters because recomputation cost is highly non-uniform across chunks: some are cheap to recompute locally, while others are better streamed. Compared with coarse layer-level or segment-level scheduling, this gives the system a finer cost model.

The third component is a runtime controller. Offline schedules are fragile under real wireless conditions and changing edge workloads. The controller monitors wireless throughput and available compute headroom over sliding windows, then dynamically migrates chunks between the streaming path and the local-compute path. The key point is that SparKV is not just cloud-edge cooperation in a generic sense; it is dependency-aware, cost-aware, and runtime-adaptive.

Relative to prior work, the differences are clear: it is not only KV compression or priority-based streaming; it is not only local prefill acceleration through kernels or sparse attention; and it is not a coarse bidirectional overlap scheme.
