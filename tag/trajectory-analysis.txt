17:T502,The core idea is a three-layer abstraction. Benchmark handles dataset loading, task definition, and scoring. Harness wraps a model into an interactive agent, including prompt formatting, state management, multi-turn tool use, and provider-specific API handling. Environment provides the isolated execution context, including command execution, file transfer, text editing, and network services. These components are connected through stable interfaces and configured through a declarative RunRequest. The request is further decomposed into BenchmarkSpec, HarnessSpec, EnvironmentSpec, ModelSpec, and ExecutionSpec, separating evaluation semantics from execution mechanics. The framework uses lightweight decorator-based registries so new benchmarks, harnesses, or environments can be added locally without modifying the central runtime. A practically useful feature is scorer execution mode: scoring can happen in memory, reuse the agent workspace, or run in a fresh isolated environment, which is especially relevant for coding agents and patch verification. On the systems side, AgentCompass includes a fault-tolerant asynchronous runtime for parallel long-horizon trajectories and trajectory-level analyzers that expose intermediate actions, tool calls, and environment feedback.18:T762,TraceGraph has a clear pipeline.

First, each action–observation step in a rollout is encoded into a sparse observable signature. Model identity is intentionally excluded at this stage so that the graph is built from shared external behavior rather than from model-specific metadata. Similarity between states is computed using IDF-weighted Jaccard, which gives more weight to rarer, more informative observable features. Using pooled trajectories from multiple models, the method constructs a mutual-kNN graph over these states.

Second, the graph is structurally decomposed using tools such as biconnected components and articulation gates. This gives a task-specific topology with stable regions and bottlenecks. Only after the graph is built does the method overlay outcome information. Successful trajectories define productive cores; failure-associated recurring regions define traps. This separation is important: the graph is meant to be a shared descriptive map first, not a supervised predictor from the start.

Third, each rollout is summarized by three events: Access, whether it reaches a productive core; Trap exposure, whether it enters a trap region; and Repair, whether it returns from a trap to a core. This is a deliberately compact process profile. Instead of reconstructing all reasoning details, the paper keeps the smallest set of events that can explain benchmark-specific process demands.

The paper then uses the same trap overlay for online intervention. On SWE-bench, when a live trajectory enters a historically risky region, the system triggers a prefix-fork recovery pipeline. Continuations resume from the same state with lightweight modifications such as a conservative diagnosis note or a temperature bump. The point is not that the recovery policy is sophisticated; the point is that graph-derived traps are actionable enough to support runtime control.19:T505,The evaluation spans five benchmark splits, 7,329 trajectories, 427 tasks, and five models. The main result is qualitative but operationally meaningful: models with similar aggregate scores can exhibit very different navigation styles on the shared graph. Some explore broadly and rely on repair, some avoid traps early but access productive cores less often, and some reach productive regions frequently while also exposing themselves to more traps. This shows that benchmark scores alone do not reveal what process a benchmark rewards.

The intervention experiment focuses on SWE-bench because it shows the clearest positive demand for Repair. Using the TraceGraph-derived trap detector as a runtime trigger, the trap-aware prefix-fork pipeline is tested on all 500 SWE-bench Verified instances. The best pooled policy improves resolved rate by +3.1 points on the per-provider fired subset (p=0.016) and by +3.8 points on common-fired instances (p=0.045). The gains are modest, but they matter because they demonstrate that the trap regions are not merely post-hoc explanations; they can support online recovery. Instead, it isolates the main branching points that matter in deployment. Ask handles ambiguity or missing information, Confirm handles risky or irreversible actions, Recover handles tool failures or observation errors, and Stop handles proper termination. Second is a nine-category trajectory-failure taxonomy covering tool-use failures, observation failures, recovery failures, safety failures, efficiency failures, and related categories. The key idea is that final failure is only the surface symptom; the trainable and diagnosable unit is where the trajectory went wrong.
