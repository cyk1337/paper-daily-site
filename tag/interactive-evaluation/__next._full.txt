19:T7c5,The contribution is a benchmark and execution environment rather than a new model. The paper defines a mobile planner as the high-level decision core of an on-device assistant: it interprets user intent, retrieves long-term memory, invokes structured business APIs, loads reusable composite skills, and delegates specialized subtasks to GUI sub-agents when direct tool use is insufficient. Around this setup, the benchmark is organized into four capability dimensions. Basic Tool Use covers utility calls, multimodal input handling, strict execution order, permission boundaries, and OS feedback. Sub-agent Collaboration measures whether the planner can decompose tasks and hand them off to downstream specialists with valid context transfer. Memory Usage tests whether the agent can retrieve persistent user context—preferences, credentials, prior state—to resolve underspecified requests before planning. Skill Usage evaluates whether the planner can invoke packaged multi-step skills instead of replanning every primitive action, reducing long-horizon error accumulation.

Operationally, MobilePA-Bench runs in an executable sandbox with live application databases and structured feedback. The key design choice is to decouple central planning from low-level visual parsing. In other words, the benchmark is intentionally not centered on pixel understanding; it is centered on deciding when to call an API, when to query memory, when to invoke a composite skill, and when to fall back to a GUI sub-agent. This keeps the evaluation focused on planner quality rather than visual noise, while still preserving realistic friction such as call dependencies, permission blocks, and dynamic state mutations.

The benchmark itself contains 1,705 real-world tasks across 13 domains and 212 tools. The task design aims at realistic workflows, such as multi-day travel planning, where success depends on cross-tool coordination and state-aware execution rather than single-step tool selection.1a:T4f3,The main empirical message is that current strong LLMs still struggle in this interactive, stateful, tool-centric mobile setting. The failure analysis is more informative than the headline score. The paper highlights four recurring weaknesses: errors under strict tool-call ordering, weak recovery from runtime system exceptions, unreliable memory retrieval for ambiguous user requests, and brittle coordination across multiple agents or execution modes. These are not superficial UI failures; they point to deficits in closed-loop planning under constraints.

In terms of scale, 1,705 tasks over 13 domains and 212 tools are large enough to support capability-level slicing. The excerpt does not expose the full per-model table, but the paper’s emphasis is clear: the benchmark differentiates models mainly through dynamic constraints and interaction feedback, not through static API matching.
