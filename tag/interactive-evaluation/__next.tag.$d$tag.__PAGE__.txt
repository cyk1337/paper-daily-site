9:T4e0,The framework defines desired agent behavior as a set of situational rules: if the current situation satisfies condition P, the agent should follow criterion Q. During evaluation, an LLM interlocutor interactively advances the conversation by uniformly sampling situations from a predefined action space. This is the main design choice. Instead of waiting for rare situations to appear naturally, the benchmark forces balanced coverage over the situation space.

A context-aware LLM judge then evaluates each agent response only against the subset of rules that apply at that turn. The output is therefore rule-wise and turn-wise, not a single opaque score for the whole dialogue. To improve judge reliability, the authors validate the judge on human-verified synthetic golden dialogues before using it in the benchmark.

The demonstration domain is Socratic math tutoring. The paper defines 12 expert-authored pedagogical rules spanning seven categories, including Socratic questioning, ambiguity clarification, and error handling. The key methodological choice is to replace reference responses with explicit behavioral rules. That is sensible for open-ended dialogue, where many responses can be acceptable if they satisfy the right constraints.a:T623,The contribution is a benchmark design, not a new model. Each task simulates a customer engagement. The agent receives a sponsor instruction, a copy of the customer’s production system, documents and historical data, a staff directory, and a constrained runtime with Python and SQLite. General internet access is blocked. After the agent finishes, the contents of system/ are deployed without modification, and production still calls the original entry points. This forces real integration into an existing codebase rather than a side demo. Scoring is based on improvement in the customer’s business metric on held-out production data, minus stakeholder-contact cost. Three design choices matter. First, the anchors are explicit: the unchanged system scores 0, the expert reference solution scores 1, and literal compliance with the sponsor request is capped around 0.2. This sharply distinguishes “doing what was asked” from “solving the customer’s problem.” Second, the four instruction levels are a clean intervention. L0 fully specifies the problem; L1, L2, and L3 progressively remove constraints and true objectives until L3 is just the original sponsor request. Because the environment, stakeholders, and grader are fixed, score differences across levels isolate the cost of missing information and failed problem discovery. Third, stakeholder interaction is priced, but the agent is not told upfront which contacts are useful or wasteful. That means the benchmark evaluates information-gathering strategy, not just willingness to ask more questions.b:T6c9,The benchmark contains 95 tasks from 20 customer scenarios spanning 18 sectors, adapted from real delivery projects by domain experts. The paper evaluates 13 model configurations from 7 providers. On L3, the setting closest to real sponsor requests, the best configuration is Claude Opus 5.5 with a mean score of 0.56 and only 14 of 95 tasks resolved. Five of the thirteen configurations resolve none. Even an oracle that picks the best model configuration per task reaches only 0.70 overall and resolves 30 tasks, still well below the expert reference. The most informative result is the bottleneck analysis. When relevant rules and constraints are provided, the top three models score 0.73–0.82. When they must discover those constraints themselves, scores drop to 0.39–0.62. That points to unstated-constraint discovery, not implementation, as the main failure mode. Another useful observation is that on the original tasks, L3 is at most 0.08 below L1, suggesting the sponsor request often contains partial clues; the hard part is turning scattered evidence into the right intervention. The paper also shows that leading models can obtain 72%–85% of key facts from stakeholders at L3, yet their delivered systems achieve only 0.60–0.70 of the reference improvement. Stakeholder-contact cost then removes another 0.14–0.22 from final scores. So information acquisition is not the same as effective delivery. Weak models are risky in deployment terms: Claude Haiku 4.5 scores below the do-nothing baseline on 79 of 95 tasks, and Mistral Small 4 is below that baseline on 51 tasks even before contact costs are deducted. The paper defines a mobile planner as the high-level decision core of an on-device assistant: it interprets user intent, retrieves long-term memory, invokes structured business APIs, loads reusable composite skills, and delegates specialized subtasks to GUI sub-agents when direct tool use is insufficient. Around this setup, the benchmark is organized into four capability dimensions. Basic Tool Use covers utility calls, multimodal input handling, strict execution order, permission boundaries, and OS feedback. Sub-agent Collaboration measures whether the planner can decompose tasks and hand them off to downstream specialists with valid context transfer. Memory Usage tests whether the agent can retrieve persistent user context—preferences, credentials, prior state—to resolve underspecified requests before planning. Skill Usage evaluates whether the planner can invoke packaged multi-step skills instead of replanning every primitive action, reducing long-horizon error accumulation.

Operationally, MobilePA-Bench runs in an executable sandbox with live application databases and structured feedback. The key design choice is to decouple central planning from low-level visual parsing. In other words, the benchmark is intentionally not centered on pixel understanding; it is centered on deciding when to call an API, when to query memory, when to invoke a composite skill, and when to fall back to a GUI sub-agent. This keeps the evaluation focused on planner quality rather than visual noise, while still preserving realistic friction such as call dependencies, permission blocks, and dynamic state mutations.

The benchmark itself contains 1,705 real-world tasks across 13 domains and 212 tools. The task design aims at realistic workflows, such as multi-day travel planning, where success depends on cross-tool coordination and state-aware execution rather than single-step tool selection.e:T4f3,The main empirical message is that current strong LLMs still struggle in this interactive, stateful, tool-centric mobile setting. These are not superficial UI failures; they point to deficits in closed-loop planning under constraints.

In terms of scale, 1,705 tasks over 13 domains and 212 tools are large enough to support capability-level slicing.
